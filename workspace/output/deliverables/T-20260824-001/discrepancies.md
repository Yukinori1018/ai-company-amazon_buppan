## A. 実害あり

### D1 ★★★ 「過去1年最安値」列は、実際には「**全期間の最安値**」

| | |
|---|---|
| **該当箇所** | `scan_v13.py` `_stat_min(stats, 1)` → `stats["min"][1]`／CSV列「過去1年最安値」／`summary.json` の `"過去1年最安値の定義": "Keepa stats(365日) の NEW(新品最安, index=1) の最小値"` |
| **公式定義** | `stats.min` ＝「この商品に対して**これまでに記録された（ever registered）**最安値」。**stats パラメータの期間とは無関係。**期間内の最安値は **`stats.minInInterval`**（"Same as min, but restricted to the interval specified in the stats parameter"）（statistics-object.html） |
| **何が起きているか** | `stats=365` を指定していても `min` は全期間。**追跡10年の商品なら10年前の底値**が「過去1年最安値」として入る |
| **影響範囲** | 段2（値下げ耐性）の合否、`損益分岐仕入れ値`、`損益分岐仕入れ値_精緻`、`仕入れ掛け率上限%` — **`candidates_v13.csv` 全行**（約1.5MB／top100含む） |
| **方向** | **安全側に偏る**（全期間最安 ≤ 365日最安 → 損益分岐仕入れ値が低く出る → GO が過少）。損はしないが、**取りこぼしと、社長への説明の食い違い**が発生する |
| **修正** | **⚠️ 当初案（`stats["min"]` → `stats["minInInterval"]` の1語差し替え）は取りやめになりました。**`minInInterval`(365日) は **2026-02-23 の価格定義変更（listing price → landing price／glossary §3）をまたぐ**ため、定義の違う値の最小値になり「直したつもりで誤りが残る」ためです。**採用案（2026-08-24 決定・実装はタカシ）**：①主軸列＝**2026-02-23 以降の窓で自前計算した最安値**（定義が一貫した値だけを損益計算に使う）／② `minInInterval`(365日) は **`参考_365日最安(価格定義混在)`** として残す／③ **`価格定義混在` フラグ列**を新設。いずれも `--from-raw` で**0トークン** |
| **確度** | **事実**（公式原文と実装の直接照合） |

## B. 用語の誤り

### D5 ★★ 「ドロップ数＝販売件数」と断定している

- **当社の記述**：`scan_v13.py` 冒頭「Keepa 月間ドロップ数（**BSR の急落回数＝推定販売件数**）」／T-20260811-001「売れ筋ランキング線が**ガクッと下がる回数＝売れた回数**の目安」
- **公式定義**（statistics-object.html）：「`salesRankDrops30` ＝ 直近30日間の**売れ筋ランキングの下落（高い値から低い値への変化）の回数**。**販売を示すものとみなされる（considered to indicate sales）**」
- **差分**：公式は「**回数**」までしか言っておらず、「**個数と等しい**」とは書いていません。1回のランク更新で複数個売れていれば1ドロップにしかならず、**構造的に過少になりうる代理指標**です。
- **実害**：当社は**ドロップ数を主軸の抽出指標**にしています（v1.3）。指標として使うこと自体は妥当ですが、**「推定販売件数」という断定形は撤回すべき**です。「販売の代理指標（公式表現：販売を示すとみなされる）」に言い換えれば、それだけで済みます。
- **確度**：**事実**（公式原文と当社文言の照合）

### D6 ★★ `monthlySold` を「月間売上**予測**」と呼んでいる

- **当社の記述**：memory `reference_keepa_api_capabilities`「FBA手数料、**月間売上予測**」「**月間売上予測（monthlySold）**」
- **公式定義**（product-object.html / product-finder.html）：「過去1か月にこの商品が購入された回数。Amazon の検索結果ページの "bought past month" の値。**推定値ではない（It is not an estimate）**。ただし Amazon は "10+" "100+" のような**区切られた範囲**でしか提供しない。**大半のASINには値が無い。値はバリエーション単位**」
- **差分**：**「予測」は誤り。**実測値です。ただし**下限付きの区間値**（`1000` は「**少なくとも**1000回」）。
- **なぜ効くか**：AIが「予測だから外れて当然」と扱うか「実測だから正確」と扱うかで、判断の重みが変わります。**正しくは「実測だが粗い区切り。かつ大半の商品で欠測」**。
- **確度**：**事実**

### D7 ★ 資料の記述と実装が食い違っている（T-20260817-004）

- **資料の記述**：「仕入れ方針 v1.3 の足切りに既に入っています（`current_AMAZON_gte=-1 & current_AMAZON_lte=-1`＝本体在庫なし／**Amazon在庫切れ率90%以上**）」
- **実装**：`scan_v13.py` の Finder ペイロードに **`outOfStockPercentage90` 系のフィルタは存在しません**。
- **差分**：資料が実装より強く書かれています。**社長は「在庫切れ率90%以上でも弾いている」と理解している可能性があります。**
- **確度**：**事実**（コード全文を確認）

### D12 ★★ 「Keepaのデータは最大24時間古い」— **API経由では話が違います（カズヨの実機所見の補正）**

カズヨが `#!support` 実機で取得した公式FAQ（`_raw-capture-kazuyo/support-faq-ja.md`）に、当社ナレッジに無かった重要事実がありました。**ただし、そこから導かれた「当社の夜間スキャンのデータは最大24時間古い可能性がある」という所見は、APIドキュメントと突き合わせると成立しません。** 事実を正確に分けます。

| | 公式FAQ（keepa.com `#!support`・日本語UI・2026-08-24 カズヨ実機） | 公式APIドキュメント（`product.html`・2026-08-24 サトル） |
|---|---|---|
| 対象 | **Keepa がバックグラウンドで自動追跡する頻度** | **API でリクエストした瞬間の鮮度** |
| 記述 | 「誰かがその商品をトラッキングしている場合は**1時間に1回**、していない場合は**1日1回**」 | 「**最後の更新が約1時間より古い場合、配信前に自動的にリフレッシュされ、ほぼリアルタイムの価格データが保証される**」 |

**結論（重要度：高）**
- **当社の夜間スキャンが取得する「価格・売れ筋ランキング・オファー数」は、リクエスト時点で最大約1時間の鮮度です。**「最大24時間古い」は**バックグラウンド追跡だけの話**であり、API を叩いた瞬間に更新が走るため当社には当てはまりません（`update` パラメータの既定値が 1 時間。追加トークンなし）。
- **ただし「offers 関連データ」は別で、カズヨの懸念はこちらでは正しいどころか、もっと深刻です。**公式は「**offers 関連のデータはすべて独立に、不定期に、他のデータより低い頻度で更新される**」と明記しており、`offers` パラメータを付けないリクエストでは**一切リフレッシュされません**。該当するのは以下です。
  - `NEW_FBA`(10) / `NEW_FBM_SHIPPING`(7) / `WAREHOUSE`(9) / `BUY_BOX_SHIPPING`(18) / **`RATING`(16) / `COUNT_REVIEWS`(17)** / 各中古・コレクター状態 / `PRIME_EXCL`(33)
  - **当社の Finder フィルタ `current_COUNT_REVIEWS 5〜300` はここに含まれます**（D11 の懸念を裏付ける）。
  - 鮮度は csv 15 `EXTRA_INFO_UPDATES` で**測れます**（公式：「絶対値＝その時点で取得したオファー数。正なら全件取得、負なら取りきれなかった」）。保存済み raw JSON から**0トークンで**分布を出せます。
- **したがって当社が点検すべきは「価格が古いか」ではなく「レビュー件数と FBA/BuyBox 系の履歴が何日前のものか」です。** 論点をここに絞ってください。

**確度**：**事実**（FAQ原文はカズヨ実機、API記述はサトルが公式HTMLで取得。両者は矛盾しておらず、対象が違うだけ）

### D8 `variationCount_gte=1` が、バリエーションの無い商品を全部落としていないか

- **該当箇所**：Finder `"variationCount_gte": 1, "variationCount_lte": 3`

- **確かめ方**：`variationCount_gte=0, _lte=0` で `totalResults` が返るか1回叩くだけ（**10トークン程度**）。
- **確度**：**推測（確度：中）**。公式に記述がないため断定しません。

### D11 レビュー件数フィルタ（5〜300）が古いデータの上で動いていないか
