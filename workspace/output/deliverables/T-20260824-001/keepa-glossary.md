**つまり「新品最安値」という同じ列の中で、2026-02-23 を境に意味が変わっています。**過去1年の最安値を取ると、前半は送料抜き・後半は送料込みの混在データになります。FBA/プライム品は送料0なので実害は小さいですが、**FBM主体の安価な商品では過去と現在を単純比較できません**。

#### この件に対して当社が採った対処（2026-08-24 決定・実装はタカシ／別セッション）

**「`stats.min` → `stats.minInInterval` に差し替える」という当初の修正案は取りやめました。**`minInInterval`(365日) は 2026-02-23 をまたぐため、**定義の違う値の最小値**になってしまい、「直したつもりで誤りが残る」からです。採用した方針は次の3点です。

| # | 対処 | 狙い |
|---|---|---|
| 1 | **主軸列＝2026-02-23 以降の窓で自前計算した最安値**（csv の NEW 履歴を境界日で切って最小値を取る） | **損益計算には定義が一貫した値だけを使う** |
| 2 | `minInInterval`(365日) は **`参考_365日最安(価格定義混在)`** という列名にして残す | 捨てない。ただし**名前で危険を宣言する** |
| 3 | **`価格定義混在` フラグ列を新設** | 境界をまたぐ商品を人が識別できるようにする |

> **次に読む人へ：**「`min` を `minInInterval` に直せばよい」と早合点しないでください。**期間の誤りと定義変更の誤りが二重に乗っている**のがこの列の実態です。列名に定義を書き込む（#2）のは、§0.5 の4列目を増やさないための当社の防御策です。

### 5.1 実例：`B0DWMPV656` — COUNT_NEW=2 なのに、実セラーは1社だった

抽象的な定義より、この1件を覚えてください。**当社が実際に踏んだ地雷です。**
出典：`workspace/output/deliverables/T-20260817-005/seller-count-defect-report.md`（タカシ／2026-08-24・Keepa API 実測。引用許可済み）。きっかけは**社長が Keepa 実画面で「セラー数1なのに候補に出ている」と気づかれた**ことでした。

| 項目 | 実測値 |
|---|---|
| `stats.current[11]`（**COUNT_NEW**） | **2** ← 当社はこれを「出品者2社」と読んでいた |
| `stats.offerCountFBA` / `offerCountFBM` | **1 / 1** |
| `liveOffersOrder`（生存中のオファー） | `[5, 2]` ＝ 2本 |
| その2本の `sellerId` | **どちらも `A37CWH39G3AT5D`** |
| **distinct sellerId（＝真の出品者数）** | **1** |

```
COUNT_NEW = 新品オファーの本数
          = Σ（各セラーが出している新品オファー）
          ≠ 出品しているセラーの数

  1社が FBA に1本 + FBM に1本 出す  →  COUNT_NEW = 2  だが 出品者は 1社
```

**さらに悪いことに、この1社はブランド所有者（`seathestars`）自身**でした（自社ブランド647商品）。
つまり当社の条件「出品者2〜6」が**通してしまったのは、v1.3 が最も避けたい「メーカー直販の独占リスティング」**です。この条件の意図は「**そのメーカーが実際に卸している証拠**を取る」ことなので、**条件の意図と正反対のものを通していた**ことになります。

**汚染は1件では済みませんでした**：v1.3 top100 の **35%**、GO 母集団の推定 **約39%** が「実セラー数 < 2」でした（タカシ実測／推定）。

**教訓（この節の要点）**
1. **オファー数と出品者数は別物。**Keepa に「出品者数」というフィールドは存在しません。
2. 真の出品者数は **`offers` を取得 → `liveOffersOrder` で生存オファーに絞る → `condition == 1`（新品）→ `sellerId` の distinct** でしか出せません（公式が推奨する手順。当社 `seller_count.py` はこの実装で**正しい**）。
3. **「同じ商品を1社が FBA と FBM の2本立てで出す」のは珍しいことではありません。**COUNT_NEW を出品者数の代理変数に使うと、この形が全部すり抜けます。

## 10. 補足：Keepa 公式 MCP サーバの存在（社長のご懸念に直接効きます）

社長のご懸念「**keepa を読み込む AI が用語の意味を履き違えている**」に対して、公式に用意された手段が2026年時点で存在します。

- **公式 MCP サーバ `https://keepa.com/mcp`**（`api-docs/mcp.html`）。Keepa が**ホスト型サービスとして自ら運用**。インストール不要。
- 認証は**既存の API アクセスキー**（Bearer）。**新規契約・追加課金は不要**で、消費するのは**現在契約中のプランのトークン**。
- **Claude Code 向けのセットアップコマンドが公式に記載されています**（1行）。
- 公式説明：「**応答はプログラム向けではなく言語モデル向けに整形されている**。コードを書くなら REST API を直接使え」「各ツールの説明にトークン単価が書かれ、各応答に残高が付くので、接続したアシスタントは自分で支出をペース配分する」。
- **注意（公式明記）**：「APIキーは秘密。**キーを埋め込んだ設定ファイル（例：チェックインされた `.mcp.json`）を共有リポジトリにコミットしてはならない**。キーを持つ者は誰でもあなたのトークンを使える」。

> **ここから先は当社の設定変更＝サトルの領分外です。** 導入可否・キーの取り扱い（当社リポジトリの `.mcp.json` は Git 追跡下にあります）は、**カズヨ経由でタケシ（プランナー）／ITエンジニアと社長判断**にお回しください。事実として「公式手段が存在し、追加課金は発生しない」ところまでが本調査の範囲です。
