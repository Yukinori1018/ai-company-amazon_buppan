1. 結論

推奨は「案C：macOS キーチェーン + headersHelper」です。 APIキーを平文でどのファイルにも置かず、リポジトリにも Notion にも載せません。

社長にお願いするのは キーを1回だけ貼る操作で、しかもシェル履歴にも残らない形で貼れます。

社長ご希望の Notion 保管は、MCP の仕組み上そもそも成立しません（§5 で技術的な理由を説明します）。ただしご希望の狙いである複数デバイス間の同期は、iCloud キーチェーンで自動的に満たされます — Notion を経由するより素直に解決します。

2. 社長が打つコマンド（3ステップ）

ステップ1 — キーをキーチェーンに登録する（社長のみ）

security add-generic-password -s keepa-api-key -a keepa -U -w

-w を値なしで末尾に置くと、対話プロンプトが出てキーを非表示入力できます。 → キーがシェル履歴（~/.zsh_history）に残りません。 macOS の security man ページも "Put at end of command to be prompted (recommended)" と明記しています。

Keepa のアクセスキーは Keepa アカウントの API ページに表示されているものです。

ステップ2 — ヘルパースクリプトを置く（社長・コピペのみ）

mkdir -p ~/.claude/scripts
cp "/Users/yukinori/Claude Code/ai-company-amazon_buppan/workspace/output/deliverables/T-20260824-001/keepa-auth.sh.template" \
   ~/.claude/scripts/keepa-auth.sh
chmod 700 ~/.claude/scripts/keepa-auth.sh

ステップ3 — MCP サーバを登録する（社長・コピペのみ）

claude mcp add-json --scope user keepa \
  '{"type":"http","url":"https://keepa.com/mcp","headersHelper":"'"$HOME"'/.claude/scripts/keepa-auth.sh"}'

このコマンド列のどこにも API キーの文字列は出てきません。 キーが登場するのはステップ1の非表示プロンプトの中だけです。

登録後に Claude Code を再起動 → claude mcp list に keepa が出れば完了です。

4. なぜこの方式か — 3案の比較

4.1 この会社に固有の、決定的な事情

本リポジトリは PUBLIC で、AI が30分ごとに git add -A して push します（F11）。

これが判断を決めました。.gitignore は現に機能していますが（F12）、この環境では防御が一枚しかありません。.gitignore の1行が消えるか、パスが変わるか、誰かが git add -f を打つか、キーを含む新しいファイル名が生まれた瞬間に、キーは全世界に公開され、しかも Git 履歴に永久に残ります（履歴からの除去は force push ＝ §4.1 該当で、事故後の対処コストが極めて高い）。

したがって設計方針は「gitignore を信じる」ではなく、「キーをリポジトリの物理的な外に出し、かつ平文で存在させない」とします。

4.3 案A を推奨しない理由（案A も悪くはありません）

案A（claude mcp add --scope user にキー直書き）は1行で終わり、リポジトリの外に出るので、それ自体は十分許容できる選択です。 実際、案C が何かの理由で動かないときのフォールバックはこれです（§8.2）。

それでも案C を推す理由は、追加コストが実質ゼロだからです。セットアップが2コマンド増えるだけで、以後の運用負荷は同じ（ゼロ）。その2コマンドで「平文がどこにも無い」「シェル履歴に残らない」「ローテーションが1コマンド」が手に入ります。

加えてこの会社の事情として、AI エージェントが日常的にファイルを読み、その内容がセッションログに残ります。「~/.claude.json を見て MCP の設定を確認して」と頼んだ瞬間にキーがログに載る、という事故が案A では起こり得ます。案C ではキーチェーンの中身は Claude の目に触れません。

YAGNI の観点でも過剰ではないと判断しました。増えるのは「1回きりの2コマンド」だけで、継続的な複雑さ（監視、ローテーション基盤、権限管理）は一切増やしていません。エンプラ的な仕組みは入れていません。

5. 社長ご希望の Notion 保管について

ご指摘の狙い（デバイス間で同期したい）は正しいと考えています。満たすべき要求です。ただし手段としての Notion 保管には、セキュリティ以前に技術的な障害があります。

5.1 そもそも「Notion から読み込む」経路が存在しません

MCP の Authorization ヘッダは、Claude Code が接続を張るときに設定から解決します。解決できる経路は3つだけです（F4/F5/F7）。

  1. 設定ファイルに書かれたリテラル文字列
  2. 環境変数 ${VAR} の展開
  3. headersHelper が stdout に出力した JSON

「Notion から読む」はこの3つのどれでもありません。 したがって Notion に置いたキーで MCP を設定するには、次のどちらかになります。

  • (a) 人間か AI が Notion を見てコピペする → 「1回貼る」が「毎回貼る」に増えるだけで、手間が純増します。
  • (b) headersHelper に Notion API を叩かせる → Notion のインテグレーショントークンという別の秘密を、どこかに平文で置く必要が生じます。秘密を守るために秘密を増やす循環で、しかも接続のたびに10秒制限の中でネットワーク往復が入ります（F7）。

5.2 セキュリティ面でも不利です

  • キーが第三者 SaaS に渡ります。 Notion 側では検索インデックス・エクスポート・共有リンク・インテグレーショントークン保有者に露出します。当社は Notion MCP を全エージェントが常用しているため、notion-search が偶発的にヒットする面も増えます。
  • 読み込むたびにキーが AI のコンテキストに載ります。 つまり Anthropic API に送信され、ローカルのセッション記録（~/.claude/projects/.../*.jsonl）に平文で残ります。案C ではこれがゼロです。
  • Keepa 公式も「キーは秘密。埋め込んだ設定を公開・共有するな」と明記しています（F3）。

5.3 結論

Notion 保管は採用しないことを推奨します。 ただし繰り返しますが、ご希望の本質（デバイス間同期）は案C が満たします（§6）。ご希望を却下しているのではなく、より素直な手段に置き換える提案です。

6. 複数デバイス間の同期をどう解決したか

同期の要求を2つに分けて考えました。

6.1 Mac ⇄ 他の Apple デバイス（Mac / iPad）→ 自動で解決します

iCloud キーチェーンが有効なら、キーチェーンの項目は Apple デバイス間で自動同期されます。 別の Mac では §2 のステップ2・3（スクリプト配置と MCP 登録、どちらもキーを含まない）を実行するだけで、キーを再入力する必要がありません。

Notion を経由するより手数が少なく、かつ安全です。

6.2 クラウド／モバイルのセッション → 対象外と割り切ります

これは正直にお伝えします。どの案でも安全には解決できません。

Claude Code のクラウド環境には専用のシークレットストアがまだ存在せず、公式が「環境変数はその環境を使う人なら誰でも読める」と警告しています（F9）。Notion に置いてもこの状況は改善しません（むしろ露出面が増えます）。

したがって Keepa MCP は「Mac のローカル回で使う道具」と位置づけます。 モバイルから Keepa のデータが見たい場合は、ローカル回で生成済みのスプレッドシートや成果物を参照してください。

これは当社の既存の割り切りと一致します。CLAUDE.md の成果物カタログ同期も「クラウド回は CSV 追記までに留めて、次のローカル回で同期する」という同じ形です。新しい例外を作らず、確立した前例を踏襲します。

7. ヘルパースクリプトの中身

keepa-auth.sh.template として同梱してあります。全文は短いので載せます。

#!/bin/bash
# Keepa MCP 用の認証ヘッダを生成する。
# キーは macOS キーチェーンにのみ存在し、このファイルには含まれない。
set -euo pipefail

KEY="$(security find-generic-password -w -s keepa-api-key 2>/dev/null || true)"

if [ -z "$KEY" ]; then
  echo "keepa-auth: キーチェーンに 'keepa-api-key' が見つかりません。" >&2
  echo "  security add-generic-password -s keepa-api-key -a keepa -U -w" >&2
  exit 1
fi

printf '{"Authorization": "Bearer %s"}\n' "$KEY"

設計上の注意点：

  • このスクリプト自体にキーは入っていません。リポジトリに置いても無害ですが、~/.claude/scripts/ に置く前提です（リポ外）。
  • 出力は stdout への JSON オブジェクト1個。これが headersHelper の要求仕様です（F7）。
  • エラーメッセージは stderr に出します。stdout を汚すと JSON パースが壊れるためです。
  • chmod 700 にしてください（他ユーザーからの実行を防ぐ）。
  • 接続のたびに実行されキャッシュされません（F7）。キーチェーン参照はローカル処理なので体感差はありません。

8. 運用

8.1 動作確認

  1. Claude Code を再起動
  2. claude mcp list → keepa が connected で出る
  3. 単発で軽い問い合わせを1回だけ試す（例：ASIN を1つ渡して価格履歴を聞く）

ヘルパー単体の確認は次でできます（キーは表示されません）。

~/.claude/scripts/keepa-auth.sh | python3 -c "import sys,json; d=json.load(sys.stdin); print('OK: ヘッダ生成成功, 長さ', len(d['Authorization']))"

8.2 うまく動かないときの切り分けとフォールバック

症状確認すること
keepa が list に出ないClaude Code を再起動したか。claude mcp list のエラー行を読む
認証エラー（401/403）キーチェーンの値が正しいか（§8.3 で入れ直す）。Keepa API サブスクが有効か
ヘルパーが動かない上の1行テストを実行。chmod 700 が効いているか。パスが絶対パスか
それでも駄目案A にフォールバック：claude mcp remove --scope user keepa した上で、claude mcp add --scope user --transport http keepa https://keepa.com/mcp --header "Authorization: Bearer <キー>"。リポ外である点は変わらないので、暫定運用として許容できます

8.3 キーのローテーション（Keepa 側で再発行したとき）

security add-generic-password -s keepa-api-key -a keepa -U -w

これ1コマンドだけです。-U が既存項目を上書きします。MCP の設定は触る必要がありません。Claude Code を再起動すれば次の接続から新しいキーが使われます。

8.4 トークン消費についての注意（運用上いちばん効きます）

Keepa MCP のツール呼び出しは、既存プランのトークンを消費します（F2）。新規課金は発生しませんが、AI が自分の判断で呼ぶぶんだけ減ります。

  • 公式仕様として、各ツールの説明にトークン単価が書かれ、応答に現在残高が載るため、AI は自分で消費を加減できます。
  • それでも、夜間自走やループ処理から無制限に呼ばせないでください。既存の夜間スキャン（T-20260803-001 系）と同時に走らせるとトークンを食い合います。
  • 用途は「対話中の単発調査」に限定するのが安全です。大量取得は従来どおり REST API を直に叩くスクリプト側で行ってください。 Keepa 公式も「プログラムから使うなら REST API を直接使え、MCP の応答は言語モデル向けに整形してある」と明記しています。

8.5 やめるとき

claude mcp remove --scope user keepa
security delete-generic-password -s keepa-api-key

2行目はキーチェーン項目の削除＝CLAUDE.md §4.1「不可逆な削除」に触れる可能性があるため、社長ご自身の判断で実行してください。エージェントは実行しません。

論点現設計での前提法務結果が「NG」だった場合の設計変更
1シート制／キーの共有範囲キーは社長個人のマシン1台（＋同一 Apple ID のデバイス）でのみ使用。第三者への共有なし変更不要の見込み。ただし「デバイス台数の上限」が規約にある場合は §6.1 の iCloud 同期を止め、1台に限定する

  1. クラウド／モバイルからの利用は解決できていません（§6.2）。 これは当社の設計不足ではなく、Claude Code 側にまだ機能が無いためです。プラットフォーム側にシークレットストアが実装されたら再検討する価値があります。
  1. .mcp.json.example には Keepa の項を追記しましたが、これは参考用です。推奨経路（ユーザースコープ）はリポジトリ外の ~/.claude.json を使うため、.mcp.json は本来不要です。プロジェクトスコープを選びたくなったときのために形だけ示してあり、キーのリテラルは書かず ${KEEPA_API_KEY} 参照と headersHelper の2形だけを載せています。
