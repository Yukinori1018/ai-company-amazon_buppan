# Sato-Scope Discovery — 利益が出る商品の自動リサーチ（プロト骨組み）

担当: タカシ（IT エンジニア） / チケット: T-20260521-005

「利益が出る商品を自動リサーチ → 利益一覧」が **本当に作れるのか** を、実際に動く
プロトタイプで証明するための骨組みです。

> 📍 **現在のデータソース状態（2026-06-04 タカシ実測・正直版）**:
> - **仕入れ元 Yahoo!ショッピング = 本番（実データ）稼働中**。社長取得の `YAHOO_APP_ID` で
>   商品検索API v3 ItemSearch に実接続済み。実在の仕入れ候補（商品名・価格・JAN・URL）が
>   取れることを確認した（キーワード次第でJAN付与率 45〜80%）。
> - **Amazon側（売値・月販・ランキング・在庫切れ率）= まだサンプル**。Keepa 未契約のため。
>   → したがって**画面に出る純利益・利益率は「Amazon側がダミー」であり確定利益ではない**。
> - **(い)仕入れ元起点モードは、本物JANをサンプルAmazonに突合するため利益ランキングは通常0件**
>   になる（架空JANと一致しないのが正常）。代わりに**生のYahoo実在候補テーブル**を表示する。
> - **Keepa を契約した瞬間に**、この実在候補へAmazon売値・月販が付き、初めて本物の利益
>   ランキングが完成する。それまでは「仕入れ元の実在確認」までが本プロトの到達点。
> - キーが無い環境では全自動でサンプルにフォールバックし、画面に黄色バナーが出る。

## 1. 何ができるか（PoiPoi風 3フェーズUI）

2026-06-09 改修で、社長提供動画『PoiPoiポケットを活用した自動化せどり戦略』に画面構成を寄せ、
**3フェーズ縦並び**にした（旧サイドバーradio方式は廃止）。

- **① 抽出条件（Phase1）**: 「抽出方法」を選んで Amazon側で対象を絞る。抽出方法は以下を統合:
  - カテゴリから自動で探す（Keepa Product Finder・キーワード不要・**おすすめ**）
  - キーワードで探す（電脳せどり）
  - 卸から自動で探す（NETSEA）
  - Amazon売れ筋から探す（旧・上級者向け）
  - **Keepaで作った検索条件URL/JSONを貼り付け（上級者向け・任意）** ← 新規
  - プリセットに **「PoiPoi標準」** を追加（出品者≥2 / 価格≥3,000円 / Amazon本体在庫切れ / ランク5〜15万位）
- **② 取り込み・実行（Phase2）**: 「リサーチ実行」ボタンで突合＋利益自動計算（PoiPoiのインポート→自動価格差計算に相当）。
- **③ 絞り込み・最終判断（Phase3）**: 計算済み結果に **後段フィルタ**（利益額≥ / 月販≥ / 利益率レンジ / 上限売価）を
  かける。**低リスク版（利益額≥500・上限売価≤10,000）ワンクリック**ボタンつき。さらに
  **最悪相場シミュレーション**（Keepa過去価格の最安まで下落しても黒字か＝損切り回避できるか）を🟢/🔴で表示。

利益計算は **経理ハジメ検証済みの `calc/profit.py`** に丸投げしています（後段フィルタも最悪相場シミュレーションも、
**計算は profit.py に委譲**し UI 側では1円も計算しない）。

```
                │   - discover_from_supplier()  ← (い)         │

                │   - フィルタ閾値は discovery/presets.py から   │
                └───┬──────────────────┬───────────────┬────┘
                    │                  │               │
        ┌───────────▼──────┐ ┌─────────▼────────┐ ┌────▼───────────┐
        │ adapters/        │ │ adapters/        │ │ calc/profit.py │
        │ yahoo_shopping.py│ │ amazon_data.py   │ │ (利益計算/検証済)│
        │  実API or サンプル │ │  Keepa or サンプル │ │  + calc/fees.py │
        └──────────────────┘ └──────────────────┘ └────────────────┘
              │  YAHOO_APP_ID         │  KEEPA_API_KEY
              ▼                       ▼
         無ければ sample_data/   無ければ sample_data/
```

**設計の肝**: 外部API（Yahoo / Keepa）は必ずアダプタ越し。`pipeline` も `calc` も
「Yahoo」「Keepa」という単語を一切知りません。だから将来 楽天API や SP-API に
差し替えても、アダプタ1ファイルを足すだけで下流は無改修です（ロックイン回避）。

## 3. 動かし方

```bash
cd code/
pip install -r requirements.txt

# テスト（サンプルでパイプラインが利益降順を返すことを検証）
python -m pytest discovery/
```

## 4. 本番データへの切り替え手順

`code/.env.example` を参考に環境変数を設定するだけ。**コード変更は不要**です。

```bash
export YAHOO_APP_ID="（Yahooで取得したClient ID）"   # (い)の仕入元データが本番化
export KEEPA_API_KEY="（Keepaで取得したキー）"        # Amazon側データが本番化
```

| キー | これが入ると | 入らないと |
|---|---|---|
| `YAHOO_APP_ID` | Yahoo!ショッピング実検索に切替（`_search_live`） | サンプルJSON |
| `KEEPA_API_KEY` | Amazon側が `KeepaBackend` に切替 | `SampleBackend` |

> ⚠️ `KeepaBackend` は現状 **TODOスタブ**（`resolve_by_jan` / `list_products` が
> `NotImplementedError`）。Keepa 課金は **CLAUDE.md §4.1（社長承認必須）**。
> 承認後、`adapters/amazon_data.py` の TODO コメント通りに実装すれば本番化します。
> Yahoo 側（`_search_live`）は **実クライアントを実装済み**。キーを入れれば即動きます
> （ただし実レスポンスでの最終検証は未。下記「制約」参照）。

## 5. 実運用に必要な API キーと取得方法

| データ源 | 必須キー | 取得元 | 費用 | 難易度 | §4.1該当 |
|---|---|---|---|---|---|
| 仕入元(Yahoo) | `YAHOO_APP_ID` | [Yahoo!デベロッパー](https://e.developer.yahoo.co.jp/dashboard/) | **無料** | 低（5〜10分・即発行） | × |
| Amazon側(案A) | `KEEPA_API_KEY` | [keepa.com/#!api](https://keepa.com/#!api) | **€49/月**（約8千円） | 低（カード登録のみ） | **○ 課金承認必須** |
| Amazon側(案B) | SP-API 認証一式 | Amazonセラーセントラル+AWS | アカウント無料 | **高**（IAM/LWA/署名…数日級） | × ただし設定が重い |

**Amazon側は案A(Keepa)と案B(SP-API)の二択**:
- **案A Keepa**: 月€49かかるが、JAN→ASIN・ランキング・出品者数・**在庫切れ率(90日)**・
  月販推定まで1本で揃う。電脳せどりに必要な項目がほぼ全部取れる。**実装も軽い**。
- **案B SP-API**: 無料だが、在庫切れ率や月販推定は直接は取れず別途推計が必要。
  認証セットアップが重く、レート制限も厳しい。**初手としては非推奨**。

> タカシの推奨: まず **Yahoo無料キーだけ入れて (い) を実データ半分で体感** →
> 手応えがあれば社長承認のうえ **Keepa €49/月** で Amazon側も本番化、が最短ルート。

## 6. 正直な制約（過大評価しないための注意）

1. **JAN突合のヒット率は不完全**。
   - Yahoo出店者が JAN を登録していない商品が一定数ある（同梱サンプルにも1件混ぜてある）→ その行は**突合不可で除外**。
   - 同じ商品でも JAN が複数あったり、セット品で JAN が親と違うケースがある。
   - 体感の実ヒット率は **商品ジャンル次第で5〜7割程度**を見込むのが現実的（要・実データ検証）。突合できた中から利益判定する前提。
2. **APIレート制限**。
   - Yahoo: アプリ単位の日次上限あり（数万req/日規模・公式要確認）。1検索=複数商品なので大量回しは要ページング配慮。
   - Keepa: トークン制。連続大量取得はトークン枯渇で待機が必要（実装側でレート制御要）。
3. **取得できない/弱い項目**。
   - 「実際の仕入可能在庫数」「最安値の変動予測」「Amazon相乗りの将来増減」は取れない。
   - (あ)で仕入元が見つからない商品は**想定原価率での仮置き**になる（画面に明示）。
4. **料率の鮮度**。`calc/fees.py` の Amazon手数料は2026時点の代表値。改定で変わるので実運用前に Seller Central で要再確認（経理ハジメ管轄）。
5. **Yahooの`_search_live`は実レスポンスでの最終検証が未**。キー入手後に1度、実JSONのキー名（`janCode`等）が想定通りか突き合わせが必要。
6. **ToS遵守**: 本ツールは**公式APIのみ**を使い、HTMLスクレイピングは一切しません。これは設計上の固定方針です（規約リスク回避 > コスト）。
