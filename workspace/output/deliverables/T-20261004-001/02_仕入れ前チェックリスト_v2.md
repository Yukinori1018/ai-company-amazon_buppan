機械用の定義：同フォルダ `checklist_spec_v2.json`（`scripts/sourcing_gate/checklist_spec.json` と同じ形式。差し替えはカズヨからタカシへ依頼）

## 結論

- **12項目 → 21項目**にします。増えた9項目は、サトルの提案 P1〜P6 で6項目、今日の貝印の事故から1項目（カタログ JAN の一致）、P7 を「採算等級」1項目に、P8 を「取り分と在庫月数」1項目にまとめたものです。既存12項目の id は変えず、うち7項目は落とす条件を厳しくしました
- 勝ち筋は「**文章のルールを、人が1つずつ PASS/FAIL を付ける項目に変える**」ことです。全項目を必須にし、1つでも FAIL・UNKNOWN・期限切れがあれば発注案を書けなくします（推奨 A 案）
- 過去の事故10件を机上で当てたところ、**10件とも v2 のどこかの項目で止まりました**（§5）。貝印 B01DBGGW8S は3項目で止まります
- **やらないこと**：①7日間の定点観測を全 SKU に一律でかけない（条件付きにする）②出品後・リピートのルールを発注ゲートに入れない ③機械で検査できるもの（卸値÷売価 70% など）を人の項目に増やさない

## 1. 設計の原則

| 原則 | 中身 |
|---|---|
| 1項目＝1つの事実 | 人が画面を1つ見れば PASS/FAIL を付けられる粒度にする。「該当しない」も事実なので、根拠を value に書いて PASS にする（例：「危険物でない：電池・液体・スプレーなし」） |
| 判定値は3つだけ | gate.py の判定値は PASS / FAIL / UNKNOWN。「要確認・未確認・不明」を value に書くと PASS にできない（gate.py の仕様）ので、読めないときは UNKNOWN |
| 鮮度は2段 | 市場で動く事実（カート・価格・在庫・実売など）は **3日**（§3.3-26 の実測）。商品の属性（危険物・法令・仕入れ先の取引条件）は **14日**。リピートは1.2〜1.5ヶ月ごとなので、14日でも発注のたびに取り直しになる＝§3.3-29「毎回やる」と矛盾しない |
| 段階 | 21項目すべて「発注前」。発注時・納品・出品後のルールは §6 に分けて置く（ゲートに入れると発注案を書く時点で埋められない） |
| 優先順位 | 社長の直接指示（CLAUDE.md・2026-10 の新しいもの）＞ 当社の実測 ＞ 本 |

## 3. 論点 A〜E の決定

| 論点 | 決定 | 理由 |
|---|---|---|
| **A. 現在価格が90日中央値より安いとき** | **§3.3-28 を正とする。** 安いだけでは保留しない。落とすのは「前半45日より後半45日の中央値が5%以上低い（下落トレンド）」と「振れ幅30%超（UNKNOWN）」だけ（#14） | §3.3-28 は2026-10-04 の社長直接指示。playbook の「5%安ければ保留」が避けたかったのは値崩れの最中に買うことで、それは傾きで判定できる。単発の安値（傾きは横ばい）は §3.3-28 の「買い時の可能性」に当たる |
| **B. 在庫を何ヶ月分まで持つか** | **上限は6ヶ月（社長既定・FAIL の線）。** 発注点数の目安は本に従い「取り分×1ヶ月」。3ヶ月超を許すのは、卸の最小ロットかゲート10点要件で引き上げられたときだけ（#10） | 6ヶ月は社長既定（feedback_dont_present_absurd_options）で動かさない。本の「初回1ヶ月・最大3ヶ月」は落とす線ではなく、発注数量を決める目安として使う。3〜6ヶ月の理由を2つに限ったのは、人が PASS/FAIL を付けられるようにするため |
| **C. 初回の利益率** | **A 等級（中央値も悲観値も利益率20%以上）は数量の制限なし。B 等級（中央値で5%以上・A でない）は最小ロットで1回だけ。C 等級（中央値で5%未満）は落とす。** 推定値の費目が1つでもあれば最高でも B（#18） | 社長の「実績ゼロなので利益率5%でも数を打つ」（2026-08-31）と §3.3-24 の B＝「最小ロットで1回実測」は同じ方向。5%を下限にしたのは社長の発言に合わせた。§3.3-24 の B は「悲観で赤字」だけだったが、「悲観で0〜20%」の行が等級なしになるので B に含めた。B は実測で A 相当が出たときだけリピートする（リピート段階のルール・§6） |
| **D. 定点観測** | **条件付き。** 必須にするのは「キーゾンと `monthlySold` が2倍以上食い違う」とき（#9）。最小ロットが重いときは #10 の在庫月数で止まるので、観測は追加の必須にしない | 一律必須だと全発注が7日遅れ、データの鮮度3日（§3.3-26）とも合わない。根拠が一致している行に観測を足しても、判定はほぼ変わらない。**Keepa の出品者別在庫を2時点で取れば観測は機械でできる見込みだが、API でどの粒度で取れるかは未検証。サトルに Keepa offers の在庫数（stockCSV 等）の取得粒度の調査が必要です**（取れれば7日→2時点に縮む） |
| **E. 項目数** | **21項目。** 17に縮めることもできるが、縮めると1項目に事実が2つ以上入り、人が PASS/FAIL を付けにくくなる | 統合したのは P3＋法令（#19）、P7（#18 に総原価を含めた）、P8（#10 に取り分と在庫月数）。増やしたのは貝印の事故から #16（カタログ JAN）。#1 と #2 は同じ画面だが、既存 id を残すため分けたまま |

**A の決定による改訂対象**（カズヨ経由で各担当へ）
- auto-memory `knowledge_sku_screening_playbook.md` 入口4「現在値が90日平均より5%以上安ければ値崩れ中で保留」→「90日の前半・後半の中央値で下落トレンドを判定。単発の安値は保留しない（§3.3-28）」
- 同 Step3（Buy Box 資格なしの価格）は #13 に吸収済みと注記

## 4. 案の比較（A/B/C＋推奨）

| | A：21項目すべて必須（推奨） | B：既存12は必須、新規9は警告だけ | C：17項目に統合して必須 |
|---|---|---|---|
| 想定リターン | 過去の事故10型を10型とも止める（§5） | 止まるのは5型（貝印・取り分・取り寄せ型は警告で素通りしうる） | 10型を止めるが、#19 や #18 に事実が4つ以上入る |
| 想定リスク | 1 ASIN の確認が約20分→約35分に増える（推測）。候補が0件になりやすい | 「警告は読まれない」。今回の事故（要確認のまま推奨）と同じ型が残る | 1項目に複数の事実＝人が「だいたい OK」で PASS にする |
| 撤退条件 | 4週間で発注案が1件も通らなければ、§3.3-21 に従い「どの項目で落ちたか」を集計し、#10（取り分3個）と #18（5%）の線を見直す | 警告を無視した発注が1件出たら A に移る | PASS にした項目の事後監査で、見落としが1件出たら A に移る |
| 必要な打ち手 | タカシ：spec 差し替え。カズヨ：成果物36の候補を v2 で確認（タスク5） | タカシ：警告表示の実装 | 項目の再設計 |

**推奨は A 案です。** 社長の指摘は「書いてあるのに抜ける」ことで、警告（B）では構造が変わりません。35分は、1件の誤発注（9/30 の鍋は約2万円が寝た）より安い賭けです。

### 期待値（推測・確度 低〜中）
- 人が実画面で見る候補のうち、21項目すべて PASS になる割合：中央値 10%、楽観 20%（確率20%）、悲観 3%（確率20%）、**期待値 約11%**。根拠は 2026-10-01 に機械 GO の6件が実画面で全滅したこと（0/6）と、9/30 の5件の全滅（0/5）。v1 でもこの歩留まりだった
- したがって SKU を月10件積むには、月 約90件を実画面で見る必要がある（10÷0.11）。ここが新しい律速になるので、機械で前処理する項目（§6 の「機械検査」）を先に落としてから人に回す
