## 2. 原因の切り分け（Git の履歴＝改ざんできない記録で確認）

### 2-1. 「自動同期が止まった」の正体＝ブランチの取り違え

| 事実 | 出典 |
|---|---|
| main の最後の Mac コミットは 9/6 19:50 | `git log origin/main` |
| `origin/claude/nighttime-work-checkin-iTWEa` には 9/6 20:57 以降 **1,193 コミット**（うち 1,120 件は Mac の `Yukinori` 名義）、最新は **10/16 08:05** | `git log origin/main..origin/claude/nighttime-work-checkin-iTWEa` |
| 自動同期コミット `chore(auto-sync)` は 9/7〜10/16 に **毎日1〜8件**、すべてこのブランチ | `git log --all --grep='chore(auto-sync)'` |
| github-sync は「カレントブランチだけを同期」する設計（T-20260817-007） | `.claude/scripts/github-sync.sh` 冒頭 |

**最初の診断（Mac が丸ごと止まった・pre-commit が commit を止めた、を有力とした）は誤りでした。** 手元の clone が main しか取っていなかったため、他ブランチの自動同期が見えていませんでした。動作確認で起動したクラウド巡回が全ブランチを取得していて「Mac の自動同期は正常（10/16 03:09）」と返したことで気づきました。

**なぜ Mac がそのブランチに移ったか**は Git からは分かりません（9/6 20:57 の最初のコミットの親が main の 9/6 19:50 なので、その間に切り替わった）。Claude Code のセッションが作業用ブランチを作って checkout したまま戻らなかった可能性が高いですが、推定です。

### 2-2. 巡回が本当に抜けた期間と原因

Mac 版ログ（ブランチ上の `workspace/monitoring/amazon-daily-check.md`）を判定スクリプトにかけた結果：

| 期間 | 状態 | 根拠 |
|---|---|---|
| 9/6〜9/12 | 9/10 以外は実行 | ログ見出し |
| **9/13〜10/10** | **28日連続で欠測**（番犬が「未実行」行を自動挿入） | ログ本文 |
| 10/11 22:37・10/13 14:31 | 手動で実行 | コミット時刻 |
| **10/14・10/15 12:10** | **定時実行に復帰** | コミット `chore(monitoring)…` |

欠測期間も Mac は起きていて、Claude も使われていました（例：10/5・10/12 は 11〜13時台にも Mac のコミットがある）。**「アプリが閉じていた」ではありません。**
Mac 側の記録（`.claude/hooks/scheduled_task_health.py`・10/10）に原因が書かれています：**予約実行は許可モード default で起動し、最初の許可画面で誰も押さないまま「実行中」で止まる。同じタスクの上限1件が埋まり、以後は一度も起動しない。** 10/13 21:12 に許可リストへ4ツールを追加（コミット 206aa06・社長承認済み）して、翌日から定時実行に戻っています。

### 2-3. 依頼時に挙がっていた仮説の判定

| 仮説 | 判定 |
|---|---|
| Mac が丸ごと停止（電源・スリープ・未起動・ログアウト） | **否定**。自動同期は毎日動いていた |
| github-sync の push 失敗（大容量・non-fast-forward） | **否定**。ブランチへの push は毎日成功している |
| pre-commit ゲートの失敗 | Mac では**否定**（commit は毎日通っている）。ただし**クラウドでは `mktemp` のバグでゲートが毎回素通り**していた（修正済み・§4） |
| スケジュールタスクの無効化 | **近い**。無効化ではなく、許可画面での停止（2-2） |
| **（新）Mac のリポジトリが main 以外のブランチに居た** | **主因**（2-1） |

## 4. 直したもの

| # | 部品 | 何をしたか | なぜ |
|---|---|---|---|
| 1 | **ブランチ逸脱の検知**（新設） | `.claude/scripts/sync_liveness.sh`：全ブランチを最大15秒 fetch し、最新の自動同期コミットが **main に無ければ警告**、24時間以上無ければ停止警告。SessionStart **リマインダー⑩**から呼ぶ（平常時は0行） | 今回の主因。main だけを見る人に、Mac が別ブランチに居ることを知らせる |
| 2 | github-sync | main 以外のブランチに居たら macOS 通知（6時間に1回）。分岐時は作業ツリーがきれいな時だけ通常の merge を1回試し、競合なら abort で元に戻す。commit/push 失敗も通知。Mac 絶対パスの決め打ちを廃止 | Mac の中でも気づけるように。失敗が誰も読まないログにしか出ていなかった |
| 3 | 判定ロジック `amazon_check_log.py` | `--ref auto`：**Mac が実際に書いているブランチ**からログを読む。判定は**日本時間**。警告は**直近7日の欠測だけ**（古い欠測は status に残す）。40日分の日付を区間表記に | main のログは古い。コンテナは UTC。永遠に鳴る警告は読まれなくなる |
| 4 | 番犬 | パスをスクリプト位置から求める（クラウドで `--status` が動く）。本体（ログ書き換え）は Mac 専用にガード | クラウドで走るとログを書き換えて分岐の原因になる |
| 5 | **クラウド巡回**（新設） | 手順 `.claude/commands/amazon-check-cloud.md`、記録 `workspace/monitoring/amazon-daily-check-cloud.md`（Mac 版とは別ファイル） | Mac に依存しない保険。書き手ごとに1ファイルにして分岐を防ぐ |
| 6 | pre-commit | `mktemp -t 接頭辞`（BSD 専用）を両対応のテンプレートに | Linux で毎回失敗し、fail-open で**クラウドの commit は一度も検査されていなかった** |
| 7 | SessionStart | GNU/BSD `stat` の順序を修正 | Linux で `stat -f` がファイルシステム情報を返し、リマインダー⑥にゴミが混ざっていた |
| 8 | 診断スクリプト | `.claude/scripts/mac-diagnose.sh`（読み取り専用。ブランチ・同期ログ・launchd・予約タスクを1画面に） | Mac 側の確認を1コマンドで |

**やらなかったこと**
- **Mac のブランチを main へ統合する merge**：試験 merge では競合2件（`session-start.sh`・`owner-tasks.md`）で、解決案まで作りましたが、**1,193 コミットを共有の main に入れる操作は権限の判定で止められたため実行していません**。§5 の判断事項にしました。
- セラーセントラルの自動ログイン（2FA・ToS 上不可）。

### 検証

- 判定ロジック：平常（無出力）／12:00 前は今日ぶんを鳴らさない／直近7日の欠測だけ警告／クラウド巡回の停止も警告／`--ref auto` で Mac ブランチのログを読む
- SessionStart：変更前の出力を保存して diff。⑩ が増え、⑤ が区間表記と Mac ブランチの値になり、⑥ のゴミが消えた以外は一致
- pre-commit：Linux で「卸値」を含む CSV を止め、普通のファイルは通す
- github-sync：使い捨てリモートで ①分岐→merge で解消→push ②競合→abort で HEAD 不変 を確認（Mac 実機ではない）
