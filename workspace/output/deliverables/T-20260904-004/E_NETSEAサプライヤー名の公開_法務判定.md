## 4. force push（A案）は有効か — **有効ではありません**

**「force push すれば消える」は誤りです。** 効果は「これから見に来る人が見つけにくくなる」までです。

1. **GitHub はダングリングコミットを即座には消しません。**参照を失ったコミットも `https://github.com/<owner>/<repo>/commit/32c6e7e…` の直接 URL で当分アクセスできます。確実に消すには GitHub Support へキャッシュ削除を依頼する必要があります（＝第三者連絡。§4.1）。
2. **既にクローン／コード検索インデックス／アーカイブに取り込まれていれば回収不能です。**push は 10:45、判定時点で約30分経過。fork 0 は有利材料ですが、保証にはなりません。
3. **コストが高い。**当該ブランチには T-20260826-004（Amazon アカウント停止対応）の成果物を含む他コミットが載っており、巻き添えになります。さらに `github-sync.sh` は**分岐（diverge）を検知したら何もせず終了**する設計（同スクリプト冒頭に明記）なので、**force push すると30分ごとの自動同期が止まります**。同期停止は別種の事故（成果物の消失）を招きます。

> **不可逆性は既に確定しています。A を選んでもリスクは実質減らず、同期停止という新たなコストだけが確実に発生します。**

## 6. 再発防止 — 「生成した瞬間に `.gitignore`」以外に手はあります

直接原因は、別セッションの `git add -A` が**未追跡の新規ファイルを拾った**ことです。現行の設計は**「既定＝載せる／例外＝除外を書く」**になっており、書き忘れが危険側に倒れます。これを反転させるのが本筋です。

| 案 | 内容 | 評価 |
|---|---|---|
| **① 既定除外＋ホワイトリスト（最有力・今日できる）** | `deliverables/<ticket_id>/.gitignore` の冒頭を `*` にし、追跡したいものだけ `!ファイル名` で明示する | **書き忘れが安全側に倒れる。**現行と逆。コストは1行。**推奨** |
| **② pre-commit フックによる機械的ゲート** | ステージ内容を検査し、`netsea.jp/shop/`・`卸値`・`仕入れ先:` 等のシグネチャを検知したら commit を中止。`github-sync.sh` は `git commit` を呼ぶので**自動同期にも効く** | **推奨。**ただし実装は IT エンジニア案件。秘書から発注が要る |
| ③ `github-sync.sh` の add 範囲を絞る（`git add -A` → 追跡済みのみ） | 新規ファイルは人が明示的に追加する | ①と組み合わせないと「成果物直納」ルールと衝突する。単独では不可 |
| ④ 行データは `agent_output/` に出す | deliverables には統計版だけ | CLAUDE.md §6 の「worktree 消滅で成果物ごと消失」対策と正面衝突。**採らない** |

**推奨は ①＋②。**①は法務でも書けますが、実装判断は秘書経由でお願いします。
