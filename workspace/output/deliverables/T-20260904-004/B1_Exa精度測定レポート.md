**② 英字の「連絡可 5社」は額面どおりではありません。**

## 5. 国税庁全件データ・gBizINFO はどうするか → **今は要りません**

Phase A（サトル）の推奨は「和名は国税庁全件データ → gBizINFO」でしたが、
今回の測定でこうなりました。

| 項目 | Exa で埋まるか | 公的DBが必要か |
|---|---|---|
| 正式商号 | 90%（和名） | 不要 |
| 所在地 | 90%（和名） | 不要 |
| 電話 | 80%（和名） | **公的DBには電話が無い**ので、そもそも代替にならない |
| 公式HP | 80%（和名） | gBizINFO の `company_url` は補完になるが必須ではない |
| 法人番号 | 50% | ここだけ公的DBが強い |

**法人番号はメーカーに連絡するのに要りません。** 商号・所在地・電話・フォームがあれば連絡できます。
法人番号が要るのは、取引が始まって請求書（インボイス）を扱う段階です。

→ **提案: 国税庁 Web-API と gBizINFO の利用申請（§4.1・社長の一手）は、今は保留してよい。**
Exa を約670社に流して連絡先を埋め、実際に取引が動いた社だけ後から法人番号を足す方が速い。
社長の手を1回節約できます。

なお法人番号が取れた6社のうち5社は、`houjin.jp` `datagojp.com` `companydata.tsujigawa.com` といった
**国税庁データの二次配信サイト**を Exa が拾ってきたものです（確度は「候補」扱い）。
エレコムの1社だけ gBizINFO（経産省）本体に当たっており、これは「確定」です。

### なぜ `needs_network = False` なのか（設計上の要点）

Exa は MCP 経由でしか使えず、Python から直接叩けません。したがって役割を分けました。

```
エージェント（タカシ）が Exa を叩く
    → 結果を pipeline/data/exa_lookups.jsonl に1社1行で追記
    → ExaLookupResolver がそれを読んでマージする
```

この形なら resolver 自身はネットワークに一切出ないので、
`config.json` の `allow_network: false`（法務ゲート）を**開ける必要がありません**。
将来 API キーを調達したら、JSONL の形を変えずにオンライン版へ差し替えられます。

優先度は `PRIORITY_SEARCH`（30）＝最弱に設定しました。
既取得55社や公的DBの値があればそちらが勝ち、Exa は空欄だけを埋めます。
