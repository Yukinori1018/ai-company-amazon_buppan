| 利益率の帯 | 旧前提 | 実測版 | 差 |

- 黒字から赤字に落ちた行: **9件**

> ハジメの見立て「中央なら20%以上の8割が維持」に対し、実測は **75%**。ほぼ一致します。
> **消えたのは主に薄利帯（5〜10%が11件→4件）です。** 1点160円の固定費は、
> 薄利の商品を狙い撃ちで殺します。**利益率5%を下限にする運用は、この費目を入れて初めて意味を持ちます。**

## 3. NETSEA送料を利益計算にどう入れたか

**商品ごとではなく、注文ごとに入れました。** 送料は注文に掛かるコストで、SKU に按分できるのは
「その注文に何を何個入れるか」が決まってからです。

- `/items` の `ship_fee` に値があるのは 257,067件中 **951件（0.37%）**。
  ＝ **99.6%の商品を「送料ゼロ」で利益計算していました**（ハジメ実測）
- 実額は `GET /tariffs`（サプライヤー別・都道府県別）にあり、これを実装済み
- `A_サプライヤー別サマリ.csv` に次の列を追加しました:

| 列 | 中身 |
|---|---|
| `この注文の送料(実費)` | その社の候補SKUを全部買ったときの実額（`/tariffs` 実データ） |
| `送料込みの見込み粗利` | 合計粗利 − 送料 |
| `初回送料無料を使えた場合の粗利` | 送料無料特集を使った場合（＝合計粗利） |
| `送料無料ライン` | **`price2==0` のときだけ**入る。「安くなる」は無料ではない |
| `送料無料ラインに届くか` | 届かない場合、**あといくら必要か**まで出す |

## 4. 低単価品の扱い（絞り込み方針の変更）

ハジメの逆算「1SKU 5,000円を10個（単価500円）だと必要掛け率40.8%で厳しい／
1個5,000円なら74.7%で楽」を、フィルタの**並び順**に反映しました。**除外はしていません**（判定材料として残す）。

追加した列:

| 列 | 中身 |
|---|---|
| `★仕入れ単価(税込)` | 1点あたりの実仕入れ単価 |
| `★1点あたり固定費` | 160円（成約料110＋納品代行12＋納品送料37.5） |
| `★固定費が仕入れ単価に占める割合%` | これが20%以上なら警告 |
| `★単価帯の警告` | 「低単価。固定費160円が仕入単価◯円の◯%を食います」 |

**警告のある行は並び順で下げます。** 予算5万円は「安いものを多数」ではなく
「単価の高いものを少数」に寄せる、というハジメの結論に沿った挙動です。

## 5. 再取得は不要でした（走行中のジョブは止めずに済む設計だった）

**生データと利益計算が分離されています。**

- `out/keepa_facts.jsonl` … Keepa から取った**事実**（価格・ランク・寸法・ASIN）
- `out/netsea_items.jsonl` … NETSEA から取った**事実**（卸値・JAN・在庫）
- 利益計算は毎回この2つから**再計算**される（`evaluate.py`）

したがってコスト前提の変更は **Keepa の再取得を1件も必要としません**。
検証済みの600件はそのまま活きています。

ただし**走行中のプロセスは古いコードを抱えたまま**なので（import 済み）、
そのまま走らせると次の CSV 出力（約3.5時間後）が旧前提のまま出ます。
そこで**ループを止めて再起動しました**。

| | |
|---|---|
| 失ったトークン | **0**（Keepa の結果は1バッチごとに JSONL へ追記済み） |
| 失った検証件数 | **0**（600件はキャッシュから再開） |
| 掛かり直したコスト | 段2 の再計算 約1.5分 |

50時間のやり直しにはなっていません。**長時間ジョブを4.5時間の周回に割ってあったことが効きました。**
