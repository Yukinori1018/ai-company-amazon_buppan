## 4. 直し方の推奨

### 4-1. 先にやること：未公開のメーカー条件を出さない（今日中・急ぐ）

| 案 | やること | §4.1 | 評価 |
|---|---|---|---|
| A | 伏せ字のコミットを足して、そのまま push | 該当しない | ✕ **履歴に残った実額が76件のコミットごと公開される。**伏せ字の意味がない |
| **B（推奨）** | **公開用のブランチを作り直す。**リモートにある基点から、伏せ字にした最終状態を1コミットで載せ、それを push する。今のブランチは消さずにローカルに残す | 該当しない（削除も force push もしない） | ○ 公開側に実額が一度も出ない。ローカルの細かい履歴は残る。失うのは公開側の細かいコミット履歴だけ |
| C | ローカル履歴を書き換え（rebase・filter-repo）てから push | **該当する**（破壊的な Git 操作） | △ 効果は B と同じ。バックアップブランチを取れば元に戻せるが、社長承認が要るうえ手数が多い |

- 手でブランチを main にマージするなど、別の経路で push しないこと（同じ理由）

### 4-2. 公開済みの (a) 11本：HEAD で伏せ字・履歴は残す（今週中）

1. 実額の行・列を「非公開（SD 規約17条）」「非公開（NETSEA API 規約15条）」と書き換える。結論（赤字か黒字か・等級・損益分岐の卸率の線）は残す

3. **伏せ字は公開ブランチ側にも反映する。**`claude/nighttime-work-checkin-iTWEa` は先頭に実額が残っているので、そのブランチにも伏せ字のコミットを普通に push する（早送りなので force 不要）。リモートブランチを消す方法は §4.1 の削除にあたり、しかもコミットは GitHub に残るので採らない

### 4-3. 履歴の書き換え（force push）は推奨しません

- **消えないから。**GitHub は参照されなくなったコミットも、SHA を指定した URL で当分見せる。本当に消すには GitHub Support への依頼が要り、これは第三者への連絡（§4.1）になる
- **自動同期が止まるから。**`github-sync.sh` は分岐を見つけると何もせずに終わる。force push すると30分ごとの同期が止まり、成果物が消える別の事故を招く

- **元に戻せないことが既に確定しているから。**公開されたのは遅くとも 10/20 で、1週間たっている。force push をしても、これから見に来る人が見つけにくくなるだけで、確定したリスクは減らない。費用だけが増える

## 5. 卸サイトに知られた場合のリスク

| 軸 | 評価 | 根拠 |
|---|---|---|
| 発生確率 | **低い** | fork 0・star 0。日本語の小さなリポで、卸サイトの担当者がたまたま見つける経路は GitHub のコード検索ぐらい。ただし、公開リポは検索の索引に入るので、ゼロではない |
| 影響の大きさ | **大きい** | SD：第10条(2)で、違反の認定がなくても予告なしに利用停止・登録抹消でき、第11条1項で賠償もされない。失うのは取引先2,176社の経路。NETSEA：会員規約8条2項1号で催告なく会員登録取消、API 規約12条1号で API 解除。主力の仕入れ経路と夜間の自動処理が止まる |
| 元に戻せるか | **戻せない** | 抹消された会員の再登録は相手の裁量で、保証されない。公開した事実も消せない |
| 金銭 | 小さい | NETSEA の違約金（会員規約27条3項）は第19条3項（サイト外での直接取引）の違反にだけかかるので、今回はかからない。一般の損害賠償（民法415条）は、相手が損害を証明しにくい |

**3軸の結論**：確率は低いが、影響が大きく元に戻せないので、警告を上げます。ただし公開から1週間たっているので、数時間を争う話ではありません。**急ぐのは未公開の §4-1 だけです。**

**相手への申告はしません**（CLAUDE.md §3.3-15）。黙って伏せ字にし、これ以上増やさない、で足ります。伏せ字にした記録（どの行を・いつ・なぜ）は、故意がなかったことの証拠になるので残してください。「弾かれたので消した」と読める書き方はしないこと（§3.3-14）。
