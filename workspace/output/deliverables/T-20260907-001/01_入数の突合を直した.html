1. 何が起きていたか（原因は2つ）

原因1 — 「解けなかった」と書きながら、入数1で利益を計算していた

pack.py は正しく「読めた数」と「自信が無い」を分けて返していました。判定は正しかったのです。
壊れていたのは受け取る側で、evaluate.py は要確認の印を付けたあと、
そのまま入数=1として利益計算を続け、CSV に利益率を書いていました。

if needs_review:
    ev.review_reason = ev.pack_reason      # 印は付ける
wholesale_for_listing = candidate.wholesale_ex_tax * ev.pack_size   # ← pack_size は 1 のまま

入数を無視すれば利益は入数倍に膨らむので、解けなかった商品が必ず利益率の上位に来ます。

印を付けることと、数字を出さないことは別です。 印は下流が読み飛ばせますが、数字は独り歩きします。
入数が解けていない行では ev.result を None のままにして、利益の列を空欄にするよう直しました。

原因2 — 助数詞の一覧に載っていない数え方は、黙って「入数1」になっていた

一覧に無い助数詞は「まとめ売りの表記なし」として素通りします。エラーにならないのが厄介でした。

表記読めていた値正しい値何が起きたか
160g×36食136「食」が無い。NETSEA の 6 と割り切れず要確認へ
×12本入×(2ケース)1224「ケース」が無い。NETSEA の 12 と一致し倍率1＝原価が半分

ケース・食・玉・束・巻・冊・組・膳・人前・ロール・杯・足・双 を追加しました。
追加したのは商品名に実際に書かれている数え方だけです。推測で埋めていません。

2. 途中で自分で見つけた取りこぼし2件（重要）

修正後の上位10件を点検したところ、1位と2位がまだ間違っていました。
そのまま提出していたら、直したはずの事故をもう一度起こすところでした。

Amazon商品名の実態読めていた値正しい値影響
…リハビリパンツＭ１６枚×４1664原価が実際の 1/4
…77.5g(2.5g×31包)×33193原価が実際の 1/3

原因は、末尾の「×N」を「他に個数が読めなかったときの代替」としてしか見ていなかったことです。
16枚 を読んだ時点で満足して、後ろの ×4 を丸ごと捨てていました。

_COUNT（数字＋助数詞）と _TRAILING_MULT（行末の数字・助数詞なし）は条件が排他なので、
足し合わせても同じ数字を二度数えません。 代替ではなく加算に変えました。

教訓: 「入れ子の掛け算に注意」とコメントに書いてあり、12個入（2種類×6個）×6袋 のような
複雑な入れ子のテストもありました。落ちていたのは 16枚×4 という一番単純な形です。
難しいケースを守って、易しいケースが素通りしていました。

3. 直っていないこと（推測で埋めない、と決めた部分）

3-1. 「両側が同じ数を読んだ」が誤りになる場合

ご指摘のとおりの論点です。NETSEA の商品名がケースを表していても、卸値は1個あたりの単価のことがあります。
その場合「NETSEA 15個 / Amazon 15個 → 倍率1」は誤りで、実際は15倍の原価になります。

これは商品名からは判別できません。日清フーズ バイオレット（1Kgx15 / 1kg×15個）が実例で、
売価が仕入の15.1倍という異常値が出ています。倍率が15なら、ちょうど帳尻が合う数字です。

推測で埋めないと決めたので、現状は比率ガード（売価が仕入の4倍超）に任せ、並べ替えから外しています。

3-2. 比率ガードは印を付けるだけで、数字を残している

config.SUSPICIOUS_PRICE_RATIO の説明には
「これを超えた行は利益判定を出さず要確認に落とします」と書いてありますが、
実装はそうなっていません（印を付けて計算を続ける）。原因1とまったく同じ形の食い違いです。

該当は 26,942行中 296行。数字を捨てる修正を入れると、
既存テスト10件の前提（卸1,000円 → 売価5,000円 ＝ 4.5倍）が壊れます。

今回は「まず並び順の汚染を止める」を優先し、下流の並べ替え側で要確認を除外する方針にしました。
契約（コメント）と実装のどちらに合わせるかは影響範囲が広いので、判断を仰ぎます。
