3. 判定1 — 商品URL単体は公開可

E の根拠（非ログインで見える）に、当職が2本の独立根拠を足します。これで3本足になり、単独論拠の脆さが消えます。

根拠①（E と同じ・実測） 卸値は非ログインで表示されない。逆に URL・社名・商品名・JAN は表示される。秘密として管理されていない情報に秘密保持義務は生じません（第15条1項は「秘密として保持し」と、対象が秘密であることを前提に書かれています）。

根拠②（新規・NETSEA 自身の意思表示） NETSEA は当該ページを検索エンジンに公開するよう自ら指示しています。

  • 商品ページの <meta name="robots" content="index,follow">（実測）
  • https://www.netsea.jp/robots.txt は /shop/ を一切 Disallow していない。冒頭で Sitemap: https://www.netsea.jp/sitemap.xml を公示（実測）
  • ページ内 JSON-LD に "url":"https://www.netsea.jp/shop/880827/na4902205323532" を自ら記載（実測）

→ 自らインデックスを要求している URL の転記が「開示または漏洩」に当たる、という解釈は成り立ちません。

根拠③（新規・条文の限定） 第15条1項の対象は「一切の情報」ではなく「本規約において提供された相手方の一切の情報」です。商品URLは API 経由でなくとも誰でも取得でき、規約に基づく提供を待つまでもありません。会員規約7条2項3号も「利用者の権利の行使の範囲を超えて」が要件ですが、非会員でも同じことができる行為は、会員としての権利行使に依拠していない以上「範囲を超えた利用」になりません。

残存リスク（明示します）

両規約とも「公知情報は秘密保持の対象外」という除外規定を置いていません。これは起草上の欠陥であり、文言だけを機械的に読めば URL も「一切の情報」に含まれ得ます。当職は明文主義を採る立場ですので、この点は隠しません。

軸評価
発生確率低。自らインデックスを要求している URL を問題視する動機が SynaBiz にない
影響度中（催告なしのアカウント停止）
不可逆性高（公開は取り消せない・停止は仕入れ導線の消滅）

→ 影響度と不可逆性が高いため、「Yes」に条件を付けます：価格・原価・利益に関する数値を伴わないこと、かつ §6 の名簿化に至らない少数掲載であること。この2条件を満たす限り公開可です。

4. 判定2 — 卸値と同じ行に並べるのは No

行ごと落としてください。URL だけ残して数値を消す、という部分対応も可としますが、行として載せるのは不可です。

理由は、URL がこの文脈では単なる出典ではなく識別子になるからです。卸値だけが単独で漏れても「どの商品のどの取引条件か」は特定できません。URL が同じ行に並んだ瞬間、特定サプライヤーの特定商品の会員限定価格という完成した情報になります。第15条1項の「開示」も会員規約7条2項3号の「範囲を超えた利用」も、ここで初めて実害を伴って成立します。

E の「黒いのは卸値だけ」は列の話としては正しいのですが、行として組み合わさったときの評価が抜けています。ここは E を補正します。

5. 逆算リスク（E に無い論点・重要）

卸値の数値を消しても、卸値が復元できる書き方があります。

同一行に「Amazon 価格」と「利益率」または「損益分岐仕入れ値」「想定仕入れ額」「利益額」が並んでいれば、FBA 手数料は公開されている以上、卸値は逆算できます。これは第15条1項の潜脱であり、数値そのものを検索して消す運用では防げません。

→ ルール：NETSEA 商品URL と「原価・利益に関する当社の計算値」を同一行に置かない。どちらか一方にする。

6. もう一つのレッドライン — サプライヤーの名簿化（価格と無関係）

会員規約第7条1項3号「本サービスを利用する他の者の情報の収集を目的とする行為」には、事前承諾による例外がありません（絶対禁止）。サプライヤーは「本サービスを利用する他の者」です。

  • 特定商品の仕入れ経路として1〜数件を引用する行為＝通常の仕入れ判断であり、収集を目的とする行為ではない。セーフ
  • サプライヤーを多数列挙した一覧を作って公開する行為＝価格が1件も無くてもアウト。7条1項3号に正面から当たる

→ 「卸値が無ければ何件並べてもよい」ではありません。件数そのものが独立の判定軸です。

7-1. 現状の何が誤っているか

netsea.jp/shop/ を「1件で止める強い印（＝NETSEA 卸値）」として扱う設計は、印と守りたいものが一致していません。守りたいのは卸値であり、URL は §3 のとおり公開情報です。

7-2. 誤検知の害（依頼で指摘のあった論点）

当職はこれを軽く見ません。ゲートが無害な作業を止めた実績が既に3回あり、バイパス手段（--no-verify／ALLOW_WHOLESALE_DATA=1）はフックのメッセージ自身が案内しています。誤検知が続く限り、バイパスは必ず常態化します。そのとき本物が来ても止まりません。

4件目が本書です。当職はこの判定書を commit しようとして自分のゲートに止められました（結論表のセルに検知語そのものを書いたため）。「この文字列は公開情報である」と論証した文書が、その文字列を含むという理由だけで公開できない。これが誤検知の典型です。当職はバイパスを使わず、結論表の文言のほうを書き換えて通しました。つまりゲートが文書の書き方を歪めています。これは無害な副作用ではありません。次に同じことが起きた者は、文言をいじるより --no-verify を打つほうが早いと学習します。

なお、html のセル抽出ロジック自体は設計どおり動いています（当職が最小ケースで検証。表の外の地の文は走査範囲に入りません）。実装の不具合ではなく、印の選び方の問題です。

法務としての評価：現在の設定は「保護効果ゼロ・バイパス習慣化リスク大」であり、安全側ではなく危険側の設定です。保守側に倒すというのは、印を増やすことではなく、印を当たりに行かせることです。
