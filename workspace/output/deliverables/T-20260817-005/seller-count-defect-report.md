# 「出品者数」欠陥の原因究明と対策 — Keepa COUNT_NEW はセラー数ではない

作成: IT エンジニア タカシ / 2026-08-24 / チケット T-20260817-005
きっかけ: 社長の Keepa 実画面確認（ASIN `B0DWMPV656` は「セラー数1」なのに候補に出ている）

> **この資料の読み方**
> 〔実測〕= 今回 Keepa API を叩いて確認した事実。〔推定〕= 標本からの外挿。〔未確認〕= まだ測っていない。
> 数字は1つも丸めていません。100件に届かないものは届かないまま書いています。

## 0. 結論（30秒）

1. **社長のご指摘は完全に正しく、原因は仮説どおりでした。** Keepa の `COUNT_NEW` は
   **新品オファーの本数**であって出品者数ではありません。1社が FBA と FBM の両方に出すと
   セラー1社でも `COUNT_NEW = 2` になります。`B0DWMPV656` の**実セラー数は 1**でした〔実測〕。
2. しかもそのセラーは **ブランド所有者 seathestars 自身**（自社ブランド647商品）で、
   v1.3 が最も避けたい「メーカー直販の独占リスティング」でした。
   「出品者2〜6」という条件の意図（＝**そのメーカーが実際に卸している証拠**）と正反対のものを通していました。
3. **汚染は1件のノイズではありません。** v1.3 top100 の **35%**、GO 母集団の推定 **約39%** が
   「実セラー数 < 2」でした〔実測 / 推定〕。
4. **1件の事実訂正**: `B0DWMPV656` は **v1.3 の候補リスト（`candidates_v13_top100.csv` / `candidates_v13.csv`）には入っていません**。
   出所は **T-20260804-001 のメーカー台帳**（Googleシート「⭐月販実測あり(60商品)」タブ）です。
   同じ欠陥が2つのチケットに別々に実装されていた、というのが正確な状況です。
5. 対策として `seller_count.py`（実セラー数の正しい数え方）を切り出し、`scan_v13.py` に
   **段0の必須条件「実セラー数 >= 2」** を実装しました。クリーン版 top100 を出力しています。

## 1. 原因究明 — `B0DWMPV656` で何が起きていたか

### 1-1. 実測データ（`GET /product?asin=B0DWMPV656&offers=20`）〔実測〕

| 項目 | 値 |
|---|---|
| `stats.current[11]`（COUNT_NEW） | **2** |
| `stats.offerCountFBA` / `offerCountFBM` | 1 / 1（＝社長の画面「Buy Box 対象オファー数 新品FBA:1 / 新品FBM:1」と一致） |
| `stats.buyBoxSellerId` | `A37CWH39G3AT5D` |
| `liveOffersOrder`（生存中のオファー） | `[5, 2]` = **2本** |
| その2本の `sellerId` | **どちらも `A37CWH39G3AT5D`** |
| セラー名（`GET /seller`） | **`seathestars(適格請求書発行事業者)T9240001017589`** |
| そのセラーの自社ブランド | `ｓｅａ　ｔｈｅ　ｓｔａｒｓ`（647商品・`productCountWithAmazonOffer` 0） |
| **実セラー数（distinct sellerId）** | **1** |

生存2本の内訳は `index 5 = FBA / 新品` と `index 2 = FBM / 新品`。
**同一セラーが FBA 用と FBM 用に2本出しているだけ**でした。

### 1-2. 他の可能性を潰す〔実測〕

社長・カズヨの仮説以外の説明が成り立たないことも確認しました。

| 疑った要因 | 結果 |
|---|---|
| コンディション違いの混入 | `offers` 配列の残り4本は全て**中古**（`condition` 2〜4）。COUNT_NEW（新品）には元々入りません |
| 別セラーが中古で出している | その4本は `ANNLLU4HTZVX9` = **`Amazonアウトレット`**。中古なので新品カウントに無関係 |
| 在庫切れオファーの残存 | `offers` には数か月前に消えたオファーが残る（`lastSeen` が最大305,740分＝約212日前）。だから `liveOffersOrder` で生存だけに絞る必要がある |
| 海外セラー | 該当なし（生存新品オファーは国内1社のみ） |

### 1-3. 機序のまとめ

```
Keepa COUNT_NEW = 新品オファーの本数
                = Σ（各セラーが出している新品オファー）
                ≠ 出品しているセラーの数

  seathestars が FBA に1本 + FBM に1本  →  COUNT_NEW = 2  だが セラーは 1社
```

v1.3 のフィルタ `current_COUNT_NEW_gte=2 / _lte=6` を「出品者2〜6社」と読み替えて実装したこと、
そして CSV の列名を **`出品者数`** としたことが誤りでした。

## 2. 汚染度の定量

### 2-1. v1.3 top100（**全100件を実測**）〔実測〕

| 指標 | 件数 |
|---|---|
| 実測できた件数 | 100 / 100 |
| **実セラー数 < 2** | **35件（35.0%）** |
| 　うち 実セラー数 = 1 | 34件 |
| 　うち 実セラー数 = 0（生存新品オファーなし＝実質リスティング死亡） | 1件 |
| CSV の `出品者数`(COUNT_NEW) と実セラー数が食い違う | 36件（36.0%） |

実セラー数の分布: `0:1 / 1:34 / 2:59 / 3:5 / 4:1`
（元 CSV の `出品者数` 分布は `2:94 / 3:6` — つまり **94件が「2社」に見えていた**）

**機序の内訳**（offers 取得と同時刻の COUNT_NEW を `csv[11]` の最終値から読んで判定）〔実測〕

| 機序 | 件数 |
|---|---|
| **同一セラーが FBA + FBM に二重出品**（＝カズヨの仮説どおりの主犯） | **23件** |
| COUNT_NEW 系列の更新ラグ（生存新品オファーは1本なのに COUNT_NEW=2 のまま） | 8件 |
| 生存新品オファー 0 | 1件 |
| スキャン後の3日間で本当に1社に減った | 3件 |

> 2番目の8件について正直に書きます。Keepa の COUNT_NEW は **独自の更新頻度を持つ時系列**で、
> `lastUpdate` が2〜4分前でも COUNT_NEW の最終データ点は **3,492〜124,590分前**（2.4日〜86日前）でした。
> 「定義の違い」か「単なるラグ」かはこちらからは分離できません。**どちらにせよ COUNT_NEW を
> 出品者数として使えないことは変わりません。**

### 2-2. GO 母集団の推定汚染率（**サンプルです**）〔推定〕

| 項目 | 値 |
|---|---|
| 母集団 | `candidates_v13.csv` の GO 2,479件から top100 を除いた **2,379件** |
| **標本サイズ** | **150件**（シード `20260824` 固定の単純無作為抽出） |
| 実セラー数 < 2 | **58件 = 38.7%** |
| 95%信頼区間（正規近似） | **約 31% 〜 46%** |
| COUNT_NEW と実セラー数が食い違う | 81件 = 54.0% |

実セラー数の分布: `1:58 / 2:47 / 3:24 / 4:11 / 5:9 / 8:1`

> **上限側も破れています。** 実セラー8社の商品が1件ありました（COUNT_NEW では6以下に見えていた）。
> 少数ですが「相乗り過多を弾く」側の条件も COUNT_NEW では担保できていません。

## 3. 対策（実装済み）

### 3-1. 正しい「出品者数」の求め方 — これが結論です

**`GET /product?asin=...&offers=20` を叩き、次の3段で数える。**

1. `liveOffersOrder`（生存オファーの index 配列）で **今生きているオファーだけ**に絞る
   — `offers` 配列には数か月前に消えたオファーがそのまま残っています
2. `condition == 1`（新品）だけを残す — 中古セラー（`Amazonアウトレット` 等）を混ぜない
3. `sellerId` の **distinct 数**を数える

**使ってはいけない代理変数**

| フィールド | 実体 | 使えない理由 |
|---|---|---|
| `current_COUNT_NEW` / `csv[11]` | 新品オファー数 | 同一セラーの FBA+FBM で二重計上。更新頻度も別 |
| `stats.offerCountFBA + offerCountFBM` | Keepa UI の「Buy Box 対象オファー数」 | これもオファー数（社長の画面の 1+1=2 がまさにこれ） |
| `stats.buyBoxSellerId` | カート獲得者1社 | 1社しか分からない |

> **Product Finder には distinct seller のフィルタがありません。** よって
> 「Finder で COUNT_NEW 2〜6 に粗く絞る → 詳細取得 → 段1・段2 → **通った行だけ offers で実セラー確定**」
> という二段構えが必要です（下記 3-3 のトークン事情による）。

### 3-2. コード変更

| ファイル | 変更 |
|---|---|
| `seller_count.py`（**新規**） | 実セラー数の数え方を1モジュールに切り出し。`seller_profile()` が実セラー数／セラーID／FBA・FBM本数／二重出品フラグを返す |
| `scan_v13.py` | 列 `出品者数` → **`新品オファー数`** に改名（列名が誤読の元だったため）。**`実セラー数` / `セラー名一覧` / `メーカー直販フラグ`** を追加。**Phase2.5** を新設し **段0 の必須条件に `実セラー数 >= 2`（上限6）** を適用。`--verify-sellers` / `--verify-limit` を追加 |
| 出力 | `candidates_v13_top100_clean.csv`（**実セラー数が実測済みで2以上の行だけ**）を新規出力 |

`raw_offers/` に offers レスポンスを gzip 保存しているので、閾値を変えた再集計は
`--from-raw --verify-sellers` で **トークン0** で回せます。

### 3-3. トークン単価（実測 2026-08-24 / domain=5）〔実測〕

| リクエスト | 単価 |
|---|---|
| `/product`（stats 付き・offers なし） | **1 トークン/件** |
| `/product?offers=20` | **約5.6 トークン/件** |
| `/seller`（100 ID まで1リクエスト） | **1 トークン/ID** |
| `/token`（残高確認） | 0 |

offers は素の product の**約6倍**です。GO 2,479件すべてに掛けると約14,000トークン＝
補充20/分で **約12時間**。だから「段1・段2 を通った行だけ・良い順に上から必要な分だけ」
掛ける設計にしました。

## 5. T-20260804-001（メーカー台帳）への波及〔報告のみ・未修正〕

**同じ欠陥があります。しかも根本原因は共有アダプタです。**

```
workspace/output/agent_output/T-20260521-005/code/adapters/amazon_data.py
  def _pick_offer_count(stats):
      """新品出品オファー数（相乗り出品者数の代理）。stats.current[11]=COUNT_NEW。"""
                          ^^^^^^^^^^^^^^^^^^^^^^ ここが誤り
```

- `maker_scan.py`（T-20260804-001）の基準②は **「FBAライバルセラー2人以上（current_COUNT_NEW>=2）」**
  と、コメントにもそのまま書かれています。`AmazonProduct.offer_count` を使う
  **全パイプラインが同じ誤りを引き継いでいます**。
- 影響範囲の目安〔実測（CSV集計）〕: `maker_products.csv` の `criteria_ok = True` 7,764行のうち、
  **`rival_sellers == 2` が 3,788行（48.8%）**。これが最も汚染されやすい帯です。
  `rival_sellers` が3以上でも二重出品ぶんだけ過大なので、帯全体が上振れしています。
- Googleシート「メーカー仕入れ台帳」の `ライバル数` 列、および `⭐月販実測あり(60商品)` タブの
  同列も同じ値です（`B0DWMPV656` の `2` がまさにそれ）。

RESULT_LEDGER_PLACEHOLDER

**修正はしていません**（本チケットの指示は報告まで）。着手するなら次の順で、別チケットが妥当です。

- A. アダプタ `_pick_offer_count` を残しつつ `real_seller_count` を新設し、呼び出し側を移す（**推奨**）
  — 既存の呼び出しを壊さず、名前で誤読を防げる
- B. `_pick_offer_count` を廃止して全面置換 — 影響範囲が広く、offers のトークン費用が全件に乗る
- C. 台帳の `ライバル数` 列に注記だけ足す — 安いが、次に見た人がまた同じ読み違いをする
