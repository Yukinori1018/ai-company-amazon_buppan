## 0. 結論（30秒）

1. **社長のご指摘は完全に正しく、原因は仮説どおりでした。** Keepa の `COUNT_NEW` は
   **新品オファーの本数**であって出品者数ではありません。1社が FBA と FBM の両方に出すと
   セラー1社でも `COUNT_NEW = 2` になります。`B0DWMPV656` の**実セラー数は 1**でした〔実測〕。
2. そのセラーは **ブランド所有者 seathestars 自身**（自社ブランド647商品）。
   v1.3 が最も避けたい「メーカー直販の独占リスティング」で、
   「出品者2〜6」の意図（＝**そのメーカーが実際に卸している証拠**）と正反対のものを通していました。
3. **汚染は1件のノイズではありません。** v1.3 top100 の **35%**、GO 母集団の推定 **約39%** が
   「実セラー数 < 2」でした〔実測 / 推定〕。
4. **1件の事実訂正**: `B0DWMPV656` は **v1.3 の候補リストには入っていません**。
   出所は **T-20260804-001 のメーカー台帳**です。同じ欠陥が2つのチケットに別々に実装されていました。
5. あわせて **D1〜D4（サトルの公式突合）も同じ修正に折り込みました**。結果、
   **修正前 top100 のうち 36件が入れ替わり、残った64件も中央値15位ぶん順位が動き、1位も交代**しました〔実測〕。
6. **前のリストはどれだけ信用できなかったか（社長が一番知りたい点）**:
   **並び順は信用できません。顔ぶれも3分の1が入れ替わります。** ただし
   「売れている商品を拾う」という当たり自体は外していません（下記5章）。

## 1. 原因究明 — `B0DWMPV656` で何が起きていたか

### 1-1. 実測データ（`GET /product?asin=B0DWMPV656&offers=20`）〔実測〕

| 項目 | 値 |
|---|---|
| `stats.current[11]`（COUNT_NEW） | **2** |
| `stats.offerCountFBA` / `offerCountFBM` | 1 / 1（＝社長の画面「Buy Box 対象オファー数 新品FBA:1 / 新品FBM:1」と一致） |
| `stats.buyBoxSellerId` | `A37CWH39G3AT5D` |
| `liveOffersOrder`（生存中のオファー） | `[5, 2]` = **2本** |
| その2本の `sellerId` | **どちらも `A37CWH39G3AT5D`** |
| セラー名（`GET /seller`） | **`seathestars(適格請求書発行事業者)T9240001017589`** |
| そのセラーの自社ブランド | `ｓｅａ　ｔｈｅ　ｓｔａｒｓ`（647商品・`productCountWithAmazonOffer` 0） |
| **実セラー数（distinct sellerId）** | **1** |

生存2本の内訳は `index 5 = FBA / 新品` と `index 2 = FBM / 新品`。
**同一セラーが FBA 用と FBM 用に2本出しているだけ**でした。

### 1-2. 他の可能性を潰す〔実測〕

| 疑った要因 | 結果 |
|---|---|
| コンディション違いの混入 | `offers` 配列の残り4本は全て**中古**（`condition` 2〜4）。COUNT_NEW（新品）には元々入りません |
| 別セラーが中古で出している | その4本は `ANNLLU4HTZVX9` = **`Amazonアウトレット`**。中古なので新品カウントに無関係 |
| 在庫切れオファーの残存 | `offers` には数か月前に消えたオファーが残る（`lastSeen` が最大305,740分＝約212日前）。だから `liveOffersOrder` で生存だけに絞る必要がある |
| 海外セラー | 該当なし（生存新品オファーは国内1社のみ） |

### 1-3. 機序

```
Keepa COUNT_NEW = 新品オファーの本数
                = Σ（各セラーが出している新品オファー）
                ≠ 出品しているセラーの数

  seathestars が FBA に1本 + FBM に1本  →  COUNT_NEW = 2  だが セラーは 1社
```

`current_COUNT_NEW_gte=2 / _lte=6` を「出品者2〜6社」と読み替えたこと、
そして CSV の列名を **`出品者数`** としたことが誤りでした。

## 3. 対策① — COUNT_NEW 問題（実装済み）

### 3-1. 正しい「出品者数」の求め方 — これが結論です

**`GET /product?asin=...&offers=20` を叩き、次の3段で数える。**

1. `liveOffersOrder`（生存オファーの index 配列）で **今生きているオファーだけ**に絞る
   — `offers` 配列には数か月前に消えたオファーがそのまま残っています
2. `condition == 1`（新品）だけを残す — 中古セラー（`Amazonアウトレット` 等）を混ぜない
3. `sellerId` の **distinct 数**を数える

**使ってはいけない代理変数**

| フィールド | 実体 | 使えない理由 |
|---|---|---|
| `current_COUNT_NEW` / `csv[11]` | 新品オファー数 | 同一セラーの FBA+FBM で二重計上。更新頻度も別 |
| `stats.offerCountFBA + offerCountFBM` | Keepa UI の「Buy Box 対象オファー数」 | これもオファー数（社長の画面の 1+1=2 がまさにこれ） |
| `stats.buyBoxSellerId` | カート獲得者1社 | 1社しか分からない |

> **Product Finder には distinct seller のフィルタがありません。** よって
> 「Finder で COUNT_NEW 2〜6 に粗く絞る → 詳細取得 → 段1・段2 → **通った行だけ offers で実セラー確定**」
> という二段構えが必要です。

### 3-2. トークン単価（実測 2026-08-24 / domain=5）〔実測〕

| リクエスト | 単価 |
|---|---|
| `/product`（stats 付き・offers なし） | **1 トークン/件** |
| `/product?offers=20` | **約5.6 トークン/件** |
| `/seller`（100 ID まで1リクエスト） | **1 トークン/ID** |
| `/token`（残高確認） | 0 |

offers は素の product の**約6倍**。GO 2,383件すべてに掛けると約13,400トークン＝
補充20/分で **約11時間**。だから「段1・段2 を通った行だけ・良い順に上から必要な分だけ」
掛ける設計にしました。

## 4. 対策② — D1〜D4（サトルの公式突合）を同じ修正に折り込み

### D1 ★★★「過去1年最安値」が実際は「全期間の最安値」だった — さらに落とし穴付き

**一次の誤り**: `stats.min[1]` は公式定義で「**これまでに記録された**最安値」。`stats=365` と無関係でした。
**二次の落とし穴**: では `minInInterval[1]`（365日）に替えればよいかというと、**替えられません**。
公式（product-object / changelog）によれば `NEW` 系列は
**2026-02-23 より前＝出品価格（listing price）／以降＝着地価格（＝出品価格＋送料）**と、
**同じ列の中で意味が変わっています**。今日は 2026-08-24 なので 365日窓は必ず境界をまたぎ、
**前半が送料抜き・後半が送料込みの混在データの最小値**になります。

**採用した実装**

| 列 | 中身 |
|---|---|
| **`過去最安値(送料込・2026-02-23以降)`** | **主軸**。保存済み raw の `csv[1]` から、境界以降に記録されたデータ点だけで自前計算〔0トークン〕 |
| `参考_365日最安(価格定義混在)` | `minInInterval[1]`。捨てずに残す |
| `価格定義混在` | 365日窓が境界の両側にデータ点を持つ行＝`はい`（**4,002行中 3,866行**） |
| `採用窓` | `2026-02-23以降`（3,915行）／`繰越(境界後の記録なし)`（87行） |
| `窓差率%` | （主軸 − 365日窓）÷ 365日窓 |

**損益分岐仕入れ値・損益分岐仕入れ値_精緻・仕入れ掛け率上限% は、すべて主軸の値で計算し直しました。**

#### D1 で数字がどちらにどれだけ振れたか（社長が誤解しないための数字）〔実測〕

窓を約6ヶ月に狭めたので、**「1年の底値」より高い最安値**になります。
→ **損益分岐仕入れ値は「甘く（高く）」出る方向**に振れます。修正前（全期間最安＝安全側に偏りすぎ）とは逆方向です。

`窓差率%` の分布（4,002行全件）:

| 窓差率 | 件数 | 割合 |
|---|---|---|
| **0%（同値・振れていない）** | **2,406件** | **60.1%** |
| 0〜5% | 392件 | 9.8% |
| 5〜10% | 372件 | 9.3% |
| 10〜25% | 461件 | 11.5% |
| 25〜50% | 179件 | 4.5% |
| 50%超 | 192件 | 4.8% |

> **6割の行は1円も動いていません。** 影響が出たのは 1,596件、うち **差が10%超は 832件**です。
> **この832件だけを人が見ればよい**（＝境界より前にだけ深い底があった行）。
> クリーン版 top100 に限れば、**0%が79件・10%超は15件**です。

#### D1 追加検証: 「FBA のみの行なら365日窓を使ってよいのでは？」→ **実測して不採用にしました**

送料が0なら境界前後で値は変わらないはず、という推論を**実測で検証**しました（0トークン）。

| 群 | 件数 | 比較可能 | 365日窓と境界後窓が**一致** |
|---|---|---|---|
| FBM オファー無し（`csv[35]` 最終値 = -1） | 199件 | 198件 | **117件（59.1%）** |
| FBM オファーあり | 3,363件 | 3,283件 | 1,919件（58.5%） |
| 判定不能（`csv[35]` 系列なし） | 440件 | 434件 | 318件（73.3%） |

**FBM 無し群の一致率 59.1% は、FBM あり群 58.5% とほぼ同じでした。**
つまり **FBM が無いことは何の保証にもなりません**（不一致の主因は送料ではなく、
「境界より前の期間にだけ深い底があった」という窓の狭まりそのもの）。
→ **追加2は不採用。全行を 2026-02-23 以降窓で統一しました。**

### D2 ★★★「BuyBox価格」列は Buy Box 価格ではなかった

`stats.buyBoxPrice` は `offers` / `buybox` パラメータ付きでしか設定されません。
Phase2 はどちらも付けていないため、**実際に入っていたのは常にフォールバックの `current[1]`
（＝NEW＝新品最安・2026-02-23 以降は送料込みの着地価格）**でした。

→ **(a) 列名を `新品最安値(送料込)` に改める**を採用しました（**0トークン・0円**）。
`仕入れ掛け率上限%` の分母はこの列です（＝「いま並んでいる売値の何%まで出せるか」）。

> **(b) 案の見積り（社長が後で選べるように残します）**: `buybox=1` を付けると
> **+2トークン/件**。3,000件で **6,000トークン**、補充20/分で **約5時間**。
> 本当の Buy Box 価格（送料別・`buyBoxShipping` が別フィールド）が取れます。
> 現時点では**採っていません**。掛け率の分母として使うなら「送料別」であることを
> 計算式に反映する必要があり、修正の範囲が広がるためです。

### D3 ★★ Amazon 本体判定が一時在庫切れの本体を取りこぼしていた

`current_AMAZON = -1` は「**今この瞬間 Amazon 価格が無い**」であって「Amazon が出品していない」ではありません。
専用フィールド `availabilityAmazon`（**-1 = Amazon のオファーが存在しない** / 0=在庫あり / 1=予約 / 2=不明 / 3=入荷待ち / 4=出荷遅延）を使います。

→ `evaluate()` に **`availabilityAmazon != -1` なら「Amazon本体あり」で除外**を追加〔0トークン・後段フィルタ〕。
　 Finder ペイロードにも `"availabilityAmazon": -1` を追記（**次回スキャン用**。今回は再クエリしていません）。

**効果〔実測〕: 保存済み 4,002行のうち 20件が新たに除外されました。**
社長方針「Amazon が出品している商品は除外」（2026-08-17）への取りこぼしが、実際に20件あったということです。

### D4 ★★「想定月販」の分母が COUNT_NEW のままだった

`est_monthly = drops30 / (COUNT_NEW + 1)` → **`drops30 / (実セラー数 + 1)`** に修正。

- 実セラー数が取得済みの行は **実セラー数** を使用
- 未取得の行は従来どおり COUNT_NEW を使用し、**`分母の根拠` 列**（`実セラー数` / `COUNT_NEW(未検証)`）で必ず区別できるようにしました
- **クリーン版 top100 は 100件すべてが `実セラー数` 基準**です（混在していません）

> この修正が **top100 の並び順そのものを変えます**（top100 は消化月数の昇順のため）。次章。

## 6. クリーンな候補リスト

**`candidates_v13_top100_clean.csv` — 100件ちょうど。水増しはしていません。**

| 指標 | 値 |
|---|---|
| 件数 | **100件**（GO 母集団から補充して充足） |
| 実セラー数 | **2社:91件 / 3社:9件**（全件が実測済み・2以上） |
| `分母の根拠` | **100件すべて `実セラー数`**（未検証行の混入なし） |

## 8. 範囲外だが確認した2件（D8 / D11）— **修正はしていません**

### D8 `variationCount_gte=1` は当たりでした 〔実測・33トークン〕

Finder に同一条件で `variationCount` だけ変えて投げ、`totalResults` を比較しました。

| 条件 | totalResults |
|---|---|
| `variationCount` 指定なし（ベースライン） | 647,546 |
| **`variationCount` 0〜0** | **97,484** |
| `variationCount` 1〜3（現行 v1.3） | 93,574 |

**`variationCount = 0` の商品は実在し、しかも現行フィルタが拾っている 1〜3 の帯より多い（97,484 > 93,574）。**
v1.3 の `_gte=1` は、この **97,484件を丸ごと落としています**。
バリエーションを持たない単品商品はメーカー仕入れの主戦場になりうるので、**母集団の作られ方が変わる論点**です。

> **これは母集団の設計＝方針の話なので、修正は社長／タケシの判断待ちにします。**
> 直すなら `variationCount_gte` を **0** に下げるだけ（0トークン・再スキャンは必要）。

### D11 レビュー件数の鮮度 → **「古い」以前に、こちらでは測れないことが分かりました** 〔実測・0トークン〕

保存済み raw 4,002件を調べた結果:

| 項目 | 結果 |
|---|---|
| `csv[17]`（COUNT_REVIEWS の履歴）が存在する商品 | **0 / 4,002件（0.0%）** |
| `stats.current[17]`（現在のレビュー件数） | **4,002件すべてが `-1`（データ無し）** |
| `csv[15]`（EXTRA_INFO_UPDATES＝offers 鮮度の指標）が存在する商品 | **0 / 4,002件（0.0%）** |

**`offers` を付けないリクエストでは、レビュー件数は履歴も現在値も一切返ってきません。**
つまり Finder の `current_COUNT_REVIEWS 5〜300` は **Keepa 内部のインデックス値だけで動いており、
こちらの手元データからは検証も鮮度測定もできません**。鮮度を測るには全件に `offers` を掛ける
（約5.6トークン/件）しかなく、**それ自体が5〜11時間コース**です。

> サトルの指摘「壊れているとは言っていない。**鮮度を測っていない**ことを指摘している」は正確でした。
> そして今回、**測る手段が手元に無い**ことまで確定しました。この論点は
> 「レビュー件数を機械ふるいの1つに使い続けるか」という方針判断に上げるべきです。
