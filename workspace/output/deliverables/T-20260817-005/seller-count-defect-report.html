3. 対策① — COUNT_NEW 問題（実装済み）

3-1. 正しい「出品者数」の求め方 — これが結論です

GET /product?asin=...&offers=20 を叩き、次の3段で数える。

  1. liveOffersOrder（生存オファーの index 配列）で 今生きているオファーだけに絞る

— offers 配列には数か月前に消えたオファーがそのまま残っています

  1. condition == 1（新品）だけを残す — 中古セラー（Amazonアウトレット 等）を混ぜない
  2. sellerId の distinct 数を数える

使ってはいけない代理変数

フィールド実体使えない理由
current_COUNT_NEW / csv[11]新品オファー数同一セラーの FBA+FBM で二重計上。更新頻度も別
stats.offerCountFBA + offerCountFBMKeepa UI の「Buy Box 対象オファー数」これもオファー数（社長の画面の 1+1=2 がまさにこれ）
stats.buyBoxSellerIdカート獲得者1社1社しか分からない
Product Finder には distinct seller のフィルタがありません。 よって
「Finder で COUNT_NEW 2〜6 に粗く絞る → 詳細取得 → 段1・段2 → 通った行だけ offers で実セラー確定」
という二段構えが必要です。

3-2. トークン単価（実測 2026-08-24 / domain=5）〔実測〕

リクエスト単価
/product（stats 付き・offers なし）1 トークン/件
/product?offers=20約5.6 トークン/件
/seller（100 ID まで1リクエスト）1 トークン/ID
/token（残高確認）0

offers は素の product の約6倍。GO 2,383件すべてに掛けると約13,400トークン＝
補充20/分で 約11時間。だから「段1・段2 を通った行だけ・良い順に上から必要な分だけ」
掛ける設計にしました。

4. 対策② — D1〜D4（サトルの公式突合）を同じ修正に折り込み

D1 ★★★「過去1年最安値」が実際は「全期間の最安値」だった — さらに落とし穴付き

一次の誤り: stats.min[1] は公式定義で「これまでに記録された最安値」。stats=365 と無関係でした。
二次の落とし穴: では minInInterval[1]（365日）に替えればよいかというと、替えられません。
公式（product-object / changelog）によれば NEW 系列は
2026-02-23 より前＝出品価格（listing price）／以降＝着地価格（＝出品価格＋送料）と、
同じ列の中で意味が変わっています。今日は 2026-08-24 なので 365日窓は必ず境界をまたぎ、
前半が送料抜き・後半が送料込みの混在データの最小値になります。

採用した実装

D2 ★★★「BuyBox価格」列は Buy Box 価格ではなかった

stats.buyBoxPrice は offers / buybox パラメータ付きでしか設定されません。
Phase2 はどちらも付けていないため、**実際に入っていたのは常にフォールバックの current[1]
（＝NEW＝新品最安・2026-02-23 以降は送料込みの着地価格）**でした。

→ (a) 列名を 新品最安値(送料込) に改めるを採用しました（0トークン・0円）。
仕入れ掛け率上限% の分母はこの列です（＝「いま並んでいる売値の何%まで出せるか」）。

(b) 案の見積り（社長が後で選べるように残します）: buybox=1 を付けると
+2トークン/件。3,000件で 6,000トークン、補充20/分で 約5時間。
本当の Buy Box 価格（送料別・buyBoxShipping が別フィールド）が取れます。
現時点では採っていません。掛け率の分母として使うなら「送料別」であることを
計算式に反映する必要があり、修正の範囲が広がるためです。

D3 ★★ Amazon 本体判定が一時在庫切れの本体を取りこぼしていた

current_AMAZON = -1 は「今この瞬間 Amazon 価格が無い」であって「Amazon が出品していない」ではありません。
専用フィールド availabilityAmazon（-1 = Amazon のオファーが存在しない / 0=在庫あり / 1=予約 / 2=不明 / 3=入荷待ち / 4=出荷遅延）を使います。

→ evaluate() に availabilityAmazon != -1 なら「Amazon本体あり」で除外を追加〔0トークン・後段フィルタ〕。
　 Finder ペイロードにも "availabilityAmazon": -1 を追記（次回スキャン用。今回は再クエリしていません）。

効果〔実測〕: 保存済み 4,002行のうち 20件が新たに除外されました。
社長方針「Amazon が出品している商品は除外」（2026-08-17）への取りこぼしが、実際に20件あったということです。

D4 ★★「想定月販」の分母が COUNT_NEW のままだった

est_monthly = drops30 / (COUNT_NEW + 1) → drops30 / (実セラー数 + 1) に修正。

  • 実セラー数が取得済みの行は 実セラー数 を使用
  • 未取得の行は従来どおり COUNT_NEW を使用し、分母の根拠 列（実セラー数 / COUNT_NEW(未検証)）で必ず区別できるようにしました
  • クリーン版 top100 は 100件すべてが 実セラー数 基準です（混在していません）
この修正が top100 の並び順そのものを変えます（top100 は消化月数の昇順のため）。次章。
