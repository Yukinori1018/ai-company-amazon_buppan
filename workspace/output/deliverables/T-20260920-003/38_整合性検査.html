機械は「落とす」だけ、「通す」には人が要る（3項目）

#項目機械でできること／できないこと

15Amazon 側のセット構成確度が「確定・単独」なら通す。「不一致・不明・食い違い」は1 と決め打たず UNKNOWN

人が実画面・書類・現物で見るしかない（12項目）

ゲート種別／出品ボタンの状態／ゲート書類の成立／仕入れ先が Amazon 出品を許しているか／新品出品者数と内訳／

知財申立てのサイン／実売（ASIN単位）／生産終了でないか／カタログ JAN と納品物の一致／卸の取引条件／

理由は3つに分かれます。①ログインの先にしか無い（セラーセントラル・卸の会員画面）、

②形の読み取りが要る（出品者数グラフの崖落ち、価格線が水平、条件文の「△」）、

③現物が来ないと分からない（納品物の JAN、期限の表記）。

🔴 #9 実売は、データがあっても人に回します。§3.3-16 で「最後は人が実数を見るまで確定しない」と決まっており、
月販の表示が無いのと3か月0個は機械では区別できません。

設計で意識的に決めたこと

  1. 入力が無い検査は「不合格」ではなく「対象外」。 空欄を NG にすると、2回目の実行で自分が空けた欄を

自分が NG にし続けて永久に収束しません。

  1. 数字を黙って直さない。 どちらが正しいか分からないので、NG の行は採算欄を空にするだけです。

捨てた値は consistency_report.json に原本ごと残します（隠すのではなく、独り歩きを止める）。

  1. 番兵も採算欄を空にします。 印を付けながら数字を出し続けると、解けなかった行が必ず利益率の上位に来ます

（2026-09-07 に実際にそれで上位10件が全滅しました）。

  1. 売価と日付は消しません。 採算の*入力*であって結果ではなく、消すと「なぜ落ちたか」が読めなくなります。
  2. timeline_stale は警告に留めました。 NG にすると、表が1日古くなるだけで648行ぜんぶの数字が消えます。

§3.3-17 の「空にする」は算術が崩れている行への処置です。鮮度は発注ゲート側が ASIN ごとに見ています。

  1. 料率は「どの段か」を当てません。 カテゴリーがCSVに無いので、どの段でもないことと

崖の向きを間違えていることだけを見ます（出所に依存しない検査にする）。

4. 確認記録を 2件 → 648件 に

scripts/sourcing_gate/autofill.py。候補CSVから機械で決まる項目だけを記録します。

対象 648 ASIN × 21項目 = 13,608件の判定
  PASS 2,723件（20%） / FAIL 302件（2%） / UNKNOWN 10,583件（78%）
  • human の12項目を PASS にしません。 UNKNOWN ＋「なぜ決まらないか」＋「取り方」を書きます。空欄で埋めません。
  • 🔴 人が付けた記録を機械が上書きしません。 checked_by が autofill 以外の記録は触りません。

実際に B008FIPMP2（カズヨの20項目）と B01DBGGW8S（12項目）はそのまま残り、空いていた項目だけが埋まりました。

  • 整合性検査が NG の行は、採算の項目を PASS にしません。
  • PASS は「買ってよい」ではなく「人が実画面で見る価値がある」の意味です（§3.3-16）。

発注ゲートを通る ASIN は 648件中 0件です。 未充足は最小15項目・最大20項目。

これは仕組みの失敗ではなく、当社がまだ1件も人の確認を終えていないという事実がそのまま出ただけです。

5. 発注ゲートに繋ぎました

gate.py が記録の consistency キーを見るようにしました。

21項目が全部 PASS でも、整合性検査が NG なら発注案を書けません。

21項目の○は「人が見た事実」の記録であって、「表の算術が合っている」ことの保証ではない ── 別の軸なので別に止めます。

実機で確認済み：

  • 21項目を全部 PASS にして consistency: NG を入れると、order-gate-guard.py が exit 2 で書き込みを止める
  • check_record.py set <ASIN> consistency --result PASS で手から通す道は無い（consistency は spec に無い id なので弾かれる）
  • 既存のフック回帰テスト 53件 は全部通ったまま（ゲートを緩めていない）

6. 検算（§3.3-17「2回目で0行になるまで完成していない」）

回書き換えた行
1回目648行（整合性検査 列が新規なので全行）
2回目0行
3回目0行。1回目の出力とバイト一致

収束のしかけ：採算欄を空にすると、その欄を使っていた検査は次回「対象外」になって所見が消えます。

素朴に印を書き直すと毎回変わって収束しないので、既にある印と詳細を読み戻して新しい所見と和を取るようにしました。

消えた所見は「前回こう落ちた」として残り、新しい所見だけが増えます。印が消えて行が健全に見えることは起きません。

さらに、是正後のCSVを check にかけると所見は0件になりますが、それを「健全」と読み違えないよう

「🔴 前回の NG の印が残っている行 8行」を必ず併記するようにしました。

7. テスト（80件・全件通過）

python3 scripts/sourcing_gate/test_consistency.py

  • 検査ごとに「崩れている行で鳴る」「正しい行で鳴らない」の両方を見ます。片方だけだと、常に鳴る検査と絶対鳴らない検査が緑のまま通ります
  • 縮退した入力（§3.3-20）：全項目が空欄／全項目が同じ値（1）／1行だけ／ヘッダだけ／採算の列が無いCSV／セット数が不明で採算を止めている行。いずれも化けず、NG にもなりません
  • 年末年始をまたぐ日付の鎖（12/28 → 01/05）を逆順と誤判定しない
  • num() が 「未確定（月販非表示・3ヶ月で仮置き）」を 3 と読まない（仮置きが確定値に化ける事故を防ぐ）
  • 金額はすべて架空の合成値。PUBLIC リポなので実際の取引条件は1つも書いていません

テストを書いて見つけた自分の間違い

最初に「good_row() の正しい等級は B」と書いてテストが6件落ちました。

実際は悲観の手残り 1,500円 が下限400円を超えるので A が正しい。コードではなくテストの前提が誤りでした。

ここで規定と実装の食い違いを1つ見つけました（§3.3-22 の型）。

**CLAUDE.md §3.5 の等級の定義は「A＝中央値も悲観値も利益率20%以上」ですが、実装は
「利益率20%以上 または 手残り400円以上」の OR です。**
OR は 2026-10-04 の社長指示（「単価ではなく利益額で切る」・実践者N=6は全員が単価の下限を置いていない）に基づくもので、
実装の方が正しく、文書が追いついていません。
検査は実装＝社長指示に合わせました。§3.5 の表の修正をお願いします（下の「社長判断」参照）。

8. 使い方

# 検査するだけ（何も書き換えない）
python3 scripts/sourcing_gate/consistency.py check <候補CSV> [--private <卸値つきCSV>] [--show]

# 是正する（NG行の採算欄を空にし、印を立てる）。必ず2回走らせて0行を確認する
python3 scripts/sourcing_gate/consistency.py fix <候補CSV> --out <出力> --report <JSON>

# 機械で決まる項目を記録する（人の記録は上書きしない）
python3 scripts/sourcing_gate/autofill.py <候補CSV> [--private <...>] [--coverage] [--dry-run]

# 発注してよいか
python3 scripts/sourcing_gate/check_record.py verify <ASIN>...

--private には卸の取引条件を持つCSV（agent_output/ 専用）を渡します。

卸値・卸率・最小発注数・卸サイトのURLはコードにもテストにも書いていません。
