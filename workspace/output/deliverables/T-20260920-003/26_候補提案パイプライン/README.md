## 標準手順：**外部 API のフィルタは、使う前にプローブする**

Keepa Product Finder は**知らないフィールドをエラーにせず黙って無視します**。
`{"bogusField_gte":1}` でも HTTP 200・`error:null` で返り、件数は無条件検索と同じ。
**綴りを1文字間違えると、フィルタが効かないまま「条件どおり抽出できた」と誤認します。**

```bash
python3 product_finder.py --probe 'monthlySold_gte=50' 'current_SALES_lte=100000' 'bogusField_gte=1'
#   monthlySold_gte     有効  baseline 265,341,900 → 443,300
#   current_SALES_lte   有効  baseline 265,340,200 → 12,086,900
#   bogusField_gte      ★無視されている★  265,340,000 → 265,340,000   ← 対照
```

**やり方**：ベースラインの `totalResults` を取り、フィールドを1つ足して件数が動くかを見る。
動かなければ無視されています。**必ず「効かないはずの対照フィールド」も1本混ぜる**
（対照が「有効」と出たら、プローブ自体が壊れています）。1プローブ約11トークン。

これで実際に2つの誤りを見つけました。
- 🔴 `current_AMAZON_lte=-1`（本体不在）は **該当0件**。**私の過去メモが誤っていました。**
  Keepa は -1 を「データなし」の印に使っており、価格として比較できません。
  本体の有無は後段の `outOfStockPercentage365` で判定します（それが正しい方法でもある）
- `monthlySold_gte` は**有効**（2.65億件 → 443,300件）。入口条件に使えることを確認

**この手順は Keepa に限りません。**「フィルタを指定したのに件数が減らない」は、
黙って無視される API すべてで起きます。**減ったことを確かめるまで、絞れたと思わないこと。**

## 判定は GO / NO-GO / UNKNOWN の3値

**UNKNOWN を GO に畳みません。**「調べれば分かる」と「調べて駄目だった」を混ぜると、次に何をすればいいのかが分からなくなります。

| # | チェック | 落ち方 |
|---|---|---|
| 1 | カートの販売元（独立3根拠の一致） | 本体なら FAIL／根拠が1本 or 食い違いなら UNKNOWN |
| 2 | 本体の365日在庫履歴（`outOfStockPercentage365`） | 在庫率が高ければ FAIL |
| 3 | 出品一覧の実数（ライブの新品オファー） | 本体が混ざれば FAIL／一覧が打ち切られていれば UNKNOWN |
| **5** | **メーカー直販・ブランド公式**（新規） | セラー名がブランド名を含めば FAIL／「公式」を名乗るが一致しない・オファー1社ならUNKNOWN |
| **生存** | **その棚に市場があるか**（唯一の積極条件） | 90日平均ランクが50万位より下で月販も無ければ NO-GO |
| **単位** | **Amazon 側のセット数** | 個数が読めないセット品は UNKNOWN（原価の倍率が確定できない） |
| **仕入れ** | **卸の商品ページが特定済みか**（§3.3-6） | `購入先URL` が未確認なら UNKNOWN |
| **品目** | **賞味期限管理が要るカテゴリか** | ドラッグストア／食品・飲料／サプリは UNKNOWN＋「要期限管理」 |
| 採算 | 赤字・**実質赤字**・**手残りが誤差幅未満**・回転6ヶ月超 | 赤字は FAIL、誤差幅未満は UNKNOWN |

**落とすのはこの3つだけです**（2026-09-30 カズヨ訂正 / CLAUDE.md §3.1）:
①カート保持者が Amazon 本体 ②カート保持者がメーカー本人／ブランド公式 ③今の価格と今の卸値で1個あたり赤字。

⚠️ **月販（`monthlySold`）を GO/NO-GO のフィルタに使いません。**列には出しますが、それだけでは落としません。
`monthlySold` は月50個未満だと Amazon が表示しないだけで、「売れていない」ではありません
（社長が発注を決めた B0DJNX12KZ はキーゾン実測で月10個）。社長は条件を緩めています
──「最初は入口を多く持ちたい。利益が少なくても、量を増やせば、何とかなる可能性があるかもしれない。
やった後で評価し、継続判断を行う」（2026-09-30）。

1つでも FAIL → NO-GO、FAIL が無く UNKNOWN が残る → UNKNOWN、全部 PASS → GO。

その結果、**誰も売っていない棚だけが全部のゲートを通り抜けます。**

#### 閾値の校正（実測・2026-09-30）

| 90日平均ランク | 実際の売れ方 |
|---|---|
| 2,900 / 3,600位 | 月200個 / 月500個（`monthlySold` 表示あり） |
| **24,150位** | **月10個**（キーゾン実測。社長が発注を決めた B0DJNX12KZ。`monthlySold` は出ない） |
| 680,000〜1,650,000位 | **3か月で 0〜3個** |

ここから2本の線を引きました（`ALIVE_RANK` / `DEAD_RANK`）。

| 条件 | 判定 |
|---|---|
| `monthlySold` が取れる | **PASS**（実際に売れている。唯一の積極的な根拠） |
| ランク **10万位以内** | **PASS**（死んでいない。月10個の実例が24,150位） |
| ランク **10万〜50万位** | **UNKNOWN**（売れているとも死んでいるとも言えない。人がキーゾンで3か月を見る） |
| ランク **50万位より下** | **NO-GO**（直近3ヶ月の実績が実質ゼロ） |
| 90日平均は圏外だが現在10万位以内 | **UNKNOWN**（新規で伸びている途中かもしれない） |
| ランクが取れない | **UNKNOWN** |

⚠️ **ランクは「死んでいないこと」の確認に使い、「売れている」の根拠にはしません。**
バリエーションのランクは family 共有なので、兄弟が売れていれば死んだ子にも順位が付きます。
ドロップ数は観測回数であって販売数ではないので使いません（memory: `knowledge_keepa_dropcount_is_polling`）。
**だから GO は「発注してよい」ではなく「人がキーゾンで実数を見る価値がある」という意味です。**

#### 「月100個以上」のフィルタとは別物です

社長が緩めたのは**閾値**の話です（「最初は入口を多く持ちたい。利益が少なくても、量を増やせば……」）。
**ゼロは閾値ではありません。量を増やしても、ゼロは何倍してもゼロです。**
だから `monthlySold` が無いことは落とす理由にしません（月10個の B0DJNX12KZ は通します）が、
**実績が実質ゼロの棚は落とします。**この2つを混ぜないこと。

**この生存ゲートは発掘の段（`discover.py`）にも掛けています。**
売れていない棚をプールに入れると、後段の §3.3 判定で 6トークン/ASIN 払ってから落とすことになります。
発掘の段ならランクは既に手元にあるので**追加トークン0**で落とせます。

### 仕入れが実在するかの段（§3.3-6）

**卸サイトの商品ページ URL が特定できていない行は GO にしません。**URL が無い＝在庫・入り数・卸値のどれも裏が取れていない、という意味です。

2026-09-30、利益率64.7%で断トツだった B0015XNJMW（オリヒロ 玉葱エキス粒 600粒）は、
§3.3 の3点（カート＝第三者・本体不在・キーゾン平均10個/月）を**通過**しましたが、
**Amazon の JAN 2本が NETSEA に1件も存在せず、仕入れ自体がありませんでした**。
私は「内容量の不一致を疑え」と申し送りましたが、疑うべきは**その前段の「買う先があるか」**でした。

**賞味期限管理が要るカテゴリ**（ドラッグストア／食品・飲料／サプリメント／栄養補助食品／酒類）は、
FBA の残存期間要件（60日以上で納品・45日で販売不可）と混合在庫の制約、
さらにカテゴリー型ゲート（ブランド申請では開かない）が絡むため、**UNKNOWN＋「要期限管理」**にします。初回の SKU には使いません。

### 手残りが誤差幅を下回る行は GO にしない

**誤差幅 = 売価 × 7% + 200円。**これを下回る手残りは「儲かる」でも「損する」でもなく**読み切れていない**ので、UNKNOWN にします。

| 項 | 根拠 |
|---|---|
| 売価 × 5% | BuyBox 価格の振れ。Keepa の値は取得時点のスナップショット |
| 売価 × 1.4% | 販売手数料の読みの差（Keepa の率を税抜とみて ×1.1 するか否か） |
| ＋200円 | 保管料・納品送料・梱包資材の 206円は**商品台帳 L001 という1点の観測**を全商品に当てている。大型・重量物では数倍になるので、全額を誤差と見る |

売価に比例させたのは、**高額品ほど誤差が大きい**からです。売価26,800円のソファカバーの手残り355円は、
誤差幅2,076円の中に埋もれています（利益率2.1%）。一方 3,900円の商品の手残り645円は誤差幅473円を超えます。
**固定の±300円では高額品を取りこぼし、低額品を通しすぎます。**

NO-GO ではなく UNKNOWN にしているのは、**人が実額（送料・サイズ区分・今の売価）を詰めれば GO になりうる**からです。

### 単位を揃える段（`set_count.py`）

**卸サイトは「1点あたり」で売り、Amazon は「N点セット」で売ります。**突き合わせる前に単位を揃えます。

2026-09-30、カズヨが実画面で発見。B0DJNX12KZ は Amazon 側が **【2点セット】…×2点セット**、
NETSEA 側は **1点920円（税抜）**。私は原価1,012円/個として**利益率33.3%・GO** と出しましたが、
正しい原価は **2,024円/個**で **手残り ▲227円/個**。損益分岐売価3,194円に対し売価2,980円。
**手数料をゼロにしても+278円**しか残らず、どう組んでも黒字になりません。バリエーション7種も全部「2点セット」系で単品版の ASIN はありません。

- 商品名の `【N点セット】` `×N点セット` `N個セット` `N枚組` `Nパック` `N袋` `セット数:Npcs` `ペアセット` を読み、**原価 = 卸単価 × N**
- **読めないときは 1 と決め打たず None → UNKNOWN**（人が見る）。1 にすると原価をN分の1に見誤ります
- 複数の読みが食い違ったら None（黙って片方を採らない）
- `set_num`（NETSEA の最小発注ロットの倍数）とは**別の概念**。`amazon_set_count` は**原価の倍率**、`set_num` は**発注数の丸め**
- 数えない語を持っています: 「600粒」「420ml」「幅30×奥行30」は個数ではない／「ヘッドセット」「簡単組立」「富士パックス販売」はセット品ではない

### チェック5（メーカー直販）の作り

`maker_direct.py`。Keepa の `/seller` でカート保持者の**名前**を引き、ブランド名・メーカー名と突き合わせます。

- 名前がブランド／メーカー名を含む → **FAIL**（`サンワサプライ直営【サンワダイレクト】`・`マーナ公式 アマゾン店`・`SOLCION公式ストア`）
- 「公式」「直営」を名乗るが、ブランド名との一致は取れない → **UNKNOWN**（人が実画面で見る）
- 新品オファーが1社だけ → **UNKNOWN**（「オファーが少ない」は有利の証拠ではなく、メーカーが1社で売っているサインのことがある）
- セラー名が取れない → **UNKNOWN**（「名前が無いから直販ではない」は 9/30 の事故と同型）

比較は法人格（株式会社・Co.,Ltd. 等）と記号を落として NFKC で畳んでから。短い英字の鍵（`ISM`）は完全一致のみ（`PRISM` に当てない）。

## （参考・上記の訂正対象）供給の向きについての当初の所見

**落ちた理由の85%が「生存」＝その棚に市場が無い。**
これは個別の商品の問題ではなく、**供給の設計の問題**です。

いまの流れは **NETSEA → Amazon**（「卸にあるものが、Amazon で売れているか？」）。
NETSEA の承認済みサプライヤーが持っている棚は、**Amazon で売れていないものが大半**でした。
実測：JAN 248件 → Amazon にヒット167件 → 生きている棚は104件 → 候補8件 → **GO 0件**。

必要なのは逆向きです。**Amazon → NETSEA**（「売れている棚を、NETSEA で買えるか？」）。
Keepa Product Finder で「`monthlySold` が付いている／ランク上位・本体不在・出品者少」から入り、
その JAN が NETSEA にあるかを突合します。**生存を入口の条件にしてしまえば、後段で85%を捨てずに済みます。**

キュー（JAN 14,672件・残り174社）はそのまま使えますが、**この向きのままトークンを注ぎ込むのは効率が悪い**ので、
先に逆順の供給を作ることを勧めます。

### 🔴 SD が 429（Too Many Requests）を返しました（2026-09-30）

**その日の125リクエストのあと、SD がレート制限をかけてきました。**

最初の実装はこれを**1件ずつの失敗として飲み込み**、「JAN 付き0件」という
**無害そうな結果**を返していました。原因は trace の中だけにあり、標準出力からは
「SD に何も無かった」ように見えます。**「相手に無い」と「こちらが止められた」を混ぜていました。**

直した内容:

- `Fetcher.RateLimited` という**専用の例外**にし、429/503 で**全体を即停止**する（1件の失敗にしない）
- **自動で再試行しません。**待つ以外に正しい対処が無いので、人が判断します
- 打ち切りの理由を**標準出力に出し、終了コード 2 を返す**（ルーチン・フックが気づける）
- `report_stop()` が「上限到達（＝異常ではない・0）」と「レート制限（＝2）」を書き分ける

**規約違反ではなく行儀の問題ですが、跳ね返るのはアクセス制限や会員資格です。**
当社は 11/30 のサイトオープン条件を背負っているので、ここは踏みません。
**法務ハルオへ規模の再判定を依頼中**で、判定が出るまで SD への取得は止めています。

### 冪等の鍵を「JAN だけ」にしなかった理由

鍵は **(仕入れ先, JAN)** です。同じ商品が NETSEA と SD の両方にあるなら、それは
**安い方を選べるという情報そのもの**なので、別行で残します。
同一の仕入れ先で入り数の違う口（SD の S1＝2点・S2＝3点）が複数あるときは
**入り数の小さい口を残し、落とした口を備考に書きます**。黙って捨てると
「1セット3点しか無い」を「1点で買える」と読み違えます。

### 空欄を作らない／推測で埋めない

| 状態 | 書く値 | 書かない値 |
|---|---|---|
| 卸価格が取れない | `未確認` | **0** |
| SD の承認が無い | `卸価格未承認` | 「不可」「無し」（申請すれば見える） |
| NETSEA API に項目が無い（消費者直送可否） | `未確認` | 推測の ○/× |
| 該当 ASIN が不明 | `未確認` | 「なし」 |

税込化は `×1.10` 固定です。`consumption_tax_class`（0/1/99）の意味が公式スキーマに無いので
**推測で 1.08 にしません**。原価が高く出る側（保守側）に寄せ、税区分の番号を備考に残します。
**原価を安く見積もる方向の推測はしません**（利益が出る方向に間違えるので）。

## 既知の制約（正直に）

- **NETSEA の `set[].price` は「1個の値段」、`set_num` は「最小発注ロットの倍数」**として扱っています。人が実額で検算した3行（B0DJNX12KZ・B0FN3NWKYZ・B0171AC6PI）に合わせた解釈です。**一度これを割ってしまい、卸率1.5%・利益率71% という嘘の数字を台帳に書きました**（同じ実行で直しています）。JAN が同一でも入り数の違う口があると原価を読み違えます。**発注の直前は人が卸サイトで単価を見てください**
- **JAN 突合でしか卸値を当てられません。**JAN が無い候補は採算が計算できず UNKNOWN になります
- **キーゾンの列（平均月販・過去1〜3ヶ月）は埋めません。**Keepa の `monthlySold` を「平均月販」の欄に入れ、出所を明記しています。キーゾンは人が画面で見るものです
- **ゲート（出品許可）は判定しません。**全件「未確認」
- 赤字判定は「今の Amazon 価格」基準です。価格が戻れば成立する棚もありますが、**戻る前提の提案はしません**
- **`1個粗利` は成果物22・23 と同じ定義**（販売手数料＋FBA配送代行＋原価を引いたもの）で、保管料・納品送料・梱包資材を**含みません**。それらは `profit.OTHER_UNIT_COSTS_YEN = 206`（台帳 L001 実測）として別に持ち、**手残りがマイナスなら「実質赤字」で NO-GO**にします。シートの `1個粗利` 列は22・23 と揃えるため粗利のまま入れています
- `--asins` で ASIN を直接指定しても、**プールの卸値・手数料は引き継ぎます**。引き継がないと採算が計算できず、GO だった行を UNKNOWN で上書きします（9/30 に一度やりました）
- **ランクと内容量は `判定理由` の先頭に `【ランク 90日平均 24,150位・現在 20,748位】【内容量 600粒】` の形で書いています。**
- **内容量は `判定理由` の先頭に `【内容量 600粒】` の形で書いています。**台帳は32列固定（条件付き書式が列位置に紐づく）なので列を増やさず、人が最初に読む欄に置きました。列を1本増やす判断が出れば移します
- **セット数は商品名からの読み取りで、実物の確認ではありません。**「中身の量が違う」型のずれ（卸は300粒・Amazon は600粒 など）は**商品名では見抜けません**。`set_count.py` が拾えるのは「N点まとめ売り」だけです。**発注の直前は人が卸サイトと Amazon の両方で内容量を見てください**
- 販売手数料は **Keepa の率 ×1.1**（税抜表示とみなす）で計算しています。当リポの既定（成果物22・23、商品台帳 L001）に合わせた**いちばん保守的な**読みで、税抜のまま見る場合より手数料が1割高く出ます

## 🔴 まとめ売り突合（2026-10-01 追加・`set_family.py`）

### なぜ要るか — 単品では構造的に黒字になりません

カズヨが SD の実画面で卸価格を取り、**日用消耗品の単品は数式の上で成立しない**ことが確定しました。

必要な売価の下限 = **(821 + 1.1 × 卸値税抜 × n) ÷ 0.8376**

- 分子の固定ぶん **821円** = FBA 配送代行 415 ＋ 保管/納品/資材 206 ＋ 誤差幅の固定ぶん 200
- 分母 **0.8376** = 1 − 販売手数料 9.24%（税込）− 誤差幅 7%
- **固定費は Amazon の1個につき1回しかかかりません。**だから n（1個が卸の何点か）を増やすと
  1点あたりの必要売価が下がります

| n | 必要売価（卸178円/点のとき） | 1点あたり |
|---|---|---|
| 1 | **1,214円** | 1,214円 |
| 2 | 1,448円 | 724円 |
| 3 | 1,681円 | 560円 |
| 5 | 2,149円 | 430円 |
| 10 | 3,318円 | **332円** |
| 20 | 5,655円 | 283円 |

**1個1,214円のたわしは売れません。**だから「×10点セット」等のまとめ売りを1商品として出し、
固定費を10個で割るのが前提になります。`required_sell()` / `required_sell_table()` /
`min_profitable_set_count()` がこの計算です。

### 🔴 JAN は単品とセットで同一 — だから JAN 突合はいつも単品に当たる

旭化成 ズビズバ あみたわし（4901670106107）は、SD の「1点」「×10点」「×200点」が**すべて同じ JAN**。
**9/30・10/1 の単位ずれは、個別の読み間違いではなくこの構造が原因でした。**

### 🟢 救い — Keepa の `code` 逆引きは、はじめからセット品を全部返していた

2026-10-01 に実測（1リクエスト・10トークン）。JAN 4901670106107 の1回で **10 ASIN**。

採る基準は「ランクが一番上位」＝ほぼ単品。つまり**まとめ売りの口があるのに、
必ず赤字になる口だけを見て落としていた**という作りでした。

`parentAsin` と `variations` も同じレスポンスに入っているので `extra_asins()` で拾えます
（採算を見るには `stats` が要るので、安い段 1トークン/ASIN で取り直してください）。

### セット数は「商品名 × packageQuantity」の独立2本で決める

`packageQuantity` は**商品名の正規表現とは独立した2本目の情報源**です（CLAUDE.md §3.3-17）。

| 状態 | `confidence` | 倍率 | GO に進めるか |
|---|---|---|---|
| 商品名と `packageQuantity` が一致 | `確定` | その値 | **進める** |
| 食い違う（B00H2E0JLW: 商品名2・pq 1） | `不一致` | **大きい方** | ✗ UNKNOWN |
| 片方だけ読めた・n = 1（単品） | `単独` | 1 | 進める |
| 片方だけ読めた・n > 1 | `単独` | その値 | ✗ UNKNOWN |
| どちらも読めない | `不明` | None | ✗ UNKNOWN |

- **食い違ったら大きい方**で計算します。**原価を安く見積もる方向へは推測しません。**
- `numberOfItems` は**判定に使いません**。1 が既定値として入る実例があります
  （B01MCR1XMK は ×3個セットなのに `numberOfItems = 1`）。記録だけ残します
- `packageQuantity` は **1〜1000** まで受けます（商品名側の上限60では ×200 の大口を切り落とす）
- `packageQuantity = 0 / -1` は「データなし」。**0 を「0個セット」と読みません**

### 卸側の口（1点 / 10点 / 100点）を選ぶ

`set_family.pick_mouth()`。**1点あたりが安い口 → 余りが少ない口**の順で選び、
`入り数` が読めない口は**候補から外します**（1 と決め打つと原価を取り違えます）。
選べる口が無ければ `mouth=None`（＝UNKNOWN。人が卸サイトを見る）。

🔴 **SD の卸価格を受け取る形が変わりました（`価格の単位` が必須）。**

```json
{"13681795S1": {"卸価格": 178, "価格の単位": "1点あたり",   "入り数": 1,  "承認状態": "承認済み"},
 "13681795S2": {"卸価格": 1600, "価格の単位": "1セットあたり", "入り数": 10, "承認状態": "承認済み"},
 "13681795S3": {"承認状態": "卸価格未承認"}}
```

同じ JAN に複数の口が並び、**画面の数字が1点あたりなのか1セットあたりなのかは口によって違います**。
`価格の単位` が無い行は **`wholesale_price_excl` を埋めず、理由を `notes` に残します**
（推測で埋めれば 9/30・10/1 に続く3回目の単位ずれになります）。
`1セットあたり` のときは `入り数` で割って1点あたりに直し、**割り切れないときは切り上げ**ます。
雛形: `agent_output/T-20260920-003/pipeline/sd_wholesale.example.json`

### 既知の制約（正直に）

- **ファミリが10倍に増えるので、段B（6.9トークン/ASIN）の予算配分は変わりません**が、
  0トークンのゲート（生存・売価なし・確定した赤字）で大半が落ちます。
  実測（ズビズバ1家族・卸178円）: 10口 → 死2・赤字6 → **候補2件はどちらも UNKNOWN**
- **上代を「1点あたりの実売」の代理に使っています。**上代は Amazon の実売より高めに出るので、
  `tier()` は**並べ替えの材料**でしかありません。採算の結論は後段（実売価・実手数料）で出します
- **セット品 ASIN が Amazon に無ければ、まとめ売りは成立しません。**この実装は
  「あるものを拾う」だけで、**無いものを作りません**（新規ASIN登録は別の話）
- **`extra_asins()`（parentAsin / variations）はまだ本線に繋いでいません。**
  安い段で取り直す配線が要るので、ファミリの実測が溜まってから判断します
