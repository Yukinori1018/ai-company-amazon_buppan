当社の失敗は**人の注意力で防げる種類のものではなかった**ので、機械の検査にしました。

### 人が実画面・書類・現物で見るしかない（12項目）

ゲート種別／出品ボタンの状態／ゲート書類の成立／仕入れ先が Amazon 出品を許しているか／新品出品者数と内訳／

## 2. 実装した整合性検査（17本）

`scripts/sourcing_gate/consistency.py`。1つでも崩れたら**その行を NG にして採算欄を空にします**（§3.3-17）。

| 検査 | 見ていること | 重さ |
|---|---|---|

| `unit_cost_from_wholesale` | Amazon1個あたり原価 ＝ 卸の1点あたり原価 × セット数 | NG |
| `min_lot` | 発注点数 × セット数 が卸の最小発注数を満たすか | NG |
| `net_per_unit` | 1個手残り ＝ 売価 − 販売手数料 − FBA − その他固定費 − 原価 | NG |
| `net_total` | 手残り合計 ＝ 1個手残り × 発注点数 | NG |
| `margin_pct` | 利益率 ＝ 1個手残り ÷ 売価 | NG |
| `referral_cliff` | **750円の崖**。750円以下は一律5%・最低30円／750円超は公式の段のどれか | NG |

| `timeline_stale` | 発注日が過去になっていないか | 警告 |

### 設計で意識的に決めたこと

1. **入力が無い検査は「不合格」ではなく「対象外」。** 空欄を NG にすると、2回目の実行で自分が空けた欄を
   自分が NG にし続けて永久に収束しません。
2. **数字を黙って直さない。** どちらが正しいか分からないので、NG の行は**採算欄を空にする**だけです。
   捨てた値は `consistency_report.json` に原本ごと残します（**隠すのではなく、独り歩きを止める**）。
3. **番兵も採算欄を空にします。** 印を付けながら数字を出し続けると、解けなかった行が必ず利益率の上位に来ます
   （2026-09-07 に実際にそれで上位10件が全滅しました）。
4. **売価と日付は消しません。** 採算の*入力*であって結果ではなく、消すと「なぜ落ちたか」が読めなくなります。
5. **`timeline_stale` は警告に留めました。** NG にすると、表が1日古くなるだけで648行ぜんぶの数字が消えます。
   §3.3-17 の「空にする」は**算術が崩れている行**への処置です。鮮度は発注ゲート側が ASIN ごとに見ています。
6. **料率は「どの段か」を当てません。** カテゴリーがCSVに無いので、**どの段でもないこと**と
   **崖の向きを間違えていること**だけを見ます（出所に依存しない検査にする）。

## 4. 確認記録を 2件 → 648件 に

`scripts/sourcing_gate/autofill.py`。候補CSVから**機械で決まる項目だけ**を記録します。

```
対象 648 ASIN × 21項目 = 13,608件の判定
  PASS 2,723件（20%） / FAIL 302件（2%） / UNKNOWN 10,583件（78%）
```

- **human の12項目を PASS にしません。** UNKNOWN ＋「なぜ決まらないか」＋「取り方」を書きます。**空欄で埋めません。**
- 🔴 **人が付けた記録を機械が上書きしません。** `checked_by` が `autofill` 以外の記録は触りません。
  実際に B008FIPMP2（カズヨの20項目）と B01DBGGW8S（12項目）はそのまま残り、空いていた項目だけが埋まりました。
- **整合性検査が NG の行は、採算の項目を PASS にしません。**
- **PASS は「買ってよい」ではなく「人が実画面で見る価値がある」の意味**です（§3.3-16）。

**発注ゲートを通る ASIN は 648件中 0件です。** 未充足は最小15項目・最大20項目。
これは仕組みの失敗ではなく、**当社がまだ1件も人の確認を終えていないという事実**がそのまま出ただけです。

## 6. 検算（§3.3-17「2回目で0行になるまで完成していない」）

| 回 | 書き換えた行 |
|---|---|
| 1回目 | 648行（`整合性検査` 列が新規なので全行） |
| **2回目** | **0行** |
| 3回目 | 0行。1回目の出力とバイト一致 |

収束のしかけ：採算欄を空にすると、その欄を使っていた検査は次回「対象外」になって所見が消えます。
素朴に印を書き直すと毎回変わって収束しないので、**既にある印と詳細を読み戻して新しい所見と和を取る**ようにしました。
消えた所見は「前回こう落ちた」として残り、新しい所見だけが増えます。**印が消えて行が健全に見えることは起きません。**

さらに、是正後のCSVを `check` にかけると所見は0件になりますが、それを「健全」と読み違えないよう
**「🔴 前回の NG の印が残っている行 8行」を必ず併記**するようにしました。

## 7. テスト（94件・全件通過）

`python3 scripts/sourcing_gate/test_consistency.py` … **94件**

第2版で足したもの：料率の段をカテゴリーで完全一致／卸の条件が同じ行にある場合の検算／基準売価の宣言どおりか／**実画面の価格で計算した行を誤検知しない**（第1版の誤検知を固定）／等級UNKNOWN に金額を残していないか。

- 検査ごとに「崩れている行で鳴る」「正しい行で鳴らない」の**両方**を見ます。片方だけだと、常に鳴る検査と絶対鳴らない検査が緑のまま通ります
- **縮退した入力**（§3.3-20）：全項目が空欄／全項目が同じ値（1）／1行だけ／ヘッダだけ／採算の列が無いCSV／セット数が不明で採算を止めている行。いずれも化けず、NG にもなりません
- 年末年始をまたぐ日付の鎖（12/28 → 01/05）を逆順と誤判定しない
- `num()` が **「未確定（月販非表示・3ヶ月で仮置き）」を 3 と読まない**（仮置きが確定値に化ける事故を防ぐ）
- 金額はすべて架空の合成値。PUBLIC リポなので実際の取引条件は1つも書いていません

### テストを書いて見つけた自分の間違い

最初に「`good_row()` の正しい等級は B」と書いてテストが6件落ちました。
実際は**悲観の手残り 1,500円 が下限400円を超えるので A が正しい**。コードではなくテストの前提が誤りでした。

ここで**規定と実装の食い違い**を1つ見つけました（§3.3-22 の型）。

> **CLAUDE.md §3.5 の等級の定義は「A＝中央値も悲観値も利益率20%以上」ですが、実装は
> 「利益率20%以上 **または** 手残り400円以上」の OR です。**
> OR は 2026-10-04 の社長指示（「単価ではなく利益額で切る」・実践者N=6は全員が単価の下限を置いていない）に基づくもので、
> **実装の方が正しく、文書が追いついていません。**
> 検査は実装＝社長指示に合わせました。**§3.5 の表の修正をお願いします**（下の「社長判断」参照）。
