## 0. 先に伝えるべきこと（発注内容に1点だけ異論があります）

依頼は「2,175社の商品を列挙してシートに積む」でした。**列挙そのものは可能ですが、これだけでは判定に届きません。**理由は3つ、いずれも実測です。

| # | 事実 | 出典 |
|---|---|---|
| 1 | **一覧ページに JAN が無い。**`/p/do/dpsl/<dealer_id>/all/<pg>/` の HTML に「JAN」は0件。JAN は**商品ページ**にしか出ない | 2026-09-30 実測（丸進 102452 の1ページ目・HTML 全文検索） |
| 2 | **SD 商品ページの JAN 記載率は 71%（27/38）。**29% は JAN が無く、Amazon と機械で突合できない | 2026-09-20 実測（27_卸サイト横断調査） |
| 3 | **仕入れ先起点の探索は歩留まり 15%。**「卸にあるものが Amazon で売れているか」を問うと実測で85%が「市場が無い」で落ちた | CLAUDE.md §3.3-9（2026-09-30・N=55） |

**当社の商品規模**：SD 全体で 2,213,533商品／3,446社 → 1社平均642点。**2,175社なら約140万点**。一覧ページは120点/ページなので**約11,600ページ**。1ページ2.2秒でも約7時間、JAN を取るなら**140万ページ**で現実的ではありません。

### そこで、2本立てにしました

| レーン | 向き | 何をするか | 誰が回すか | 規模 |
|---|---|---|---|---|
| **A：索引レーン**（依頼どおり） | 仕入れ先 → 商品 | 2,175社の商品を**商品名＋商品コード＋卸価格**で列挙してシートに積む。**JAN は取らない**（一覧に無いので） | 索引の骨（商品名・コード）は `sd_dealer_index.py` が**非ログインの HTTP** で。**卸価格の上書きだけ**カズヨがブラウザで | 約11,600ページ |
| **B：突合レーン**（本筋・§3.3-9） | **Amazon → 卸** | Amazon で売れている ASIN の JAN を `sd_jan_lookup.py` に投げ、**SD に在るか／どの企業が持つか**を1リクエストで判定 | **非ログインの HTTP だけで完結**（ログイン不要） | **1 JAN = 1 リクエスト** |

**B は A の 1/100 のコストで、判定に直結します。**A を止める必要はありません（棚の全体像と企業の得意分野が見えるのは資産です）が、**「次の1件を決める」のは B です。**どちらを先に回すかはカズヨの判断でお願いします。

## 3. 罠（先に踏んでおきました）

| 罠 | 対処 |
|---|---|
| **www は連続取得で Cloudflare に落ちる**（2026-09-20 に190件で失敗・2秒間隔でも復帰せず） | `sd_dealer_index.py` は `Just a moment` を検知したら**その場で保存して終了**。間隔は既定2.2秒。日を分ける前提で書いてあります |

## 5. 🔴 今日わかった最大の制約：SD は HTTP からの連続取得を 429 で止める

**2026-09-30 実測。** 4秒間隔にしても、8→16→32→64秒のバックオフを入れても復帰しませんでした。
`sd_dealer_terms.py` は書き上げて構文まで通っていますが、**今日は1社も取れていません**（全件 429）。

| 経路 | 実測 | 結論 |
|---|---|---|
| **HTTP（非ログイン・curl/python）** | 1セッションで約250リクエストを越えたあたりから **429 が連続。**4秒間隔・64秒バックオフでも復帰せず | **大量スキャンには使えない。**少量（JAN 数十件）なら可 |
| **ログイン済みブラウザの同一オリジン iframe** | **44ページを1回の実行で・1ページ約1秒**（カズヨ実測） | **大量スキャンはこちらが正解** |

> 推測（確度：中）：SD はログインセッションと非ログインで別のレート制限をかけている。ログイン済みは「会員の正常な利用」として通る。
> **したがって、私（サトル）が HTTP で全件を舐める設計は筋が悪く、ブラウザ側（カズヨ）で回すのが正しい分担です。**依頼の3点目（「取得ロジックは書いてよいが実行は私に」）は、能力の問題ではなく**技術的にもそれが唯一の道**でした。

## 6. カズヨへの手順（この順で）

### 手順1（最優先・所要 約40分）: 2,176社の Amazon 可否を確定する
```
# Chrome（SD ログイン済みタブ）で
<sd_price_fill.js 全文を Runtime.evaluate>
SDX.termsSeed(<[[dealer_id,name],...] 2,176社>)
await SDX.terms()      // done:true になるまで繰り返す。1回で約80〜90社
```
返ってくる `rows` をそのままシート『取引条件』タブへ。
**判定は ○ / 要確認 / × / 不明 の4値で返します。○ 以外を商品スキャンの対象から外してください。**
人気順 N=55 のサンプルでは態度が判明した48社の35%が Amazon 名指し不可だったので、**ここで数百社落ちる想定**です。落ちた社の商品を列挙するのは全部無駄になります。

### 手順2: ○ の社だけ、商品と卸価格を取る
```
SDX.seed(<○ の dealer_id を優先順に並べた配列>)
await SDX.run()        // done:true まで繰り返す
```
- 1回で約60〜80ページ（120件/ページ）。**初回の `rows[0].raw` を必ず目で見て、`price_text` のどこが「卸価格単価」「セット卸額」「ご注文セット数」かを確定**してください。私はログインできないので DOM を推測で決め打ちしていません（`raw` を返しているのはそのためです）。
- 優先順は `priority.py` が出す `sd_dealer_order.txt`。ただし**ジャンルの識別力は弱い**（生活雑貨だけで1,550社以上＝ほぼ全社が該当）。**実際に効く優先順は手順1の判定（○ が先）**です。

### 手順3: Amazon 起点の突合（ログイン不要・私が回せます）
```
python3 sd_jan_lookup.py --jan-file <売れている ASIN の JAN> --out <agent_output>/sd/sd_jan_hits.jsonl --sleep 6
```
**1 JAN = 1 リクエスト。**これが「次に何を仕入れるか」を決める本体です（CLAUDE.md §3.3-9）。
JAN 数が数十件なら 429 に当たらずに走れます。
