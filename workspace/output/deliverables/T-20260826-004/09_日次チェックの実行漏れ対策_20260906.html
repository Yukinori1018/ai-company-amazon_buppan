2026-09-05（金）の Amazon 日次チェックが実行されませんでした。その原因と、打った手をまとめます。

問い答え

2. 原因（裏取りの結果）

スケジュールタスクの実行履歴そのものは残っていませんでした。代わりに別系統の記録で裏を取りました。

記録9/5 の状況
git log（監視ログの更新）9/4 11:17 の次が 9/6 10:45。9/5 は1件も無し
launchd の github-sync（30分ごと）9/5 の 07:03 / 13:03 / 15:33 / 18:33 / 21:03 / 22:33 に正常稼働
Claude のセッション記録（~/.claude/session-env/）9/4 14:21 が最後。次は 9/6 10:33。9/5 はゼロ件

読み取れること。Mac は一日中起動していました。launchd も動いていました。落ちていたのは Claude だけです。

スケジュールタスクは Claude アプリが起動している間しか発火しません。9/5 は Claude を一度も開かなかったため、12:00 に何も起きませんでした。推定ではなく、3つの記録が一致した事実です。

もう1つ見つかった不具合。 9/6 に手で書いた「## 2026-09-05 未実行」の行が、検知の仕組みを黙らせていました。

旧リマインダー⑤は「ログの先頭にある日付」を最新とみなす作りでした。手で足した 9/5 の行が先頭に来た結果、「最新は 9/5 = 昨日 = 正常」と判定し、9/6 のセッションで警告を出しませんでした。欠測を記録した行が、欠測の検知を殺していたことになります。

3. 直したもの

部品は増やさない方針で、既存の3つ（スケジュールタスク／ログ／SessionStart フック）を強くしました。追加したのは launchd の番犬1つだけです。理由は §4 に書きます。

3-1. 判定ロジックを1箇所に集約（新規 .claude/scripts/amazon_check_log.py）

「実行された日／されなかった日」を決めるコードを1ファイルにまとめました。フックと番犬の両方がここを呼びます。判定を2箇所に書くと必ずズレるためです。

直した判定は3点です。

  1. 最新日を「先頭の見出し」ではなく「全見出しの最大値」で採る。並び順は人が手で書くので、いつか必ず崩れます（実際 9/5 が 9/6 の上にありました）。
  2. 本文に「未実行」とある日は、見出しがあっても実行されていないと数える。§2 の不具合の修正です。
  3. 閾値を「2日以上前」から「1日でも欠けたら」に。

3-2. SessionStart リマインダー⑤の強化

  • 欠測が1日でもあれば警告します。欠測した日付を具体的に列挙します。
  • 今日ぶんは 12:00 を過ぎるまで鳴らしません。巡回は12:00予定なので、朝のセッションで毎日鳴ると警告そのものが無価値になります。
  • 番犬（§3-3）の最終実行時刻も一緒に出します。検知する側が死ぬと、静かに元に戻るためです。
  • 平常日は1行も出ません（従来どおり）。

3-3. アプリ非依存の通知（新規 launchd com.aicompany.amazon-buppan.amazon-check-watchdog）

毎日 12:30 と 19:00 に走ります。やることは3つだけです。

  1. 過去の欠測日に「未実行」の行をログへ自動挿入する
  2. 今日ぶんが 12:30 を過ぎても無ければ、macOS の通知センターに出す
  3. 自分が走った時刻を workspace/monitoring/watchdog-last-run.txt に残す

Amazon には一切アクセスしません。ログを読んで通知を出すだけです。パスワードも 2FA も扱いません。

今日ぶんを先回りして「未実行」と書くことはしません。12:00 に遅れて走る場合があり、先に書くと嘘になります。嘘をつくログは価値がゼロになります。

3-4. 1コマンドでの復旧（新規 /amazon-check）

欠測に気づいたら、Claude で /amazon-check と打つだけで巡回が回ります。手順は既存の SKILL.md を参照する形にしてあり、二重には書いていません。

4. なぜ launchd を足したか（部品を増やした理由）

指示は「部品を増やさず既存3つを強くせよ」でした。それでも launchd を1つ足しました。理由は1点です。

SessionStart フックは、Claude を開いた時にしか鳴りません。今回の故障は「Claude を開かなかったこと」そのものです。壊れている時にだけ鳴らない仕組みでは、検知になりません。

そして §2 のとおり、9/5 に launchd は6回正常に走っていました。落ちるのは Claude であって launchd ではないことが、実測で分かっています。同じ日に動いていた層に乗せるのが、いちばん確実です。

代わりに、番犬の役割は通知だけに絞りました。巡回・ログイン・Amazon アクセスは一切させていません。増えた面倒は「通知が出たら /amazon-check と打つ」だけです。

5. 直せないもの（正直に）

できないこと理由
巡回の完全自動化セラーセントラルは 2FA 付きです。cron から headless では入れません。社長のログイン済み Chrome が必須で、それは Claude 経由でしか触れません
Claude が閉じている日に巡回すること上と同じ。通知はできますが、巡回はできません
飛んだ日を後から取り返すことAmazon の画面は「今の状態」しか見せません。9/5 に何があったかは、もう確認できません。分かるのは「9/4 と 9/6 で変化が無かった」ことだけです
satoyselect@gmail.com をコネクタで読むこと従来どおりの穴です。ブラウザ経由でのみ読めます
通知が確実に見えることの保証macOS の通知許可が off だと出ません。§6-3 で必ず1回確認してください

「毎日必ず動きます」とは書きません。書いた瞬間に、止まった時の信用ごと失うためです。

6. 社長が「動いているか」を自分で確認する手順

6-1. いま欠測があるかを見る（5秒）

ターミナルでリポジトリのフォルダに移動して、次を打ちます。


bash .claude/scripts/amazon-check-watchdog.sh --status

こう出れば正常です。


最後に実行できた日=2026-09-06 / 今日は済 / 欠測1日: 2026-09-05
番犬の最終実行: 2026-09-06 11:04 実行 / 今日=済 / 欠測=1日 / 最終成功=2026-09-06

「番犬の最終実行」が昨日以前なら、番犬自身が止まっています。

6-2. 番犬が登録されているかを見る（5秒）


launchctl list | grep amazon-check-watchdog

- 0 com.aicompany.amazon-buppan.amazon-check-watchdog と出れば正常です。真ん中の数字が最後の終了コードで、0 以外なら異常です（127 = ファイルが無い、126 = 実行権が無い）。1行も出なければ登録されていません。

6-3. 通知が本当に届くかを1回だけ確認する（最重要・30秒）


bash .claude/scripts/amazon-check-watchdog.sh --test-notify

画面右上に通知が出るか見てください。出なければ、システム設定 > 通知 > スクリプトエディタ を許可してください。ここが off だと、番犬は動いていても社長には何も届きません。この確認だけは必ず1回やってください。

6-4. 改ざんの効かない確認（git log）


git log --format='%ad %s' --date=short -- workspace/monitoring/amazon-daily-check.md | head

日付が1日ずつ並んでいれば動いています。飛んでいる日が、飛んだ日です。
