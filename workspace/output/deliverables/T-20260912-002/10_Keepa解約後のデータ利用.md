# 10 Keepa 解約後のデータ利用（ハルオ・2026-09-14）

論点③（Keepa API を 10/4 の更新前に解約）の法務確認です。解約・ログイン・規約同意は何もしていません。

## 結論

- 条件付き可。解約後も、取得済みの Keepa データ（生 JSON・CSV・集計・打診先リスト）を社内の業務目的で保存・利用し続けてよい。削除義務は無い。
- 根拠は API T&C（Version of July 28, 2026）§11(2)。"The user may save or print out contents ... for their own business purposes, with a non-exclusive and unlimited right of use"。
- §11(1) 第2文は「取得・表示の権利」を契約期間に限る（"limited to the duration of the contractual relationship"）。保存したものは §11(2) が別に定め、こちらは "unlimited"。
- 削除・返還を求める条項は全文に無い。"delete" が出るのは §12(1) のアカウント削除だけ。
- 条件は2つ。
  1. 支払いを済ませる。§11(2) ただし書で、未払いなら権利を取り消せる。チャージバックは §8(5) で重大な違反になる。
  2. 自社の業務目的に限る（§2(2)・§11(1)(2)）。
- 公開・第三者への開示は、解約前と同じく不可。解約後は §11(2) の許諾の外なので、根拠はむしろ弱くなる。

## 1. 行為別の判定

| 行為 | 判定 | 根拠 |
|---|---|---|
| 生 JSON・CSV をローカル（agent_output・素材フォルダ）に持ち続ける | 可 | §11(2) |
| 社内で集計・ランキング・判定を作る、見直す | 可 | §11(2)「own business purposes」。API は JSON を返して加工させる商品（§2(1)）。§11(1) の "edit" はサイトの contents の改変の話。社内の計算まで止める読み方は BGB §305c(2)（多義は作成者に不利）で採られにくい |
| 打診先リスト（メーカー名・連絡先）を作る、使う | 可 | メーカー名・ブランドは Amazon のカタログ属性。連絡先は当社が各社サイトから取ったもの。Keepa 固有の値ではない |
| 仕入れ判断に使う | 可（古くなる） | §11(2)。§2(4) で正確性は保証されず、妥当性の確認はユーザーの義務。出品当日の価格は Amazon の画面で取り直す（08 §3 と同じ） |
| 社長の Google シートに置く | 可 | 共有先が社長本人だけなら社内。リンク共有にしない |
| 打診文でメーカーに Keepa の数字を伝える | 不可 | 第三者への開示。09_波1 は数字を書かない設計で、規約に合っている |
| PUBLIC リポに Keepa 固有の値を置く | 不可 | §11(1) reproduce 禁止。解約後は §11(2) の許諾の外 |
| PUBLIC リポに ASIN・現在価格・ランク・オファー数を置く（今の運用） | 形式的には抵触、実害はほぼ無い | 前回判定（T-20260904-004 E2）の区分のまま。Amazon の画面で誰でも見られる値 |
| 第三者に売る、渡す | 不可 | §2(2)・§6.1(1) |

## 2. PUBLIC リポの運用は規約に合っているか

- 今のファイル（HEAD）は合っている。Keepa 固有の加工値の列は 2026-09-06 に削除済みで、pre-commit ゲートもある。今日の実測でも、追跡下の CSV のヘッダに残っているのは除外の注記だけ。
- 履歴は合っていない部分が残る。`git log origin/main -S'月間ドロップ数'` で23コミット（2026-08-17〜09-06）。過去のコミットを開けば列が見える。
- 解約してもこの評価は変わらない。変わるのは制裁の形。

| | 解約前 | 解約後 |
|---|---|---|
| 本命の制裁 | API 遮断（§13） | 遮断に意味が無くなる |
| 金銭 | §14(3) で12ヶ月の料金の2倍が上限 | 上限は "during the Term" の文言で、解約後の請求に効くか不明確。効く前提は置かない |
| 新しく出る論点 | — | 再契約の拒否。§3(3) "reserves the right to decline any user's offer ... without providing reasons" |

- 論点③の「必要な月だけ再契約」は、Keepa が再契約を受ける前提で成り立つ。需要先行スキャン（T-1 型）には Keepa 以外の代わりが無い（08 §2 #4）。
- 3軸：確率は低い × 影響は中（補給月の手段が消える） × 不可逆性は高め（理由を示さず断れるので争えない）。確率は低いがアラートを上げる。
- 推奨：既定（2026-09-06 社長判断「Private 化せず、列を抜く」）は変えない。グレーを残すので3点セットを置く。
  - リスクシナリオ：Keepa から照会・警告が来る。または再契約を断られる。
  - 発生時の対応：リポを Private 化（1操作・可逆）して履歴ごと閉じ、照会に答える。Private 化は §4.1 で社長承認。
  - 撤退条件：照会・警告が1回来たら即 Private 化。再契約を断られたら Keepa 前提の補給計画を止め、SP-API（05）と Amazon の画面での確認に切り替える。

## 3. 解約前に秘書が済ませること

1. 解約はダッシュボードの subscription の cancel で行う。アカウントは削除しない。
   - §12(1) では、アカウント削除で契約そのものが終わる。支払済みの期間が残っていても即日使えなくなる恐れがある（推測。条文は終了の手段としか書いていない）。
   - プライバシーポリシーは「アカウント削除で個人情報がすべて消える」と書いている。請求書を取り直せなくなる。
2. 請求書を全期間分保存する（9/4〜10/4 分を含む）。電子取引のデータ保存義務（電子帳簿保存法7条）がある。解約後にダッシュボードへ入れるかは未確認なので、解約の前に落とす。
3. 最後の請求まで支払い、チャージバックをしない（§11(2) ただし書・§8(5)）。
4. 10/2 までに抽出（T-3・S-3）を終える。取ったデータは agent_output か素材フォルダに置く。deliverables に置くなら列を落とす（既存ルール・pre-commit ゲート）。
5. 解約後、keepa.com のサイトにスクリプトを向けない。無料サイトの規約は自動化を禁じ、違反者は "immediately and permanently banned"。永久停止になれば再契約の道が閉じる。list-builder の STOP は外さない（08 §3）。人が拡張やサイトを見るのは可。
6. 再契約するときは、その日の termsAPI.txt の版を確認してから同意する。新規契約はその時点の規約になる（§19 の6週間前通知は既存契約の話）。同意は §4.1。
7. データの削除は要らない。生データ・鍵ファイルを消す作業は発生しない（消すなら §4.1）。
