# NETSEA 仕入れ起点 × Keepa 検証 — 利益が取れる商品を抽出する

T-20260831-006 / 2026-08-31 / IT エンジニア タカシ

**仕入れられることが確定している棚**（NETSEA の承認済みサプライヤー）から始めて、
Amazon で実際に売れて利益が残る商品だけを残すパイプラインです。

## なぜ向きを反転させたか

| | Amazon 起点（行き詰まった） | **NETSEA 起点（これ）** |
|---|---|---|
| 仕入れられるか | 最後まで分からない | **確定**。そこに売っている |
| 仕入れ値 | 推定（社長の最大の不満） | **確定値が載っている** |
| Keepa の役割 | 発見 | **検証** |

卸値と Amazon 売値の両方が実額なので、利益計算に推定が入るのは
**納品送料・保管料・雑費の3つだけ**です。その3つは内訳列に出しています。

## 実測（2026-08-31）

### 母集団

| 項目 | 実測 |
|---|---|
| 承認済みサプライヤー | **225社**（API で取得。**ログイン不要**） |
| 5社ぶんの商品 | 3,303商品 → 規格展開 6,690件 |

> 先頭100社しか見ていませんでした（125社を静かに取りこぼしていた）。本チケットで修正済み。

### 歩留まり（サプライヤー5社・150件を Keepa 検証）

| 段 | 件数 | 備考 |

| NETSEA 商品 | 3,303 | 0トークン |
| 規格(set)展開 | 6,690 | JAN は規格ごとに違うのでここが正しい粒度 |
| 段2 通過 | 1,998 | **JANなしで 4,282件（64%）が脱落** |
| Keepa 検証 | 150 | `--keepa-limit` で絞った |
| Amazon に存在 | 80 | |
| Amazon に無い | 70 | **好機か需要ゼロかは区別できません**（後述） |
| 利益プラス | 5 | |

### Keepa の実効コスト

| 項目 | 実測 |
|---|---|
| 投げた JAN | 150件 |
| 消費トークン | **95** |
| **1件あたり** | **0.633トークン** |

**ヒットしなかった JAN は課金されません。** 未ヒットの70件をまとめて再投入したところ、
返却0件・**消費1トークン**でした（リクエスト1回あたりの基本料のみ）。
つまり「NETSEA にあるが Amazon に無い商品」の仕分けは、ほぼ無料で終わります。

上限1,200・補充20/分なので、**1日あたり約2万件**の JAN を検証できる計算です。

## 使い方

```bash
cd workspace/output/deliverables/T-20260831-006

# まず小さく試す（サプライヤー5社・Keepa 150件まで）
python3 netsea_scan.py --suppliers 5 --keepa-limit 150

# 全225社を収集（無料。約25分）。段1だけなので Keepa は使わない
python3 netsea_scan.py --stage harvest --suppliers 0

# 収集済みデータに対して Keepa 検証だけ回す（再開可能）
python3 netsea_scan.py --stage verify --keepa-limit 1000

# 利益ラインを超えた行だけ実セラー数を確定（6.5トークン/件と高い）
python3 netsea_scan.py --stage verify --verify-sellers

```

主なオプション: `--min-wholesale` `--max-wholesale` `--min-profit` `--keepa-batch`
`--keepa-limit`（トークンの安全弁）`--allow-regulated` `--allow-used`。

## 正直に書いておくこと

### 1. 「Amazon に無い」は好機か需要ゼロか、**区別できません**

同一 JAN の ASIN が見つからない場合、それは
**(a) 誰も出していない＝競合ゼロの好機** か **(b) そもそも需要が無い** のどちらかですが、
**この観測だけでは同じ数字に見えます。** 5社サンプルでは 150件中70件（47%）がこれでした。
区別するには商品名での Keepa 検索（10トークン/回）か、人が判断するしかありません。

### 2. 利益率が高くても売れていない商品が上位に来ます

初回実走で **利益率55.9%・純利益7,230円**の商品が最上位に来ましたが、
`salesRankDrops30 = 0` ＝**直近30日で売れた形跡がありません**。
在庫は現金です。売れない在庫は利益率が何%でも現金を潰します。

そこで **`総合判定` 列**で利益と回転を重ねています。
利益が出ていても「直近30日に売れた形跡なし」「回転が遅い(30日で約N個)」と書き分けます。
**`利益率%` だけで並べ替えないでください。**

### 3. JAN を持つのは約36%

規格6,690件のうち4,282件（64%）が JAN 無しでした。JAN が無いと Keepa の1トークン検証に
載せられないため、**現状は捨てています**。商品名での検索は10トークン/回と16倍高いので、
母数を稼ぐ段階では割に合いません。

### 4. 1サプライヤー2,000件で打ち切っています

`--max-items` の既定が2,000件で、実際に多くの社が上限に当たっています（ログの「打ち切り」）。
**取りこぼしがある状態です。** 上限を上げれば取れますが、その分時間がかかります。

### 5. 出品者数は「オファー本数」です

`--verify-sellers` を付けない限り、出品者数の列は Keepa の `COUNT_NEW` ＝
**新品オファーの本数**で、出品者数ではありません（1社が FBA と FBM に出せば2）。
`出品者数の出所` 列に必ず書いてあります。実数が要るなら 6.5トークン/件を払ってください。

### 6. 手数料の確度

料率は `calc/fees.py`（T-20260521-005 / 2026-08 更新）が唯一の正で、
**このパイプラインは料率を1つも持っていません**。ただしその表自体に
〔未確認〕項目が残ります（`deliverables/T-20260817-005/fee-rates-2026-08.md` §6）。
**実発注の直前には、セラーセントラルの FBA 料金シミュレーターで最終確認してください**（無料・5分）。

## 法務上の制約（ハルオ判定 2026-08-31 / `01_NETSEA仕入れの適法性判定.md`）

実装に落としたもの:

| 制約 | 実装 |
|---|---|
| `deal_net_shop_flag != Y` は**除外**（フィルタではなく） | 段2で除外。**CLI に解除オプションを置いていません** |
| 中古・USED・ヴィンテージは除外（**古物商許可が未取得**） | 段2で除外。`--allow-used` は許可取得後のみ |
| 規制品の義務は転売者にも及ぶ（電安法27条ほか） | **除外せず** `法令要確認` 列にフラグ |
| サプライヤーの「販売条件」自由記述は API で取れない | 全行に `発注前に必ず確認` 列＋商品ページURL |

**残るリスク（自動化できません）**

- **サプライヤーの「販売条件」に「Amazon不可」「モール不可」「売価厳守」が書かれうる。**
  この自由記述テキストは API の商品スキーマに存在しません。**発注前に人が読むしかありません。**
- **NETSEA の納品書は公式に「社内管理用」と明記されています。**
  Amazon の出品制限（ゲート）解除に使う請求書として通る保証はありません。
- **⛔ NETSEA で見つけた相手に、NETSEA の外で連絡・契約してはいけません。**
  違約金200万円＋売買代金50%＋事業者名の公表（会員規約 第27条4項）。
  `adapters/netsea.py` に `assert_procurement_use()` の関門を置いてあります。

## 構成

```
netsea_scan.py          CLI。3段の司令塔。再開可能
pipeline/config.py      しきい値・キーワード・コスト前提（数字を触るならここだけ）
pipeline/screen.py      段2。0トークンの前段フィルタ。純関数のみ
pipeline/keepa_verify.py 段3。JAN→ASIN とトークン予算
pipeline/evaluate.py    利益計算と CSV 行。料率は calc/fees.py から取る
pipeline/store.py       逐次保存と再開（1件ごとに fsync）
tests/                  47件
```

料率表を**コピーしていません**。2箇所に増えた瞬間どちらが正か分からなくなるためです
（T-20260817-004 で実際に起きた事故）。`pipeline/paths.py` が
`deliverables/T-20260521-005/code` を `sys.path` に通しています。
