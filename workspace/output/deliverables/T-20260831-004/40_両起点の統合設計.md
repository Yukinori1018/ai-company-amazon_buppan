## 1. ランク条件の決着（宿題①(a)(b)(c)）

### (b) 当社は大カテゴリ順位を使っている。取り違えは起きていない

`scan_v14.py` 809行 `current_SALES_gte/lte` は Keepa の **SALES＝そのASINの参照カテゴリ（大カテゴリ）順位**です。サブカテゴリ順位（`salesRanks`）は判定に使っていません。**厳しい側の読み方であり、事故ではありません。**

念のため両者の差を実測しました（3,045商品）。

| | 件数 | 割合 |
|---|---:|---:|
| 大カテゴリ順位 ≤5万位 | 2,953 | 97.0% |
| サブカテゴリ最良順位 ≤5万位 | 3,037 | 99.7% |
| 大カテゴリ>5万位 だが サブ≤5万位 | 84 | 2.8% |

**大カテゴリ順位はサブ最良順位の中央76倍**（p25=14倍／p75=248倍）。つまり「サブで5万位以内」は条件としてほぼ無意味です（99.7%が通過）。**セミナーの5万位は大カテゴリ順位と解釈すべき**で、当社の実装はそれに一致しています。

### (a) 帯を動かしても中小メーカーには寄らない

手作業ラベル200社を、そのメーカーの商品ランク中央値で帯分けしました。

| 帯 | メーカー数 | 本命率(A1+A2) |
|---|---:|---:|
| 1〜5,000位 | 114 | 15.8% |
| 5,001〜10,000位 | 56 | 21.4% |
| 10,001〜20,000位 | 12 | 8.3% |
| 20,001〜50,000位 | 8 | 0.0% |
| 50,001位〜 | 10 | 10.0% |

単調ではなく、n も小さい。**帯の位置は本命率を説明していません。**

さらに重要な事実：**候補プール2,635件のランク分布は中央値3,840位、96.8%が5万位以内**です。RANK_MAX は30万位に設定されているのに、実際には5万位以内しか集まっていません。理由は Finder のソートが `salesRankDrops30 降順`（＝よく売れている順）だからです。**社長が2026-08-04に指示した「5万〜15万位」は、設定上は入っているのに、データ上は1.2%しか実現していませんでした。**

### (c) 提案：ランクは条件から外し、上限だけ残す

| 案 | 内容 | 判定 |
|---|---|---|
| セミナー通り5万位以内 | 現状と実質同じ（96.8%が該当） | 変える意味がない |
| 社長修正 5万〜15万位 | 未検証。今の実装では集まらない | **ソートを変えないと検証すらできない** |
| サブカテゴリで5万位以内 | 99.7%通過。フィルタとして機能しない | 不可 |
| **帯を条件から外す（推奨）** | `current_SALES` は上限30万位のまま。**代わりに `salesRankDrops30 ≥ 10` を実需の下限として使う** | **採用** |

**理由**：ランク順位は「カテゴリ内の相対順位」であって販売個数ではありません（`reference_keepa_reading_pitfalls`）。当社が本当に見たいのは実需で、それは月間ドロップ数が直接表します。ランクで切ると**カテゴリの大きさの違いをそのまま持ち込む**（DVDの5万位とペット用品の5万位は別物）。実測でも帯は本命率を説明していません。

**ただし社長の問題意識（「10万位以下＝中小メーカーが多いはず」）は未検証のまま残ります。** 検証は Finder のソートを変えた1本の走行（約300トークン・課金なし）で済みます。§9 に実験として置きました。

## 2. Amazon起点をセミナーに忠実に作り直す（v16 ゲート定義）

セミナー原本の基準は3つ＋前提1つ。当社の実装との対応を1行ずつ埋めました。

| セミナー | 当社 v15 の実装 | v16 で直すこと |
|---|---|---|
| ①Amazon本体がいないこと | `current_AMAZON=-1` かつ `availabilityAmazon=-1` | **本体の過去180日在庫率も見る**（現在いなくても、断続的に戻る商品は交渉価値が落ちる）。実測：候補の90%は在庫率0%、上位10%だけが8%以上 |
| ②FBAライバルセラーが2人以上 | `distinct sellerId ≥ 2` | **自演401件の問題。「独立セラー数≥1 かつ 国内事業者≥1」に置き換え済み**（下記） |
| ③ランキング5万位以内 | `current_SALES ≤ 300,000`（実データは96.8%が5万位以内） | **条件から外す。`salesRankDrops30 ≥ 10` に置き換える** |
| 前提：中小メーカー狙い。大手は代理店卸で不可 | **実装されていなかった** | **gBizINFO の従業員数・資本金を列に持つ（実装済み・30番台）。足切りにはしない（社長訂正）** |

### ②の再定義（自演401件への対処）

`distinct sellerId ≥ 2` は卸の証拠になりません。実測で **401件がブランド自身の別名ストアの並び**でした（`Ailewu` は4セラー全部が自社の「メーカー直営店」）。

```
独立セラー数 = 全セラー − ブランド名を冠する店 − 直営/公式/正規販売店を名乗る店 − 名前が解決できない店
必須ゲート  = 独立セラー数 ≥ 1 かつ そのうち国内事業者 ≥ 1
```

**「2人以上」に落とさなかった理由**：独立セラー1社と2社で本命率は 12.0% vs 10.9% と差がありません。2社を要求する根拠がデータにない。セミナーの「2人以上」は**メーカー直販を含めた数**と解釈すれば、当社の「独立1社＋直販1社」と一致します。

### v16 のゲート適用順（トークン効率）

安い判定を先に置きます。`offers`（6.5トークン）の前で 62.6% を落とせるので、**同じ予算で商品2.19倍**を検査できます。

```
1. Finder      本体不在 / COUNT_NEW 2-6 / 価格帯 / drops30≥10 / 追跡180日以上   … 20トークン/1000件
2. product     カテゴリ除外（DVD・CD・本・洋書・ゲーム・PCソフト）             … 1トークン/件
3. product     日本実体判定・中国系判定（brand / manufacturer / EAN）
4. offers      独立セラー数・国内事業者の有無                                … 6.5トークン/件
5. gBizINFO    従業員数・資本金（列に出すだけ。足切りにしない）                  … 0トークン
6. 困り度      §3。価格・オファー数の履歴から算出                             … 0トークン（取得済みデータ）
```

**5と6は追加トークンがかかりません。**

## 3. 「困っている度合い」スコア（本命）

### 3.1 何を測っているか（推論と観測を分ける）

**観測**：Amazon上で値崩れと相乗り増加が実際に起きているか。
**推論**：それがメーカーの困り事につながっているか。
**この2つは別物です。** スコアが測るのは前者だけです。セミナー第5章の「メーカーの困り事＝値崩れ・無断販売者・仕組みが分からない」に対応します。

### 3.2 材料の採否（全て実データに当てて決めた）

| 材料 | Keepa の出所 | 採否 | 実測 |
|---|---|---|---|
| **D1 下方向の値幅** (中央値−下位10%)/中央値 | `csv[1]` NEW 価格履歴180日 | **採用** | 中央9.3%・上位10%は40%超 |
| **D2 価格改定回数**（±1%超）/180日 | 同上 | **採用** | 中央20回・上位10%は89回 |
| **D3 直近30日の下落率** 30日中央値 vs 180日中央値 | 同上 | **採用** | 中央0%・上位10%は13% |
| **D4 新品オファー数の増分** 直近30日 − 90〜180日前 | `csv[11]` COUNT_NEW | **採用** | 中央0・上位10%は+2 |
| Amazon本体の在庫率 | `csv[0]` AMAZON | **ゲートへ**（スコアに入れない） | 候補の90%が在庫率0%＝差がつかない |
| 上方向の値幅（値上がり） | `csv[1]` | **不採用** | 転売プレミア（MEDICOM TOY 13,820→19,800円）を「困っている」と誤判定する |
| BuyBox の奪取回数 | `csv[18]` | **不採用** | `offers` を付けた回のみ更新されるため、時系列が歯抜けで比較できない |

> **COUNT_NEW は出品者数ではありません。「新品オファー数」です。**1社がFBAとFBMに出すと2になります（`knowledge_verify_field_semantics_not_names` の事故6件のうちの1つ）。スコアでは「増分」だけを見るので、この定義の差は方向を歪めません。

**スコア = 4成分をそれぞれ0〜1に正規化して平均 ×100。** 正規化の上限は実測の90パーセンタイル（D1=0.30 / D2=40回 / D3=0.20 / D4=+3.0）。履歴120日未満の商品は判定しません。

成分どうしの相関は最大でも D1×D3 = +0.43。**重複していません。**

### 3.3 交絡チェック（「単に人気商品を拾っているだけ」ではないか）

| 相関 | r |
|---|---:|
| 困り度 × 現在のオファー数 | +0.184 |
| 困り度 × ランク | +0.020 |
| 困り度 × 価格 | +0.066 |
| 困り度 × 履歴の長さ | −0.025 |

**どれも弱い。**「オファーが多い商品」「売れている商品」を言い換えているわけではありません。

### 3.4 一番大事な負の実測 — 本命ほど困っていない

手作業ラベル200社の商品で、区分別に困り度を出しました。

| 区分 | 商品数 | 困り度の中央値 | 45以上の割合 |
|---|---:|---:|---:|
| **A1 日本の小規模メーカー（本命）** | 37 | **24.4** | 13.5% |
| A2 日本の中堅 | 15 | 25.2 | 13.3% |
| B 大企業 | 105 | 31.2 | 24.8% |
| C 版元・レーベル | 107 | 32.4 | 22.4% |
| D 中国系OEM | 153 | 28.7 | 20.3% |
| E 海外（非中国） | 16 | 22.2 | 12.5% |

成分別に分解すると理由が分かります。

| 区分 | 下方向値幅の中央 | 「オファー+1以上」の割合 | 「値崩れ15%以上」の割合 |
|---|---:|---:|---:|
| **A1 日本の小規模** | 7.7% | **10.8%** | 27.0% |
| B 大企業 | 9.3% | 35.2% | 24.8% |
| C 版元 | 8.3% | 36.4% | 40.2% |
| D 中国系OEM | 5.0% | 44.4% | 22.9% |

**相乗りが増えているのは大企業・版元・中国系OEMであって、日本の小規模メーカーではありません（10.8% 対 35〜44%）。** 値崩れ（15%以上）は A1 でも27%起きており、そこは差がない。

> **したがって困り度スコアを母集団全体の並べ替えに使うと、本命が沈み、外したはずのノイズが浮きます。**
> **使い方は1つだけ：適格性フィルタを通した後の並べ替え。** 順番を逆にすると、前チケットで潰したノイズがそのまま戻ってきます。

## 4. 非Amazon起点：類似商品からの売上予想

### 4.1 「類似」の定義を4通り実装して比べた

被説明変数は Keepa の **月間販売数（monthlySold）**。Amazon表示の実測値で、階級値（100/200/300/500/1000…）です。取得できたのは2,635商品中1,424件（54%）。

**交差検証（Leave-One-Out：自分自身を除いた同群の中央値で自分を当てる）**

| 「類似」の定義 | 説明力 R²(LOO) |
|---|---:|
| **① 大カテゴリのみ** | **15.8%** |
| ② 中カテゴリ | 5.8% |
| ③ 小カテゴリ | 11.2% |
| ④ 中カテゴリ × 価格帯（1.6倍刻み） | 9.9% |
| ⑤ 小カテゴリ × 価格帯 | 5.8% |
| ⑥ 中カテゴリ × 価格帯（n≧10の群のみ） | 10.3% |

**細かくするほど悪くなります。** 群あたりの件数が1〜2件に落ちるためで、見かけのR²（過学習込みなら60%）と交差検証の値は別物です。**最も単純な「大カテゴリのみ」が最良でした。**

**キーワード一致は効きませんでした。**

| 同じ中カテゴリ内のペア | n | 月間販売数の差（中央値） |
|---|---:|---:|
| タイトル語の重なり15%以上 | 190 | **2.00倍** |
| 15%未満 | 3,794 | **2.00倍** |

**完全に同じ。** タイトルの語が一致していても、売れる量は近づきません。**「同用途／キーワード一致」で類似を定義する実装はしないでください。**

### 4.2 どこまで言えて、どこから言えないか

実務形（コホート中央値 ÷（出品者数+1）＝キーゾンの式のコホート版）で予測したときの誤差を実測しました。

```
n=587  予測比の p10 / p50 / p90 = 0.33倍 / 1.00倍 / 4.29倍
→ 80%区間はおよそ 0.3〜4.3倍（13倍の幅）
```

| 言えること | 言えないこと |
|---|---|
| 「このジャンル・この価格帯は月**30個**が中央値」 | 「**この商品**が月30個売れる」 |
| 「桁」（月3個か30個か300個か） | 「30個か60個か」 |
| 「そのジャンルに需要があるか無いか」＝**行く/行かないの足切り** | **初回の仕入れ数量** |

**中央値で言った数字は、実際には0.3〜4.3倍の間に落ちます。** 月30個と言ったら、実際は10〜130個です。

**比較のため**：その商品がAmazonに既にあってランクが取れる場合、ランク（対数）だけで説明力39.5%です。

```
log10(月間販売数) = 4.302 − 0.598 × log10(ランク)
→ 1万位で月82個 / 5万位で月31個 / 15万位で月16個
```

**非Amazon起点の予測は、Amazon起点の約40%の情報量しかありません（15.8% 対 39.5%）。** これが両起点の質の差であり、資源配分の根拠です（§7）。

### 4.3 だから設計をこう変える

**予測精度を上げようとしないでください。上げられません（実測済み）。**
代わりに**外れても死なない発注量**で回します。これはセミナーの「初回は最小5個」と同じ結論です。

| 場面 | 使い方 |
|---|---|
| メーカーに連絡するかどうか | コホート中央値が月**10個未満**なら連絡しない（下振れ0.3倍でも3個。話にならない） |
| 見積が返ってきた後 | **初回ロットは5個固定。** コホート予測を数量決定に使わない |
| リピート判断 | **実売2週間の実測に切り替える。** ここで初めて予測を捨てる |

### 4.5 手順の順序 — カズヨの案でよい。ただし0番を足す

カズヨの案「①候補メーカー発見 → ②Keepaで類似商品の売上予想 → ③卸値を聞く → ④利益計算」は**順序として正しい**です。売れないジャンルのメーカーに連絡する時間を省けます。

**ただし②の前に「0番」が要ります。**

```
0. そのメーカーの商品が既にAmazonにあるか、メーカー名で検索する   … 10トークン
   → ある  → Amazon起点の判定に合流（ランクが取れる＝説明力39.5%）
   → 無い  → 1へ進む
1. 候補メーカー発見（展示会出展社名簿 2,353社／Keepa由来との重複0.1%）
2. コホートで需要推定（既存群なら0トークン）→ 月10個未満なら打ち切り
3. メーカーに連絡して卸値を聞く   ← §4.1（第三者連絡）＝社長承認必須
4. 利益計算 → 初回5個
```

**0番を飛ばすと、Amazon起点で既に拾えている会社に、情報量の少ないやり方で連絡することになります。** 展示会名簿とKeepa由来の重複は0.1%（2社）と実測済みなので、実際にはほとんど1へ進みますが、この1手は10トークンで確実に効きます。

## 8. やらないこと（5件）

1. **ランク帯のチューニングをしない。** 実測で本命率を説明していない。`salesRankDrops30 ≥ 10` に置き換える
