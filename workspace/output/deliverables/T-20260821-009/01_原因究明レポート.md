# `_inbox_社長共有` 運用崩れ — 原因究明レポート

- チケット: T-20260821-009
- 作成: 庶務マリエ / 2026-08-21
- 社長の指摘: 「共有したファイルが整理されていない。最初の方はきちんと運用されていたが、今はできていないみたい」

---

## 1. 結論（真因）

> **inbox の後片付けが「チケットのタスク分解に、起票者が手書きで1行足したときだけ実行される属人的ステップ」だった。**
> 恒久ルール・受け皿・検知のどれも存在せず、その1行を書き忘れた瞬間に運用が止まった。

社長の体感（「最初はできていた／今はできていない」）は**完全に正確**でした。
そして「最初はできていた」理由が、そのまま「今できていない」理由です。
**6月に成功したのは仕組みがあったからではなく、たまたまその1行が書かれたから**でした。

補足として、**チケットにすらならないファイル**（社長が置いたが申告し忘れたもの）は検知手段が一切なく、
**永久に放置される**構造でした。実際、残留21件のうち **2件がこの経路**で、
しかもその2件が今回いちばん惜しい取りこぼし（現役の高価値資料と、未反映のナレッジ）でした（§5）。

## 3. 秘書の初期仮説5点の検証結果

「鵜呑みにせず実地で裏取りを」との指示に従い、5点すべてを検証しました。
結果として、**5点は同格ではありません。**2点が真因、3点は増幅要因です。

| # | 仮説 | 検証結果 | 判定 |
|---|---|---|---|
| 2 | ルールが CLAUDE.md にも agents/ にも無い | `grep -rn "_inbox"` の結果、ルールらしき記述はゼロ。ヒットするのはチケット本文と reference README の「受領経路の記録」だけ | ✅ **真因（中核）** |
| 3 | プル型トリガー依存（社長の申告が起点） | README.txt の手順②が「チャットで一言伝える」。8月の資料が全部チャット経由に移行し、inbox に置いただけのファイル（xlsx・026）は**申告されず永久放置**された | ✅ **真因（第2の柱）** |
| 1 | `.gitignore` 対象で Git 差分に出ない | `.gitignore:24` に `_inbox_社長共有/` を確認。既存フック3本（session-start / ticket-notion-sync-reminder / owner-tasks-sync-check）の発火条件を全部読んだところ、**いずれも `workspace/tickets/` 等の追跡ファイル変更が起点**で、inbox は全フックの死角 | ⚠️ **増幅要因**（原因ではなく「なぜ12日間も気づけなかったか」の答え） |
| 4 | マリエの定常責務に未登録 | `agents/general_affairs/agent.md` を確認。Notion同期・カタログ同期は責務化されているが inbox は無し | ⚠️ **増幅要因**（#2 の系。ルールが無いので責務にも登録されていない） |
| 5 | 処理済みの行き先が未定義 | README.txt は「移動されることがある」のみ | ⚠️ **寄与要因**（ただし6月は受け皿無しでも移動できたので、単独では原因にならない。「毎回どこへ置くか判断が要る＝摩擦」として効いた） |

**#1 を単独の原因と誤認しないことが重要です。**仮に inbox が Git 追跡下にあっても、
後片付けのルールが無ければ「差分に出るが誰も片付けないファイル」になるだけでした。

## 4. 対策（3点セット。1つでも欠けると再発する）

真因が「ルール不在」＋「プル型依存」なので、**明文化と自動検知の両方**が要ります。

| # | 対策 | 実装 | 効く仮説 |
|---|---|---|---|
| A | **検知の自動化** | `.claude/hooks/session-start.sh` に「リマインダー③」を追加。inbox 直下の未処理ファイル数と最古日付を毎セッション通知。`_archive/` `README.txt` `.DS_Store` は除外 | #3・#1 |
| B | **ルールの明文化** | `CLAUDE.md` §6 に inbox 節を新設／`agents/general_affairs/agent.md` に「定常責務」表を新設し #4 として登録／手順書 `agents/general_affairs/skills/inbox-intake.md` を新設 | #2・#4 |
| C | **受け皿の設置** | `_inbox_社長共有/_archive/YYYY-MM/<ticket_id>_<内容>/` を作成。各フォルダに中身一覧の `README.md` を必須化 | #5 |

**A が要（かなめ）です。**B と C だけでは「ルールを読む人がいなければ元通り」ですが、
A があれば社長が何も言わなくても毎セッション勝手に卓上に載ります。

あわせて、README.txt を**社長の手数が1ステップ減る**方向に改訂しました。
旧: ①置く ②チャットで伝える → 新: **①置くだけ**（申告は任意。会社側から声をかける）。

## 5. 棚卸しで判明した副産物（実害の把握）

放置の実害は「散らかっていた」ことだけではありませんでした。

### ⚠️ 実害1: 高価値資料が12日間死蔵されていた（xlsx）

`FBA納品代行業者_比較表`（2026-08-09・11社）は、**どのチケットにも紐づかず**放置されていました。
これは社長が挙げたメーカー仕入れ 信用構築3点の**③「FBA納品の外注先を決めておく」に直結する一次資料**です。

しかも内容が、現行チケット **T-20260817-006 の判断根拠を一部覆します**。

- T-20260817-006 の③評価: 「急ぐ必要なし。**先に契約すると月額固定費 2,000〜4,000円が売上ゼロで出続ける**」
- 本資料の事実: **就労支援系（A型/B型）は月額固定費ほぼ無料**、単価も 10〜50円/点（一般物流系は 40〜100円/点）

→ 「固定費が出続けるから急がない」という論拠は、**一般物流系にしか当てはまりません**。
　 → `docs/reference/fba-prep-center/` へ収納（原本 xlsx ＋ テキスト版 ＋ 索引 README、いずれも Git 追跡）。

### ⚠️ 実害2: 未反映のナレッジが埋もれていた（FireShot 026）

026 は **keepa.com「出品者概要」ページ**（セラー単位の分析画面）で、08-12 に追加で置かれたものです。
T-20260811-001 の入力素材は 021〜025 の5枚のみで、026 は**どのチケットにも属していません**。

納品済みの `deliverables/T-20260811-001/keepa-usage-guide.html` を検索したところ、
「出品者概要」「出品者検索」「セラー分析」いずれの語も**ヒットせず**＝機能そのものが未収録。
memory `knowledge_keepa_operation_umizou.md` にも記述なし。

→ **Keepa のナレッジに穴が空いたままでした。** T-20260811-001 の完了確認時に、
　 反映するかスコープ外として明示的に切るかの判断が要ります（→ §6）。

### 記録の訂正: T-20260812-001 の「13枚」は実際は14枚

実ファイルは14枚あります。差分の1枚は `11.44.58`（別キーワード `Relaxation Spa Gift Pack for Men` での実データ画面）で、
検索語が他13枚と異なるため読解対象から漏れたと見られます。
ただし**既知機能の別データ例にすぎず、採否判断（A案＝今は契約しない）の結論には影響しません。**記録の正確性のための訂正のみ。
