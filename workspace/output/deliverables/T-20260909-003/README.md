## A. .gitignore をどう直したか

ホワイトリスト方式（`*` で全除外＋`!ファイル名`）だったのは2フォルダだけでした
（T-20260904-004 / T-20260906-004）。この2つを反転しました。

| | 変更前 | 変更後 |
|---|---|---|
| 既定 | 載せない（`*`） | **載せる** |
| 除外のしかた | 許可リストに書き忘れたら落ちる | 危険な「形」（`*.csv` `*.jsonl` `_*cache.json`）＋卸値を含む個別ファイルの名指し |
| 書き忘れたとき | 黙って公開されない＝資料が消える | 追跡される。危険物は pre-commit が止める |

**追跡ファイル数は 723 のまま変わらず、除外されているファイルの集合も変わっていません。**
変わったのは「なぜ除外されているか」が1行で分かるようになったことです。
（`git check-ignore -v` の理由が `*` から `*.csv` や具体的なファイル名になりました）

守りは3枚になりました。1枚目を抜けても2・3枚目で止まります。

1. 各フォルダの `.gitignore`（形＋名指しの除外）
2. `.githooks/pre-commit` — 卸値・Keepa 加工値・認証情報を検知して commit を中止
3. `build_catalog.py --check-untracked` — 追跡漏れの検知

### 追跡漏れを黙って通さないための検知（新設）

- **pre-commit**: catch-all `*` で除外されたファイルがあれば警告を出します。**commit は止めません**
  （公開してよいかの判断は社長・法務の領分で、機械が決めてよいものではないため）。
- **SessionStart リマインダー⑦**: 同じ検査をセッション開始時に出します。
  平常時は1行も出ません。ホワイトリスト方式が復活したその日に鳴ります。

検証は両方向で行いました。実リポでは 0 件（＝正常な commit を邪魔しない）、
`*` を書いた使い捨てリポでは 2 件を検知（＝本当に鳴る）。

```bash

python3 scripts/catalog/build_catalog.py --dry-run  # 件数だけ確認
python3 scripts/catalog/build_catalog.py --check-untracked   # 追跡漏れの一覧
```

人が書いたタイトルがある行は、そのタイトルを活かして付番だけを足しています。

## 残る論点（社長・マリエの判断が要るもの）

1. **GitHub リンクが作業ブランチ固定のまま**（原因②）。
   生成時の `git rev-parse --abbrev-ref HEAD` を使うので、いま生成すると
   `claude/nighttime-work-checkin-iTWEa` になります。main にマージされていないので
   main を指すと全部 404 になるため、勝手に main へは書き換えていません。
   **本質的な解決は main へのマージ**で、これは私の判断で踏める操作ではありません。
   なお社長の閲覧は file:// リンクなので、この論点は実害を伴いません。
2. **要記入が 508 件**。棚卸し（載せる/載せない）と要約の記入はマリエの担当です。
   テストコード・自己診断スクリプトなど、成果物と呼びにくいものも含まれます。
3. **03 の HTML を公開するかどうか**。公開するなら卸値の列を落とした版を作る必要があります
   （手順は memory: `knowledge_column_level_redaction_public_repo`）。現状は据え置き。
4. **本人特定情報のフォルダ**（`T-20260817-006/公開用/` `会社概要_配布用/`）は、
