A. プレモーテム — 無人常駐スキャナ（T-20260831-002 / Phase A）

シミュレーター マサル / 2026-08-31
対象: scan_v14.py を launchd で常駐化し、時間上限を外して回し続ける案

0. 結論

  1. このまま常駐させると、稼働14日目に母数を掘り尽くし、以後は1日28,800トークンを新規0件のために焼き続けます。 しかも画面表示は「全シャードを掘り切りました」＝正常終了に見えます。確度85%。
  2. 一番怖いのは落ちることではなく、落ちたのに成功と表示されることです。 現行コードは Keepa の API エラーを「母数の枯渇」と誤って記録します（後述 F2）。night-shift が14日間 exit 127 で死んでいたのと同じ構図が、より気づきにくい形で再発します。
  3. 「やらなければよかった」の本命は技術ではありません。 6日前に作った822社のリストが、連絡先も無く、店舗も停止中で、1社も使われていない。そこへ12,000社を足す計画です。積み上げ件数と使用件数を分けて見ると、悪いシナリオでの使用件数は0〜20社です。

判定: タケシ／タカシへ差し戻し。 下記 M1〜M7 を満たすまで常駐させてはいけません。あわせて、ゴールを「無限に積む」から「毎朝10社を出す」へ変える案を社長判断に上げるべきです。

2.2 F2 — 失敗が成功として記録される（最優先で潰す）

これが技術面の最重要バグです。

keepa_get() は payload["error"] を検知すると {} を返します（scan_v14.py 545行〜）。呼び出し側はこうなります。

Finder が {} を返す → asins が空 → exhausted.add(band)
→ 25シャード全部が exhausted → watch.stop("全シャードを掘り切りました")
→ progress.json / STATUS.md / FINISHED に「掘り切りました」と書かれる

つまり APIキー失効・プラン切れ・Keepa の障害・アカウント制限が、すべて「母数を掘り尽くした」という正常終了として記録されます。 秘書も社長も STATUS.md を見て「順調に終わった」と解釈します。

  • 予兆: なし。ログに API エラー の行は出ますが、v14/*.log は gitignore されていて誰も読みません
  • 12時間の走行でAPIエラーは0件でした。つまりこのエラー処理は一度も本番で動いたことがありません。2,160時間の常駐では、Keepa 側のメンテ・5xx・キー更新で必ず発火します
  • 打ち手: 「0件」と「エラー」を必ず区別する。エラー由来なら exhausted に入れず ALERT を書く（M2）

3手先まで: うちが誤報告する → 秘書が「枯渇したので条件を広げましょう」と提案する → タケシが母集団の再設計に着手する → 実際はキーが死んでいるだけなので、広げても0件のまま → 数週間を溶かす。

2.3 F3 — 14日目からの「動いているが無価値」

exhausted はメモリ上の集合で、永続化されていません（859行〜）。launchd の KeepAlive を付けた場合こうなります。

掘り切る → exit 0 → KeepAlive が10秒後に再起動
→ 25シャードを頭から再探索（1シャード20トークン ≒ 500トークン ≒ 25分）
→ また掘り切る → 再起動 …

トークンは20/分でしか回復しないので、プロセスは大半を Budget.wait で過ごし、回復した28,800トークン/日を全額 Finder の空振りに使い、新規0件を生産し続けます。 表示は「掘り切りました」。ディスクだけは静かに増えます。

  • 正味の新規流入（掘り切った後に本当に増える件数）: 追跡180日超という条件があるため、母集団48,760件への月次流入は推定3〜8% ＝ 1日あたり50〜130件（確度50%・未検証）
  • 容量3,588件/日に対し、実需は1.4〜3.6%。 96%以上が無駄撃ちになります
  • 打ち手: 掘り切ったら止めるのでも回し続けるのでもなく、鮮度の古い順に巡回し直すモードへ切り替える（M10）。ただし追記CSVのままでは重複するので M5 が前提

2.4 F4 — 全社の自動同期が止まる

github-sync.sh は30分ごとに git add -A します。スキャナの出力 01_〜.csv 02_〜.csv 03_〜.csv 00_候補リスト.html はGit 追跡対象です。

2つの経路のどちらかで必ず問題になります。

経路起きること
コミットされ続ける1日18回前後 × 数MB〜数十MBのCSVが履歴に積まれる。現在 .git は65MB。2週間で1.5〜3GBに膨らむ（確度60%）
コミットされないQUIET_MIN=5。スキャナは約8分ごとにCSVへ追記するため、同期のたび「編集中」と判定されて HOLD になる。実測比率で6割前後の同期回がコミットを見送る。他エージェントの未コミット成果物も巻き添えで放置される（確度70%）

さらに決定的なのは100MB の壁です。追記のみで重複排除が無いため、鮮度更新のために全件を1周し直すと 01_候補プール_全件.csv は 53.8MB → 107.6MB になり、GitHub の1ファイル100MB上限を超えて push が恒久的に失敗します。CLAUDE.md に「30分ごとの自動同期が丸ごと止まる」と明記された事故が、約4週間後に確定的に起きます。

  • 予兆: workspace/.sync/github-sync.log に ERROR push に失敗 が並ぶ。誰も見ていない
  • 打ち手: 全件CSV・HTML・DBは追跡外へ。リポに載せるのは日次サマリ（数十行）と 03 の差分だけ（M6）

2.5 F5 — 静かな死（この会社の実績値は「2本中1本」）

night-shift.plist は8月17日から exit 127 で死んでいます。 原因は単純で、ProgramArguments が指す .claude/scripts/night-shift.sh が存在しません（.claude/scripts/ には github-sync.sh しかない）。stderr ログには同じ行が30本以上並んでいますが、14日間誰も読んでいません。

この案件で同じことが起きる具体的な口は3つあります。

  1. .env の場所: scan_v14.py は起動時に workspace/output/agent_output/T-20260521-005/code/.env をモジュール読み込み中に open() します（96行）。agent_output/ は gitignore 対象で、CLAUDE.md が「worktree が消えると成果物ごと消える」と明記している層です。消えた瞬間、import 時に例外 → 即死 → KeepAlive が10秒ごとに再起動を繰り返す
  2. private import: from adapters.amazon_data import _map_category_key — 他チケットの agent_output 配下にあるアンダースコア付き関数に依存しています
  3. PIDベースの生存判定: watch_v14.py の alive() は os.kill(pid, 0)。再起動後にPIDが再利用されると死んでいるスキャナを「走行中」と表示します
  • 打ち手: 心拍ファイル（60秒ごとに mtime 更新）＋ SessionStart フックで「最終心拍 N 分前」を毎回表示（M1）。依存チェックに失敗したら ALERT を書いて exit 0（再起動ループを作らない・M3）

2.6 F6 — 二重起動

run_v14.sh の多重起動ガードは kill -0 $(cat v14/scan.pid) です。

  • 再起動後にPIDが再利用されていると「すでに走っています」と誤判定 → 起動しない（静かな死）
  • 逆に launchd と run_v14.sh を両方使うと2プロセスが並走します。raw_idx は起動時の len(glob("*.json.gz")) で決まるので、両者が同じファイル名を書いて上書きし合います。CSVには重複行が入り、トークンは倍速で枯れ、双方が Budget.wait で待ち続けます
  • 打ち手: flock による単一インスタンス保証。起動口を launchd の1本に集約し、run_v14.sh は警告を出す（M4）

2.7 F7 — Keepa 側からの遮断（低確率・最大損害）

Keepa は本事業の生命線です。ここだけは確率でなく損害で判断すべき項目です。

  • 連続アクセス自体はトークンで律速されており、通常運転が規約違反になる確率は低い（10%未満・確度60%）
  • 危ないのは F3 の再起動ストームです。10秒間隔で再起動しながら Finder を叩き続ける挙動は、レート制限側からは異常に見えます
  • 未検証の重要事項: 2026年3月の改定で データクォータ（毎時5%回復） が導入されています（マサルのメモリ index に記載）。Budget クラスは tokensLeft しか追跡しておらず、このクォータを一切見ていません。常駐でこれを焼き切った時に何が起きるかは読めません
  • 打ち手: Keepa からの警告通知が1通でも来たら即時停止（撤退条件B-4）。データクォータの有無と挙動をタカシが公式で確認してから稼働（M11）

2.8 F8 — 台帳が消えると、社長の連絡順が静かに壊れる

seen_asins.txt は gitignore 対象で、v14/ 配下にあります。git clean -xdf や別環境での clone で消えます。

seen が消える → 全ASINを再取得 → append_rows は重複排除しない → CSV_GO に同じASINが2行
→ rebuild_maker_csv() の 該当商品数 = len(items) が2倍に
→ 03_メーカー名寄せ.csv は「該当商品数の多い順」でソート
→ 社長が上から連絡するリストの先頭が、重複でかさ増しされた企業に入れ替わる

件数は増え、順番は壊れ、見た目では判別できません。 社長の時間という最も高価な資源を、水増しされた順序に沿って消費させます。

  • 打ち手: ASIN を主キーにした upsert（SQLite）へ移行。CSVは派生物に降格（M5）

2.9 F9 — データの腐敗

FIELDS に 取得日時 はあります。しかし MAKER_FIELDS（社長が実際に見る 03_メーカー名寄せ.csv）には日付列が1つもありません。

想定仕入れ金額(上限) は取得時点の価格スナップショットから逆算した値です。90日前の価格で「この金額以下なら利益率20%」と判断し、その額で交渉して合意すると、現在価格が15%下がっていればそのまま赤字仕入れになります。

  • 社長の使い方は「片っ端から連絡して、想定仕入れ金額以下なら仕入れる」です。腐った数字が直接お金に変わる導線が既にできています
  • 店舗停止中は発注しない可能性が高いため、3ヶ月内の実損確率は20%程度に留まります。ただし復旧直後が最も危険です（古いリストしか無い状態で一気に動く）
  • 打ち手: 03 に 最終取得日 を必須列で追加。30日超は「要再取得」フラグ。連絡直前に1コマンドで引き直す導線（M9）

2.10 F1 — 本命。増えるほど使われなくなる

技術の話ではありません。これが「やらなければよかった」の直接原因です。

現在の事実だけを並べます。

事実出典
候補1,520件・822社が 8月25日から存在している00_サマリ.md
822社の連絡先はまだ取得できていない（取得手段の確立が別チケットで進行中）T-20260831-001
日本店は8月1日から停止中。CA店のKYCは8/28に却下、サポートケースは回答ゼロで閉鎖T-20260826-004
1SKUも出品していないT-20260826-004
社長がこれまでに連絡したメーカー数記録なし＝おそらく0社

ボトルネックは上流（リストの件数）ではなく、下流（連絡先・社長の架電時間・売る場所）にあります。 822社を消化できていない状態で12,000社を足す行為は、渋滞の先頭ではなく最後尾に車を追加するのと同じです。

社長の実行容量を見積もると:

ペース1社あたり3ヶ月の到達
良い15分 × 10社/日 × 20日 × 3ヶ月600社
普通3社/日 × 15日 × 3ヶ月135社
悪い（店舗対応に忙殺）—0〜20社

すでにある822社ですら、良いペースでも1.4ヶ月分の在庫です。 3ヶ月で12,000社に増やしても、使用率は最良で5%、中央値で1.1%にしかなりません。

さらに悪い連鎖があります。

リストが12,000社になる → 社長は「どこから手を付けるか」が分からなくなる
→ 開かなくなる → 「増えている」という報告だけが毎日届く
→ 3ヶ月後「毎日増えていると聞いていたが、何も進んでいない」

打ち手（これは実装ではなく方針の変更なので、社長判断に上げる必要があります）:
成果物を「リスト」から「毎朝の10社」に変える。スキャナの出力は社長には見せず、今日連絡する10社.md（連絡先入り・鮮度検証済み・重複除外済み）だけを毎朝出す。件数の報告をやめる。

この3シナリオが示す構造は単純です。 積み上げ件数は良いシナリオと悪いシナリオで大差ありません（36,000 vs 15,000〜50,000）。分かれるのは使用件数だけで、その差は30倍以上です。 つまりスキャナの性能はほとんど結果を決めません。 決めるのは、下流（連絡先・鮮度・毎朝10社）が繋がっているかどうかです。

4. 撤退・停止条件

4.1 スキャナ自身が自動で止まる条件（そのままコードに書ける粒度）

ID条件動作
S1直近24時間の新規ユニークASIN < 200件探索モードを終了し巡回モードへ切替（M10）。切替先が無ければ停止
S2直近6時間で新規候補行 = 0 かつ消費トークン > 3,000停止 + ALERT 書き出し（＝無価値に焼いている）
S3直近100リクエストのAPIエラー率 > 20%停止 + ALERT。「掘り切りました」とは絶対に書かない
S4tokensLeft が 90分以上 必要数に届かない停止 + ALERT
S5連続例外3回（import / 認証 / ディスク書込）停止 + ALERT + exit 0（KeepAlive の再起動ループを作らない）
S6v14/ 合計 > 20GB または ディスク空き < 50GB停止 + ALERT
S7Git 追跡対象の単一ファイル > 40MB追記停止（100MBの半分で先に止める）
S8flock が取れない即終了（二重起動防止）
S9STOP ファイルが存在現行どおり安全停止（維持）
S10心拍が 10分以上更新されていない（外側の監視から）プロセスを kill し ALERT

4.2 人間が「やめる」と判断する条件

ID時点条件判断
W1稼働30日社長が連絡したメーカー数 < 30社常駐を週1回・1時間へ縮退。積み上げに意味が無いことの証拠
W2稼働60日累計連絡 < 100社常駐を停止し、必要時の手動起動へ戻す
W3随時github-sync が 48時間 push できていないスキャナを止める（優先順位はリポ > リスト）
W4随時Keepa から警告・制限の通知が 1通でも来る即時停止し社長へ報告（生命線のため例外なし）

6. 判定

この案は、まだ社長承認に上げられません。タケシ／タカシへ差し戻します。

理由は3つです。

  1. M2 が未実装のまま常駐すると、壊れたことを検知する手段がありません。 障害が「正常終了」として記録される設計で無人運転を始めるのは、night-shift の14日間と同じ失敗を、より発見しにくい形で繰り返すことになります
  2. M5 / M6 が無いと、約4週間後に全社の自動同期が確定的に止まります。 これはスキャナの問題ではなく会社全体の問題です
  3. F1（使われない）に対する打ち手が案の中にありません。 現在の案は「もっと積む」ですが、詰まっているのは下流です。P1 を決めない限り、技術的にどれだけ完璧に動いても3ヶ月後の使用件数は変わりません
