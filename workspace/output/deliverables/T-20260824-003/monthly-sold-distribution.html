結論（先に3行）

1. 値は完全に階級値でした。 4,002 ASIN の現在値に出た値は 11 種類のみ（50, 100, 200, …, 1000）。連続値は1つもありません。公式定義「"10+" "100+" のような区切られた範囲でしか提供しない」と完全に一致。

2. 欠測は 66.5%（2,663/4,002）。 公式定義「大半のASINには値が無い」も一致。しかも当社データは*回転の速い商品だけに絞った母集団*なので、Amazon 全体ではもっと欠測が多いはずです。

3. 「月50個以上の商品にしか出ない」は、スナップショットとしては正しく、フィールドの性質としては誤りでした。 現在値の最小は確かに 50 ですが、同じ商品の monthlySoldHistory には 10 / 20 / 30 / 40 が実在します（1〜49 を履歴に持つ ASIN が 4,002 件中 1,732 件）。50 は Keepa の下限ではなく、この時期のたまたまの下限です。>= 50 を前提にしたコードを書いてはいけません。

回転が速いほど出現率は上がります（18.7% → 84.3%）が、32〜50ドロップ帯でも 15.7% は欠測。

実例として ドロップ数 49 の B0DQCC4CTB は欠測、逆に ドロップ数 9 の B0F1S2P3TM は 50 が入っています。

→ monthlySold の欠測を「月50個も売れていない」と読んではいけません。 単に Amazon が表示していないだけです。

　 欠測を 0 とみなす／欠測を足切りに使う実装は誤判定を生みます。

4. 実装上の申し送り（scan_v13 系を触る人へ）

  • 欠測はキーの不在。product.get("monthlySold") は None を返す。-1 や 0 での判定は不要（現在値には出ない）が、monthlySoldHistory の中では -1 が欠測マーカーなので履歴を扱う時だけ弾くこと。
  • monthlySold=50 は「50〜99」の意味。掛け算して売上を出すなら下限見積りとして扱う。上振れ側は無限。
  • >= 50 を前提にしない。10/20/30/40 は実在し、いつ戻るか読めない。
  • 値は「バリエーション単位」（公式定義）。色・サイズ違いが1つに合算されるため、特定 SKU の販売数ではありません。単一 ASIN の仕入れ数量計算に直接使うと過大評価になります。
  • monthlySoldHistory は追加トークンなしで付いてくる。現在値が欠測でも履歴に値が残っていることがあるので、粗い当たりを付けたい時は履歴の直近非 -1 値を見る手があります（ただし古さの確認は必須。lastSoldUpdate あり）。
