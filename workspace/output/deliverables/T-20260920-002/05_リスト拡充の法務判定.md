### 2-2. 著作権法上の整理（依頼の3点に答えます）

| 論点 | 判定 | 根拠 |
|---|---|---|
| 社名・電話番号・URL・取扱品目の**事実データの複製** | 著作権が及ばない | 2条1項1号「思想又は感情を**創作的に表現**したもの」に当たらない |

| 名簿の**全件をそのまま外部に出す** | **不可** | 30条の4の「必要と認められる限度」を超える。ただし書（著作権者の利益を不当に害する）にも触れる。§3-2 の PUBLIC 判定と同じ結論 |

### 2-3. robots.txt が無い団体（#2・#3・#4）の扱い

**「禁止されていない＝OK」とは扱いません。正しくは「robots.txt は許諾を与える文書ではなく、拒否の意思表示の置き場である」。無いことは意思表示が無いことに過ぎず、適法性は §2-2 の著作権法の論証で立てます。**

タカシへの実装上の差分（ここが一番大事です）：

```
8/31 の実装制約「robots.txt の取得失敗時は『許可なし』と扱う」は、
HTTP 404 には適用しない。404 = ファイルが存在しない = 制限の宣言が無い → 取得してよい。
403 / 5xx / タイムアウトでの取得失敗 = サーバ側が拒んでいる → 「許可なし」として当該ホストを打ち切る。
この2つを区別しないと、NAPAC・JPPMA・JAFTMA の3本（計394社）が理由なく落ちる。
```

## 3. 論点② メーカー自社HPからの取得と、電話番号の保存

### 3-1. 範囲は変わりません

8/31 判定は「robots.txt 尊重・同一ホスト3秒・UA明示・会社概要/問い合わせ系パス限定・1社10ページまで」。今回の運用（**1社3ページ・トップ＋会社概要＋問い合わせ**）はその内側で、**新たな論点は生じません**。`MAKER_MIN_INTERVAL = 2.5` は 3.0 に上げてください（8/31 の数字と揃える。2.5 にする根拠がありません）。

取得した電話番号を**社内リストに保存し、営業電話に使うこと**の可否：

| 論点 | 判定 | 根拠 |
|---|---|---|
| **法人の代表電話は個人情報か** | **非該当** | 個情法2条1項は「**生存する個人に関する情報**」。個人情報保護委員会ガイドライン（通則編）「法人その他の団体は『個人』に該当しないため、法人等の団体そのものに関する情報は『個人情報』に該当しない」 |
| 個人事業主のメーカーで代表者氏名と電話が紐づく場合 | **該当する** | 同ガイドライン。事業情報がそのまま個人の情報になる。**S-B 実測で法人格表記があるのは85.2%**＝14.8%は判定できない |
| 実務上の扱い | **データセット全体に個人情報の取扱いルールを適用する** | 1,006行を1件ずつ法人/個人事業主に仕分けてから扱いを分けるのは破綻します。全体に掛けるのが最も安全で最も安い |
| 営業電話に使うこと | **可**。法的障害なし | 事業者間の電話勧誘は特商法の電話勧誘販売（26条1項1号で営業のためのものを除外）の対象外。特定電子メール法は電話に及ばない |
| 利用目的 | 「当社のメーカー仕入れに係る取引先候補の調査、連絡、商談管理のため」で確定（17条） | 目的外利用の禁止（18条）。名簿販売・他事業への転用は不可 |
| 利用目的の通知または公表（21条1項） | **公表の場を先に用意する**（自社サイトに1ページ）。連絡開始より前に | 1,006社に個別通知は本末転倒。8/31 判定と同じ |
| 代表者氏名 | **取得しない・保存しない** | 個人情報の混入経路を1本潰せば、以後の議論がまるごと消えます |

### 3-2. 電話番号を PUBLIC リポジトリに置いてよいか → **NO**

理由は4つ。いずれか1つでも足ります。

1. **個情法27条1項**（第三者提供の制限）。個人事業主が混ざる前提である以上、commit＝不特定多数への提供。本人同意はありません。
2. **NAPAC の不許諾宣言**（§2-1 #2）。事実データに著作権は及びませんが、161社分を丸ごと再公開すれば「元の名簿の代わりになる形」であり、段階2（公開）＝不可の型に入ります。
3. **不可逆性**。このリポは PUBLIC で30分ごとに自動 push されます。commit した瞬間に世界へ公開され、取り消しには `force push`＝§4.1。確率が低くても止める類の話です（行動原則1）。
4. iタウンページを将来買う場合、**第11条2項（第三者提供の禁止）に正面から違反**し、第18条の違約金（使用料の3倍）が起動します（§5-2）。置き場を今のうちに分けておけば、後から設計を作り直さずに済みます。

**置き場の指定（タカシへ）**

| **実データの正** | 社名・電話番号・FAX・住所・自社HP・品目・接触状況の全列 | **限定共有の Google スプレッドシート**（マリエ運用・社長が電話しながら見る画面もこれ）。共有範囲は社長アカウントのみ |

## 4. 論点③ EC出店の有無

### 4-0. 第一選択：相手のサーバに1リクエストも送らない方法

**メーカー自社HPの外部リンク先ドメインで判定してください。** 「公式オンラインショップ」「楽天市場店」「Yahoo!店」のリンクは会社概要・トップに載っています。これは §3（メーカー自社HPの取得）の範囲内で完結し、**楽天・Yahoo!・Amazon のサーバにアクセスしないので、各社の規約の名宛人になりません**。判定は 0円・0リスクです。

```
判定ロジック（実装そのまま）
  リンク先ホストが *.rakuten.co.jp          → モール出店:楽天 = 有（出典: 自社HP URL）
               shopping.yahoo.co.jp / *.store.yahoo.co.jp → Yahoo = 有
               *.amazon.co.jp                → Amazon = 有
               *.base.shop / *.stores.jp / *.thebase.in / *.myshopify.com / cart 語 → 自社EC = 有
  リンクが無い場合 → 「無」と書かない。必ず「未確認」と書く（出店していてもHPに貼らない社がある）
```

### 4-1. 楽天市場
