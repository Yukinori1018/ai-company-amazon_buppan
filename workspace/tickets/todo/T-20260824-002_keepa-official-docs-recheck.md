# 概要

**Keepa 公式ドキュメントと当社の用語解釈・実装を、四半期ごとに突合する定期タスク。**

## なぜ定期でやる必要があるのか

T-20260824-001 で用語の取り違えが **20語**見つかった。そこで判明した構造：

> **方向が「安全側」の誤りは、日常の運用では自力で発見できない。**

- COUNT_NEW の誤り（**危険側**）は「セラー1社の商品が候補1位」という目に見える異常として社長が発見できた
- D1 の誤り（**安全側**＝判定を厳しくする方向）は赤字を出さないため、**候補を取りこぼし続けても誰も気づかない**。実際に何ヶ月も残った

「おかしな結果が出たら調べる」という受動的運用では、**安全側の誤りだけが永久に残る**。能動的な突合を仕組みで持つしかない。

さらに Keepa は**仕様変更が多い**（2026-02-23 価格定義変更 / 2026-03 csv 34,35 追加・31退役 / 2026-04-20 eBook追跡終了 / 2026-03 料金改定）。放置すると資料が腐る。

## 手順

1. **`https://keepa.com/api-docs/changelog.html` を最初に読む。** 前回突合日以降の変更を洗い出す（仕様変更が誤りの起点になっている実例が多い）
2. 変更があったフィールドについて `product-object.html` / `statistics-object.html` / `seller-object.html` / `product-finder.html` の定義を再確認
3. **`workspace/output/deliverables/T-20260824-001/keepa-glossary.md` §0.5 の4列対応表を基点に突合。**
   新たな取り違えが見つかったら4列目（当社が過去に取り違えた内容）に追記する。
   **「なし」の欄を空欄にしない**（空欄＝未調査と区別がつかなくなる）
4. 当社の実装（`scan_v13.py` 等）で使っているフィールドを機械照合し、影響範囲を出す
5. **特に「安全側の誤り」を意図的に探す。**「厳しすぎて取りこぼしていないか」という観点で見る
