# 進捗マークの判定基準

ヒデアキ（コンテンツ制作）が 2026-08-26 に確立し、社長が使っている基準です。
これがブレると、社長は「先週より進んだのか」を数字から読めなくなります。

## 3つのマーク

| マーク | 意味 | 付ける条件 |
|---|---|---|
| `[x]` | 実行した | **その行動が現実に起きた**。証拠となるチケット・成果物・画面確認がある |
| `[~]` | 着手中・部分的 | 設計・調査・準備は済み、実行が残っている。または一部だけ実行した |
| `[ ]` | 未着手 | 何も起きていない |

## いちばん間違えやすいところ

**「調べた」「ナレッジにまとめた」「ルール化した」は `[x]` ではありません。**

例：古物商許可。要否の判定はナレッジ化まで終わっていますが、許可そのものは
取っていないので `[ ]` です。ナレッジがあることと、許可証があることは違います。

例外は、**その小項目自体が調査タスクである場合**。「4手法を比較表にする」なら
比較表ができた時点で `[x]` です。行動＝調査だからです。

小項目の文を読んで「これは何をしたら終わりなのか」を先に決めると迷いません。
動詞が「取得する」「提出する」「送る」「発注する」「登録する」なら、
その動作が物理的に起きた記録が要ります。

**「満たす」「一致させる」「揃える」「切り替える」も物理事実です。**
状態を指す動詞なので「条件を調べた」と読み替えたくなりますが、問われているのは
**今その状態にあるか**です。現状がその条件を満たしていることを画面で確認してから
`[x]` にしてください。

2026-08-31 の実例：7-1「カート獲得の5条件を**満たす**」を `[x]` にしていました。
根拠にしたチケット自身が「小口ではカートを獲得できない」と書いています。
「5条件を確認した」を「5条件を満たす」と読み替えた誤りです。正しくは `[ ]` でした。

この動詞の一覧は `scripts/evidence.py` の `ACTION_VERBS` にあります。
`todo.sh build` は、この動詞で終わる小項目が `[x]` なのに根拠へ裏書きの一言
（`〔T-…・画面確認〕` のような注記）が無いとき、警告を出します。

## 迷ったら

`[~]` にして、根拠チケットIDを付けます。`[x]` に寄せて過大に見せるのも、
`[ ]` に寄せて過小に見せるのも、どちらも社長の判断を狂わせます。
`[~]` は「まだ確定していない」を正直に表す札です。

判断がつかず社長の一言で決まるものは、`[~]` のまま **D章に列挙**して、
「社長の一言で `[x]` に上がりうる項目」として明示します。

## 判定の前に根拠本文を読む（2026-08-31 追加）

`todo.sh prepare` が `agent_output/<ticket_id>/02_evidence-excerpts.md` を作ります。
資料に出てくる全 `〔T-…〕` について、そのチケットの「現在地」「完了報告」「結果」「ログ」を
抜き出したものです。**マークを更新する前にこれを読んでください。**

タイトルと要約だけで判定すると、2026-08-31 の10件と同じ間違いをします。あのときは
1-4 の開業届で、**開業日 8/20 を提出日と取り違えて「2枚同時送信は未実施」と誤判定**
しました。チケット本文には「開業届＋青色申告承認申請書を提出完了」と明記されていました。
本文を開いていれば起きなかった誤りです。

抜粋の冒頭には「資料より新しいチケット」が並びます。ここに挙がったものは
**資料の記述が覆っている可能性がある**ので、必ず本文を読んで narrative ごと直します。
2026-08-26 生成の記述が 8/28 の却下で覆っていたのに残っていた、というのが日付凍結です。

## 根拠チケットIDの付け方

- 行末に `〔T-YYYYMMDD-NNN〕` を足す。複数なら `〔T-A / T-B〕`。
- **根拠IDは、そのチケット本文に該当記述があることを確認してから書く。**
  無ければ書かない。知識が出どころなら `〔memory: <ファイル名>〕` にする。
  - `〔T-…〕` ＝ **実行の証拠**（そのチケットでその行動が起きた）
  - `〔memory: …〕` ＝ **知識の出典**（そう決めた／そう分かっている）
  - 併記してよい。例：`〔T-20260726-003 / memory: knowledge_seller_official_operations〕`
  - 2026-08-31 に14件が「本文に該当記述なし」でした。うち T-20260601-001（成果物カタログ）を
    レビュー規約の根拠にしていた例まであります。**手近な既知IDを埋めてはいけません。**
- チケット以外の証拠（画面確認・受信通知など）も同じカッコに書いてよい。
  例：`〔T-20260820-002・e-Tax受信通知 2026-08-21 提出確認〕`
- **個人特定情報は書かない。** 利用者識別番号・受付番号・口座番号・電話番号は
  このリポジトリが PUBLIC なので、書いた瞬間に公開されます。「確認した」で足ります。
- `[ ]` の行にはチケットIDを付けない（根拠が無いから未着手なので）。

## done チケットの扱いに関する注意

done 61枚のうち 37枚は「現在地」「完了報告」が空でした（2026-08-26 実測）。
その分の `[x]` は、タイトルと要件からの推定を含みます。台帳の「報告欄」列が `無` の
チケットを根拠に `[x]` を付けたときは、D章の食い違い表にその旨を残してください。
推定を推定と書かないのが、いちばんまずいやり方です。

## 数字は awk の出力をそのまま貼る

A章のサマリ表・チケット本文・完了報告に書く「済 / 着手中 / 未着手」は、
**`todo.sh build` が出す awk の集計をそのままコピーします。** 手で数えない、
前回の数字から差分で足し引きしない。

2026-08-31 は、資料は 51/43/114 に直したのにチケット本文だけ古い 49/43/116 が
残りました。集計を書き換えたら、貼った先を全部同じ値にしてください。
資料の検算（`verify.py`）はチケット本文までは見ません。ここは人の責任です。

## 中項目の「現在地」1行

各中項目の直下に `> 現在地：…` を1行置きます。読み手が小項目を全部読まずに
「ここは何が終わって何が残っているか」を掴めるようにするためのものです。
進捗が変わった中項目だけ書き直せば十分で、変わっていない中項目の文は触りません。
