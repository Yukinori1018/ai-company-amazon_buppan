# マスターToDoリストの更新

社長の定常運用です。**変わるのは進捗だけ**で、208 小項目の骨格は変わりません。
毎回ゼロから作り直すと、サトルが一次情報で裏を取った数値と、社長が3回入れた
図の指摘が消えます。既存ファイルを流用して、進捗と数字だけを差し替えます。

## 全体の流れ

```
scripts/todo.sh prepare [ticket_id]     ← 機械: 作業場の用意 / チケット棚卸し / 根拠本文の抜粋
   ↓
根拠の抜粋を読んでマークを更新           ← 判断: ここだけ人（あなた）の仕事
   ↓
scripts/todo.sh build [ticket_id]       ← 機械: 集計・ボード更新・HTML生成・検算
   ↓
git commit → カズヨへ board のパスを返す
```

`ticket_id` の既定は `T-20260826-002`（社長の既存リストを上書き更新）。
別 ID を渡すと、既存リストを骨格として複製してからそこに作り直します。

## 1. prepare

```bash
.claude/skills/buppan-todo/scripts/todo.sh prepare
```

やること: 納品先の用意 → 更新前の控えを保存 → `workspace/tickets/` を全数棚卸し →
**根拠チケット本文の抜粋を作成**。

棚卸しは**前回の台帳から分類を引き継ぎます**。106 枚を毎回読み直すと分類が揺れ、
社長には「何もしていないのに数字が変わった」と見えるからです。出力の
「要分類」に挙がったチケットだけ読んで、段階（0〜8）と40字要約を台帳に書き足します。
段階の定義は生成された台帳の冒頭表にあります。

`ticket_id の重複` が出たら採番の事故です。自分で直さず、カズヨへ報告してください。

### 根拠抜粋（2026-08-31 追加・ここが最重要）

prepare は `agent_output/<ticket_id>/02_evidence-excerpts.md` を作ります。資料に出てくる
全 `〔T-…〕` について、そのチケットの「現在地」「完了報告」「結果」「ログ」を抜き出した
ものです（51枚 / 約130KB）。**マークを更新する前にこれを読んでください。**

タイトルと要約だけで判定すると誤判定します。2026-08-31 に社長の指摘から全数再検証した
ところ、誤判定10件・根拠IDの不整合14件が出ました。最初の1件は 1-4 の開業届で、
**開業日 8/20 を提出日と取り違えて「2枚同時送信は未実施」と誤判定**していました。
チケット本文には「提出完了」と明記されています。開いていれば起きなかった誤りです。

抜粋の冒頭に「資料より新しいチケット」が並びます。ここに挙がったものは資料の記述が
覆っている可能性があるので、小項目だけでなく **A章の narrative も直します**。

なお prepare を通さずに build は通りません。抜粋を作った時点のチケット内容を索引に
記録し、build がそれと現物を突き合わせるためです。

## 2. マークを更新する（ここが本体）

編集するのは `workspace/output/deliverables/<ticket_id>/01_master-todo.md` だけです。

**208 小項目の本文は1文字も書き換えません。** 変えるのは次の4つ。

1. 各行のマーク `[x]` / `[~]` / `[ ]`
2. 行末の根拠チケットID `〔T-…〕`
3. 中項目直下の `> 現在地：…` の1行（進捗が動いた中項目だけ）
4. A章のサマリ表・C章（社長タスク）・D章（空白地帯）

始める前に2つ読みます。**`references/judgement.md`**（判定基準）と、prepare が作った
**`agent_output/<ticket_id>/02_evidence-excerpts.md`**（根拠チケットの本文）です。
根拠を読まずにタイトルで判定するのが、誤判定の最多要因でした。
要点だけ先に書くと、`[x]` は「その行動が現実に実行された」場合のみで、
**調べた・ナレッジ化した・ルール化しただけは `[x]` にしません**（その行動自体が
調査タスクである場合を除く）。迷ったら `[~]` にして根拠を書きます。

C章の4分類は、台帳の waiting/todo から拾い直します。

- C-1 §4.1 該当（承認必須。時間が経っても可決されない）
- C-2 社長本人にしかできない手作業
- C-3 判断・Go 待ち
- C-4 納品物レビュー待ち

A章のサマリ表の数字は、次の build が検算します。**手で数えないでください。**
数え間違いは必ず起きるので、先に build を1回走らせて awk の集計値を見てから
表に書き写すのが速いです。

新規調査はしません。骨格に項目を足す・減らすのは別の依頼です。

## 3. build

```bash
.claude/skills/buppan-todo/scripts/todo.sh build
```

やること（全部機械）:

- `aggregate.awk` で 済/着手中/未着手 を中項目・大項目・全体で集計
- `03_process-board.html` の**数字だけ**を差し替え（narrative と Mermaid の描き分けと
  拡大/縮小/幅に合わせる/全画面のボタンは触らない）
- `01_master-todo.html` を再生成（社長既定の HTML 併出力）
- `verify.py` で検算 — 骨格が 02 と一致するか / 見出しの件数 / A章の表 / マーク記法 /
  個人特定情報の有無 / **根拠の実在・鮮度・整合** / ボードの数字

**NG（納品できない）になる条件**

| 条件 | なぜ止めるか |
|---|---|
| 根拠IDのチケットが実在しない | 事実の誤り。読まずに書いた証拠 |
| `〔memory: …〕` のファイルが実在しない | 同上 |
| 資料の「更新: YYYY-MM-DD」より新しいチケットがある | 資料の記述が覆っている可能性がある（日付凍結） |
| prepare 以降に根拠チケットの本文が変わった | 読んだ内容と今の内容が違う。抜粋を作り直して読み直す |
| 根拠抜粋の索引が無い（prepare 未実行） | 本文を読まずに判定する経路を塞ぐ |

**▲（警告。止めないが必ず目を通す）**

| 条件 | 見るべきこと |
|---|---|
| 根拠チケットの本文にも成果物にも該当語が1語も無い | 出典が memory ではないか。無関係なIDを埋めていないか |
| 「満たす」「提出する」等で終わる小項目が `[x]` なのに裏書きの注記が無い | その動作・状態を画面で確認したか |

警告は数を絞ってあります（現状9件）。**多いから無視する、をやらないための調整です。**
- 更新前との差分（マーク行のみ）を表示

**検算が NG なら納品しません。** 出た指摘を直して build を再実行します。

## 4. 締め

1. `git add` して commit（push はしない。30分ごとの自動同期に任せる）
2. チケット本文の「現在地」「ログ」を更新
3. カズヨへ返す。**Artifact の発行はカズヨの仕事**なので、こちらは
   `03_process-board.html` の絶対パスを渡すところまで

## 触ってはいけないもの

- `02_lifecycle-checklist.md` — サトルが一次情報で裏を取った原本。数値・しきい値の
  出典表つき。ここが書き換わると 208 項目の根拠が消えます
- `03_process-board.html` の Mermaid の線の意味 — **内訳＝矢じりなしの細い線
  （`---`）、順序＝矢印（`-->`）**。社長が明示的に指摘して直させた区別です
- ボードのズームボタン（拡大 / 縮小 / 幅に合わせる / 全画面）と縦積みレイアウト —
  「画面が小さい。最大限に大きくして」への対応として入っています
- 個人特定情報 — 公開リポジトリです。利用者識別番号・受付番号・口座番号・電話番号は
  成果物に書きません。「画面で確認した」と書けば足ります
