# 収束 Yes が社長に却下された理由と、キャッシュ条件の案を読む型 — T-20260914-003 / 2026-09-14

## 1. 前回（T-20260912-005 2周目）の収束 Yes が却下された理由

- 私は「12ヶ月中央 月商44〜52万・累計損益 −9万」を「成立率と取り分の実測を買う期間」と言い換え、条件付き・確度70%で収束 Yes を出した。
- 社長（2026-09-14）：「12ヶ月で現金が増えない事業をやったらダメでしょ。この規模で赤字出してたらやる意味がない。もっと儲かる確度の高いやり方を編み出して。」
- 却下の芯は「中央が赤字の案を、言い換えで通した」こと。収束条件（中央で目標KPI・悲観で撤退条件を踏まない）の「目標KPI」を、私が勝手に「実測を買う」に置き換えていた。
- 以後のルール：
  - 社長の設計条件（今回は「12ヶ月の実質現金>0 を中央で」「悲観で予備25万を割らない」）は、言い換えずにそのまま判定する。満たさなければ No。
  - 「確度の高い」と言われたら、P を5割前後で出すことを恐れない。盛らない。P≈50%は「確度が高い」ではないと書く。
  - 収束 Yes の前に「社長が最後に見る1行（中央・P・悲観）」を自分で書き、社長の原文と並べて読む。

## 2. キャッシュ条件（実質現金）の案を読むときの穴

| 穴 | 今回の実例 | 確かめ方 |
|---|---|---|
| 前提と撤退条件が矛盾している | せどり「週12ロット」前提と、撤退条件 S-2「2週で週5ロット未満なら停止」。実測密度（JAN あたり3.0%）なら S-2 は97〜100%発動＝案C の実体は「案B＋2週の試行」 | 撤退条件の各線を、実測の base rate の世界で踏む確率に翻訳する（二項分布で1分） |
| 前提が実測の何倍かを見ていない | 週12ロット＝採用率15〜24%/件。実測の真値3.0%の5〜8倍、誤突合込みの生値8.5%の2〜3倍 | 「定常◯◯」は、社長の作業量×実測の率から積み上げ直す |
| 閾値＝止めたい世界の値 | S-1「ゲートなし率10%未満」は10%の世界で43%しか発動しない | 閾値は「止めたい世界で8割発動・続けたい世界で誤発動5%」で置く |
| 月次モデルがリードタイムを持たない | タケシの月次 MC は発注月に半月分売れる。日次（cf_base）だとリード15〜20日で、発注停止時の売れ残りが増える。案B で約6pt | 発注停止（刈り取り）を含む案は、必ず日次の計算器で回す |
| 測り方が行動を歪める | 実質現金（在庫と Amazon 未入金を数えない）を満たすには月10の発注停止が要る。停止は累計損益>0 の確率を78%→63%に下げ、24ヶ月の累計損益を約20万削る（quick の値） | 測り方の論点には「その測り方を満たすために捨てる価値」を数字で添える |
| 独立でない社長の時間 | せどりの目視と送信を独立に置いていた。同じ社長の時間なので連動させる（目視が止まった世界では送信の低稼働50%） | 社長の手を使うレーンが2つ以上あれば、共通の「社長レジーム」を置く |

## 3. 実装の事故（再発防止）

- `01_mc.py` で、せどりの採用率 `h` をクロージャ `h_eff` が参照していたのに、後段の SKU ループで保有月数を `h` に再代入した。採用率が約100倍になり1経路6,828発注。**1経路の発注回数を最初に数える**（数十〜数百が正常）。クロージャが参照する変数名は関数内で再利用しない。
- 並列（multiprocessing）はスクリプト直実行なら fork 文脈で。テストから importlib で読むときは `sys.modules` に登録してから。

## 4. 手順（キャッシュ条件の案の仮想 Do。次回も流用）

1. タケシの計算をタケシの置き値のまま自分の構造で再現（±5pt なら構造は妥当）
2. 置き値を1つずつ自分の値に置き換える分解表（どこで何 pt 落ちたか）
3. 撤退条件の各線を「中央で踏む確率」と「止めたい世界で踏む確率」に翻訳
4. 失敗した世界の特徴（倍率）でプレモーテムの順位を確かめる
5. 途中（W8・2027-01・2027-03）の実測で最終の分布がどう分かれるか＝撤退条件の較正
6. 測り方ごとの P（実質現金／累計損益／手仕舞い値）を並べ、測り方の論点に数字を渡す
