# 規則文書（CLAUDE.md）を仮想実行で評価する型（T-20261027-001 / 2026-10-27）

戦略案ではなく「ルール文書が秘書の失敗を防ぐか」を評価した初回。次に CLAUDE.md・agent.md・skill を評価する依頼が来たらこの手順で読む。

## 手順（再利用可）
1. 過去の実際の事故を1件1行のシナリオにする（依頼側が挙げる。足りなければ原因分析から拾う）
2. 読み方を2通り想定する：**先頭100行だけ**（フォルダなし開始で `head` 読み＝10/19以降の実態）／**節を探して読む**
3. 各シナリオで「規則が書いてある行番号」を引く。100行の内か外かで機械的に判定できる
4. 文書とは別に「その場面で動く仕組み（フック）」を確かめる。**フックの対象がファイル書き込みだけか、チャット・ブラウザ操作も拾うか**を見る（発注ゲートはファイル名の型だけ。チャットでの推奨は素通り）
5. ○／△／× を付け、△ と × には「文書で直す」「仕組みで直す」「文書の外（ユーザー設定・運用）で直す」を分けて書く
6. プレモーテム上位3筋に、採用後に数える指標と線を付ける（今回：ツール100回あたりの Agent 発注、基準3.9、2週続けて2.0未満でフック追加）

## 今回の学び
- **規則が読まれるかは「位置」より「入口」で決まる。**新版で §A2 を22行目に上げても、会話がフォルダなしで始まれば読まれない（10/19〜26 は23本中22本）。文書評価では最初に「その文書が読み込まれる経路」を確かめる
- **表に Agent の種類名を書くと、その種類が一覧に無い環境で「振る先が無い→自分でやる」に倒れる。**逃がし方（general-purpose＋agent.md）を同じ場所に書く
- **事実のように書いた運用（「夜間タスクで回す」）は、確かめずに「動いている」と報告させる方へ引っぱる。**規則文では状態を断定せず、「確かめ方」を書く
- **「承認済みとして扱う」型の条文は、社長の強い言葉を承認と類推させる前例になる。**§A3 側に「『質問するな』は承認ではない」を置くと閉じる
- 「別ファイルを全部読む」指示（338行）は、先頭しか読まない読み手には効かない。読む範囲は節単位で指定する
- 会話の途中で起きる抱え込み（Bash 71回）は、UserPromptSubmit のフックでは拾えない。発話ではなくツールの連続回数で検知する必要がある
