## 2. 無人ジョブを読むときの必読チェック（順番）

1. **起動口**: plist の `ProgramArguments` が指すファイルが**実在するか**。`launchctl list` の終了コードを見る（127=不在、1=例外、78=設定不備）
2. **依存の層**: スクリプトが `.gitignore` 対象の層（`agent_output/` 等）を import/open していないか。**モジュール読み込み中の `open()` は即死＋KeepAlive 再起動ループを作る**
3. **エラーの行き先**: API エラーが「正常終了」として記録されないか。**「失敗を成功と書くコード」は無人運転で最も高価なバグ**。scan_v14 は Finder のエラー時に空リストを返し、それを「全シャードを掘り切りました」と記録していた
4. **母数の算術**: 母集団件数 ÷ 処理速度 = 何日で尽きるか。**「回し続ける」依頼の9割は、実は「尽きた後どうするか」の設計依頼**
5. **無限ループ**: 時間上限を外す依頼が来たら、内側の `while True` に別の上限があるか必ず確認する。時間上限が唯一の脱出口になっていることが多い
6. **書いたものを誰が読むか**: `grep -rn "<出力先>" --include=*.py` で実証する。scan_v14 の raw/ は 1GB/日 書いて**どのコードも読んでいなかった**
7. **リポとの相互作用**: 30分ごとの `git add -A` がある環境では、追跡対象への高頻度書き込みは①履歴肥大 か ②`QUIET_MIN` による恒久 HOLD のどちらかを必ず起こす。GitHub の 100MB/ファイル上限までの余命を行単価から計算する
8. **二重起動**: PID ファイル + `kill -0` は再起動後の PID 再利用で誤判定する。`flock` を要求する

## 3. 「積み上げ系」案件の読み筋（最重要）

**上流の生産量ではなく、下流の消化能力がボトルネック。** 今回の構造：

```
スキャナ 3,588商品/日 → 候補 2,700件/日 → メーカー 数百社/日
                                              ↓
                      社長の架電能力 0〜10社/日（実績 0社）
```

**供給が需要を40〜100倍上回る案件では、供給側をどれだけ改善しても結果は変わらない。**
→ 予測表は必ず **「積み上がった件数」と「実際に使われた件数」を別の行にする**。良い/悪いシナリオで積み上げは2倍しか違わないのに、使用件数は30倍違う、という形で見せると論点が一目で伝わる。
→ 打ち手は「リストを増やす」ではなく「**毎朝10社に絞って出す**」。件数の報告をやめる提案までがセット。

## 5. 撤退条件の書き方（タカシがそのままコードにできる粒度）

- 機械が止まる条件（S系）と人間がやめる条件（W系）を**必ず分ける**
- S系は「直近N時間の◯◯が閾値未満」の形に統一する（`直近24hの新規ユニークASIN < 200` など）
- **W系の本命は必ず「社長が実際に使ったか」**。今回は `30日で連絡30社未満なら縮退 / 60日で100社未満なら停止`
- 削除を伴う条件は `_trash/` への移動＋週次提示に留める（CLAUDE.md §4.1 不可逆な削除）

## 6. 社長のこだわり（今回の依頼から読めたもの）

- **表現がくどいのを嫌う**。前置きなし・一文短く・表に。結論を先頭3行に置く
- **暴走を怖がっている**（12時間上限は「大きな意図はない」と言いつつ自分で入れた）。止め方が1つあることを明示すると安心される
- **課金に敏感**。Keepa の従量課金の有無は「たぶん無い」で済ませず、公式確認＋証跡を要求すること
- 一般論のリスク列挙を嫌う。**実物のコードと設定ファイルを読んだ上での固有の失敗**しか価値がない、と明示された（今回の依頼文）
