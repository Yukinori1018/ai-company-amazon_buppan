社長がGoogleシートを見ながら「この列はどう計算しているの？」「この商品を1個売ったらいくら？」と聞いてきた回。

**社長のこだわり（観察された事実）**
- **シートの数字を鵜呑みにしない。** 列の定義を自分で理解してから使いたい。→ 列を作ったら**必ず定義書をセットで出す**（今回は事後に出す羽目になった）。
- **抽象論より「1個売ったらいくら」の具体。** 100件のリストより1件の完全な内訳のほうが判断材料になる。
- **副業初心者**（`owner_side_business_beginner`）。用語には毎回補足を付ける。「掛け率」「BuyBox」「ROI」「損益分岐」も例外なく。
- 分量のある資料は **テキスト＋HTML 併出力**（`owner_html_output_rule`）。今回も両方出した。

**うまくいったこと**
- 「〔確定〕〔仮〕〔要見積り〕」のタグを全行に付けた。社長のボトルネックは「推定と実測が混ざること」（`feedback_research_accuracy_blocker`）なので、この形式は今後も標準にする。
- 【A】シート再現 →【B】経理精査 →【C】現実の卸掛け率 の3段構え。**Aで「シートの数字は正しく再現できます」と示してからBで穴を指摘する**と、シートを否定せずに前に進める。
- 最後に「無料・不可逆でない・1時間で終わる不確実性つぶし3手」を付けた。社長のDoは希少なので、**何をすれば結論が確定するか**まで書く。

## 2026-09-04 / T-20260904-004 C-1（推定値の実測化）

**依頼のパターン（ルーチン化候補）**
「◯◯の前提が推定のままなので実測に置き換えて」は今後も来る。次回はこの順で処理する。

1. **推定値が実装のどこに書かれているかを先に読む。**コメントに根拠が書いてあることがある
   （今回 `pipeline/config.py` に「160サイズ1,500円/1箱15個と仮定」とあった）。
   仮定の中身が分かれば、何を実測すれば置換できるかが決まる。
2. **抜けている費目を探すほうが、推定値を精密化するより効く。**
   今回は保管月数を2.0→1.5に直しても1点あたり10円だったが、
   欠落していた小口基本成約料は110円だった。**桁が違う。**
3. **実測の入手経路は3段。**①公式料金ページ ②業者の公開料金表（相見積り不要で「実測」になる）
   ③自社が既に持っている生データの再集計（今回 NETSEA 257,067件を集計）。
   ③は最強で、しかもタダ。**外に探しに行く前にリポ内を集計する。**
4. **全数値に〔実測〕〔二次〕〔推定〕〔未確認〕を付ける。**取れなかったものは値を空欄にする。
5. **最後に「この修正で既存の判定がどう動くか」を必ず添える。**社長が知りたいのは
   前提の正しさではなく「で、候補は減るのか」。

**成果物の形（今回採用・次回も同じでよい）**
- `.md` + `.html`（社長閲覧用）
- `.json`（他エージェントがコードから読む用。`confidence` と `source` を必ず全項目に）
- `.csv`（JSONの表形式。Excelで開ける）
- `.xlsx`（社長が数字をいじれる。既存シミュレータの構造を流用し、追加行だけ色を変える）

**他チケットの納品物（xlsx）は上書きしない。**構造を流用して自チケットに新規作成する。
上書きすると元チケットの再現性が壊れる。

**同じ deliverables フォルダを他の担当が同時に使っていることがある。**
今回 IT タカシが `candidates.csv` をライブで上書きしていて、分析中に行数が1,200→200に変わった。
**分析に使う入力ファイルは、読んだ時点の値をメモに残す**（後から再現できなくなる）。
