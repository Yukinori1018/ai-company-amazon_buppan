# 名簿（社名だけ数千行）に公式窓口を付ける — 規模を上げたときの律速と手順（T-20260929-001 / 2026-10-05）

用途：「展示会・補助金などの名簿 N千社に、公式サイトの電話・フォーム・公表メールを付けて」と来たら最初に読む。
作業場所：`agent_output/T-20260929-001/15_contacts/`（g1.py → guess.py → ws.tsv＋apply_ws.py → ex.py → build.py → rec14.py）
成果の置き場：シート『メーカー連絡先台帳』の「名簿拡張_窓口」タブ（非公開）＋ 14 の件数欄だけ（PUBLIC リポに社名を書かない）

## 律速は WebSearch のセッション上限（実測）

- **WebSearch は約180回でセッション上限**（"You've hit your session limit · resets 5:10pm"）。上限は時刻でリセットされる（今回 15:25 に到達・17:10 リセット表示）
- 1社1回でも、社名だけの名簿は 1,700 社で約1,300 回必要 → **上限の窓が7回ほど要る**。100社/回のペースは検索の窓で決まる
- Gemini の検索グラウンディングは 2026-10-05 時点でも 429（8/31 と同じ）。代替にならない
- 検索エンジンを curl/WebFetch で叩いて上限を回避するのはやらない（回避行為）

| ドメイン推測 | カナ→ローマ字（長音の揺れ・接尾語「製作所/工業/商店」を落とす）＋英字トークン × .co.jp/.jp/.com → DNS → トップに社名（法人格を除いた芯）があるか | **551社中107（19%）・800社中175（22%）** |

**推測ドメインの罠**：ドメイン売り場（leasetoown 等）に転送されるページでも社名が本文に出る（stem／TRUNK）。英字・短い社名（H.I.T.、THREE、赤堀）は同名別会社を拾う（h-i-t.jp は大阪の IT 会社）。→ 転送先の売り場判定・短い社名は所在地一致を必須に。

## 抽出（ex.py）で直したこと

- フォーム判定：`form` の部分一致は information に当たる。**問い合わせ系ページで `<textarea>` か外部フォームサービス**があるときだけフォームとする。Shopify のニュースレター欄を拾わない
- 電話：ラベル無しの10〜11桁は ID・品番を拾う（0001-02-5565 等）。**ラベル無しは区切り記号つきだけ・00 始まり除外・11桁は携帯/0120 系のみ**。表記はページの原文のまま（市外局番の切り方を機械で決めない）
- メール：Python の `\w` は日本語に当たる（"info@giemon.comまでに"）。ASCII 限定。mailto に全角の伏せ字（〇〇〇@〇〇〇）が入るサイトがある
- 「営業・勧誘・売り込みお断り」は問い合わせページに1行で書いてある（100社中4社）。原文を列に残し、メール可否を ×（13 §3-3）

## 追記 2026-10-07（②101〜1719・再開回）

### 律速の正体：WebSearch は「1セッション200回」の固定上限（設定値）
- 10/5 は「約180回でリセット時刻つきの上限」と見えたが、10/7 は **200回目で `this session has used its web search budget (200 of 200)`** と明示された。設定 `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` の値。**サブエージェントは設定を変えない**（変えられるのは社長だけ）。上限の引き上げは社長判断の選択肢としてカズヨに出す
- 実測：1セッション＝検索200回＝②の約285行ぶんの解決（1〜300で「検索待ち」0）。壁時計は約35分（検索15本並列＋pipe/build は1分以内）
- **上限に当たったら止まらずに「検索待ち」を判定に分けて全件をシートに出す**（build.py：`searched` が無い未解決行＝「検索待ち（Web検索未実施）」）。公式未特定と混ぜると窓口あり率が実態より低く見え、次回どこから検索すればよいかも消える

### 推定ドメインの拡張（guess3.py）は歩留まりが低い
- 接尾語（kk/inc/net/japan/jp/corp）×TLD（.net/.ne.jp/.shop/.biz）を足して全行のホストを平坦化→DNS を200並列：②未解決1,242行で 97,926ホスト→生存2,976→社名一致91行→**所在地照合で75行が別会社→正味16行（1.3%）**。数分で終わるので毎回回してよいが、検索の代わりにはならない

## 追記 2026-10-07 午後（①a Keepa入口 1万円以上342行＋5,000〜1万円624行）

### ①a は②と別物：社名欄が「ブランド名・販売店名・海外ブランド」の名簿
- Keepa の manufacturer 欄が元なので、**大手・上場（Meta/TEAC/JUKI/カシオ等）・海外ブランド（中国・欧米）・販売店（〜ショップ／ワインショップ）**が混ざる。966行中 大手90・海外67・販売店22（計18%）。窓口の母数から分けるため判定コードを2つ追加：`FOREIGN`＝海外ブランド（国内の窓口未確認）／`SHOP`＝販売店・小売（メーカーでない）。輸入元らしきカート保持者は備考に「輸入元の可能性」と推測で書く
- **gBiz の完全一致がブランド名に当たると別会社**（「Meta」→新宿の同名社、「TENKU」→同名複数）。①a では rej.py が 65〜74行を落とした。逆に正しい公式も落ちる（teac.co.jp・logos.co.jp 等は gBiz 候補の所在地と合わず却下）→ **却下URLのタイトルを一括取得して目視**し、正しいものは `KC:` で戻す
- **推定ドメインの英字一致は誤爆が多い**：factory.com／harvest.com／hotel.jp／carry.com／arrows.com／seabox.com／hugedomains（売り場）／飲食店・美容院・病院の同綴りドメイン。英字だけで一致した行は**全件タイトルを取って目視**し、外れは `RESET`（検索待ちに戻す）。①aで RESET 66行

### 検索を使わずに公式を当てる手（今回の効き目）
- `K:`＝知っている公式URLを ws.tsv に書き、apply_ws が取得してページに社名/ブランドが出たら採る。`KC:`＝社名の機械照合は外れたがタイトルを目視して公式と確認したもの（m+ online・庖丁工房タダフサ等）。①aで K/KC 130行＝検索130回分の節約
- **K: の落とし穴**：ブランドの英字だけで照合すると同名の別会社を通す（seeker.co.jp＝ホンダ車チューニング会社が「SEEKER」で通った）。rej.py で一度落ちた URL を K: で戻すときは必ずタイトルを見る
- 1社1検索の型は維持。検索結果の要約に出た電話番号は転記しない（値は ex.py が公式ページから取る）。公式URLが検索結果に出ない社（楽天・Yahoo!の店だけ）は `NONE` で「公式URLは検索で出ず」と書く

### 速くするために効いた手順
1. **検索の前に、自分が知っている公式URLを一括取得してタイトルを目視**（34本→21本採用）。DNS が引けない推測（000）は捨てて検索に回す
2. **検索結果の要約に「運営会社」が出たら G: で運営会社の公式へ飛ばす**（ブランド名だけの行の約3割がこれ）。輸入ブランドの日本総代理店が公式を持つ場合は FOREIGN にせず代理店URLを G: で採る（窓口が国内にあるため）
3. **大手の子会社・上場グループのブランドは BIG**（ナカバヤシのREVEX、日本甜菜製糖のラフィノース、DICのIZANO、総医研の子会社、ディノスのブランド等）。カート保持者が販売店なのに社名欄が大手製品のケースが①aには多い
4. 検索で公式が出なかった行は無理に推測せず NONE／AMBIG（同名多数）で止める。同名の公式はあるが**事業が出品カテゴリと合わない**（飲食コンサル×DIY工具、サプリOEM×調理器具、不動産×自動車用品）は AMBIG と理由を書く
5. 1メッセージ15本並列で約13往復。WebSearch の要約は英語で返ることがあるが、URL一覧から公式を選べば足りる

### 注意（精度）
- 社名欄と gBiz 候補の所在地が違っても、検索で業種が出品と整合すれば P:（推測）で採り「gBiz候補とは所在地が別」と書く（コスモ＝のれん工房は桐生市、gBiz は渋谷区）。build.py では「窓口あり（紐付け要確認）」に落ちる
- 登記閉鎖（合併）の社は NONE と理由を書く（レラコスメチック→山田製薬に合併）
