# 基準の食い違いを「社内確定値」へ統一する手順（T-20260826-002 / 2026-08-31）

依頼＝マスターToDo 208項目のうち、memory 由来の一般基準5行を方針v1.3の確定値へ書き換える。
社長判断は「方針v1.3で。」の一言。**判断は降りているので、こちらの仕事は"確定値を誤りなく写す"ことだけ。**

## この手順が再利用できる形

1. **依頼者が渡してきた対応表を、そのまま信じない。** カズヨから5行の新旧表を受け取ったが、
   「私が写した時点で誤写している可能性がある」と自ら申告があった。実際に**2点誤っていた**（下記）。
2. **確定値の探索順は 実装 → チケット本文 → memory。** 数値は実装が一番新しい。
   今回は `workspace/output/deliverables/T-20260817-005/scan_v13.py` 冒頭の
   `# v1.3 の基準値（社長裁可 2026-08-17）。ここだけ直せば条件を変えられる。` ブロックが
   単一の正だった。**この「定数ブロック」を先に開くのが最短**。
3. **逐語一致が検算条件の資料は、2ファイルを同一の置換辞書で機械置換する。**
   手で2回打つと必ずズレる。Python の `(old, new)` リスト＋`assert s.count(old) == 1` が確実。
4. **納品済み資料の訂正は消さずに重ねる**（ヒデアキの原則）。D-4 は章ごと残し、
   表に「状態＝書換済」列を足し、旧記載を「不採用」と明記した。取り消し線も使える。

## 指示表 vs 実装で食い違った2点（型として記録）

| 論点 | 依頼者の表 | 実装で確認した正 | なぜズレたか |
|---|---|---|---|
| 月間ドロップ数の下限 | 一律 `≥10` | プリセットA（1,500〜8,000円）＝≥10 ／ **B（8,000〜20,000円）＝≥4** | v1.0 の値だけを見て v1.1 の「価格帯2本立て」改訂を拾っていない |
| Amazon本体の判定 | `current_AMAZON` 不在フィルタ | **`availabilityAmazon = -1`** | `current_AMAZON = -1` は「今この瞬間 Amazon 価格が無い」だけで**一時在庫切れも通す**。実装は D3 補正済み |

→ **どちらも「versionの取り違え」と「フィールド意味の取り違え」**。当メモリの
`feedback_verify_field_semantics_not_column_names` と同型。**Keepa 関連は6件目**。
フィールド名が意味を語っていると思った瞬間に事故る。

同じ理由で `出品者数 2〜6` にも注記を足した：**`COUNT_NEW`（新品オファー数）ではなく
distinct sellerId の実セラー数**。1社が FBA と FBM を同時に出すと COUNT_NEW は2になる。

## 波及の潰し方（今回やったこと）

「5行だけ直す」依頼でも、同じ数値を参照している箇所が資料内に散る。grep で潰した先：

- 中項目直下の `> 現在地：…`（2-2 / 3-3 の2本が「食い違っています／社長判断」と書いていた）
- A章の「グレードCの一覧」（Cの理由が"食い違い"だった5行 → 解消。**C 14→9 / B 47→52**）
- D-4 章の本文と表
- 02 末尾の「数値・しきい値の照合表」（該当行が無かったので**新規に小表を追加**）
- ついでに凍結していたチケット枚数（106→108・md と html の両方）

**検索語は"数値そのもの"で引く**（`5万位` `10名以内` `70%` `4桁`）。項番や見出しで引くと漏れる。
