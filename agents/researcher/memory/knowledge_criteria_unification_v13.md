# 基準の食い違いを「社内確定値」へ統一する手順（T-20260826-002 / 2026-08-31）

依頼＝マスターToDo 208項目のうち、memory 由来の一般基準5行を方針v1.3の確定値へ書き換える。
社長判断は「方針v1.3で。」の一言。**判断は降りているので、こちらの仕事は"確定値を誤りなく写す"ことだけ。**

## この手順が再利用できる形

1. **依頼者が渡してきた対応表を、そのまま信じない。** カズヨから5行の新旧表を受け取ったが、
   「私が写した時点で誤写している可能性がある」と自ら申告があった。実際に**2点誤っていた**（下記）。
2. **確定値の探索順は 実装 → チケット本文 → memory。** 数値は実装が一番新しい。
   今回は `workspace/output/deliverables/T-20260817-005/scan_v13.py` 冒頭の
   `# v1.3 の基準値（社長裁可 2026-08-17）。ここだけ直せば条件を変えられる。` ブロックが
   単一の正だった。**この「定数ブロック」を先に開くのが最短**。
3. **逐語一致が検算条件の資料は、2ファイルを同一の置換辞書で機械置換する。**
   手で2回打つと必ずズレる。Python の `(old, new)` リスト＋`assert s.count(old) == 1` が確実。
4. **納品済み資料の訂正は消さずに重ねる**（ヒデアキの原則）。D-4 は章ごと残し、
   表に「状態＝書換済」列を足し、旧記載を「不採用」と明記した。取り消し線も使える。

### 決定の射程を読み違えないための問い

社長判断が「◯◯（案の名前）で。」の形で降りてきたら、**指示表に並んだ行だけを直して終わりにしない**。
その案が**明示的に否定した設計**が資料の別の場所に残っていないかを、
案の原文（今回は T-20260817-002 §v1.3 確定）の**否定文を全部拾って** grep する。

今回 v1.3 が否定していたもの＝①ランキングでの足切り ②「初回1SKUは制限なしから」縛り
**③撤退条件の金額基準（1SKU損失上限3万円）**。③が資料に残っていた。
①は指示表に入っていたが③は入っていなかった。**指示表は"見つかった分"であって"全部"ではない。**

### 件数を報告するときの鉄則（2回続けて刺さった）

- **件数だけ報告して項番リストを渡さない → 誰も再現できない。** 今回は復元に往復2回かかった。
- 復元の結果、原監査14件 / カズヨ再構成14件 / ヒデアキ表13件 の**和集合が16件**になり、
  どれが原14件か判別不能。**多い側（16）を採った**（グレードCは疑わしい側に倒す＝数を少なく見せない）。
- 数を出したら、同じ成果物に**項番の全リスト**を必ず置く。表の行数と集計値が食い違ったら即バグ。
