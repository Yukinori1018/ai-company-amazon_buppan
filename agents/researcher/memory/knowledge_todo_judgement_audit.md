# マスターToDo 判定の全数再検証（T-20260826-002 / 2026-08-31）

208小項目の進捗マーク `[x]/[~]/[ ]` を、根拠チケット本文まで遡って全数再検証した記録。
発端＝カズヨが 1-1 を誤判定（開業日 2026-08-20 を提出日と取り違え）し社長に指摘された件。

## この監査で使った手順（再利用可）

1. `awk` でマーク数を機械実測 → 資料内の集計表（A章・中項目ごと）と突合。**人が書いた集計は必ずズレる。**
2. `grep -n '^- \['` で208行を抽出し、行末の `〔T-…〕` を全部拾う
3. 根拠IDごとにチケット本文（結果／完了報告／ログ）を**全文読む**。frontmatter とタイトルは見ない
4. 本文に該当記述が無ければ `memory/` と `deliverables/` を横断 grep して**真の出典**を突き止める
5. 「マークの妥当性」「根拠IDの妥当性」「記載内容の鮮度」の3つを**別々に**判定する

## 見つかった失敗の型（今後もここを疑う）

### 型1：根拠チケットIDが「内容の出典」ではなく「話題が近いチケット」になっている
最多。94件中14件がこれ。とくに **T-20260817-002 は8回引用のうち5回が誤り**。
実際の出典は memory `knowledge_seller_research_profit`（＝T-20260726-001）だった。
- 対策：数値を含む項目は、その数値で `memory/` を grep してから ID を書く。

### 型2：本文が更新されているのに、資料の根拠文が古い日付で固まっている
マスターToDo は 2026-08-26 生成。T-20260826-004 はその後 8/28・8/30・8/31 と3回大きく動き、
「CAのビジネス情報認証は完了」という 8/26 の読みは 8/28 に**外れと確定**していた。
- 対策：`waiting/` の高頻度更新チケットは、資料の生成日と `updated_at` を必ず比較する。

### 型3：動詞を読み飛ばして「調べた＝実行した」にしてしまう
7-1-01「カート獲得の5条件を**満たす**」を `[x]` にしていた。本文には
「小口出品ではカートを獲得できない」と明記され、条件①が構造的に未充足。
- 対策：judgement.md の「この小項目は何をしたら終わりか」を**声に出して**先に決める。
  「満たす／登録する／提出する」は物理事実、「確認する／理解して使う」は調査タスク。

### 型4：日付の種類の取り違え（今回の発端）
開業日／提出日／受信日／next_check_at／updated_at／作成日は全部別物。
- 今回の全数検査では、**発端の1-1 以外に同型のミスは無かった**（明記しておく）。
- ただし型2（資料生成日と本文更新日のズレ）は日付起因の別型として5件出た。

## 社長のこだわりに直結する点

- 「推定と実測を分離」の思想は判定にも効く。**証拠グレード A（一次証拠）/ B（本文記載）/ C（推定）を
  項目ごとに付けると、どこが脆いかが数で出る。** 今回は A33 / B47 / C14。
- 数を盛らない。`[x]` に寄せるのも `[ ]` に寄せるのも社長の判断を狂わせる（judgement.md）。
