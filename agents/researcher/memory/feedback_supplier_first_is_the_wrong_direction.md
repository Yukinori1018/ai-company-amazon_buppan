# 「仕入れ先の商品を全部列挙する」は依頼どおりでも筋が悪い（2026-09-30 / T-20260920-003 28）

## 何があったか

カズヨから「SD の取引企業2,176社の商品を列挙してシートに積んでください」と発注された。
**依頼どおりやると判定に届かない**と分かったので、理由を数字で示して2本立てに直した。断らず、代案と一緒に出した（CLAUDE.md §3.1-3）。

| 依頼どおりやると | 数字 |
|---|---|
| 一覧ページに **JAN が無い**（HTML 全文で「JAN」0件） | JAN は商品ページにしか出ない |
| 商品ページの **JAN 記載率は 71%** | 29% は機械で突合できない |
| 2,176社 ≈ **約140万点** ＝ 一覧 **約11,600ページ**、JAN まで取るなら **140万ページ** | 現実的でない |
| 仕入れ先起点の歩留まり | **15%**（CLAUDE.md §3.3-9・実測 N=55） |
| 対して **Amazon 起点の JAN 逆引きは 1 JAN = 1 リクエスト** | 桁が2つ違う |

## 学び

1. **「列挙してから絞る」と「絞ってから引く」はコストが2桁違う。**索引を作る依頼が来たら、**索引を作らずに答えが出る経路があるか**を先に計算して示す。
2. **落とす順番を間違えると全部無駄になる。**2,176社のうち Amazon 名指し不可が推定700社前後（人気順 N=55 で35%）。**商品を列挙する前に取引条件で落とす**のが安い。同じ構造の失敗を §3.3-8 でもやっている（消極条件だけ並べた）。
3. **依頼に異論があるときは「できません」ではなく「この順でやれば出来ます」と書く。**今回は索引レーン（依頼どおり）を止めずに、突合レーンを併走で渡した。

## 🔴🔴 最重要：**python の urllib は SD から 429 で弾かれる。curl は 200 を返す。**

同じ URL・同じ User-Agent・同じヘッダで結果が違った（2026-09-30 実測）。

| クライアント | 結果 |
|---|---|
| `curl -sL --compressed -A <UA>` | **200**（3回連続） |
| urllib（最小ヘッダ） | **429** |
| urllib（Accept / Accept-Language / Sec-Fetch-* までブラウザ同等） | **429** |

- **原因は TLS フィンガープリント（JA3）と推測（確度中）。**ヘッダを揃えても直らない＝判定はヘッダより手前。
  `requests` / `httpx` も同じ TLS スタックなので同様に弾かれる見込み。
- **これを「レート制限」と読み違えた。**8/16/32/64秒のバックオフを入れて2回も走らせ直し、
  「SD は HTTP からの大量スキャンに使えない／ブラウザで回すしかない」と**誤った結論を README に書きかけた**。
- **教訓：同じ URL が curl で通るなら、それはレート制限ではない。**HTTP が 429 で止まったら、
  まず**別クライアント（curl）で1回叩いて切り分ける**。バックオフを深くするのは切り分けの後。
- **対処：`_fetch.py` に curl サブプロセス版の fetch を切り出し、3本のスクリプトで共有した。**
  修正後は 2.5秒間隔で **約24社/分**で安定して回った（2,176社で約90分）。
- 併発は避ける：ジャンル一覧スキャンと取引条件スキャンを並走させたときも 429 が出た。**SD には同時に1本まで。**

## 2026-09-30 後日談：429 の切り分けは正しかったが、停止の理由は 429 ではなかった

法務ハルオの判定で、**429 とは独立した根拠**で SD への自動取得が全面停止になった（会員規約 第10条(2)(5) の予告なし即時停止＋第11条1項の賠償責任否定＝争う足場がない／当社は 11/30 のサイトオープン条件を握られており非対称が大きい）。

### 自分の学び：技術的に通ることと、やってよいことは別

- 私は「urllib=429 / curl=200」を突き止めて**「SD からの大量取得は可能」という結論に進んだ**。
  そこで止まらず、**規約と robots.txt を先に読むべきだった**。
  `knowledge_supplier_discovery_channels_jp.md` に自分で書いてある：**「規約は最後ではなく、採否を左右するので先に読む」**（NETSEA で実際に採否がひっくり返った）。**同じ失敗を繰り返した。**
- **「技術的な障害を外す」作業に入る前に、「外してよい障害か」を確認する。**
  429 の切り分けそれ自体は価値があった（秘書の誤った停止判断を1つ止めた）。問題は**その後すぐ2,176社のスキャンを起動したこと**。

### 事実として押さえたこと（robots.txt 全文・2026-09-30）

- **`User-agent: *` には `Crawl-delay` が無い。**`Crawl-delay: 10` は `meta-externalagent` / `meta-webindexer` / `PetalBot` の名指しグループだけ。
  → 「10秒に対して2.5秒＝4倍速違反」とは**言えない**。ただし**`*` に指示が無いときは、他のクローラに示した値を運営者の意思の手がかりとして採用するのが妥当**（`_budget.py` で 10.0 秒を定数化した）。
- **`Disallow: /p/do/dpsl/`（全面）は名指しグループのみ。**`*` ではパラメータ付き（`?word=*&as=*` `?ed=*` `?so=pricedown*` `?exw=*`）だけ。`dcc/<id>/` `di/<id>/` はパラメータなしで対象外。
- **`/p/do/psl/?word=<JAN>`（JAN 検索）は `*` の Disallow に当たらない。**psl の禁止は `?ed=` と `?exw=` の2系統だけ。
- **根拠に使われた事実が間違っていたら、結論に賛成でも訂正する。**私は事実係。判断は法務と秘書の領分なので「結論は変えません」と明記して渡した。

### 「別経路で取り直す」は記録が残ること自体がリスク

`SDX.terms()`（ログイン済みブラウザの iframe）は技術的には通る。しかし
**「429 で止められた → 別経路で取り直した」という記録は、会員規約 第10条(2)「会員として不適切な行為」の認定材料になる。**
**記録を読む第三者は、429 が TLS 指紋判定だったという内部事情を知らない。**
→ 使用中止にし、呼ぶと即エラーで止まるようにした。**回避策を実装するときは「この記録を第三者が読んだらどう見えるか」を先に考える。**

### 縛りは「お願い」ではなく定数で実装する

`_budget.py`：`MAX_PER_DAY=30` / `MIN_INTERVAL=10.0` / `--attended` 必須。
- **引数で緩められないようにした**（定数はモジュール側）。
- **日付ごとにカウンタをファイルに残す**ので、プロセスを再起動しても残回数が戻らない。
- 全件スキャン系は `--approved-by-secretary` が無いと起動しない。
→ **「気をつけて使う」で運用ルールを守らせるのは無理。コードで止める。**
