依頼の型：「1行＝1仕入れ先で、取引状態・値段が見えるか・Amazon 可否・書類・取得方法・台帳行数」。次回は差分更新で済む。

## 手順（再利用）
1. 商品判定台帳を**読み取り専用スコープ**で取得して写しを置く（`ledger_refresh.py` の CRED/SHEET_ID を流用、scope=`spreadsheets.readonly`）。`卸サイト × 購入元の名前 × 判定` で数える
2. SD の取引状態：9/30 の `sd/sd_trading_partners_20260930.tsv`（取引企業一覧）＋チケットの申請ログ＋秘書の実画面
3. SD の Amazon 方針：`sd/sd_dealer_terms.jsonl`（9/30）と `sd_buylist20261009/terms/sd_dealer_terms.jsonl`（10/09。**dealer_name が空**なので ID で引く）。無い社は「未調査」
4. NETSEA：台帳の行は API 索引＝承認済みサプライヤー由来。Amazon 方針はサプライヤー単位ではなく商品の注意事項にある→「サプライヤー単位は未調査」
5. 生成スクリプト `agent_output/T-20260920-003/supplier_master/build_supplier_master.py`。台帳の写しを差し替えて再実行すれば行数列が更新される

## 気づき
- **「値段が見える」と「Amazon で売ってよい」は別の列。**秘書は「ヤザワは値段が見える」で SD 経路に切り替えたが、ヤザワの SD 取引条件は社内に記録が無かった。GO 2件の発注前に1回読む必要がある
- 秘書の依頼文にある事実（創健社・健康フーズへの申請）がチケットに無いことがある。出典欄に「秘書の依頼文」と書き分け、ID が無いことを残課題にする
- 成果物の連番は**書く前に ls で確認**。50 は秘書の計画書が直前に使っていた（ID 重複の memory と同型）
- 経路の構成比：NETSEA 85.9%／SD 12.4%（2,018行）。§3.3-31 の80%超で、しかもその経路が停止中
- 毎日確認で自動化できるのは NETSEA の公開告知（503/200＋第N報）だけ。SD・直販のログイン後画面は人が見る。審査メールの差出人・件名は未確認→初回受信で埋める
