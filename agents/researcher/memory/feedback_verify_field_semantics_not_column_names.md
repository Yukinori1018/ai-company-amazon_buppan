# 教訓：列名を信じるな。データの「出どころのフィールド定義」まで遡れ（T-20260824-001）

- **記録日**: 2026-08-24 / **記録者**: サトル（リサーチャー）
- **種類**: 失敗パターンの分類（社長フィードバック `feedback_research_accuracy_blocker` の直系）

## 何が起きたか

社長の指示は「keepa の用語の意味を正確に知りたい」だった。公式APIドキュメントと当社スクリプト `scan_v13.py` を1行ずつ突き合わせた結果、**社長が2026-08-24に自ら指摘した COUNT_NEW の取り違えと、まったく同じ構造の誤りがあと3件**見つかった。

| 列名（当社が付けた名前） | 実際に入っている値 | なぜ起きたか |
|---|---|---|
| 過去1年最安値 | **全期間の最安値**（`stats.min` は ever。期間内は `minInInterval`） | `stats=365` を指定したから min も365日だと思い込んだ |
| BuyBox価格 | **新品最安値（送料込）**（`buyBoxPrice` は `offers`/`buybox` パラメータ必須。付けていないので常にフォールバック） | 「フォールバックを書いた」時点で、フォールバックが常時発動することを検算しなかった |
| 出品者数（旧） | **新品オファー数**（COUNT_NEW） | 名前が似ていた |
| Amazon本体あり | **今この瞬間 Amazon 価格が無い**（一時在庫切れを見逃す。専用フィールド `availabilityAmazon` がある） | 「-1 なら本体なし」で十分だと思った |

## 法則（再現性がある）

1. **「〜すれば〜になるはず」で書いたコードは、公式定義で検算していない。**特に `stats=365` のようなパラメータは、**どのフィールドに効いてどれに効かないか**が公式に明記されている（`avg`/`atIntervalStart`/`minInInterval` には効き、`min`/`max`/`avg30..365` には効かない）。
2. **フォールバック（`a or b`）を書いたら、b が常時発動していないか必ず1回検算する。**「まれに使う保険」のつもりが本番の値になっている。
3. **オプションパラメータを付けないと set されないフィールドが山ほどある。**公式ドキュメントには「The following fields are only set if …」という節が必ずある。**そこを読まずにフィールド名だけコピーしない。**
4. **列名は仮説であって事実ではない。**列名を付けた瞬間、後から読む人間もAIもそれを定義として扱う。**列名の横に「どのAPIフィールドから来たか」を必ず書く。**
5. **方向が「安全側」の誤りほど発見が遅れる。**「過去1年最安値」の誤りは判定を厳しくする側なので、赤字は出ないが**取りこぼしが出て、しかも誰も気づかない**。

## 次からこうする

- **Keepa 由来の列を追加するときは、`keepa-glossary.md` の「公式定義」列に対応する行があるか確認してから名前を付ける。**無ければ glossary に追記してから使う。
- **修正の前に「再スキャンが要るか」を必ず判定する。**今回は `raw/` に gzip 保存された生JSONがあったので、**4件中3件が0トークンで再計算可能**だった。**生JSONを保存しておく設計は正解だった**（T-20260803-001 の設計判断）。
- **「実害あり／用語の誤り／未解決」を分けて報告する。**全部を「誤り」と並べると、直す順番が分からなくなる。
