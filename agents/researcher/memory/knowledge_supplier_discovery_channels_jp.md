## 2. 一番大事な発見 — 母集団が重ならない

| 母集団 | 件数（正規化ユニーク） |
|---|---|
| Keepa起点で逆引きしたメーカー（T-20260817-005 v14） | 1,249 |
| ギフトショー出展社 | 2,346 |
| **重複** | **2社（0.1%）** |

正規化：NFKC → 法人格語除去 → 記号/空白除去 → lower。
**この1行が、探索の向きを反転させる根拠。** ただし読み違えないこと：
**「重ならない＝競合がいない」と「重ならない＝需要が無い」は同じ数字で観測される。** 切り分けは Keepa の仕事。

## 3. Keepa を検証役に使うときの型（実測済み）

```
GET https://api.keepa.com/product?key=<KEY>&domain=5&code=<JAN13>&stats=90
→ 1トークン（実測）。JAN13 から ASIN を確定できる
→ stats.salesRankDrops30 が概算販売個数の代理指標
```

**社名でのテキスト検索は当たらない。**
`/search&type=product&term=<会社名>` は商品タイトルの部分一致。返却の `brand`/`manufacturer` と突合しない限り汚染される。
実測：出展社名40件サンプルのうち、社名が brand/manufacturer に一致したのは少数。
→ **検証に必要な入力は「会社名」ではなく「ブランド名」か「JAN」。展示会で現物・カタログを取る意味はここにある。**

レスポンスは gzip。`Accept-Encoding: gzip` を付けて `gzip.decompress` すること（付けなくても gzip で返ってきて UnicodeDecodeError になる）。

## 4. 実務者の数値（EC STARs Lab.・二次情報）

返信率30% → 見積取得8〜10% → **成約3〜5%**／月300社アプローチ（1日10社・30分〜1時間）／月利50万に取引50社。
→ **50社と取引するには 1,000〜1,600社への接触が要る。** 母数の目標値はここから逆算する。
なお同社の推奨探索法は「カテゴリーリサーチ」「セラーリサーチ」で**どちらもAmazon起点**。今回の反転は実務者の標準からも外れる打ち手。

## 5. 手順のルーチン（次に同種依頼が来たら）

1. **「発見」と「検証」を分けて設計する。** 発見＝現物/名簿側、検証＝Keepa。混ぜると母集団がAmazonに引きずられる
2. 経路を出したら**必ず既存母集団との重複率を測る**。重複が高い経路は新しい母数を生まない＝やる価値がない
3. 名簿系は **PDF直リンク → sitemap → robots.txt → 規約の禁止条項** の順で当たる。**規約は最後ではなく、採否を左右するので先に読む**（NETSEAで実際に採否がひっくり返った）
4. 件数は「◯◯社と書いてある」ではなく**自分で数える**（sitemapのURL数・PDFのトークン数）
5. 会員登録・トークン申請は **§4.1（規約同意）**。サトルは実行しない。表で分離して社長に上げる
