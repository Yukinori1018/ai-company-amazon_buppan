# 買う候補を「索引の未解決JAN → Keepa逆引き」で量産する手順（2026-10-09 / T-20260920-003）

## 依頼パターン
社長「蛍光灯だけで事業が回ると思っているのか。早く買うものをリスト化して、本当に仕入れられるのか、
利益が出るのかをチェックしていけ」→ **母数を増やして候補を散らす**仕事。

## 手順（次に同じ依頼が来たらこの順）

1. **トークン0で落ちた理由を集計する。**`score_20261004.py --relax` と、ゲート×PASS/UNKNOWN/FAIL の
   クロス集計。**新しいスキャンを回す前。**（`feedback_candidates_die_from_filters_not_economics` の手順）
2. **Keepa 残高を最初に測る。**`/token`（無料）。**`--compressed` を付けないと gzip のまま返って
   JSON パースが落ちる。**残高上限は 1,200（= refillRate 20/分 × 60）
3. **索引の未解決 JAN を shop_id ラウンドロビンで選ぶ。**先頭から順に取ると1社で埋まり、
   ブランド分散が作れない（実装：`buylist20261009/resolve.py`）
4. **`code` 逆引き（`stats=90&history=1`・`buybox` なし）**で ASIN を起こす
5. **絞ってから `buybox=1`** でカート保持者を確定（1件3トークン）
6. **`score_20261004.build()` をそのまま呼ぶ。**判定のぶれを作らないため、入力だけ差し替える
   （`score_new.py`。`row` を10/04のプールCSVと同じ形に組む）

## 実測した数字（N と期間つき）

| 項目 | 実測 |
|---|---|
| `code` 逆引きのトークン単価 | **2.24トークン/JAN**（JAN 100件 → 商品 201件・600 JAN で 1,083トークン） |

| `buybox=1` で取り直した結果 | 14件中 **第三者9・カート空5・Amazon本体0** |

## 🔴 二度と間違えないこと

1. **`code` 逆引きだけで「カート保持者」は判定できない。**入るのは Amazon 本体のときだけなので、
   「本体以外は全部 UNKNOWN」になる。**第三者がカートを持っている証拠は `buybox=1` でしか取れない。**
   逆に言えば、**逆引きの段で `buyBoxSellerId` が入った行は本体確定＝0トークンで落とせる。**
2. **Keepa のトークンは会社で1本（20/分・上限1,200）。**2026-10-09、私の逆引きと SD レーンの
   `fetch_jan.py` が同時に走り、**両方が「残47 → 300秒待機」で停止**した。
   並行インスタンスがいるときは**先に `ps` で他のKeepa利用を確認**し、譲るか時間帯を割る。
3. **仮説が外れたら外れたと書く。**「`fbaFees` が無い302件は寸法から区分を引けば復活する」と
   実装したが **回復0件**（`fbaFees` が無い行は寸法も無い行とほぼ同じ集合）。
   実装は残した（別のデータ源で寸法が入れば効く）。
4. **採算ゲートは「等級 UNKNOWN」を PASS にしている。**`build()` は `grade == "C"` のときだけ FAIL に
   するので、**寸法不明で採算が計算できていない行が候補に混ざる**（43件中6件）。
   報告では「採算未確定」として分けて出すこと。利益率1.9%の行が候補に入っていた。
5. **実売 UNKNOWN を1つに畳まない。**(a) ランクが30万位以内で兄弟共有＝キーゾン1手で決まる、
   (b) **売れ筋ランクが付いていない**＝最弱。43件の内訳は B8/C18/**D17**で、D は 10/01 に同型を
   実画面で見て全部だめだった型。**母数を増やすと D が増える。**
