# 制作原則: リサーチ成果物を「内容を1文字も変えずに」HTML化するときの型

記録 2026-09-04（T-20260903-001 / サトルの `research/draft.md` をHTML併出力）。
**「この成果物のHTML版を作って」系の依頼を受けたら、着手前にこれを読むこと。**

## この依頼の性質を最初に見極める

今回の依頼文には強い制約が付いていた。

> 「**内容を足さない・削らない・言い換えない。** draft.md の事実と数値をそのまま HTML 化する。あなたの知識で補完しない」
> 「『わからなかったこと』『この資料の信頼度』の章は**省略しない**。むしろ目立たせる。**ここを削ると資料の誠実さが消えます**」

つまりこれは**編集の仕事ではなく、組版の仕事**。ヒデアキの通常モード（推敲して短くする・構造を組み替える）を**オフにする**判断が最初に要る。
「余計なことがゴチャゴチャ」（2026-08-24）と言われた時とは真逆の指示なので、**過去の学びを機械的に適用すると事故る**。

> **判定規則：依頼に「原稿が唯一の正」と書いてあるか。書いてあれば推敲禁止。組版と検証に全力を注ぐ。**

## 手でHTMLを書かない（今回いちばん効いた判断）

原稿(.md)から**機械変換**した。手書きすると、原稿を1行直すたびにHTMLがズレ、片側だけ直す事故が起きる。
実装は汎用スキルに昇格させた → [skills/md-to-standalone-html.md](../skills/md-to-standalone-html.md) / `skills/md_to_standalone_html.py`。

**置き場所の判断**: 変換スクリプトを `agent_output/` に置くと `.gitignore` 対象で worktree ごと消え、**HTMLを再生成できなくなる**。
かといって `deliverables/` はビルド道具の置き場ではない。→ **`agents/content_creator/skills/` が正解**。
「テキスト+HTML併出力」は常設ルールなので、この道具は今後も必ず使う＝スキルとして持つのが筋。

## 検証は「機械照合」と「描画して目で見る」の2本立て（省略禁止）

自作コンバータは**静かに文章を落とす**。md では正常に見えるのでテキストだけ見ていたら永久に気づかない（2026-08-24に実際に10箇所以上落とした）。
今回は双方向で照合した。**片方向では不十分**。

| 方向 | 何を守るか |
|---|---|
| md → html | **削っていない**こと（446件の行/セルを全数照合） |
| html → md | **足していない**こと（原稿に無い文字列の混入検出。許可リストは目次・↑・注記のみ） |

加えてマーカー数（`[#n]`=285件 / `[要確認 #n]`=17件）・見出し数・表数・**表の行数(109)**まで突合した。
数を突合すると「表が1行だけ落ちた」類の事故が拾える。

## 描画して初めて見つかった不具合（4件）— 目で見なければ全部素通りしていた

1. **目次が「1. 1. 結論」と二重採番** — 見出し文言が既に番号を持つのに `<ol>` も採番した
2. **リード文が目次の下に落ちた** — 目次を H1 直後に差し込んだ副作用。原稿の順序が変わっていた
3. **囲み枠の内側に区切り線** — `---` を `</section>` より先に出していた。**ライトでは目立たず、ダークで初めて見えた**
4. **目次の入れ子が字下げされない** — `.toc ul`(0,2,1) が `.toc-l2`(0,1,0) にCSS詳細度で勝っていた

> **教訓：ライト・ダーク・狭幅・印刷の4条件で見る。**3はダークでしか、2はライトでしか気づけなかった。

## 誤診しかけた1件（headless Chrome の罠）

390px でスクリーンショットを撮ったら本文が右端で切れており、「スマホで横溢れしている」と判断しかけた。
**実際はレイアウト幅の下限が500pxで、画像だけ390pxに切られていた**（`scrollWidth==clientWidth` で溢れなしと確定）。

> **教訓：レイアウトの不具合をスクリーンショットの見た目だけで断定しない。数値で確かめる。**
> 計測用のコピーに一時的にJSを仕込んで `--dump-dom` で読む。**納品物にJSは入れない。**

## 足さなかったもの（意図的な不作為）

読み手は初心者なので「親切に足したくなる」場面が3つあったが、すべて見送った。理由も含めて残す。

| 足したくなったもの | 見送った理由 |
|---|---|
| `[#n]` の凡例（「これは出典番号です」） | 原稿に無い。**必要なら原稿側に足してもらってから再生成する**のが筋。HTML側で独自に補うと2つの正が生まれる |
| 表の「← 横スクロール →」ヒント | 20回以上出て煩い。CSSの端フェードで代替（**UIの工夫は content の追加ではない**という線引き） |
| 結論の要約ボックス | §1がそのまま結論なので、要約すると**言い換え**になる。§1自体を囲み枠で強調する形にした |

**ただし1つだけ足した**: 末尾の出所注記（「内容の唯一の正は draft.md です」）。
これは**内容ではなくメタ情報**で、2つのファイルのどちらが正かを読み手が判断できるようにするためのもの。足す/足さないの線引きは「**原稿の主張に足しているか、原稿の在り処を示しているか**」で引いた。

## 引き渡し時に必ず伝えること

- **`[#n]` の出典一覧が draft.md に無い。** 読み手は `[#5]` を見ても何の資料か辿れない。
  組版側では解決不能（原稿に無いものは作れない）。**リサーチャーへ差し戻す論点として明示する。**
- assignee が自分でないチケットの一部作業を頼まれることがある（今回 assignee=researcher）。
  **成果物の置き場は依頼元チケットのIDに従う**。勝手に別チケットを立てない。
