# メーカーが条件に「はい」と答えた後の返信（発注前の確認）の作り方

初出 2026-10-19（T-20260930-001 / 91_アイビーアール_返信_発注前・ムカデ博士の粒剤）。
兄弟：knowledge_maker_reply_thanks_and_referral.md（お断り・紹介への返事）／knowledge_business_reply_email_drafts.md（審査窓口への返信）／maker-outreach スキル（打診の正）。いずれも Mac 側ブランチ `origin/claude/nighttime-work-checkin-iTWEa` にある。クラウドのローカルには無いことがあるので `git fetch` → `git show` で読む。

## 1. 型（7段・宛名と署名を除き約430字）
名乗り＋お礼 → 数量と単価（「お願いしたいと考えております」）→ 今後の流れ（出品・FBA 手続き → ラベルと納品先がそろい次第「改めて正式にご注文」）＋ラベル貼付の確認 → 未回答だった点の再確認1文 → 書類のお願い（逃げ道つき）→ 請求書の宛名 → 結び＋固定署名

## 2. 判断の要点（次も同じ判断になるもの）
- **このメール自体を注文と読ませない。**先方の流れが「発送準備ができたら請求書 → 入金で発送」の場合、「発注します」と書くとラベル・納品先がそろう前に請求書が来る。「お願いしたいと考えております」＋「改めて正式にご注文」の二段にする
- **合意した単価は本文に再掲する**（文面で条件を固定）。実額を書いたファイルは agent_output に置く（PUBLIC リポ）。.gitignore に当たるかを `git check-ignore -v` で確かめる
- **先方が明言していないことは確認形で聞く。**今回「バーコードをいただくことになります」＝貼るとは言っていない →「貼付をお願いできますでしょうか」
- **前回答えてもらえなかった質問は、1文＋括弧に畳む。**「並行出品」のような業界語は使わない（身構えさせる）
- **書類の依頼には逃げ道**：「ご用意がなければ、お気になさらないでください」
- **依頼文の言葉をそのまま使うと不自然になることがある。**「請求書の宛名は署名どおりで差し支えない」→問われていないことに「差し支えない」は変なので「署名のとおりでお願いいたします」。意味は変えず、変えた理由を納品物に書く
- **相手が出した別商品（今回は補強剤）を見送るときは、本文で触れないのを既定に。**触れたい場合の1行を「要確認」に用意して渡す（見送りを書くと値下げ交渉の前置きに読まれる余地）

## 3. 手順
1. スキル・兄弟 memory・ハジメの採算 memo（agents/accounting/memory/knowledge_maker_offer_*.md）を Mac 側ブランチから読む。採算 memo に「返信で聞く点」が書いてあるので、依頼との抜けを照合する
2. 本文を scratchpad の body.txt に書き、空白を除く字数を python で測る。稿2で501字→削って445字（宛名込み）
3. 署名は SKILL.md の署名ブロックを抜き出して diff（一致を機械で確認）
4. 禁止語 grep（少量・小ロット・本件のみ・ご不要・配信・Markdown 記号・「失礼」「致します」）

## 4. 制約・失敗しかけた点
- 元メール（当社の質問・先方の回答）の原文がリポに無く、カズヨの要約で書いた → 件名・担当者名・法人格・商品の呼び方を差し込み欄にし、「原文未照合」を妥協点に明記
- チケット本体がクラウドのローカルツリーに無かった（Mac 側ブランチにだけある）。commit 禁止の依頼だったので、チケットへの追記はカズヨに依頼して返した
