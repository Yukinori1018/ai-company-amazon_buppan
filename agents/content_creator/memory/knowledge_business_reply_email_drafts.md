# 取引先（審査窓口）への返信メール文案の作り方

初出 2026-09-12（T-20260904-005 / スーパーデリバリー追加書類の返信 A版・C版）。

## 再利用できる手順

1. **元メールを必ず自分で読む**（チケットの要約だけで書かない）。今回、PDF を読んで初めて「着信先＝satoyselect@gmail.com」「件名の正確な文字列」「#1 の目的＝販売ページ確認」が確定した
2. **送信元アカウントを元メールの着信先で決める。**社内 memory の「Amazon 関連は 1018 から」のような既定は、別の取引先には当てはまらない。スレッドを割らないことが優先
3. 納品物に入れるもの：使い分け表 → 共通設定（送信元／宛先／件名 Re:／新規作成でなく返信）→ 本文（コードブロック）→ 添付ファイル名の表 → 送信前チェック → 表現の意図 → 妥協点
4. 添付ファイル名は **「お客様番号_項目番号_内容」**。受け手の担当者は自分のチェックリストで照合するので、番号をそろえると処理が早い
5. 個人情報はプレースホルダ［　］。リポジトリは PUBLIC。お客様番号のような先方の照合キーは、すでにチケットに公開済みで照合に必要なら残す
6. 延長依頼は **具体的な日付＋「難しい場合の進め方を教えてほしい」** の2点セット。後者は、断られた時に無回答扱いで自動キャンセルになるのを防ぐ一文

## 受け手視点（稿3）で毎回見る点

- 受け手が審査で「一番見たいもの」を本文にも書く（今回は「大口出品」。画像の中を探させない）
- 書類の目的が「ページ確認」なら URL を本文に入れる
- 事情説明は依頼範囲を超えない。詳細を書くと、先方に別の審査論点を立てさせる
- 不利な事実（今回は小口であること）は、延長を頼む理由として必要なら書く。隠すと後で食い違う
- Gmail の添付は 25MB を超えるとドライブリンクに化ける。スマホ写真7枚で上限に近い → 送信前チェックに入れる

## 失敗しかけた点

- 稿1で e-Tax 受信通知を落としていた（チケットの「要訂正」として明記されていたのに）。**チケットの訂正事項は、本文を書く前にチェックリスト化してから書く**
- 「運転免許証（推奨）」と書いたが、社長が持っているかは未確認だった。推奨は前提つきで書く
- **HTML 変換でメール本文が壊れていた。**自前の変換スクリプトがフェンス付きコードブロックに未対応で、``` が文字のまま出て、本文中の「1. 2. 3.」が `<ol>` に組み直されていた。見出し数や「OK」表示では気づけない。**`<pre>` の数と中身を md と機械照合して初めて分かった。**スクリプトに対応を追加し、照合手順をスキル文書に書いた（skills/md-to-standalone-html.md §フェンス付きコードブロック）
- 並行作業との衝突：README とチケットへの私の追記は、同時刻に commit したサトルの commit 5324b36 に巻き込まれて入っていた。**commit 前に `git log` と `git status` を必ず見る。**差分が空なら、すでに誰かが commit している
