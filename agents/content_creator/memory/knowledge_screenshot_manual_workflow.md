# 手順: スクショ由来マニュアルの「追補」依頼をどう処理するか

記録 2026-08-21（T-20260811-001 §6 追補）。**既存マニュアルへの追記依頼を受けたら、この順で回す。**

## 1. 素材は必ず自分の目で開く（README を鵜呑みにしない）

今回はマリエの読み取りREADMEが付いていたが、実画面を開いて初めて分かったことが3つあった。

- 026 の分析対象セラーが、**既存 §3 の Buy Box 表に載っている業者と同一**（評価件数4,721で一致）→ 章の導線が作れた
- **既存 §3 に事実誤りが1件**（セラーBのFBA欄が空欄。実画面はチェックあり）→ 追補ついでに修正
- 「プロ」メニュー配下＝有料プラン前提の疑い（READMEには無い観点）

**依頼が「追記」でも、隣接する既存記述は実素材で検算する。** 追補は既存の品質保証をやり直す好機。

## 2. 拡大して読む（`PIL` でクロップ → 再読）

小さい文字（許可番号・ラベル名）は原寸のままだと誤読する。
`python3 -c "from PIL import Image; Image.open(p).crop((x0,y0,x1,y1)).save(out)"` で該当ブロックを切り出し、もう一度画像として読む。今回は基本情報カードとパフォーマンス行で実施。

## 3. 「浮かせない」ための3点セット

既存文書に新章を足すときは、章を書く前に**接続部**を設計する。今回やったこと：

1. **冒頭の前提を1文だけ更新** — 既存は「Keepaは商品ページに埋め込まれる。単独アプリではない」と断言していた。新章は keepa.com 本体の画面なので、放置すると**新章が既存の前提と矛盾する**。「入口が2つある」と1文足して橋を架けた。
2. **既存章から新章への導線** — §3 の表に「販売者名はリンク。クリックで §6 へ」を追記。
3. **まとめ節にも1行** — 巻末「3ステップ」の③に「迷ったら §6 まで踏み込む」を追加。**まとめを更新し忘れると、新章は読まれない。**

## 4. 第三者情報のマスク（既定運用にする）

実在事業者名・住所・電話・代表者名・許可番号は **セラーA/B/C/X** に置換。
**既存章に残っていた実名も、この機会にまとめてマスクした**（初版は実名のまま納品されていた）。
例外として **Amazon.co.jp だけは残す** — 「本体と競合しているか」がその表の要点であり、匿名化すると教材価値が消えるため。
納品物の README に「元画像は社外に出すな」を明記。

## 5. 出力形式（社長既定）

分量のある資料は **HTML＋テキスト（.md）の併出力**。初版は HTML のみだったので .md を新設した。
**ファイル名は変えない**（`deliverables-catalog.csv` からリンクされているため。リネームすると成果物カタログが切れる）。
`README.md` に版歴と未確認事項リストを置くと、次に触る人が差分を追える。

## 6. レンダリング確認（headless Chrome）

CSSクラスを流用しても、表セル内の `.tag`（丸バッジ）が折り返して崩れることがある。目視は必須。

```
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --hide-scrollbars --window-size=900,9000 --screenshot=out.png --virtual-time-budget=3000 "file:///…/x.html"
```

ウィンドウ高さ＝ページ全高を指定しないと下が切れる。PILでクロップして節ごとに読む。
あわせて `html.parser` でタグの閉じ忘れと**実名の残留（マスク漏れ）を grep で機械チェック**するとよい（今回テンプレ化した）。

## 7. 妥協点は必ず報告に書く

今回の妥協：①無料プランで開けるか未確認（社長の実機1クリックで解消）／②メーカー仕入れ逆引きは未検証の仮説／③ §1〜§5 は初版記述を流用（全面再検証はしていない）。
**「隠さず書く」ほうが、次の依頼の精度が上がる。**
