## 1. 数字を1つも手で打たない ─ 「改変ゼロ」は言葉ではなく実装で担保する

依頼は「データを改変しない。機械変換＋双方向照合で確認」。やったのは次の3つ。

| 手段 | 中身 |
|---|---|
| **合計を書かない、足す** | 46,188円・14,736円・0円はすべて `sum(CSV列)`。本文の「粗利1,763円の差」も `A1粗利 − B1粗利` |
| **社長決定の値と突き合わせて、違ったら出力しない** | 検算12件（SKU数・社数・金額・粗利）を生成前に判定し、1つでも外れたら `SystemExit`。CSV が入れ替わったまま古い数字の資料を出す事故を構造的に潰す |
| **双方向照合** | 前向き＝CSV の全セルが HTML にあるか／逆向き＝**HTML に出てくる「N,NNN円」がすべてデータに戻せるか**。逆向きが本命で、これで初めて「勝手に足した数字がゼロ」と言える |

**逆照合はタグを消してから走らせてはいけない。** タグを消すとセルをまたいで数字が繋がり、
`5,136円` + `4口` が `15,136` のような**存在しない数字**として山ほど検出される。
タグを `\x00` に置換して境界を残すこと。

**本文の記述も機械で確かめられるなら確かめる。** 初稿で
「B1 は A1・A2 から選び直したものではなく、母集団から割り付け直したもの」と書いたが、これは推測だった。
実際に ASIN を突き合わせると **B1 = A1 の上位4SKU + A2 の上位4SKU** で、そのとおり書き直して assert を足した。
**推測を1行混ぜた瞬間に、資料全体の「改変ゼロ」が嘘になる。**

## 2. クラス名の衝突は、画面では絶対に見つからない

印刷幅で表の右端が切れる原因を1時間追った。犯人は自分が付けた `<div class="chk">` で、
**基本CSSの `.chk` は「nowrap の小さなバッジ」**（チェックリスト用）だった。長い文をそこに入れたため、
セル幅の最小値が紙幅を超えていた。画面は `overflow:auto` なので何も起きず、**印刷だけが黙って切れる**。

> **一般則: 共有CSSのクラス名を再利用する前に、そのクラスの定義を読む。**
> 独自要素には独自クラス名（今回は `.nk`）を付ける。1文字ケチって半日溶かす。

**印刷の溢れは `table.scrollWidth` だけでは診断できない。** `offsetWidth`（表そのものの幅）と
`scrollWidth`（はみ出した中身を含む幅）を分けて測り、**溢れている子要素を `getBoundingClientRect().right` で名指しさせる**。
「どの要素が」まで出さないと原因に辿り着けない。

**印刷で表を絶対に切らせない確実な手は `table-layout:fixed` + 百分率。**
基本CSSの印刷ブロックが `table{table-layout:auto}` に戻すので、上書きが要る。
auto は最小内容幅が紙幅を超えた瞬間に破綻するが、fixed なら表幅は必ずコンテナ幅に一致する。

## 3. 🔴 公開リポでは「作ったファイルが勝手にコミットされる」ことを前提に設計する

**今回いちばん重い学び。**

`03` は商品名・JAN・NETSEA のサプライヤー社名を含むため、元データ `D_*.csv` と同じく Git 除外にする判断をした。
ところが **.gitignore に書く前に、別セッションの `git add -A` 相当が走り、03 を巻き込んでコミットしていた**
（コミットメッセージは全く別チケットのもの）。このリポジトリは **30分ごとに自動 push** される。

- **出してよいか迷うファイルは、生成した直後・中身を書く前に `.gitignore` へ登録する。**
  「完成してから判断する」では間に合わない。**判断が終わるまでの数十分が、そのまま公開リスクの窓**になる
- 除外の判断基準は自分で発明しない。**同じフォルダの `.gitignore` に前任が書いた理由をそのまま踏襲する**
  （今回は「NETSEA API 利用規約 第7条2項5号／第19条3項の論点があるため載せない側に倒す」）
- **履歴からの削除は §4.1（不可逆な削除・force push）。自分でやらない。**
  できるのは `git rm --cached` ＋ `.gitignore`（＝これ以降は追跡しない）まで。**残りは秘書に上げる**

## 4. 「打診可能◯◯社」のような数字は、単独で出さない

02 の元 CSV が 195社 → 399社 に増え、法務注記も v1.1 に上がっていた。増えた注記の要点は
**「`optout_notice_status` が『未取得』の社は、お断り表示が無いと確認した社ではない」**。
そこで区分表の直後に「打診可能381社／うち確認済み86社／未確認295社」を必ずセットで出し、
**一覧の各行にも `optout_notice_status` のピルを足した**（本文に「一覧にある」と書いた以上、無いと嘘になる）。

**依頼書の数字をそのまま書き写さない。** 依頼には「打診可能336社・確認89社・未確認247社」とあったが、
CSV から数えると 381 / 86 / 295 だった。**数字はデータから出し、食い違いは秘書に報告する**（前回の学びがそのまま効いた）。

**版番号をベタ書きしない。** 02 に「法務判定 v1.0」と手書きされていたが、CSV 側は v1.1 に上がっていた。
「版はこの注記の中に書かれています」に直した。**ベタ書きは古くなった瞬間に嘘になる。**

## 5. 「発注書」の情報設計

読み手は資料を読みに来るのではなく、**この画面を見ながら発注する**。したがって：

- **サプライヤーごとに区切り、その単位で1回ずつ発注する形にした**（送料は社ごとに1回かかるため、社が発注の単位）
- 1SKU = 主行（金額・利益・回転）＋ 注記行（サイズ・中古・ブランド・リスク・**発注前に必ず確認**・発注URL）。
  注記行は4行とも同じ文言になるが**削らない**。1点ずつ確認する用途なので、行ごとに完結していないと使えない
- **不採用案も表で残す。**「なぜ粗利の大きい方を蹴ったか」が無いと、後から読んだ人が必ず蒸し返す
- **「候補が出た＝買ってよい、ではありません」を第1部の直後に、第1部と同じ強さで置いた。**
  未了2件（ゲート未確認・中古は文字判定のみ）は、成果物の見栄えより優先する
