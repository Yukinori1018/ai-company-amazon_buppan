# 制作原則: 「答え合わせ」が来た納品物を改訂するときの型（要確認 → 公式定義）

記録 2026-08-24（T-20260811-001 第3版／裏取りは T-20260824-001 サトルの Keepa公式APIドキュメント精読）。
**「前に出した資料の“分からない”に、後から一次情報の答えが付いた」系の依頼を受けたら、着手前にこれと `knowledge_correcting_delivered_docs.md` を両方読むこと。**

## 何が起きたか（結論から：第2版の判断は正しかった）

第2版で私は、Keepa の日本語UIラベルのうち意味を断定できないものを**「要確認」と明記し、「判断に使わないでください」と本文で釘を刺した**。
2026-08-24 に公式APIドキュメントで答え合わせをしたところ：

| 第2版での扱い | 結果 |
|---|---|
| 「BUY BOX の平均売上数」＝意味不明・使用禁止 | **推測していたら確実に誤読していた。** 公式 `avgBuyBoxCompetitors` ＝ **Buy Box を争う平均競合出品者数**。日本語UIが**完全な誤訳**で、素直に読むと**数字の意味が真逆**（競合の多さを売れ行きの良さと読む） |
| 「購入ボックス切り替えの所有者」＝カート保有割合と**推定**（要確認） | 推定どおり（`buyBoxNewOwnershipRate`＝新品 Buy Box 平均獲得率） |
| 「評価 -1%」＝データなしと**推定**（要確認） | **公式に定義が存在せず、今も未解決。** 据え置きが正解 |

サトルが定義集に書いた法則が全てを言っている：
> **「要確認」と明記して放置したものは、後から全部救えた。危険なのは断定して使ってしまったもの。**

**教訓：資料の「分からない」は欠陥ではなく、後から回収できる資産。埋めた瞬間に負債になる。**

## 逆に、今回見つかった自分の誤りは全て「断定しすぎ」だった

公式と突き合わせて是正したのは、要確認にした箇所ではなく**自信を持って書いた箇所**だった。

| 自分が書いた文 | 公式 | 誤りの型 |
|---|---|---|
| 「ランキングが下がる回数**＝売れた回数**の目安」 | 「下落の**回数**。**販売を示すものとみなされる**」 | **代理指標を実数と同一視**（「目安」と添えても、＝で結んだ時点で断定） |
| 「先月の購入＝直近の販売数の**目安**」 | 「購入された回数。**推定値ではない**」 | **実測値を推定値に格下げ**（逆方向の誤り。慎重に書いたつもりが不正確） |
| 「Buy Box対象オファー数＝**それだけ競合セラーがいる**」 | 「Buy Box に**適格な**オファーの数」 | **単位の取り違え**（オファー ≠ 出品者）。当社が実際に事故（候補top100の35%汚染） |
| 「%獲得＝カートを取っている割合」 | 「獲得していた**時間**の割合。**非プライム客に対して**」 | **限定条件の脱落** |

**チェック観点として言語化しておく（次に数字を説明する文を書くときに使う）：**
1. **「＝」で結んでいないか。** 代理指標・近似・階級値を「＝」で書いた瞬間に断定になる。
2. **単位は何か。** 件数／人数／回数／時間の割合／金額。**「数」とだけ書いてある画面の値は必ず疑う。**
3. **母数と対象は何か。**（誰に対して／どの範囲で／いつの時点で）
4. **「目安」「とみられる」は保険にならない。** 実測値に付ければそれ自体が誤り。

## 改訂版の構造（第3版で採った形・再利用可）

1. **冒頭に「【第3版で直したところ】第2版を読んだ方は、ここだけ先に」**。既読者が差分だけ拾える入口を作る（初読者は読み飛ばせるよう見出しで明示）。
2. **最重要の1件だけ専用の表**（画面表記／英語原語／公式定義／**正しい読み方**／**数字の向き**／第2版での扱い／出典）。**「数字の向き」の行が効く** ── 大きいと良いのか悪いのかが、誤訳の被害の本体だから。
3. **訂正一覧表（旧の書き方 → 公式でどうなったか）**と、**「分からないままにしたもの」表**を並べて置く。**直した件数と、直さなかった件数を同じ大きさで見せる**のが誠実な改訂。
4. 本文の該当箇所には**訂正ボックス**を残す（消して書き換えない）。バッジで `第3版で確定` / `第3版で訂正` / `第3版でも未解決` を色分け。
5. **巻末に「まだ分かっていないこと」表**（項目／状態／**決着のさせ方**）。決着手段まで書くと、放置ではなく宿題になる。
6. **出典に URL と最終確認日を必ず併記**（Keepa は仕様変更が多く、2026-02 に価格定義、2026-03 にオファー数項目が変わっている実例あり）。

## 局所修正で済ませず「格上げ」する判断

依頼元（カズヨ）から「§3 の修正にとどめず、必要なら冒頭の大前提にも入れて」と言われた件（**オファー数 ≠ 出品者数**）は、**冒頭の「大前提その4」に格上げした**。判断基準として残す：

> **その誤解が「1箇所の読み違い」ではなく「資料全体を通した読み方の癖」になっている場合、章内の注記では効かない。冒頭の前提に上げる。**

あわせて**当社が実際に踏んだ事故（ASIN・数字・被害率）を本文に書いた**。抽象的な定義より、`B0DWMPV656` は「オファー数2・実セラー1社」という1例のほうが記憶に残る。**恥ずかしい記録ほど、資料の中では最も効く。**

## 一般化の誤りを、逆方向に一般化し直さない（再掲・今回も踏みかけた）

カズヨの実機FAQ所見「Keepa のデータは最大24時間古い」をそのまま大前提に書きかけたが、サトルの差分レポートに**「API経由は別ルール（リクエスト時に自動更新・最大約1時間）」**とあった。
→ 大前提には**画面の話として書き、「API経由は別」と1行の注記を添えた**。**社内の別文脈（夜間スキャン）に誤って一般化されるのを、書く側で止める。**

## 手順の再利用（同型依頼の段取り）

1. 一次情報（定義集・差分レポート・実機キャプチャ）を**全部読む**。要約や依頼文だけで直さない（今回、依頼文に無い誤り2件が差分レポート本文に載っていた）
2. **自分の納品物を「断定形」で grep する**（「＝」「です」「とみなせる」）。要確認箇所ではなく断定箇所が危ない
3. .md と .html を**同時に**直す
4. **機械チェックを最後に回す**：①異言語文字の混入（今回、自分の原稿に `10年선수` というハングル誤入力が1箇所混入していた。目視だけでは見落とす）②タグの開閉数の一致 ③**md↔HTML の主要用語 grep 照合**（20語ほど左右で数を突き合わせる。片側だけ直す事故が消える）
5. headless Chrome で全ページ画像化して目視（`--window-size=900,14000` → `sips -c 高さ 幅 --cropOffset Y 0` で分割。**offset+高さが画像高を超えると sips は無言で原寸を返す**ので注意）
6. README の版歴・未確認事項を更新 → チケットに旧→新の表とログを追記 → **status は動かさない**
