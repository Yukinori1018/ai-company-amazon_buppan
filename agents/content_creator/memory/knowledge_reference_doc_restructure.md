# 制作原則: 「調査記録」を「引くための辞書」に作り替えるときの型

記録 2026-08-24（T-20260824-005 / T-20260824-001 のKeepa用語集を正式版へ再構成）。
**「前に出した資料が読みにくい／余計なことが書いてある」系の改稿依頼を受けたら、着手前にこれを読むこと。**

## 何が起きたか

社長レビュー（原文）：

> 「成果物をレビューしました。**余計なことがゴチャゴチャと書かれていた**ので、整理して、**正式な用語集**として、まとめて下さい。（今まで作った成果物は消す必要はありません）」

対象は T-20260824-001 の `keepa-glossary.md`（62KB・40表）。**中身は正確だった。**公式APIドキュメント30ページの精読に基づき、事実関係に誤りはほぼ無い。
**問題は品質ではなく「用途の取り違え」だった。**1つのファイルに、用語の定義／当社の取り違え履歴／4つの法則／運用結論／事故の実例と汚染率／別文書の管理番号（D1〜D13）／訂正の経緯が同居していた。
つまり「**Buy Box って何だっけ**」と引きに来た人が、**事故の反省文を読まされる構造**になっていた。

> **教訓：文書の欠陥は「間違っている」だけではない。「正しいものが混ざっている」も欠陥。**
> 資料をレビューするときは「事実は合っているか」の前に「**この文書は誰が、どういう動作で使うのか**」を1つに決められるかを見る。決められないなら分割する。

## 「引くための辞書」に作り替える手順（再利用可）

1. **合格条件を1文で決めて、それだけで判断する。**今回は「**1つの語を調べて30秒で閉じられる**」。迷ったら全部これに戻す。
2. **残す／削るを列単位で決める。**元資料は「日本語UI｜APIフィールド｜意味｜**当社が過去に取り違えた内容**」の4列だった。**4列目を落とすだけで大半のノイズが消えた。**個々の文を推敲するより、列を1本抜くほうが速く確実。
3. **「危険な語の警告」は削らない。書き換える。**反省文と警告は見た目が似ているが役割が違う。
   - ✗ 「当社は『売上個数』だと読んでいた。top100 の35%が汚染された」
   - ○ 「**売上ではありません。**Buy Box を争っている出品者数の平均です。**大きいほど競合が多く不利**」
   - **判定規則：主語が「当社」なら反省文（削る）。主語が「その語」なら辞書の機能（残す）。**
4. **表の列構成を全節で統一する。**今回は全定義表を `用語｜APIフィールド名｜意味｜注意｜出典` の5列に揃えた。**揃えると索引を機械生成できる**（下記）ので、統一は美観ではなく機能。
5. **「不明」は残す。ただし理由は書かない。**辞書に要るのは「不明である」という事実だけ。なぜ不明かの経緯は元の調査記録側に置く。
6. **索引を必ず付ける。**日本語（五十音）と英語（アルファベット）の2本。**辞書に索引が無いのは致命的。**

## 索引は手で書かない（今回いちばん効いた判断）

**原稿を機械で読んで索引を生成した**（`build.py`：md の定義表をパース → 見出し語と掲載節を抽出 → md に差し込み → HTML も同じ原稿から生成）。

- 手書きだと**本文を1行直すたびに索引がズレる**。ズレた索引は無いより悪い。
- 副産物として **md と HTML が同一原稿から出る**ので、「片側だけ直す事故」が構造的に消える。
- **並べ替え用の読み（カナ）は内部キーとして持ち、紙面には出さない。**初稿では「読み」列を表示したが、ソート用に小書き文字を大書きしていた（シユツピンシヤスウ）ため**誤字に見えた**。列ごと削除して解決。
- **空見出し（cross reference）を10件ほど入れる。**「平均売上数 →「BUY BOX の平均売上数」」「最安値 →「stats.min」（全期間）」など。**利用者が探す言葉と、画面の表記は一致しない。**ここが索引の価値。

## HTML は「読み物」ではなく「道具」として作る

- **上部に検索窓（sticky）**。打鍵すると全表から該当行だけ残す。**辞書に必要なのは目次より検索。**
- 節への丸いナビボタン。`§3.5` という本文中の表記を**全文一括でアンカーへ変換**（正規表現1本）。md 側はプレーンなまま保てる。
- JS を切っても全内容が見える設計にする（既定で何も隠さない）。

## 自作 Markdown→HTML コンバータの落とし穴（実際に踏んだ）

この環境には `markdown` / `mistune` / `pandoc` が無く、毎回サブセットのコンバータを書いている。**今回、段落の判定条件にバグを入れた。**

```python
# 誤り：'*' 始まりを一律で段落から除外していた
not lines[i].startswith(('|', '#', '>', '-', '*'))
# 正：リスト記号は「記号＋空白」で判定する
not re.match(r'^([-*]\s|\d+\.\s)', lines[i])
```

`**強調で始まる段落**` が **HTML から丸ごと消えていた**（リード文・索引の見出し・§3.1 の価格定義変更の注記など計10箇所以上）。
**md では正常に見えるので、テキストだけ見ていたら永久に気づかない。**headless Chrome で描画して初めて発覚した。

> **再発防止（次も必ずやる）：**
> 1. **描画して目で見る。**`--headless --screenshot --window-size=1240,40000` → PIL で帯にクロップ。**sips の `--cropOffset` は中心基準**で直感と違う（かつ範囲外だと無言で原寸を返す）ので、PIL があるなら PIL を使う。
> 2. **md の全段落が HTML に存在するかを機械照合する。**空白除去＋タグ除去して部分一致を取るだけで、この種の欠落は全部拾える。
> 3. 主要用語20語の **md↔HTML 出現回数の突合**（差分はナビ等の既知分だけか確認）。
> 4. 禁止語 grep（今回は「当社／事故／汚染／top100／法則／教訓／D番号」）で、削ったはずのものの再混入を確認。

## 素材を信じすぎない（今回1件見つかった）

「事実の再調査は不要」と言われた依頼でも、**抜き出すときに疑義が出たら公式に当たる。**今回は Domain ID の記載ゆれで、素材は「Seller Object は 11 までしか載せていない」としていたが、**公式HTMLでは `seller-object.html` は 12 まで載せており、11 止まりは `product-object.html` だった。**
もう1件、`COUNT_NEW` は**公式の説明文自体が "count of marketplace merchants"（出品者の数）と書いており、フィールド名（offer count）と食い違っている**ことが分かった。これは「Keepa の翻訳が悪い」のではなく**公式ドキュメント内の矛盾**なので、辞書には両方を書いて「出品者数として使うな」で閉じた。

> **抜き出し作業は転記ではなく検算。**素材が正確でも、**引用の粒度を変えると誤りが顔を出す**（今回は「どのページが」という粒度に落としたときに出た）。

## 今回の妥協点（次回への申し送り）

- **総量は元の 62KB → 69KB で、減っていない。**反省文を全部落とした一方、定義を約80フィールド増やした（元資料は当社が使う語に偏っていた）。**辞書として引ける範囲を広げるほうを優先した**が、社長が「短くなったか」を見る可能性はある。README に「通読を前提としない」と明記して緩和した。
- **日本語UI表記の一部は「推定」のまま。**Keepa は UI 用語集を公開しておらず、実画面確認は §3.5（出品者概要）だけ。節ごとに「推定を含む」と注記して逃げた。確定させるには Product Finder の「Show API query」を実機で押す必要がある（カズヨの領分）。
