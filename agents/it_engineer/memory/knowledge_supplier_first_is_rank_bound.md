## 一行で

NETSEA の承認済み221社・JAN 67,662件から当てた候補は、**採算は通るのにランクで落ちる**。
**仕入れ先起点では、入口の積極条件（実売）を機械で先に掛けられない**のが構造的な弱点です。

## なぜこうなるか

- **卸サイトに安く載っている商品は、Amazon で売れていないから安い。**
  売れている商品は卸側でも値引きされない（上代ベースの絞り込みで上に来るのは廃盤・アウトレット）
- **Amazon 起点（売れている棚 → 卸にあるか）は逆の弱点を持つ。**
  monthlySold ≥ 50 で取った250件を NETSEA の67,662 JAN に当てたら **当たったのは1件**。
  売れている棚の商品は、承認済み221社の品揃えにほぼ無い

→ CLAUDE.md §3.3-9 の「どちらか一方に寄せない」はこの2つの非対称のこと。
**仕入れ先起点の価値は「候補」ではなく「突合先の台帳」**であり、候補の歩留まりを期待してはいけない。

### 前段フィルタを0トークンで効かせる式

| 卸値（税抜） | 必要な売価 | 必要な倍率 |

| 500円 | 1,637円 | 3.3倍 |
| 1,000円 | 2,293円 | 2.3倍 |

## 「あと1つで通る」の正しい定義は、判定値そのもの

人に見せる「見れば確定する行」を最初は「落ちた断片がちょうど1本の行」で絞り、**0件**になりました。
生存の断片が1本混じるだけで全部こぼれるからです。

**正解は「判定が UNKNOWN の行」**でした。UNKNOWN は定義上「機械が読み切れなかった」＝人が見れば確定する。
NO-GO には FAIL（実画面でも覆らない事実）が1本以上入っているので、見ても結論は変わりません。
**fail-closed の3値判定を自分で作っておいて、その意味を使わずに文字列を数えていた。**

## 集計は wave の JSON ではなく台帳から

`--out-json` の出力を `stageb_wave1.json` 固定名で書いていたため、**2回目の実行で1回目の根拠を消しました。**
台帳（シート）は消えないので、内訳も「あと1つで通る行」も**台帳の `判定理由` を解析して作る**。

## 順序ファイルは台帳で引き直してから使う

`stageb_order.json` を作った時点では未判定でも、次の実行までに判定が進みます。
判定済みばかりの塊を渡すと `candidate_pipeline` が「未判定の候補がプールに残っていません」と答え、
**ループが「プール全体が尽きた」と誤解して1波で終了しました**（残り171件あったのに）。

## 🔴 単位ずれが再発した（2026-10-01 夕方・カズヨが実画面で発見）

`B0FNWB76NG`（カップ麺 110g・**18食入り**）を **卸率5.2%・利益率75.5%・1個手残り +3,706円** と報告。
正しくは **Amazon の1個 ＝ 卸18点**で、原価は268円ではなく **4,824円**＝**▲778円/個の赤字**。
CLAUDE.md §3.3-7 と**同じ型が2日で再発**した。

### 直接の原因は `set_count` の取りこぼし

`COUNTABLE` に **食** が無く、「18食入り」が単品（倍率1）と読まれた。
「2P」（バスタオル2P）も同様に素通りしていた。

**しかし「正規表現に単位を足す」は解決ではない。**
同じ書き方で意味が逆になるからである。

| 表記 | 意味 | 倍率 |
|---|---|---|
| カップ麺 **18食入り** | カップ麺18個＝卸18点 | 18 |
| 青汁 **90包入り** | 1箱の中身＝卸1点 | 1 |

**機械では決められない。**だから `1` とも `N` とも決めずに **None（UNKNOWN）** を返し、人に回す。
`set_count` の元からの思想（「読めないときは 1 にしません」）に、**曖昧な単位を先に見る段**を足した。
数が大きいとき（>60）は内容量と見なす（600粒・90包）。これは heuristic だが、**外しても UNKNOWN 側に倒れる**。

### 本当の対策は「数字そのものを疑う番兵」

読み間違いは今後も起きる。だから**パターンに依存しない検査**を別に置いた。

| 番兵 | 値 | 根拠 |
|---|---|---|
| 卸率が低すぎる | **15%未満 → UNKNOWN** | 卸は普通 売価の40〜70%。5%は単位がずれているサイン |
| 利益率が高すぎる | **50%超 → UNKNOWN** | 同じサインの裏側（§3.3-6「利益率が突出して良い行は仕入れの実在を疑う」） |
| 1 SKU の発注額 | **8万円超 → NO-GO** | 残枠を超える案は生成も提示もしない（§3.1） |

**この2つの番兵は独立ではない**（卸率が低ければ利益率は必ず高い。同じ式の裏表）。
両方置いているのは、どちらの側から見ても気づけるようにするため。テストで固定してある。

### 「同じ CSV の中で単位が揃っていない」のが見逃された形

`発注額 = 268 × 18 = 4,824` は**計算として正しく見えた**。
**原価が「卸の1点」・点数が「卸の点数」で、たまたま辻褄が合っていた**だけ。
`1個手残り` だけが「Amazon の1個」で、**1つの表の中で単位が2種類混ざっていた。**

    ❌ 原価(税込・1個あたり) / 入り数(点) / 発注点数   ← どれの「1個」か分からない
    ✅ 卸の1点あたり原価 / Amazon側のセット数 / Amazon1個あたり原価 /
       卸の最小ロット(点) / 発注点数(Amazon何個) / 発注する卸の点数 / 単位の整合チェック

**列名に単位を書く。**「1個」と書いた時点で、読む人と書く人が別のものを思い浮かべる。
整合チェック列は `発注額 ≒ Amazon1個あたり原価 × 発注点数` を機械で検査し、
**崩れていたら数字を黙って直さず「NG」と書く**（黙って直すと、どちらが正しいか分からないまま辻褄だけ合う）。

## 是正スクリプトは冪等でなければ是正ではない（同日に2回踏んだ）

全240行を引き直す `recompute.py` で、**2回踏んだ**。

1. **新しい値を古い値で上書きしようとした。** 発掘キャッシュの売価で再計算したら、
   段Bで取り直した**より新しい売価**を上書きし、利益率が 24.7→30.4 と勝手に動いた。
   → 直したいのは**原価の単位だけ**。売価・手数料は台帳の値のままにし、
   手数料は恒等式 `手数料 = 売価 − 原価 − 1個粗利` で**引き算で復元**する。
2. **丸めた値から復元したので、走らせるたびに数字が漂った**（1969 → 1964 → …）。
   卸率は小数1桁で保存されているので、そこから戻した原価は数円ずれ、誤差が手数料に入る。
   → 本当の原価は「卸の1点 × 整数」なので、**整数倍の中から一番近いものを選ぶ**と厳密に復元できる。

さらに、**自分が前回書いた `再計算.` の節を剥がさずに追記していた**ため、
判定理由が毎回伸びて 240行が毎回「変わった」ことになっていた。
そして Sheets は `"34.8%"→"34.80%"`、`"2.0"→"2"` と**書式を変えて返す**ので、
生の文字列比較では永遠に一致しない。

    ✅ 是正スクリプトは「2回目で0行」を確認するまで完成していない。

## Sheets の書き込みは 60リクエスト/分

240行を `update_row` で1行ずつ送って **429（Write requests per minute）で半分だけ書けた状態**になった。
`batch_update` なら1リクエストで何行でも送れる。`ledger_sheet.update_rows` を足した。
