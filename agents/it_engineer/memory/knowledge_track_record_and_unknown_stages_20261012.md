# 実績枠（GO（実績枠））と UNKNOWN の段階解消（2026-10-12・T-20260920-003）

## 何を作ったか
- **実績枠**（CLAUDE.md §3.5 #18・社長「プラマイ0でも卸で実績を作る」）
  - 規定は `scripts/sourcing_gate/consistency.py` の `track_record()`（純関数・テスト15件）。判定文字列は `TRACK_RECORD = "GO（実績枠）"`、`GO_VERDICTS = ("GO", "GO（実績枠）")`、`count_verdicts()` で**通常 GO と分けて数える**
  - 台帳側は `ledger_refresh.track_record_frame()`。条件＝中央値の手残り（等級の中央シナリオと損益の手残りの**小さい方**）0円以上・取り分 月1個以上・**最小ロット1回**（書類申請は10点）の在庫6か月以内・ほかの項目は全部 PASS
  - 取り分だけ未計算の C（実売 PASS・内訳なし）は落とさず UNKNOWN「実績枠の候補・取り分待ち」。ただし**競合ゼロでも最小ロットが6か月で捌けない行は候補にしない**（見ても入らない行を人に回さない）
- **UNKNOWN の段階解消** `26_候補提案パイプライン/unknown_stages.py`（plan / run / status）
  - 判定理由の `#番号 … UNKNOWN/FAIL` から未決の項目を取り出し、人の合流で同じ項目が `PASS` なら決まった扱い
  - 機械の段 ①#9（キーゾン再現式）②#13-14・#10 内訳（Keepa 取り直し）③#11（12か月ランク）を **1バッチ（100件）ずつ**ラウンドロビン。④実画面・⑤人手はファイル出力
  - 状態は `agent_output/T-20260920-003/unknown_queue/state.json`（next_stage・段ごとの処理日・履歴）。同じ段の再処理は7日（季節は30日）空ける
  - Keepa は「バッチ必要量＋予備」に足りなければ**待たずに止めて次回その段から**。取り直しは `unknown_queue/keepa_stage_<日付>.jsonl` に追記し、ledger_refresh（FRESH）と screen_checks（offers）が新しい方を使う
  - ①の結果は `ledger20261010/kz_estimate_stages.csv`（日付つきファイルより名前順で後＝勝つ）

## 気づき・失敗
- **実績枠を足しても件数はほとんど増えない**（初回は GO（実績枠）1件・候補4件）。秘書が数えた「#18 と #10 だけで落ちた19行」の大半は、**最小ロット（24〜100点）で在庫が6か月を超える**か中央値が赤字だった。律速は採算の線ではなく**ロット**。#10 の「こう変えれば」に「◯点以下で買える仕入れ先（小分け卸）なら実績枠」を出すようにした
- **B で取り分だけ足りない行（例 手残り497円・取り分1.7個）も実績枠に入れた**。C を通して B を落とすのは逆転なので（§3.1 で私が決めた。規定文は「C に落ちた行」）。秘書に要確認として返す
- **SD 行はキーゾン再現値を判定に使っていなかった**（sd_screen が `covers`＝人の確認だけで合流）。`has_any` に変えたら SD の UNKNOWN 73行が「3か月0個」で NO-GO に解けた。機械だけの合流は見出しを「（キーゾン再現値を反映）」にして人の確認と区別
- **2回目で数字が漂う原因を1つ潰した**：price_history の90日窓の「いま」が秒単位の現在時刻で、同じ日に2回走らせると境界の値替えで中央値が動いた（B002BN428K 115↔136円）。既定を当日0時に揃えた
- Keepa は共有キー。昼でも他の作業が使い切っていることがある（今回 残28）。「足りなければ止めて続きは次回」で設計したのは正解だった
- `git stash` は他エージェントの作業中ファイル（チケット）まで巻き込む。**検証に stash を使わない**（今回は pop で戻ったが危ない）
- test_consistency.py には私の変更前から失敗が5件ある（good_row の その他固定費 460円が現行モデルと不一致＝fixture が古い）。別途直す

## 再利用できる手順
1. 規定の追加は「純関数＋テスト（consistency.py）→ 台帳側で呼ぶ」の順。判定文字列を増やすときは `GO_VERDICTS` を使っている箇所（LEGAL・復旧待ち注記・ゲート待ちキュー・record_extra）を全部見る
2. 台帳を書く前に `ledger_refresh.py --dry-run` を基準として保存 → 変更後の dry-run と行順で比較（ASIN キーは重複行があるので使わない。卸率列はシートの表示が%なので正規化）
3. 書いた直後にもう一度 dry-run してシートと比較し、差分0を確かめる（§3.3-17）
