# 利益率だけで並べたリストは、社長に嘘をつく（2026-08-31 / T-20260831-006）

## 何が起きたか

NETSEA×Keepa の利益スキャンを初めて実走したところ、最上位に来たのがこれでした。

| 商品 | 純利益 | 利益率 | **salesRankDrops30** |
|---|---|---|---|
| 黒球式熱中症指数計 | 7,230円 | **55.9%** | **0** |

`calc/profit.py` の判定は **「原石」**（利益率15%以上かつ純利益500円以上）。
でも `salesRankDrops30 = 0` は **直近30日で1個も売れた形跡が無い**という意味です。

**在庫は現金です。売れない在庫は利益率が何%だろうと現金を潰します。**
これを「原石」としてリストの1位に置いたら、社長は仕入れます。それは事故です。

## なぜ起きたか（構造の問題であって、うっかりではない）

`calc/profit.py` は**回転を知りません**。知らないのが正しい設計です
（利益計算は純関数であるべきで、Keepa のフィールドを知るべきではない）。
問題は、**その出力をそのまま最終判定として使ったこと**でした。

> 層を分けたときは、**分けたせいで落ちる観点**を上の層で拾い直す。
> 「下の層が返した verdict」をそのまま最終回答にしない。

## 対処

`evaluate.overall_verdict()` を足して、利益と回転を重ねた `総合判定` 列を作りました。

| 条件 | 総合判定 |
|---|---|
| 赤字 | はずれ(赤字) |
| 黒字・drops30 が不明 | 利益は出るが販売実績が不明 |
| 黒字・drops30 = 0 | **利益は出るが直近30日に売れた形跡なし** |
| 黒字・drops30 < 3 | 利益は出るが回転が遅い(30日で約N個) |
| 黒字・drops30 ≥ 3 | 原石 / あやしい |

README にも「**`利益率%` だけで並べ替えないでください**」と明記しました。

## 一般化して覚えること

**「良さそうに見える指標が1つある」ときは、それを打ち消す指標を必ず同じ行に並べる。**

- 利益率 ⇔ **回転**（売れないなら利益率は絵に描いた餅）
- 出品者数の少なさ ⇔ **需要**（競合ゼロは好機か、誰も欲しがらないかのどちらか）
- 卸値の安さ ⇔ **最小発注数**（単価が安くても10個単位なら寝かせる現金は10倍）

社長は「データは正直であれ」を求めています。**数字が間違っていないことと、
その数字が誤解を招かないことは別物です。** 後者まで面倒を見るのがこちらの仕事。

## 社長の基準（2026-08-31 更新）

- **利益率は 5% から候補に入れてよい**（従来の社内 KPI は20%）
- ただし**捨てずに段階で見せる**。`5%未満 / 5〜10% / 10〜20% / 20%以上` の区分列を持たせ、
  **社長が自分で線を引ける**ようにする
- **利益率だけで並べない**。回転を必ず併記する

「絞り込んで少数精鋭を出す」のではなく「**母数を出して、判断材料を全部添えて、線は社長が引く**」。
これは `owner_maximize_pool_not_precision` と同じ方向です。
