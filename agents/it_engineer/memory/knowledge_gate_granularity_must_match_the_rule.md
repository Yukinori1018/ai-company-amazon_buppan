# ゲートの粒度は、規定の粒度に合わせる — 「本体の存在」で落として224件を捨てていた

2026-10-04 / T-20260920-003 / タカシ

## 何が起きたか

CLAUDE.md §3.3-1 の規定は「**カート保持者が `Amazon.co.jp` なら発注しない**」。
実装（`verdict.py`）はそれを3つのチェックに分け、**3つすべてが FAIL を出せる**作りにしていた。

| チェック | 旧 | §3.3-1 が言っていること |
|---|---|---|
| 1. カートの販売元 | 本体なら FAIL | ✅ これが規定 |
| 2. 本体の在庫履歴 | 365日在庫率 >2% なら **FAIL** | ❌ 規定は「在庫を持つな」ではない |
| 3. 出品一覧の実数 | 本体が1本混ざれば **FAIL** | ❌ 規定は「出品するな」ではない |

**実測（N=648）：本体あり373件のうち 295件（79%）は、カート保持者が本体ではなかった。**
本体が在庫を持っていることと、本体がカートを取っていることは、まったく別の事実だった。

この1箇所を直すだけで **224件が NO-GO から外れた**（そのうち採算が A/B なのは84件）。
同時にやった原価モデルの直し（固定費206円→区分別・誤差幅の撤去）で復活したのは63件。
**ゲートの粒度の誤りは、計算式の誤りより大きかった。**

## 学んだこと

### 1. 「安全側に寄せた」つもりの実装は、規定より厳しい別の規定になる

チェック2・3 は「本体不在をもっと確実に確かめるため」に足したものだった。
ところが**確かめるべき命題（誰がカートを持っているか）とは別の命題**を測っていて、
それで落としていた。**補強の指標に FAIL を持たせると、新しい規定を勝手に作ることになる。**

対処：**FAIL を出せるチェックを1つに絞る。**他は `status=PASS` ＋ 注記（補助情報）にした。
数字は `evidence` と理由文に残す。**隠すのではなく、落とさないだけ。**

### 2. 閾値が1%だと「出入りしている」と「本体の棚」が区別できない

`buyBoxStats` で本体が期間中にカートを取った割合を 1% で FAIL にしていた。
実測では 1.7〜2.7% の行が多数あり、それは**第三者が98%以上カートを持っている棚**だった。
**50%（過半）に変えた。**過半なら実質「本体の棚」なので落とす。1〜50% は注記つきで通す。

### 3. 緩めてよい線と、緩めてはいけない線を分けて書く

緩めなかったもの（レビューで最初に聞かれるので、README に明記した）：
- **カート保持者が決まらない行は UNKNOWN**（独立2本の一致が要る。1本でも AMAZON を指したら FAIL）
- **取得できなかった行は UNKNOWN**（§3.3「1つでも未確認なら発注を提案しない」）
- 単位ずれの番兵、回転上限6ヶ月、1 SKU 8万円の予算枠

### 4. 既存テストが赤くなったら、それは「仕様が変わった証拠」として書き直す

`test_verdict.py` の6件・`test_pipeline.py` の10件が落ちた。
**消さずに、テスト名と docstring を「新しい規定」に書き換えた**
（`test_amazon_had_stock_all_year_is_no_go` → `..._is_not_no_go` ＋ 変更理由と実測値）。
テストは仕様書なので、**何をやめたかが読めないと半年後に戻される。**
さらに「落とさないが数字は消さない」ことを確かめるテストを足した
（`test_stock_history_is_still_reported`）。

### 5. 定数を疑う順番

§3.3-19 の「候補が出ない原因は、社長の条件より先に自分のコードを疑う」の実例が
またあった。今回の入口フィルタは `product_finder.selling_shelves(price_min=2_000)`。
**売価2,000円以上しか探していなかった**ので、750円以下（販売手数料5%）の帯を
入口で全部捨てていた。500円に下げた。
**「固定費が高いから低単価は無理」という誤った前提から引いた線**が、入口に残っていた。
計算式を直したら、その式から導かれた定数も全部洗う。
