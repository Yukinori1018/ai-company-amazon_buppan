# 「未調査（batchZ3の範囲外）」の数字を値として拾う（2026-10-13・T-20260930-001）

## 何が起きたか
- criteria_check.py / dashin_order.py は実画面の列（過去1ヶ月の販売数・新品出品数）を `re.search(r'-?\d[\d,]*')` で数値化していた
- batchA〜Y の未調査行は「未調査（batchYの範囲外）」で数字が無く無害だった。**Z1 からバッチ名に数字が入り**、「未調査（batchZ3の範囲外）」→ 月販3・新品3 と読まれた
- 結果：Z の277行が全部「月販n<50」で基準NG。接触候補3社もここで落ちていた。エラーにならず、それらしい NG 理由が付くので気づきにくい

## 直し方
- `_shown_int()`：「未調査」「未確認」で始まる値は None（＝次の出典＝候補CSVへ回す）。数字を拾う関数に「値でない文字列」の入口判定を必ず付ける
- 検出のきっかけ：「接触候補なのに落ちた理由」を1件ずつ読んだこと。NG 理由の集計に急に新しい種類（月販 277）が出たら、まず新しく入った行と一致するか見る

## Z の反映手順（再利用）
1. `batchZn/xdup.py Zn` を全バッチ再実行（先に照合したバッチは後から完成したバッチを見ていない）。誤検知（社名の部分一致）は手で捨てる。直すのは recs.py → build.py --public
2. シート退避（gspread で get_all_values を json）→ `cd agent_output/T-20260930-001; python3 sync_ledger.py --dry-run --through=batchZn --recheck=recheck,recheck2`
3. 本番2回以上・出力とシート全セルが一致することを確認。criteria_check と dashin_order は sync_ledger の中で走る（単独実行は不要）
4. シートを読み直して行数・第1弾の社名集合を前後比較（集合で比べる。63_打診第1弾.csv は送信順の番号がずれるので bytes 比較は不一致になる）
5. 出品可否が未実測の接触候補は `--unchecked-out=64_出品可否_未判定_<tag>.csv` で書き出し、秘書へ（Chrome の実画面確認が要る）
