# 無人ジョブは「失敗を成功として記録する」ことが最大の欠陥（2026-08-31 / T-20260831-002）

マサル（シミュレーター）のプレモーテムで指摘され、実際にコードに存在していた欠陥。
**常駐・バッチ・夜間自走のコードを書くときは、まずこの観点でレビューすること。**

---

## 何が起きていたか

`scan_v14.py` の `keepa_get()` は API エラー時に `{}` を返していた。呼び出し側はこう動く。

    Finder が {} を返す → asins が空 → 「このシャードは掘り切った」と記録
    → 25シャード全部が掘り切り → stop_reason = "全シャードを掘り切りました"
    → STATUS.md / progress.json / FINISHED に **正常終了として**書かれる

つまり **APIキー失効・プラン切れ・Keepa の障害・ネットワーク断が、すべて
「母数を掘り尽くした」という成功として記録される**。ログには `API エラー` の行が出るが、
そのログは gitignore されていて誰も読まない。

12時間の実走行で API エラーは0件だった。
**＝このエラー処理は一度も本番で動いたことがなかった。**

## なぜ致命的か

社長は「尽きたら、尽きたと言って終了してよい」と指示している。
その報告が API 障害由来だと、**報告そのものが嘘になる。**
さらに3手先で、秘書が「枯渇したので抽出条件を広げましょう」と提案し、
プランナーが母集団の再設計に着手し、実際はキーが死んでいるだけなので何も直らない。
**数週間を溶かす。**

## 直し方（一般化）

「空だった」を1つの状態にしない。**必ず2つに割る。**

| 見えたもの | 意味 | やること |
|---|---|---|
| `totalResults` が整数で、件数が0 | **本当に無い** | 掘り切りとして記録してよい |
| HTTP 非200 / `payload.error` / 例外 / レスポンスが壊れている | **障害** | 掘り切り扱いにせず ALERT を書いて停止 |

    if not asins:
        if API.last_failed or not isinstance(total, int):
            write_alert(...); watch.stop("Finder が異常応答を返しました"); break
        exhausted.add(band)     # 正常な0件だけがここに来る

あわせて入れたもの:

- **直近100リクエストの成否をリングバッファで持ち、エラー率20%超で停止**（S3）
- **HTTP 402 は即停止**（契約が無効。リトライしても直らない。課金の話なので秘書へ差し戻す）
- **ALERT ファイルが存在する間はジョブを走らせない**。人が見て消すまで待つ
- 429（トークン切れ）は**正常なレート制御なのでエラーに数えない**

## 同じ形の欠陥を探すチェックリスト

無人で動くコードをレビューするとき、次を必ず見る。

1. **`except: pass` / `return {}` / `return []` が、正常系と同じ扱いになる経路はないか**
2. **「終わった」と書く直前で、終わった理由を区別しているか**
3. **例外が出る経路にタイムアウト（絶対上限）があるか**
   — 今回 `Budget.wait()` は `token_status()` が投げ続けると `starving_since` が
   一度も立たず、**永久に10秒スリープを繰り返していた**。「時間で止めない」は
   「無限に待ってよい」ではない
4. **生死の判定に PID を使っていないか** — 再利用されるので嘘をつく。心拍ファイルの mtime を使う
5. **異常の通知先が、人が必ず通る導線になっているか** — 誰も読まないログは無いのと同じ
