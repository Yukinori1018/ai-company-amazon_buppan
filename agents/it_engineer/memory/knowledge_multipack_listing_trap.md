# 卸の単価 × Amazon のケース売り ＝ 幻の利益（2026-08-31 / T-20260831-006）

**卸サイトと Amazon を JAN で突き合わせる仕事では、必ず踏む罠です。** 最初に読むこと。

## 何が起きたか

NETSEA×Keepa の利益スキャンで、最上位に並んだのがこれでした。

| 項目 | 値 |
|---|---|
| NETSEA の卸値 | 蒟蒻ゼリー **1個 117円**（税込） |
| Amazon の価格 | **6,798円** |
| 計算された利益率 | **77.1%**（純利益5,240円） |

実際の Amazon 出品名は
**「オリヒロ ぷるんと蒟蒻Plus グレープフルーツ味 130gパウチ×48本入」**。
**48本ぶりの売値に、1個ぶんの卸値**を突き合わせていました。

**同じ JAN に「単品」と「ケース」の ASIN がぶら下がるのは例外ではなく普通です。**
JAN は商品を指すのであって、**出品の売り方（何個で1注文か）を指しません。**

汚染度の実測: 「利益が出て回転もある」候補 **19件のうち12件（63%）が幻**でした。

## 直し方

**売値が N 個ぶんなら、原価も N 個ぶん。** 卸値に入数を掛けるだけです。

```python
wholesale_for_listing = candidate.wholesale_ex_tax * facts.pack_size
```

同じ例で、修正すると 利益率77.1% → **赤字**になります。

## 入数の読み方（ここが本体）

商品名から読みます。実データで確認した形:

| 商品名 | 入数 |
|---|---:|
| グロー球・ナツメ球お取り替えセット | 1 |
| 【3個セット】グロー球・ナツメ球セット | 3 |
| 変換名人 LAN 中継アダプタ LAN-BB ×10 | 10 |
| 130gパウチ**×48本入** | 48 |
| **(20gパウチ×12個)×12袋入** | **144** |

### 急所1: 入れ子の掛け算

最後の行が肝です。**内側だけ読むと12、外側だけでも12、正解は144。**
見つかった掛け算を **全部掛け合わせる** のが正しい。片方だけ読む実装は
「直したつもりで12倍間違えたまま」になります。

### 急所2: 寸法の `×` を掛け算と読まない

「抗菌まな板 **20×30cm**」を掛け算と読むと入数600になります。
`×N` を数えるのは **後ろに個/本/枚/袋などの助数詞が付くとき**、
または **行末の `×N`** に限ること。

### 急所3: 読めなかったら 1 を返す（安全側の向き）

入数を**大きく**見積もると原価が膨らみ、利益は**小さく**出ます。
小さく見積もる（＝儲かって見える）よりずっとまし。
ただし **「読めなかった＝単品」ではない**ので、
CSV には入数の列を出し、「発注前に現物を確認」と必ず添えること。

### 急所4: 導出できる値をキャッシュに依存させない

`pack_size` をフィールドとして JSONL に保存すると、**それ以前に書いた行は空**です。
空を1として読めば罠がそのまま復活します。
**商品名から毎回計算し直す**のが正解（`_dict_to_facts` でやっている）。

## もう一段一般化すると

**「同じ識別子で結んだ2つの数字が、同じ単位を指しているか」を必ず疑う。**

同種の事故はこれで3件目です。

| 事故 | 中身 |
|---|---|
| `COUNT_NEW` を出品者数と読んだ | オファー本数であって社数ではない（top100の35%汚染） |
| `stats.min` を期間内最安と読んだ | 記録上の最安で、期間と無関係 |
| **卸の単価 × ケースの売値** | **単位が「1個」と「48個」でズレていた** |

列名も識別子も**単位までは保証しません**。突き合わせる前に、
**両側が何を1単位としているか**を実データで確かめること。
