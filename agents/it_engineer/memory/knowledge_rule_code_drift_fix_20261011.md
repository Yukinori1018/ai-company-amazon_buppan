# 規定と実装のずれは本体で直す・複製を全部探す（T-20260920-003・2026-10-11）

## 何をしたか（再利用できる手順）
1. 閾値を `grep -rn "300_000\|0.05\|TARGET_MARGIN"` で**リポ全体＋agent_output**から探す。今回、同じ規定の実装が4箇所にあった：
   `score_20261004.velocity_of`／`sd_score.velocity_of`（agent_output の複製）／`fba_cost.grade`／`consistency._c_grade_rule`（検査側）
2. 複製は**本体に委譲**させる（sd_score は `score_20261004.velocity_of` を呼ぶだけにした）
3. 呼び出し側の「読み替え」暫定コード（ledger_refresh.reread_gates）は本体修正と同じ commit で撤去
4. テストは**規定の式そのもので期待値を作り、原価を1円刻みでスイープ**して全域一致を見る。「A/B/C が全部出る」ことも検査（縮退したスイープを防ぐ）
5. 書き込み前後の JSON で「人の行（確認者=カズヨ）が1セルも変わっていない」を照合

## 学び
- **暫定の読み替えで出した結果と、本体修正後の結果が NETSEA では完全一致した**＝読み替えは正しかった。差が出たのは**読み替えが届いていなかった口（SD）だけ**（33行 NO-GO→UNKNOWN、確認待ち +10）。読み替えは呼び出し口ごとに漏れる
- `ledger_refresh` は**既存の SD 行を `continue` で飛ばしていた**。「再実行すれば SD 行が確定する（冪等）」と前回報告していたが事実ではなかった。冪等を主張するなら「既存行が更新されるか」を件数で確かめる
- 「推定費目ありは最高 B」は天井。`estimated=` 引数で渡し、C を B に上げる効果はない（テストで固定）。検査側（consistency）は表から推定費目を読めないので「数字 A・表 B」は NG にしない（安全側の格下げ）
- consistency の既存テスト 5件失敗（other_costs の固定値ずれ）は**修正前から**。stash して確認してから報告する
- シートの「卸率(売価比)」列は % 書式で 32.9 が「3290.00%」と表示されている（既存の表示バグ・未修正）
