# 社長のこだわり: 「絞る」より「母数」— 2026-08-24 の方針転換

> 「トークンが続く限り、母数を取り続けて欲しい（ただし、暴走しないように定期的に中断は必要だと
> 思っている）。**ランキングが重要ではない。利益が取れる商品をいかに仕入れられるかの勝負なので、
> 利益率の高い商品を狙い撃ちするというのは愚策。どんどん、母数をとって、仕入れられそうな商品を
> リストアップしていって下さい。私はそのリストを見て、片っ端から連絡していくのみです。**
> その為には脳死で連絡をして、利益が確保出来る金額で仕入れられるのであれば、仕入れたいので、
> **想定仕入れ金額もリストにして欲しい**というのはそういう意味です。」

## 何を間違えていたか

こちらは v13 まで「**良い候補を100件に厳選する**」ことに労力を注いでいました。
消化月数でソートして top100 を作り、順位が36件入れ替わった、中央値15位動いた、と報告していた。
**社長はその順位を一度も使っていません。** 上から順に電話するだけなので、
100件しかないリストは「100件で電話が尽きる」という意味しか持たない。

## これから守ること

| 論点 | 誤り（v13まで） | 正しい（v14以降） |
|---|---|---|
| 成果物の形 | 厳選 top100 | **落とせるだけ長い候補プール** |
| フィルタの向き | 良いものを選び取る | **明らかに無理なものだけ落とす** |
| 順位付け | 消化月数でソートして順位を磨く | 列として出すだけ。**磨く労力は無駄** |
| 社長の1列 | ランク・利益率 | **想定仕入れ金額（上限）＝提示できる金額** |
| 単位 | 商品 | **メーカー**（社長はメーカーに連絡する） |
| 連絡先 | 触れていなかった | **メーカー名・検索リンクが無い行は価値が低い** |

### フィルタを外した実効果〔実測〕

条件を2つ緩めただけで母集団が **11,812 → 48,760（4.1倍）** になりました。

- `variationCount` 下限 1 → **0**（0 の商品が 97,484件あり、拾っていた 1〜3 の帯より多かった）
- レビュー件数 5〜300 を **撤廃**

**「絞る条件」を1つ足すたびに母数が数分の1になる**、という感覚を持っておくこと。
条件を足すときは、必ず Finder の `totalResults` を前後で測って、いくら捨てるのかを数字で示す。

## 「想定仕入れ金額」の意味を取り違えないこと

社長が欲しいのは **「メーカーにいくらまで出せると言えるか」** です。赤字ラインではない。

- 主列 `想定仕入れ金額(上限)` = **純利益率20%（会社KPI）を確保できる上限**
- 補助列 `赤字ライン(これ以上は赤字)` = 純利益0の上限
- 基準売価は **「現在の新品最安値」と「2026-02-23以降の最安値」の小さい方**（値下がりを織り込む保守側）

計算は `procure_limit.py` に切り出し、UI/ハーネスから独立させてテストしてある。
**「出せないときは None を返す。0 で埋めない」** — 0 だと「0円なら仕入れられる」と誤読される。

## 暴走防止はセットで要求されている

「母数を取り続けて」と「定期的に中断は必要」は**同じ発話の中にあります**。
長時間走るものを作ったら、**必ず自動停止条件と手動停止手段をセットで用意して報告する**こと。
片方だけ実装して「走らせました」と報告するのは、この社長の依頼を半分しか読めていない。
