# 発注セットを組むと、効くのは送料ではなく「卸の最小ロット」だった

初出: 2026-09-09 / T-20260909-002（初回発注セットの組成）
実装: `workspace/output/deliverables/T-20260909-002/order_set.py`
前提の書: `knowledge_netsea_order_set_economics.md`（あちらは送料の話。**こちらが上書きする論点**）

## 何を間違えかけたか

T-20260904-004 では「5万円で一番効くのは送料」と書いた。今回、実際に発注できる5SKU まで
絞り込んだら、**効いていたのは送料ではなく最小発注数（MOQ）だった。**

- 5件のうち **3件は、MOQ を1回買うだけで26〜47ヶ月分の在庫**になった
- 回転が遅い商品を選んだのではない。**卸が小さく売ってくれない**だけ
- 送料の差は500〜1,000円。MOQ が強いる余剰在庫はその何十倍もの拘束になる

**「送料無料ラインに届くか」を先に考えると、この問題が見えない。**
発注セットを組むときは、**MOQ ÷ 月販見込 を最初に出す。**

## 依頼の前提を実データで潰した3つ

チケットには「アイオロスが3SKU 持っている。1社にまとまれば送料1回で済む」とあった。
実際に `/tariffs` と MOQ を当てたら、3つとも違った。

1. **3SKU 同時は予算に入らない。** MOQ 合計が予算の1.5倍。同時に買えるのは最大2SKU
2. **その社は送料が定額・段階設定なし。**積んでも安くならない。集約の金銭的な得はほぼゼロ
3. **そもそも4SKU が組めない。**最も安い4件の MOQ を足すだけで予算超過。上限は3SKU

依頼文の前提は仮説であって事実ではない。**`/tariffs` と MOQ を引くまでは、
「1社にまとめれば得」と書かない。**

## 実装で気をつけたところ

- **NETSEA の1口と Amazon の1出品は別物。**ケース売り商品は 1出品 = 数口。
  MOQ は「入数の倍数」に切り上げる。端数の口は出品にならず在庫として死ぬ
- **送料は粗利から引く。**送料は原価。「粗利」と「送料を引いた手残り」を別の列にした
- **積み増しは「1円あたり手残りがいくら増えるか」で選ぶ。**
  こうすると送料無料ラインをまたぐ手が特別扱いなしで勝つ（条件分岐を書かなくていい）
- ~~回転が MOQ で既に上限超過の SKU は、超えたまま候補に残す。~~ **2026-09-12 に撤回。** 上限超過は候補から外し、落選理由として残すだけにする（`feedback_turnover_cap_is_a_hard_rule.md`）。以下の旧記述は履歴として残す。
  落とすと候補が消えるだけで判断材料にならない
  （`knowledge_flag_without_suppressing_the_number` と同じ）

## 「組み直せる形」の作り方

続報（生産終了チェックの13〜25位）が後から来ると分かっていたので、
**名簿を CSV（`pool.csv`）に外出しし、コードは名簿の `供給ステータス == 現行` だけを読む**形にした。
続報が来たら行を足して再実行するだけ。コードは触らない。

SKU が十数件のうちは組み合わせを総当たりで回して十分（YAGNI）。
50件を超えたら考え直す、とコメントに書いておく。

## 上流に返した論点

「回転検証＝通過」のフィルタ（`T-20260907-001/selection_rules.py`）は
**「売れているか」しか見ておらず、「MOQ が何ヶ月分か」を見ていない。**
`MOQ ÷ 月販見込 ≦ N ヶ月` を条件に足すべきだが、**N は社長が決める数字**なので
本チケットでは実装せず論点として置いた。実装を先にすると条件が既成事実になる。
