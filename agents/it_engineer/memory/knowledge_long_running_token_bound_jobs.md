# 数十時間かかるトークン律速ジョブの作法（2026-09-04 / T-20260904-004）

Keepa 検証 26,942件（約50時間）を回すために直した3つの欠陥と、その一般形。
**1日で終わらないジョブは、1日で終わるジョブとは別の作り方が要ります。**

---

## 欠陥1: 「残高が少ない」を「死んでいる」と読んだ

`TokenBudget.wait_if_needed()` はこう書いてありました。

```python
if self.left >= threshold:
    self.starved_since = None      # ← ここでしか解除されない
    return True
if self.starved_since is None:
    self.starved_since = time.time()
elif time.time() - self.starved_since > 60*60:
    return False                   # 停止
```

**トークン律速のジョブでは「待つ→撃つ→また待つ」が正常な定常状態**で、
`wait_if_needed()` の入口では残高はほぼ常にしきい値を下回ります。
つまり `starved_since` は一度立ったら**二度と解除されません**。

結果、2026-08-31 の実走は **620件を正常に処理しながら**
`!! トークンが 60 分回復しません。停止します` と記録して自己停止しました。
そして `run_stats.json` には「1,200件を評価した」と正常終了として残りました。
秘書はそれを読んで「トークン制約で7.9%しか進まなかった」と報告し、
**5日間、誰も原因がバグだと気づきませんでした。**

### 一般形

> **生存判定は「リソースが潤沢か」ではなく「仕事が1つでも進んだか」で行う。**

直し方は `note()`（＝APIが成功して課金が発生した地点）でタイマーを解除するだけ。

```python
if consumed > 0:
    self.starved_since = None      # トークンを実際に使えた＝生きている
```

これは `knowledge_unattended_job_must_not_lie`（PID を生死に使うな／心拍の mtime を見ろ）の
**同じ誤りのトークン版**です。今回も「残高」という*状態*を見て、*進捗*を見ていませんでした。
生死を測る量は、常に **単調増加する成果のカウンタ**であるべきです。

## 欠陥2: しきい値のラチェット

```python
self.min_before_batch = threshold   # threshold = max(実測レート×batch×1.3, min_before_batch)
```

`threshold` の計算に `min_before_batch` が入っているのに、その `min_before_batch` を
`threshold` で上書きしていました。**一方向にしか動きません。**
1回コストが跳ねると、以後ずっと余計に待ちます。50時間走ると効きます。

> **導出値を、その導出の入力に代入しない。** 毎回計算し直せば済みます。

## 欠陥3: 未着手を結果として書いた

`evaluate(candidate, facts_by_jan.get(jan, AmazonFacts(jan)))` — キャッシュに無い JAN に
空の事実を渡すと、判定は「Amazon未出品(同一JANのASINなし)」になります。
これは **「Keepa に聞いて無かった」** という意味であって、**「まだ聞いていない」** ではありません。

26,942件のうち500件しか検証していない段階でこの CSV を出すと、
残り26,442件が全部「Amazon に無い」と書かれた表が出来上がります。
後工程（出品可否の確認、コスト精査）は全部その嘘の上に乗ります。

> **無人ジョブの出力は「まだ見ていない」を必ず第3の値として持つ。**
> 空 or デフォルト値を「結果」として同じ列に混ぜてはいけない。

直し方: キャッシュにある JAN だけ評価し、`unverified_remaining` / `coverage_pct` を
統計に出す。CSV には出さない。

## 長時間ジョブは「短いジョブの繰り返し」に割る

1本の50時間プロセスにすると、**最後まで1度も成果物が出ません**。
`--new-limit N`（**キャッシュ済みは数えない**新規件数の上限）を足して、
「新規N件だけ処理して、その時点の全結果を書いて正常終了する」形にし、
シェルの for ループで回しました（`run_verify_loop.sh`）。

得られたもの:

- 約4.5時間ごとに CSV が最新化される（完走を待たずに中身を見られる）
- 落ちても損は1周ぶん
- ループ側で `run_stats.json` の `unverified_remaining` を読んで終了判定できる
  （**`ps` でもログの grep でもなく、実数で判定する**）
- `out/STOP` を置けば次の周の頭で止まる（人が介入できる導線）

コストは1周あたりの再計算1.5分だけでした（50時間に対して無視できる）。

**注意: `--keepa-limit` のような「先頭N件」型の上限では周回できません。**
毎回同じ先頭N件を選び、それが全部キャッシュ済みになって0件で終わります。
**上限は「未処理のうちN件」に掛けること。**

## 実測値（Keepa・2026-09-04）

| 項目 | 値 |
|---|---|
| 補充レート | **20トークン/分** = 1,200/時 = **28,800/日**（上限1,200・貯め込み不可） |
| `/product?code=` の実効コスト | **2.0〜2.6 トークン/件** |
| なぜ1件1トークンで済まないか | 1つの JAN に複数 ASIN がぶら下がり、**返った商品数ぶん**課金される |
| ヒットしなかった JAN | **0トークン**（Amazon に無いものの仕分けは実質タダ） |

**26,942件 ≒ 54,000〜70,000トークン ≒ 45〜58時間。**
Keepa は定額制（`knowledge_keepa_billing_is_flat_rate`）なので、**金で時間を買えません**。
「◯件を検証する」という依頼を受けたら、**着手前にこの割り算をして日数を宣言する**こと。

## 追記（2026-09-04 同日）— 前提が途中で変わっても、止めずに済む設計

経理から実測コストが出て、走行中（50時間ジョブの3%地点）に利益計算の前提が変わりました。
**Keepa の再取得は1件も要りませんでした。** 理由は1つだけです。

> **生データと導出値を分けてあった。**
> `keepa_facts.jsonl`（Keepa の事実）と `netsea_items.jsonl`（NETSEA の事実）だけを永続化し、
> 利益は毎回そこから**再計算**する。前提が変われば再計算すればよい。

もしキャッシュに「利益率」や「判定」を保存していたら、26,942件の再取得＝50時間のやり直しでした。
**外部APIから取った事実だけを保存し、そこから計算できるものは保存しない。** これが効きます。
（同じ設計は入数バグのときにも被害を「ASINの選択の質」だけに留めていました）

### ただし走行中のプロセスは古いコードを抱えている

import 済みなので、コードを直しても動いているプロセスには反映されません。
今回は**ループごと再起動**しました。周回に割ってあったので損失はこれだけ:

| 失ったトークン | 0（結果は1バッチごとに JSONL へ追記済み） |
| 失った検証件数 | 0（キャッシュから再開） |
| 掛かり直し | 段2 の再計算 1.5分 |

**「再起動しても損が数分で済む」状態を先に作っておくと、前提の変更を怖がらなくて済みます。**
逆に1本の長いプロセスにしていたら、ここで「止めるか、旧前提のまま50時間走らせるか」という
最悪の二択になっていました。

### 共有エンジンの既定値は変えない

`calc/profit.py` は他ツール（app.py・discovery）からも呼ばれています。
販売手数料の消費税（×1.1）を**既定値として**入れると、走行中の他ジョブの数字が黙って動きます。
`referral_fee_tax_rate: float = 0.0` を追加し、**新しい呼び出し側だけが明示的に渡す**形にしました。
既定を正しい値に寄せる作業は別チケットへ。
**共有ライブラリの既定値変更は「サイレントな全体書き換え」です。** 単独の変更として扱うこと。
