# スーパーデリバリー（SD）を「API が無いまま」読む型 — 2026-09-30 / T-20260920-003

## いちばんの学び: **道具の都合が探索範囲になっていた**

NETSEA だけを突合先にしていた理由は「Buyer API があるから機械で読める」でした。
カズヨの言葉を借りると **「道具の都合が、いつのまにか探索範囲になっていた」**。
SD は API が無いだけで、当社は既に利用開始済み・一部企業から卸価格の承認も得ています。

> 次に同じ形を踏まないための問い: **「この範囲は、目的から決めたのか、道具から決めたのか？」**
> 道具から決まっていたら、それは §3.1（目的は固定・条件は変数）の違反です。

## SD の実測（2026-09-30・非ログイン）

| 事実 | 出典 |
|---|---|
| 🔴 **JAN では検索できない。**実在する JAN でも0件 | `?word=<JAN>` を2本（実在 JAN・無意味語）で実測。件数が動く語では検索自体は効く |
| 🟢 **商品ページには卸価格以外が全部載っている**（非ログイン） | JAN・メーカー品番・SD品番・入り数（1セット◯点）・上代・出展企業名・**販売規制4項目**（消費者への直送／ネット販売／仕入れ前の販売／画像転載） |
| 卸価格だけが「会員のみ公開」 | しかも**非ログインでは承認済みと未承認が同じ表示**になる＝承認の有無は画面では判らない |
| URL の形 | 検索 `/p/do/psl/?word=` ／ 企業内検索 `/p/do/dpsl/<企業ID>/` ／ 商品 `/p/r/pd_p/<商品ID>/` ／ 規格の鍵は `SD品番 = <商品ID>S<枝番>` |
| robots.txt | `?word=` は許可。`as=` `br=` `ed=` `so=pricedown` `exw=` との組み合わせは Disallow。`/p/r/pd_p/` に禁止指定なし |
| 取得の速さ | 2秒間隔で **1語＝7リクエスト（検索1＋商品6）→ JAN 付き約9件**。＝ 約38 JAN/分 |

### JAN の直行便が無いと、向きの経済性が逆転する

| 向き | 実測 |
|---|---|
| **Amazon → SD**（売れている棚を SD で当てる） | 10件投げて **48リクエスト・一致 0件**。1件あたり最大8リクエスト（検索最大4＋商品最大4）・約16秒 |
| **SD → 索引**（仕入れ先起点で積む） | 1リクエストあたり JAN 約1.3件。**一度積めば次の突合は0リクエスト** |

**NETSEA（API あり）は Amazon 起点でよく、SD（API なし）は仕入れ先起点が正しい。**
「§3.3-9 で Amazon 起点が正」は **JAN で引ける仕入れ先に限った話**でした。条件の適用範囲を広げすぎていました。

### 0件だった理由は品揃えのズレ（これも事実）

Product Finder（月販50以上・2,000〜20,000円）が出す「売れている棚」は
**国内大手ブランドの化粧品・日用品**に偏ります。SD が強いのは生活雑貨・インテリア・ファッション雑貨。
＝ **重なりが小さい。**Amazon 側の抽出条件にカテゴリを入れないと、SD 突合は当たりません。

## 実装で効いた設計判断

1. **ログインが要る値は「呼び出し側が埋める口」にした。**`merge_wholesale(rows, filled)` に
   `{"13681795S1": {"卸価格": 620}}` を渡すだけ。カズヨがブラウザで見た値が入る。
   **社長にブラウザ操作を頼む設計にしない**（鉄則9）。認証を機械に持たせる設計にもしない。
2. **`parse_product()` はログイン済み HTML でもそのまま動く。**非ログインなら卸価格 None、
   ログイン済みなら金額を読む。**関数を2本に分けなかった**のが正解でした。
3. **卸価格は「卸価格」列（`class="stock-info"`）だけを見る。**行全体から `¥` を拾うと
   **上代を卸価格として読む**。上代は卸価格より高い＝**儲かる方向に間違える**。いちばん危ない向き。
4. **広すぎる検索から商品ページを開かない**（`TOO_BROAD_SUPPLIERS = 8`）。
   「ライオン」で25社93件・「La」で25社97件。先頭4枚を開くのは当てずっぽうで、2秒×4を捨てるだけ。
5. **取得上限に当たったら例外**（`Fetcher.CapReached`）。黙って0件を返すと
   「SD には無かった」と読み違えられる（9/30 に NETSEA アダプタで同型の事故があった）。
6. **`卸価格未承認` は UNKNOWN。NO-GO ではない。**申請すれば見えるので、落とす理由にしない。

## ⛔ 踏まない境界

- **卸価格の承認申請は実行しない**（出展企業への連絡＝CLAUDE.md §4.1）。
  `approval_requests()` は「誰に・なぜ」の一覧を作るだけ。承認はカズヨが取る。
- 画像は1枚も取らない（SD は「購入前の画像転載禁止」）。
- 規模は**人が手で見る範囲**（2秒間隔・回数上限）に留める。法務ハルオの 2026-09-14 判定
  （明示の禁止なし・手作業規模）に乗っている。**これより広く回すなら再判定が必要。**
- 卸価格・卸サイトの商品URL は**シートと `agent_output/` だけ**。リポは PUBLIC。

## 次の一手（カズヨのブラウザで1回試せば決まる）

**SD の会員側に「出展企業の商品データダウンロード」相当の機能があるか。**
あれば索引づくりは1回のダウンロードで済み、ページ取得を回す必要が消える。
無ければ、非ログイン索引を種語ベースで少しずつ積む今の型を続ける。

## 「画面に出ていない理由」を1つに決めつけない

最初の実装は「『会員のみ公開』の文字が無ければ卸価格未承認」と読んでいた。
ところが**品切れ（SOLD OUT）の行では卸価格の欄に SOLD OUT が入り、「会員のみ公開」が出ない**。
結果、非ログインの10件を「卸価格未承認」と書いていた（＝**未確認が未承認に化けた**）。

直し方は `parse_product(html, logged_in=False)` ── **文脈を呼び出し側に宣言させる**。

| 文脈 | 金額が無い | 意味 |
|---|---|---|
| 非ログイン | 当たり前 | **未確認** |
| ログイン済み | 情報 | **卸価格未承認**（申請すれば見える） |

同じ HTML でも、**どの文脈で取ったかで意味が変わる**。
パーサに文脈を推測させると、こういう化け方をする。

## 卸価格は「卸価格」列だけを見る

行全体から `¥` を拾うと**上代（メーカー希望小売価格）を卸価格として読む**。
上代は卸価格より高いので、**儲かる方向に間違える**。いちばん危ない向き。
`class="stock-info"` のセルに限定した。

## 非ログイン経路とログイン経路は「取れるもの」が違う

同日、SD 担当（別作業）はカズヨの実機でログイン後の SD を読み、
**SPA（Vue）でクライアント描画されるため生 HTML に商品が入らない**という結論を出していた。
私が読んだ**非ログインのページはサーバ描画**で、生 HTML に JAN まで入っている。
**「SD は HTML から読めない」は経路依存の事実**であって、SD 全体の性質ではない。
捨てずに足し合わせる（ログイン経路＝卸価格／非ログイン経路＝JAN・入り数・販売規制）。
