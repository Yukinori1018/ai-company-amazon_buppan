# salesRankDrops は販売ではなく「Keepa の観測回数」を測っている

T-20260906-002 / 2026-09-06 実測。**Keepa 由来の指標を使うときは必ずこれを思い出すこと。**

## 実測値（文房具・オフィス用品）

| 測定 | 値 |
|---|---|
| 30日の観測サンプル数 と `salesRankDrops30` の相関 | **0.991**（n=50） |
| 充填率 `drops30 ÷ (サンプル数-1)` の中央値 | **0.48**（最大 0.59） |
| `drops30` vs Amazon 公表の月間販売数 の順位相関 | **-0.334（符号が逆）** |
| 売れ筋ランク vs 同 順位相関 | **-0.519（符号は正しい）** |

充填率 0.5 は「ランダムに揺れる系列を離散サンプリングしたとき前回より下がっていた割合」。
つまりコイン投げ。**`salesRankDrops30 ≒ 0.5 × Keepa がその ASIN を見に行った回数`。**

平均で月 2,500 点規模が売れている群でも、ドロップ数の平均は 1 桁だった。
**観測回数で右側打ち切りされる**（月 40 回観測なら 39 が上限。実測の上限は 20 前後）。
月に 10 個売れる商品と 3,000 個売れる商品が同じ数字になる。

## なぜ「それらしく」見えてしまうのか

Keepa は照会の多い商品を高頻度で更新する。**観測頻度は人気度の代理**なので、
ドロップ数は「生きているか死んでいるか」の粗い判別には効いてしまう
（生存群の中央値 13 / 死亡疑い群 1）。**しかし量の推定と順位づけには一切使えない。**
「効いているように見える」ことが罠。

## バリエーション親子の落とし穴（閾値では絶対に直らない）

Amazon はバリエーションファミリーに**売れ筋ランキングを1本しか publish しない**。
Keepa はそれを全ての子 ASIN に付け替えて記録する。実測で、生産終了の子と現行の子の
**ランキング履歴の値が文字どおり同一**、レビュー件数も同一だった。

> **死んだ子 ASIN は、生きている兄弟の売上でドロップする。**

`parentAsin` / `variationCount` を見て親子を弾かない限り、生産終了品を検出できない。
**レビュー増分も共有されるので同じ影響を受ける。**

## 実務ルール

1. **`salesRankDrops` を回転の推定・降順ソートの軸に使わない。** 降順ソートは
   「売れ筋順」ではなく「Keepa 内での注目度順」になる。
2. **`ドロップ数 ÷ (セラー数+1)` を月販の推定として使わない。** 分子が販売量でない。
   これを分母にする「消化月数」も同じ欠陥を継承する。
3. **回転を測りたいなら `monthlySold`（Amazon 公表「過去1か月で〇点購入」）を第一に使う。**
   一次情報。ただし被覆率が帯依存（#1千未満 76% / #1千〜1万 58% / #1万〜3万 6% / #10万以下 0%）。
   **#1万位より下では「無い」が既定であり、無いこと自体は死亡の証拠にならない。**
4. **次点は売れ筋ランクそのもの。** ドロップ数より強く、取得コストは同じ（1 token）。
5. `outOfStockPercentage` が長期 100% なら**その期間の売上ゼロは断定できる**。ドロップ数より信頼できる。
