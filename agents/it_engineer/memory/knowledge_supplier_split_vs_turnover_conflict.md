# 「2社分散」と「回転N ヶ月以内」は、候補プールが薄いと両立しない（T-20260909-002）

## 結論

社長の3条件（① 1SKU を外す ② 2社以上に分散 ③ 全SKUの回転が N ヶ月以内）で
初回発注セットを組むと、**N=12 なら組めるが N=6 では組めない**。
予算の問題でも計算方法の問題でもなく、**候補プールに2社目が存在しない**。

## なぜそうなるか（構造）

回転が速い＝「最小ロット ÷ 月販見込」が小さい。これは2つの条件の積で、
**卸が小さいロットで売ってくれる** かつ **月に動く数がある** の両方が要る。
候補が薄いと、この条件を満たす SKU は特定の1社に固まる。

実際の内訳（現行と確認できた10SKU）:

| 制約 | 効き方 |
|---|---|
| 回転が速いが**最小ロット1回で予算超過** | 買えない。速さが役に立たない |
| 回転が速く予算内 | **1社に2件だけ**。ここが2社目を作れない原因 |
| 予算内だが回転が数十ヶ月 | 上限を緩めれば使えるが、在庫が寝る |

**「速くて安い2社目」が1件も無い**ので、②と③のどちらかを必ず捨てることになる。

## 実装として残したこと（`order_set.py`）

- `build_e2()` は条件を満たす案が無ければ **None を返す**。
  条件を緩めた案を代わりに返さない。**見せかけの案を作らない**
- 代わりに「②を捨てた場合」「③を捨てた場合」の最善案を一緒に返し、
  HTML 第1部B で3つ並べて差額と失うものを出す
- **社数を数えるときは「予算内で買える SKU」だけで数える。**
  最小ロットが予算を超える SKU を混ぜると「2社ある」と嘘になる（一度やらかしかけた）
- 社長が外した SKU は `EXCLUDED_ASINS` に**理由つきで残す**。候補から消さない
  （消すと半年後に「なぜ無いのか」が読めない）

## 上流への差し戻し（3回目の同じ指摘）

選定条件（T-20260907-001）に `最小ロット ÷ 月販見込 ≦ N ヶ月` が無い。
いまの条件は「売れているか」しか見ておらず、**買える単位で買えるか**を見ていない。
候補は激減するが、**減った先に残るのが本当に買える候補**。
N は社長が決める数字なので実装しない。
