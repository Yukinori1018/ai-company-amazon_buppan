# 台帳仕上げ（2026-10-11・T-20260920-003）

## 結論
- GO は 2→2。**判定の穴ではなく市場が律速**：NETSEA 1,758行 → 実売 PASS 699 → 取り分≥3 は 54 → 全 PASS 2。
  「GO を増やす」なら、取り分（月販÷(FBA＋自己発送＋1)）が効く棚＝競合が少ない棚を入口で探すのが先
- ただしその結論に辿り着く前に、**705行（35%）が一度も採点されていなかった**。集計の分母に入っていた「UNKNOWN」の
  大半は「判定保留」ではなく「データ無し」だった。**UNKNOWN の件数を見たら、まず中身の理由を集計する**

## 見つけたバグ（すべて静かに GO を隠す型）
1. 商品データ無しで build() が早期 return（「残トークン待ち」）→ 理由文だけ見ると普通の UNKNOWN に見える。
   手元の取得済み jsonl（resolve_raw・buybox_raw・kz_hist）で埋め、残りだけ Keepa（150件・450トークン）
2. 10/10 拡張行は JAN 空・購入先URL だけ → 索引を JAN で引けず卸値 UNKNOWN（382行）。
   **URL 末尾を JAN と決め打ちしない**（末尾が商品コードの店がある）。索引の supplier_url と完全一致で結合
3. 旧プールに SD 由来候補が混ざり、「NETSEA 側に無い ASIN を足す」処理が SD 行と二重に追記しかけた（250行）。
   「無ければ足す」の判定は経路を問わず台帳全体で見る
4. SD 経路だけ #9 にキーゾンを使っていなかった（表示だけ）。経路ごとに判定関数を通っているか確認する

## 人の行を守る
- 「人のキーゾン画面＝表示なし」を再現値で置き換えると GO 手前が少し解けるが、**人の行の上書き**になるので撤回。
  人の観測は「数が取れなかった」も観測。解くなら人が画面を見直す
- 照合は before/after JSON で「確認者=カズヨ の行の人の列」「カズヨ表記の消失」「社長入力欄（発注状況）」の3点を毎回数える
  （cmp スクリプトを使い回す：列ごとの変更件数を出す）
- シート読み戻しは USER_ENTERED で数値表記が変わる（71.0→71）ので、比較は書式を無視して行う
