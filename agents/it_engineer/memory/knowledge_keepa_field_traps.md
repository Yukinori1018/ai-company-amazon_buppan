# Keepa API フィールドの罠まとめ（実測・2026-08-24 / T-20260817-005）

`knowledge_keepa_count_new_is_not_seller_count.md` の姉妹メモ。
サトルの公式突合（T-20260824-001 `discrepancies.md` D1〜D4）を実装した際の実測知見。

> **通底する教訓: Keepa のフィールド名は「それっぽい名前」で、意味が名前とズレている。
> 名前で使うな。公式定義を読んで、必ず実データで裏を取れ。**

## 1. `stats.min` は「期間内の最安」ではない

- `stats.min[i]` = **これまでに記録された（ever registered）**最安値。**`stats` パラメータの期間と無関係**。
- 期間内の最安は **`stats.minInInterval[i]`**。
- 追跡10年の商品なら10年前の底値が「過去1年最安値」として入る。**安全側に偏るので損はしないが、説明と数字が食い違う。**

## 2. `csv[1]`（NEW）は 2026-02-23 に**意味が変わっている**

公式（product-object / changelog）:
- **2026-02-23 より前の記録** = 最安の**出品価格**（listing price）
- **2026-02-23 以降の記録** = 最安の**着地価格**（landing price ＝ 出品価格 + 送料）

→ **365日窓は必ず境界をまたぐ**（2026-08 時点）。`minInInterval` に替えるだけでは
「前半が送料抜き・後半が送料込みの混在データの最小値」になり、**直したつもりで誤りが残る**。

**採用した実装**: `csv[1]` から **境界以降に記録されたデータ点だけ**で最小値を自前計算（0トークン）。
`minInInterval`(365日) は `参考_365日最安(価格定義混在)` として残し、差を `窓差率%` 列で見せる。

**実測（4,002行）**: 窓差率 0%（振れなし）**60.1%** / 10%超 **832件（20.8%）**。
→ **一律の但し書きにせず、差の大きい行だけを人に見せられる**のがこの列の値打ち。

**検証して不採用にした案**: 「FBM が無い行は送料0だから365日窓を使ってよいのでは」
→ 実測すると **FBM無し群の一致率 59.1% ／ FBMあり群 58.5%** でほぼ同じ。
**FBM が無いことは何の保証にもならない**（不一致の主因は送料ではなく窓の狭まり）。
**推論のまま採用しなくてよかった典型。** 0トークンで測れることは必ず測る。

## 3. `stats.buyBoxPrice` は `offers` / `buybox` パラメータ無しでは**常に未設定**

- 付けずに叩くと、フォールバックの `current[1]`（NEW）が入る。
- しかも **NEW は送料込み、`buyBoxPrice` は送料別**（`buyBoxShipping` が別フィールド）。**基準が違う2つを1列に混ぜてしまう。**
- 対応は列名を実体に合わせる（`新品最安値(送料込)`）が0円。`buybox=1` は **+2トークン/件**。

## 4. `current_AMAZON = -1` は「Amazon が出品していない」ではない

- 「**今この瞬間 Amazon 価格が無い**」だけ。**一時在庫切れの本体を素通しする。**
- 正しいのは **`availabilityAmazon`**: **-1 = Amazon のオファーが存在しない** / 0=在庫あり / 1=予約 / 2=不明 / 3=入荷待ち / 4=出荷遅延。
- Finder にも `"availabilityAmazon": -1` を指定できる。
- **実測: 保存済み4,002行のうち20件がこれで新たに除外された。**

## 5. `offers` 無しリクエストでは「オファー系」が**一切返らない**

実測（raw 4,002件）:

| 項目 | 結果 |
|---|---|
| `csv[17]`（COUNT_REVIEWS 履歴） | **0 / 4,002件（存在しない）** |
| `stats.current[17]` | **4,002件すべて -1** |
| `csv[15]`（EXTRA_INFO_UPDATES） | **0 / 4,002件** |
| `stats.offerCountFBM` | `-2`（データ無し） |

→ **Finder の `current_COUNT_REVIEWS` フィルタは、こちらの手元データからは検証も鮮度測定もできない。**
　 測るには全件 `offers`（5.6トークン/件）が要る＝数時間コース。
　 **「レビュー件数を機械ふるいに使い続けるか」は方針判断に上げるべき論点。**

## 6. カウント系 `csv` は「0」ではなく **`-1`** で「無し」を表す

`csv[34] COUNT_NEW_FBA` / `csv[35] COUNT_NEW_FBM`（2026年3月追加）の最終値が **-1 = オファー無し**。
`== 0` で判定すると **1件もヒットしない**（実際に踏んだ）。分布を必ず先に見ること。
※ `csv[34]` は **Amazon のオファーを含む**点にも注意。

## 7. `variationCount_gte=1` は単品商品を落としている（D8・実測33トークン）

同一条件で `variationCount` だけ変えて `totalResults` を比較:

| 条件 | totalResults |
|---|---|
| 指定なし | 647,546 |
| **0〜0** | **97,484** |
| 1〜3（v1.3 現行） | 93,574 |

**`variationCount = 0` は実在し、現行が拾う 1〜3 の帯より多い。** v1.3 は97,484件を丸ごと落としている。
→ **母集団の設計＝方針の話なので、勝手に直さず社長／タケシへ**（本件は報告のみ）。

## 8. 設計上の教訓

- **列名が嘘をつくと、コードのバグより長生きする。** `出品者数` / `BuyBox価格` / `過去1年最安値` の
  3つの列名が3週間・2チケット・Googleシート2枚に伝播した。**実体に合わせて改名するのが最も安いバグ修正。**
- **判定の入口は1か所に。** 実セラー数は「段0のゲート」と「段1の分母」の両方に効くので、
  CSV を後から書き換える設計だと必ずズレる。**raw から全行を評価し直す（`--from-raw`・0トークン）に一本化した。**
- **raw を残しておいたおかげで、D1〜D4 の全修正が 0トークンで再計算できた。** この設計は必ず維持する。
