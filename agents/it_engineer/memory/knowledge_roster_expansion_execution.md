# 名簿拡張（0円の3経路）の実行手順と罠（T-20260929-001 / 2026-10-05）

09 §3-0 の「名簿拡張」を見積り（サトル 12）→ 法務（ハルオ 13）→ 実行（タカシ 14）で回した。
**次に同じ依頼（展示会の新しい回・補助金の新しい次・Keepa 条件の再緩和）が来たら、
`deliverables/T-20260929-001/14a_keepa_fetch.py` → `14b_build_roster.py --sheet` をそのまま回す。**

## 手順（再利用の型）

1. **見積りの中間データを再利用する。** サトルの 12_calc に、補助金PDFの解析済み行（mono_cls.json）・RX の社名（rx_pass.json）・
   Keepa のランク換算（rank_cut.json）・T20 の Finder 一覧（raw の finder_r12list）が既にあった。取り直さない
   （RX は 13 の条件で「1展1回」なので、取り直すと条件違反になる）
2. **Keepa の一覧は同じ選択式で組めばキャッシュに当たる**（keepa_io.finder は selection の sort_keys ハッシュ）。
   サトルの q1_sample.py と同じ W を組んで T20 は 0 token、T30 だけ新規 15本（約1,700 token）
3. 取得は `nohup python3 14a_keepa_fetch.py fetch &` → `nohup bash 14c_chain.sh <PID> &`。
   14c が ps の stat=T を見て SIGCONT、ログ90分停止で STALL を書き、段の完了ごとに 14b --bb --sheet を無人で回す
4. 14b は**全置換で冪等**。名寄せ → 上場照合 → シートの専用タブ → 実行記録の AUTO 欄（件数だけ）を書き換える。
   AUTO 欄は PUBLIC な md の中で `<!-- AUTO:14b ここから/ここまで -->` に挟む。自動同期（30分ごと）がそのまま commit する

## 罠と判断

- **社名の包含一致は使えない。** 両方5文字以上でも、88件中ほぼ全部が「クリエイト」「グローバル」「ファクトリー」
  のような一般語の誤一致だった。**完全一致（法人格・記号・括弧書きを落とす）＋法人番号**だけにした
- **英字社名でも「株式会社」が付けば国内。** ASCII 7割で海外判定するルールは、RX の「◯◯ japan 株式会社」を48社落としていた
- **「英字名 (カタカナ名)」の括弧内も上場照合に使う。** 括弧を落とす正規化だと、ブランド表記が英字の上場メーカーが素通りした。
  4文字以下の上場名は同名別会社が普通にいるので除外せず「要確認」
- **全置換で作り直すタブ（sync_ledger.py の「メーカー連絡先」）に手で行を足さない。** 次の同期で消える。
  窓口の無い社を混ぜると「送信順」の意味も崩れる → 同じシートに専用タブを作り、窓口を採った社から既存の流れで移す
- **補助金の採択一覧PDFの「事業計画名」欄には、認定支援機関名（税理士・金融機関・個人名）が混ざる。**
  列の区切りが崩れて plan の文字列に入る。13 は「保存しない」。出力には社名・法人番号・採択回・分類だけを書き、
  事業計画名は分類にだけ使って捨てる。**サトルの中間ファイルには残っている**（削除は §4.1 なので社長判断に回した）
- ③は消費財キーワードの一致で、非食品の目視適合は約3割。「業務用・設備・サービスだけの社」（畳・施設家具・システム開発…）
  を語で落とすと 508社減る。残りの精度は窓口採取の段階で落ちる前提で、行数と「見込める社数」を分けて報告した
- Finder の T30 一覧（今日取得）が T20 一覧（同日の数時間前）の部分集合にならない。索引の更新差。
  ①a/①b の区分は「①a の一覧にある か product の現在ランク ≤ R30」で決めた
- ①は ASIN の57%が既存社の商品で、残した社の約6割が既存と重複。純増は「残した社」の約4割になる
- **36,000 token の無人取得は、その間 Keepa キーを他チケットから奪う。** 報告に期間を必ず書く（knowledge_keepa_key_is_a_shared_resource）
