## 1. 一番大事な発見 — 詰まっているのは判定ではなく供給

53行まで台帳に積んで、**機械判定のみの GO は0件**だった。落ちた理由の内訳が効く。

## 2. §3.3 の5番目（メーカー直販）は「空振りの多い条件」ではない

実際に落ちた相手: 慧光 / Tillmulya 直営店 / APOLON JAPAN / WAQ(ワック) /
日東エフシー株式会社 / マーナ公式 アマゾン店 / SOLCION公式ストア / 【公式】ベビースマイルショップ。

# 追記2（2026-09-30 深夜）— 原価の計上漏れ：**項ではなく単位**

## 10. 根は「単位を揃える段が無かった」こと

カズヨが NETSEA の実画面で発見。**卸サイトは「1点あたり」で売り、Amazon は「N点セット」で売る。**

- B0DJNX12KZ：Amazon 側は **【2点セット】…×2点セット**、NETSEA 側は **1点920円（税抜）**
- 私の計算：原価1,012円/個 → 利益率33.3% → **GO**
- 正しい計算：原価 **2,024円/個** → 手残り **▲227円/個**（手数料15.4%×1.1）
  - 手数料を税抜のまま15.4%で見ると ▲181円（カズヨ算）、15%×1.1=16.5%で ▲214円。**どの読みでも赤字**
  - 損益分岐売価 **3,194円**に対し売価2,980円。**手数料をゼロにしても+278円**しか残らない
  - バリエーション7種すべて「2点セット」系で、単品版の ASIN は存在しない

**先に自分で見つけた「保管料206円の漏れ」と同じ型だが、質が違う。**

| | 何が足りなかったか | 症状 |
|---|---|---|
| 206円漏れ | 式の**項** | 薄利の行だけ符号が変わる（利益率30%では誤差） |
| 今回 | **単位** | **倍率で効く。利益率が丸ごと嘘になる**（33.3% → 赤字） |

**行動ルール**：**利益率が妙に良い行は、単価だけでなく「単位」も疑う。**
2つのデータソースを突き合わせるコードを書くときは、**突き合わせの前に単位を揃える段を必ず1つ置く**。
私は `unit_cost_incl`（税込の1個原価）という変数名を作った時点で「1個」の定義が
両側で同じだと暗黙に仮定していた。**変数名は単位を保証しない。**

## 11. 対処（`set_count.py`・純関数）

- 商品名から `【N点セット】` `×N点セット` `N個セット` `N枚組` `Nパック` `N袋` `セット数:Npcs` `ペアセット` を読む
- **読めないセット品は 1 と決め打たず None → UNKNOWN。** 1 にすると原価をN分の1に見誤る（fail-closed）
- 複数の読みが食い違ったら None（黙って片方を採らない）
- **`amazon_set_count`（原価の倍率）と `set_num`（発注数の丸め）を別概念として分離**。混ぜると同じ事故が再発する

**パーサで踏んだ「母数を静かに削る」型のバグ3件**（どれも None＝UNKNOWN に落ちて候補が消える）:

| 誤読 | 原因 |
|---|---|
| 「エレコム ゲーミング**ヘッドセット**」 | 複合語の中の「セット」 |
| 「木製 簡単**組立**」 | 「組」を助数詞なしでセット語に入れていた |
| 「**富士パックス**販売 万能包丁」 | **社名**の中の「パック」 |

→ **数字を伴わない「組」「パック」「set」はセット語に入れない。**
→ 除外語リスト（`NON_SET_WORDS`）を先に消してから数える。
→ 逆に「600粒」「420ml」「幅30×奥行30×高さ45cm」を個数に読まないよう、**助数詞は白リスト**で持つ。

## 12. 監査のしかた（今回やったこと。次も同じ手順で）

式を直したら**直した行だけでなく台帳の全行をパーサに通す**。

- GO 行のセット数 → **全件1（単品）**。同じ漏れによる誤 GO は他に無し
- セット数 N>1 または読めない行 → **19件。うち GO は0件**（すべて既に NO-GO / UNKNOWN）

「自分が直した15件だけ見て終わり」にすると、残り135行に同型が埋まったままになる。
**GO だけでなく「これから GO になりうる行」も見る。**

## 13. まだ見抜けないこと（正直に）

`set_count.py` が拾えるのは「**N点まとめ売り**」だけ。
**「中身の量が違う」型のずれは商品名では見抜けない**（卸は300粒・Amazon は600粒、卸は1L・Amazon は2L 等）。
B0015XNJMW（オリヒロ 玉葱エキス粒 **600粒**・利益率64.7%）は、まさにこれを疑うべき行。
**利益率が突出して良い行は、①終売 ②単価の誤読 ③単位の不一致 ④内容量の不一致 の4つを順に疑う。**
④は機械では無理なので、人が卸サイトと Amazon の両方で内容量を見る。

# 追記3（2026-09-30 深夜）— 「買う先があるか」を最初に問う／誤差幅の設計

## 14. 私の申し送りは1段浅かった

B0015XNJMW（オリヒロ 玉葱エキス粒 600粒・利益率64.7%）について、私は
「**内容量の不一致**を疑ってください」と申し送った。カズヨが実画面で見た結果、
原因は内容量ではなく **Amazon の JAN 2本が NETSEA に1件も存在しない＝仕入れが実在しない**だった。

§3.3 の3点（カート＝第三者・本体不在・キーゾン平均10個/月）は**通過していた**。
つまり「誰がカートを持っているか」をどれだけ厳密に見ても、**買う先が無ければ全部無意味**。

**判定の順番を間違えていた。**正しい第0問は「**買えるのか**」。
サインは台帳にちゃんと出ていた ── `購入先URL` が「未確認」。
**自分が「未確認」と書いた欄を、自分で読んでいなかった。**
「空欄にしない・不明なら未確認と書く」というルールを実装したのに、**その値を判定に使っていなかった。**

→ 一般形：**「未確認」と書く欄を作ったら、その欄が判定に効くようにする。**
   記録するだけの「未確認」は、後で誰も読まない。

## 15. 誤差幅の設計（固定値にしない）

カズヨから「手残りが誤差幅（±300円程度）を下回る行は UNKNOWN に落とす案を検討し、
閾値の理由を README に書け」と依頼。**固定値にしなかった。**

採用: **誤差幅 = 売価 × 7% + 200円**

| 項 | 根拠 |
|---|---|
| 売価 × 5% | BuyBox 価格の振れ（Keepa の値は取得時点のスナップショット） |
| 売価 × 1.4% | 販売手数料の読みの差（Keepa の率を税抜とみて ×1.1 するか否か） |
| ＋200円 | 保管料・納品送料・梱包資材の 206円は**商品台帳 L001 という1点の観測**。大型品では数倍になるので全額を誤差と見る |

**売価に比例させた理由**：固定±300円では**高額品を取りこぼし、低額品を通しすぎる**。
売価26,800円のソファカバーの手残り355円は誤差幅2,076円に埋もれるが、
3,900円の商品の手残り645円は誤差幅473円を超える。

**NO-GO ではなく UNKNOWN** にしたのは、人が実額（送料・サイズ区分・今の売価）を詰めれば GO になりうるから。
「読み切れていない」と「駄目だと分かった」を混ぜない、というこのパイプラインの芯と同じ。

## 16. ゲートを足すときは「早期 return より前か」を確認する

誤差幅ゲートを `economics_status` に入れたが、**月販不明の早期 return より後ろに置いたため空振りした**。
手残り28円の行がそのまま GO で出てきて、自分の出力を見て初めて気づいた。

→ **ゲートを足したら、必ず「効いたか」を実データで確認する。**テストが通っても順番は保証されない
（純関数のテストは「その関数を呼べば効く」ことしか示さない）。
→ 早期 return が並ぶ関数にゲートを足すときは、**関数の先頭から順に読んで挿入位置を決める**。

## 17. 台帳の列を増やさずに情報を人に届ける

カズヨから「内容量を台帳の列に書き出してほしい」。台帳は**32列固定**（条件付き書式が列位置に紐づく）で
「列を勝手に増減しない」が運用既定。→ **`判定理由` の先頭に `【内容量 600粒】`** として置いた。
既存133行にも埋め戻した（Keepa トークン0・人が確認した3行は触らず）。
**制約と依頼が衝突したら、依頼の目的（人の目に入る）を満たす別の置き場を探す。**列を増やす判断は人に残す。

## 18. GO が5件に絞れた内訳（歩留まりの実感）

GO 14件 → **5件**。落ちたのは NO-GO ではなく **UNKNOWN**（人が詰めれば復活しうる）。

| 落ちた理由 | 件数 |
|---|---|
| `購入先URL` 未確認 | 3件 |
| 手残りが誤差幅未満 | 5件 |
| 要期限管理＋仕入れ不存在 | 1件 |

**ゲートを足すほど GO は減る。**それでいい。9/30 に出した14件のうち9件は、
「判定できていないもの」を GO と呼んでいただけだった。
ただし **GO 5件のうち4件が同じ購入元（レディースバッグ1社）**なので、
分散という別の観点で人に判断を仰ぐ必要がある。**機械判定を通った集合が偏っていないかも見る。**

# 追記6（2026-09-30）— アダプタの修正と、**「下流に嘘を配る」型の不具合**

## 28. `adapters/netsea.py` の JAN 照会は「必ず失敗 → 黙ってサンプル」だった

| 直したもの | 内容 |
|---|---|
| `_MAX_SUPPLIER_IDS_PER_REQUEST` | **10 → 1**（実測: 1件=200 / 3件以上=`400 too many supplier_ids.`）。10件で投げていたので**全バッチ400で必ず失敗** |
| 失敗時のフォールバック | **削除**。`NetseaError` を投げる。「エラーで取れなかった」と「本当に0件」を混ぜない |
| `_approved_supplier_ids()` | ページング漏れ **100社 → 221社**。`list_suppliers()` は2026-08-31に直っていたが、こちらが取り残されていた |
| キーワード検索のサンプル | `last_error` に「サンプルです」と明記（`is_sample` だけでは見落とす） |

**検証**：実在 JAN `4953980278777` が **0件 → 1件**（920円税抜・不二貿易株式会社・`is_sample=False`）。
カズヨが実画面で見た卸単価と一致。テストは 192 passed（旧契約を固定していた5本を書き換え）。

**影響を受けていた過去の結論（下流に配られた嘘）**
- 🔴 `T-20260804-001/SOURCE.md`「**NETSEA から戻ってきた値はゼロ件**（全行が NETSEA該当なし＝
  実卸はメーカー見積必要）」は**この不具合によるもので根拠にならない**
- `discovery/pipeline.py` の JAN 突合（Yahoo+楽天+NETSEA 合成）で NETSEA は常に無言だった
  → 「卸で最安が取れない」系の結論は NETSEA を過小評価している
- `list_supplier_items[_raw]` を使う経路は**影響なし**
- **捏造価格は流れていない**（サンプルの JAN は `49000000000xx` の placeholder で実在 JAN と
  衝突しないため、返っていたのは0件）。**ここは幸運**で、設計の安全性ではない

## 29. 一般化：**失敗をサンプルで埋めるフォールバックは「親切」ではなく害**

このアダプタは「本番に行けないときデモが回るように」サンプルへ落ちる設計だった。
デモのためには正しいが、**仕入れ値の取得経路に同じ道を通したのが誤り**。
呼び出し側は `last_error` を見ないと嘘を見分けられず、**見ない実装が普通**。

守ること:
- **「デモ用に嘘を返す」と「本番で値を返す」を同じ関数にしない。**
  サンプルが欲しいなら `force_sample=True` のように**呼び出し側が明示**する。
- 失敗は**例外**で返す。`(空リスト, last_error)` は「0件」と区別できない。
- 共有ライブラリを直すときは、**テストが旧契約を固定していないか**を先に見る。
  今回は5本が「401ならサンプルが返る」ことを assert していた。**テストが不具合を守っていた。**

## 30. 「0件」を結論にする前に、当たるはずの入力で検算する（2回目）

私は B案の突合で「250件中0件」を見て、一度「Amazon の売れている棚は NETSEA に無い」と
読み違えかけた。救ったのは **NETSEA に実在すると分かっている JAN で検算したこと**。

**今回は検索語ではなくリクエストの組み立て**だった。

→ **「0件」を見たら、まず自分の経路を疑う。**
　 当たるはずの入力（golden case）を1つ常備しておくと、30秒で切り分けられる。
