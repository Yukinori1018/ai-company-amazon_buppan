# ZH/ZI のシート同期と「入口(c) は FBA数が未確認になる」穴（T-20260930-001・2026-10-17 早朝・無人）

## 何が起きたか
- 入口(c)（カート自己発送）の ZH/ZI 接触候補 47社のうち **31社が「基準未確認：FBA数」で第1弾にも第2弾にも入らなかった**（dry-run 1回目）
- 原因：基準3（FBA≥1）の値の取り方が「候補CSV（10_メーカー候補_完全版）→ Keepa キャッシュ offerCountFBA → カートが FBA なら下限1」の3段だけ。
  入口(c) は ①10_ に載っていない ②product を offers なしで取るので offerCountFBA=-2 ③カートが自己発送なので下限1も効かない、の3つが同時に外れる
- 事実は手元にあった：`11d_追加候補_入口c.csv` の「代表のFBA数」（Finder 条件 offerCountFBA≥1 で取った一覧の値）。**load_candidates が 11*_追加候補 を読んでいなかった**だけ
- 直し方：sync_ledger.py に `load_entry_fba()`（11_／11c_／11d_ の代表のFBA数）を足し、**候補CSVにも Keepa にも値が無い行だけ**埋める。既に値がある行の判定は変えない
- 効果（dry-run 比較）：接触候補の基準未確認 33→0、第1弾 145→147、第2弾 590→617。接触候補以外の既存行でも 基準チェック「未確認→OK」が約500行動いた（判定・打診順は変わらない）

## 型（次に入口を足すとき）
- **新しい入口を作ったら、criteria_check の6基準それぞれについて「その入口の行はどこから値を取るか」を1回数える。**入口(b) は「カートが FBA」で救われていたので穴が見えなかった。入口(c) で初めて3段が全部外れた
- 「未確認」が急に増えたら、データが無いのではなく**読む口が無い**のを先に疑う（§3.3-19「自分のコードを疑う」の同型）

## 手順（ZF/ZG と同じ型＋α）
1. recheck は `24_連絡先_recheck_20261017b.csv`（同日2本目は日付の後ろに英字。並び (日付, タグ) で b が後）
2. .bak（40・63・sync_ledger.py）→ 40_profit_cols.py --offline（既存差分0・+250）→ backup.py で全タブ FORMULA 退避
3. dry-run の差し替えが「前回 409 ＋ 新規9」＝418 になるか
4. 本番2回とシート取得2回を1本のコマンドでバックグラウンド実行（約10分）
5. 入力行数が batch より少ない分（ZH 96→89・ZI 154→128）は社名の重複で落ちた行。全部「重複」判定の行かを確かめる

## 注意
- ZF の確認時刻の訂正（03:40→02:55）はシートに出ない（シートは確認日 MM/DD だけ）。シートの JSON を grep して 03:40 が0件なのを確かめてから「時刻はシートに無い」と書く
