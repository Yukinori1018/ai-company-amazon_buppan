# Keepa の COUNT_NEW は「出品者数」ではない（再発必至の罠 / 2026-08-24 社長指摘）

> 一行で: **`current_COUNT_NEW` は新品オファーの本数であって、distinct seller の数ではない。**
> 1社が FBA と FBM の両方に出しただけで 2 になる。「相乗り2社」と読んだら間違い。

## 何が起きたか

T-20260817-005（v1.3 メーカー仕入れスキャン）と T-20260804-001（メーカー台帳）で、
**「出品者数 2〜6」という条件を `current_COUNT_NEW` で実装**していた。
社長が Keepa 実画面で ASIN `B0DWMPV656`（seathestars 小型洗濯機）を見て、
「セラー数は1（他の出品者がいない）。なぜこれがリストに出るのか」と指摘。

実測（`/product?asin=...&offers=20`）:

| 項目 | 値 |
|---|---|
| `stats.current[11]`（COUNT_NEW） | **2** |
| `stats.offerCountFBA` / `offerCountFBM` | 1 / 1 |
| `liveOffersOrder` | `[5, 2]` = 生存オファー2本 |
| そのオファーの `sellerId` | **両方とも `A37CWH39G3AT5D`** |
| セラー名（`/seller`） | `seathestars(適格請求書発行事業者)T9240001017589` |
| そのセラーの自社ブランド | `ｓｅａ　ｔｈｅ　ｓｔａｒｓ`（647商品） |

→ **実セラー数 1。ブランド所有者の直販独占。** COUNT_NEW=2 は
「同じセラーが FBA 用と FBM 用に2本オファーを出している」だけだった。

## なぜ致命的か（仕様の意図から外れる）

v1.3 が「出品者2〜6」を課した意図は **「そのメーカーが実際に卸している証拠」** を取ること。
オファーが2本あることではない。**メーカー直販の独占リスティングは、むしろ
卸してもらえない可能性が最も高い＝真っ先に外したい候補**であり、
条件の意図とちょうど正反対のものを通していた。

## 汚染度（実測）

| 母集団 | 実セラー数 < 2 |
|---|---|
| v1.3 top100（全件実測） | **35 / 100（35%）** |
| v1.3 GO 母集団（n=150 サンプル） | **58 / 150（38.7%）** |
| T-20260804-001 criteria_ok 7,764行のうち `rival_sellers==2` | 3,788行（48.8%）＝ 最も危ない帯 |

機序の内訳（top100 の35件・同時刻ベース）:
- **同一セラーが FBA+FBM に二重出品: 23件**（＝主犯）
- COUNT_NEW 系列の更新ラグ（生存オファーは1本なのに COUNT_NEW=2 のまま）: 8件
- 生存新品オファー 0（実質リスティング死亡）: 1件
- 3日で本当に1社に減った: 3件

## 正しい数え方（結論）

**`GET /product?asin=...&offers=20` を叩き、次の3段で数える。**

1. `liveOffersOrder`（生存オファーの index 配列）で **生きているオファーだけ**に絞る
   — `offers` 配列には数か月前に消えたオファーがそのまま残っている（`lastSeen` が古い）
2. `condition == 1`（新品）だけ残す — 中古セラー（例: `Amazonアウトレット`）を混ぜない
3. `sellerId` の **distinct 数**を数える

使ってはいけない代理変数:
- `current_COUNT_NEW` / `csv[11]` — オファー数。しかも**独自の更新頻度を持つ時系列**で、
  `lastUpdate` が数分前でも COUNT_NEW の最終データ点は数日〜数か月前ということがある
- `stats.offerCountFBA + offerCountFBM` — Keepa UI の「Buy Box 対象オファー数」。これもオファー数
- `stats.buyBoxSellerId` — 1社しか分からない

実装は `workspace/output/deliverables/T-20260817-005/seller_count.py`（`seller_profile()`）。

## トークン単価（実測 2026-08-24 / domain=5）

| リクエスト | 単価 |
|---|---|
| `/product`（stats 付き・offers なし） | **1 トークン/件** |
| `/product?offers=20` | **約5.6 トークン/件**（100件=553、150件=956） |
| `/seller`（100 ID まで1リクエスト） | **1 トークン/ID** |
| `/token`（残高確認） | 0 |

→ **offers は素の product の約6倍。全件に掛けてはいけない。**
`scan_v13.py` は二段構えにした:
段1・段2 は 1トークン/件の素の product で回し、**通った行だけ**に offers を掛ける。
補充は 20/分なので、offers 100件で約35分かかる（＝完全に補充律速）。

## 設計上の教訓（次に同じ穴を掘らないために）

1. **列名が嘘をつくと、コードのバグより長生きする。** `出品者数` という列名が
   3週間・2チケット・Googleシート2枚に伝播した。列名は `新品オファー数` に改名した。
   **API のフィールドを「◯◯の代理」と呼んで列名に採用するときは、代理として妥当か必ず実測する。**
2. **根本原因は共有アダプタにある**: `workspace/output/agent_output/T-20260521-005/code/adapters/amazon_data.py`
   の `_pick_offer_count()` に「新品出品オファー数（相乗り出品者数の代理）」と書いてあり、
   `AmazonProduct.offer_count` を使う全パイプラインが同じ誤りを引き継いでいる。
3. **社長は Keepa 実画面を見ている。** 画面の数字（Buy Box 対象オファー数／販売者／%獲得）と
   こちらの CSV の列が食い違ったら、**こちらが間違っている前提で調べる**のが早い。
