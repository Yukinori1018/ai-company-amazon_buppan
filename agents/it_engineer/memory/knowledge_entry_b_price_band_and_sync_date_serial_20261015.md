  **2,200 以上は既に取得済みなので帯で切る**（上限を置かないと既取得の 2万件と被って Finder の 10,000件上限に当たる）

- token の配分：product 1/ASIN と代表のカート保持者 3/社を同じ締め切りで分け合う。**先に product を締め切り（今回 00:05）で止め、残りをカート保持者に回す**。夜間タスク（02:00）と Keepa キーを共有するので締め切り 01:25

## 2. シート同期が2回目に落ちた（接触日の日付シリアル）

- 症状：sync_ledger.py の1回目は成功、2回目に `AttributeError: 'int' object has no attribute 'strip'`（OWNER_COLS の保持処理）
- 原因：同日夕方の送信反映で「接触日=2026-10-15」が文字列で入っていた。sync は USER_ENTERED で書くので、**1回目の書き込みで日付になり、FORMULA で読むと 46310（int）**になる
- 直し：`owner_cell()` で社長入力列を文字列に戻す（接触日のシリアルは ISO 日付へ）。owner 列の前後一致は「代表商品URL キーで owner_cell 同士を比較」で0件を確認
- 教訓：**「dry-run→本番→本番」の3回目までやる意味はここにある**。1回目の書き込みが値の型を変え、2回目で初めて落ちる。2回目を省いていたら、次に誰かが同期したときに止まっていた
- ついでの罠：bash の `> /tmp/../$PWD/x.log` は PWD に空白があると ambiguous redirect でコマンド自体が走らない。ログは相対パスで書く

## 3. 実画面の証跡（64b）を合流する型

- 64b（カズヨの実画面一覧）から 62b_出品可否_<組>.csv（ASIN, 新品の出品可否=OK, 出品許可の要否=要/不要…）と 65_カート確認_<組>.csv を作る。「申請で開く」＝要＝第2弾、「可」＝不要＝第1弾候補
- 本人カート疑いは 65 の「注意」に「疑い」を含めると sync が「要確認」に落とす
- **64b に月販の列が無いときは月販を書き換えない**（以前の sync は空欄を「表示なし（月50個未満）」と書いていた＝見ていない値を事実にする）。10/15 に修正
- 結果の読み方：第1弾 143→116 の内訳は「送信済で外れた32」と「出品可で入った5」。**送信済の除外を合流の効果と混ぜて報告しない**
- 流通形態の機械分類は備考の語（カート保持店が「酒類卸」）で「酒類」に当たる誤りがある（沖縄製粉）。直すのは秘書判断（70_秘書判断_*）

## 5. 秘書判断で流通形態の誤分類を解く（10/16 01:35）
- 「後回し解除」は判定列を「接触候補」に戻すだけで、**dashin_order.classify は流通形態（酒類）を別に見る**ので対象外のまま残る。判定を戻しても区分は動かない
- apply_decisions に「残す＋理由に酒類＋流通形態が酒類」の分岐を足し、流通形態そのものを書き換えた（元の値は括弧で残す）。秘書判断の語（残す／後回し／後回し解除／除外）ごとに、どの列に効くかを先に確かめること
- 「保留」は判定語「後回し」で作る（出品できる／許可が必要 の行だけ保留になる）
