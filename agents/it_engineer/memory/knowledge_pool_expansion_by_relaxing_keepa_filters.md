# 母数を広げたときの社数を、層別 HT で加法的に測る（2026-09-21 / T-20260920-005 S-1）

「条件を緩めたら送信先は何社増えるか」を Keepa で実測する型。
**S-A（[[knowledge_counting_makers_under_token_cap]]）が『現行条件で何社か』なら、これは『緩めたら何社増えるか』。**

## 設計の肝: 累積ルールを測らず、増分の層を測る

緩和案（ランク5万/10万/20万/30万 × FBA 2人以上/1人以上）を**入れ子のルールとして別々に測ると、
ブランド件数 k をルートごとに引き直す必要があり token が4倍になる**。

代わりに、重ならない**層（バンド）**に切って、層ごとに「その層で**初めて**現れる社の数」を数える。

    新規社数_h = Σ_{i∈標本_h, ストアなし} w_h × 1{lower_i = 0} / own_i

- `own` = その層の条件でそのブランドを Finder に引いた件数（HT の分母）
- `lower` = **一段内側（より厳しい）条件**での件数。0 なら「今の名簿にいない社」＝純増
- 1ブランドにつき **2クエリ（22 token）だけ**で、純増と分母が同時に取れる
- 層の和がそのまま累積ルールの母数になる（加法的）＝「ランク帯別の分布」もこれ1本で出る

## 巨大な層は一覧を取らずランク値でクラスタ標本

FBA=1ちょうど・ランク5万以内は **162万 ASIN**（全件一覧なら16,000 token）。
そこで**ランク値 r を乱数で選び `current_SALES=[r,r]` で15ルートを一気に引く**（11 token で ≈32 ASIN）。

- ランク値は全 ASIN に等確率で割り当たる → 各 ASIN の抽出確率は等しい＝不偏
- 重みは `w = バンドのランク値数 ÷ 窓の本数`（N を知らなくてよい）
- バリエーション兄弟は同じランクを共有するので**家族ごと入るクラスタ標本**。窓は丸ごと採るか捨てるかにする（途中で切ると抽出確率が壊れる）
- 分散は窓単位のブートストラップで見る

## フィールドの事実（2026-09-21・domain=5 実測）

- `offerCountFBA_lte` は Finder で有効。`gte=1 & lte=1` で「FBA ちょうど1本」= 1,618,900（`gte=1` の 1,699,900 − `gte=2` の 80,800 と一致）。**列名から推測せず引き算で突き合わせて確かめた**
- `offerCountFBA_gte=999999` で0件＝綴りが効いていることの確認（Finder は知らないキーを黙って無視する）
- **ホーム＆キッチンは `current_SALES` がランク5万あたりで尽きる**（全ランクで41,200件しかない）。
  ランク緩和で1件も増えない。ルート rank の目盛りはルートごとに別物で、**「5万位以内」の意味はカテゴリによって違う**
- 車＆バイクはランク5万超に11万件あるが、本体なし＋FBA2以上まで掛けるとほぼ0になる
