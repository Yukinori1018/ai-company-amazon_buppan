# Keepa の API キーは全チケット共有の1本。無人ジョブが残っていると他の依頼が丸ごと止まる（2026-10-01 / T-20260920-003）

## 一行で

**トークン残高が増えないときは、まず `ps -eo pid,etime,command | grep python` を打つこと。**
補充は 20/分しかなく、**別チケットの無人ジョブが同じキーで走っていれば、こちらは何もできません。**

## 実際に起きたこと

T-20260920-003（買う候補リスト）の段Bを走らせたら、残高が **121 → 81 → 41 → 0** と
**減り続けた**。自分のジョブは待機中で1トークンも使っていない。

- 最初に疑ったのは launchd の常駐ジョブ（`com.aicompany.amazon-buppan.list-builder`）。
  → **STOP ファイルがあって停止中**。無関係だった（`state/always_on.log` を見れば5秒で分かる）
- 次に疑ったのは Keepa のデータクォータ（2026-03 改定）。
  → `/token` を叩いて `tokenFlowReduction: 0.0`・`refillRate: 20`。**補充は正常**
- 真因は **別チケットの `20_fetch.py --max 9756`**（T-20260930-001）が同じ API キーで
  100件/105トークン単位の取得を**6時間ぶん**回し続けていたこと。`ps` 1回で見つかった

## 教訓

1. **「残高が増えない」は API の異常ではなく、たいてい自社の別ジョブ。**
   原因を語る前に原因を確かめる（CLAUDE.md §3.3-10）。`ps` → `launchctl list` → `/token` の順。
2. **トークンを使う無人ジョブは、他のチケットの着手不能を意味する。**
   見積りを出すときは「自分の消費」ではなく「**その時間、他の誰も Keepa を使えない**」と書く。
3. **先に取りに行く小細工は解決ではない。**
   相手が105トークン貯まるまで待つ設計なら、自分は40で取りに行けば勝てる。実際そうしたが、
   これは**2つの自社ジョブが互いを飢えさせている**状態で、どちらを先に通すかは人が決めるべき。
   **小細工で押し通さず、秘書に判定を上げること。**
4. **長時間ジョブは「残り時間」と「他がどれだけ待つか」をログに書くべき。**
   `token 待ち: 残 21 / 必要 105` は自分の都合しか書いていない。

## 次に同じ状況になったら

- 競合ジョブが**再開可能**か確認する（`20_fetch.py` は `raw/order.json` で順序を固定していて再開可能）
- 再開可能なら「45分だけ止めて先にこちらを通す」を**推奨案として秘書に出す**。自分で止めない
- 自分のジョブは**安い段（1トークン/ASIN）だけ先に通す**。高い段（offers 6.5/ASIN）は後回しにできる
