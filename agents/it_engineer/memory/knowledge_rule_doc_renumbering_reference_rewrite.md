# 規則文書の番号を付け替えたときの参照書き換え（T-20261027-001・2026-10-27）

CLAUDE.md を §4.1 型から §A3 型に付け替えた差し替えで、旧番号の参照 241件（A1）を書き換えた手順。次に CLAUDE.md や docs/rules の番号を動かすときに同じ型で回せる。

## 手順（この順で）
1. **基準テストを先に流す。**`test_consistency.py` は差し替え前から 117/122（失敗5件）だった。先に見ておかないと、自分が壊したかどうか区別できない。
2. **参照一覧を JSON にして、今の行の中身を並べて全行を目で見る。**一覧の行番号は生成時のもの。行の中身に旧番号が実在するかを先に検算する（今回 MISS 0）。
3. **行ごとに「書き換える／残す（理由）」を決める。**`§5`・`§6`・`§2` などの短い番号の大半は、他文書（法務判定書・memory・その文書自身）の節番号だった。「推定」の行は全部目で見る。
4. **置換は正規表現で末尾を止める。**`§3.3-1` が `§3.3-17` に当たらないよう `(?![0-9.\-])`。`§3.5` は `§3.5 #18` を先に処理する。同じ行に並ぶ組（`§3.3-1・§3.3-5・§3.3-22`）は先に組ごと置換して重複を潰す。
5. **dry-run → 書き換えた行に旧番号が残っていないか → 本番。**ファイル単位の変更行数を git diff と突き合わせる（今回、.gitignore 対象の `_inbox_社長共有/` 5本が差として出た＝手元だけ変わってコミットに入らない）。
6. **新しい文書に節番号が実在するかを機械で確かめる。**見出し（`## §X`・`### §X1`）と箇条ラベル（`- §C1`）を集合にし、`§F2 #N` は表の項目番号の範囲で判定。`CLAUDE.md §X「…」` の引用は、本文に同じ文字列があるかも見る。
7. **漏えい検査は書き換えた全ファイルに当てる。**手順書31 の代表値パターン（`git grep -F -f`）と、source-terms-guard に Write と同じ入力を渡す。

## 気づき
- **出所ガードは「ラベルの直後の数字」で止める。**記録を書く文で「最小発注数（…10点の…）」と書いたら止められた。会員限定の値でなくても止まる。名前を変えて逃げず、数字を書かない言い方に直す（CLAUDE.md §C9）。
- **番号だけ替えると嘘になる行がある。**「旧 §3.5 の表に OR が欠けていた」という当時の所見は、新番号にすると事実と違う文になる。こういう行は残して記録する。
- **文字列が「目印」として使われている行は触らない。**buppan-todo は「§4.1」の文字列で赤バッジを付けている。データと一緒に変えないと壊れる。
- **テンプレ機能は旧構造に依存している。**子会社化（create-subsidiary）は旧 CLAUDE.md の `{{ }}` と §7 が前提。新版には無い。YAGNI で今は直さず、残課題として返した。
- `publish_31.sh check` は作業ブランチ名で段0を止める作り。ブランチ切り替え後は 1-a・1-c のコマンドを直接流す。
