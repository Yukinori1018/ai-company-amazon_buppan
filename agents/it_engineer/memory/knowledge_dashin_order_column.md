# 打診順列の付け方と「基準は確保」の検算（T-20260930-001・2026-10-10）

## 依頼の型
社長「そのまま出品できる社から打診。ただし基準は確保」→ シートに区分列（第1弾/第2弾/下書き済/対象外（理由））を足し、第1弾の全行を基準項目ごとに機械で検算する。

## 手順（再利用可）
1. 判定ロジックは独立モジュール（deliverables/T-20260930-001/dashin_order.py）。sync_ledger.py は列追加＋移行分岐（前の列数→+1）を1つ足すだけ
2. 区分は「最初に当たった理由1つ」で書く（判定→連絡先→出品不可→基準NG/未確認→出品可否未実測→酒類→検算NG）
3. 接触ステータス（社長入力列）はシートの現在値を引き当てた**後**に区分を決める（collect() 内でやると未接触扱いになる）
4. 連番は送信順を保ったまま振る。検算：連番が1..N連続・送信順が単調増加
5. 冪等確認：2回目実行の後にシートを丸ごと JSON で読み、3回目実行後と cmp。CSV も cmp

## 失敗と是正
- 確認用スクリプトが相対パスで JSON を書き、cwd が変わって**古いファイル同士を比べて「差分0」と誤判定**しかけた。KeyError で気づいた。比較用ファイルは絶対パス（scratchpad）に書く
- 既存の基準チェック（criteria_check.py）は「カート実画面確認」「公式紐付け」を見ていない。追加検算で第2弾候補2社が紐付けNG（基準チェックとの食い違い）
- カート保持者の実画面確認の証拠は列の「確認」表記だけでなく 30_verify_cart.tsv（9/30）と 61_checked_asins.json（10/5）にもある。表記だけで見ると4社を誤って未確認にする
- 酒類（流通形態）は基準に無いが販売免許が無いので第1弾から外した（3社）。基準外の除外は報告に明記する

## 2026-10-11 追記：バッチ追加のシート反映の定型（M/N/O で実施）
1. 前の行数を数える（gspread で get_all_values・判定別と打診順別も）
2. 並行担当の「当て直し材料」は**先行バッチ側の行に**反映する（後続行は「重複」なので、sync_ledger の重複除去で先に読んだ行が勝つ）。.bak を取り、diff が1行ずつであることを確認。公開版 CSV にも同じ行を写す
3. `python3 sync_ledger.py --dry-run --through=batchX` → 本実行（`--unchecked-out=64_出品可否_未判定.csv`）。criteria_check / dashin_order は sync_ledger 内から呼ばれるので単独実行は不要
4. 後の行数を数え直し、新規行の内訳＝（後−前）から当て直しで動いた分を差し引いて出す。CSV の行数とシート増分は一致しない（同社行は寄せられる：296行→259行）
- 新規の接触候補は出品可否が未実測なので第1弾/第2弾は増えない。行数が増えても打診可能数は増えていない、と報告で分けて書く
