# NETSEA 起点で「Amazon 側の基準は通るのに卸値で落ちる」ことのほうが多い

記録: タカシ / 2026-09-29 / T-20260920-003（成果物 19）

## 一行で

**「売れている棚が空いている」のは、卸から買って並べても赤字だから空いている。**
Amazon 側の条件（売れている・本体不在・出品者少ない）を通した6件のうち、
**卸値が上限以下だったのは1件だけ**でした。

## 実測（268 ASIN・卸値は NETSEA API で 2026-09-29 に引き直し済み）

- 原価（卸値税込×入数）が「買ってよい上限」以下だったのは **93/268件**
- そのうち **monthlySold が表示されていたのは1件だけ**
- 268件の原価÷売価の中央値は**5割台**。手数料＋FBA を引くと利益率20%はほぼ残らない水準

最良の棚がいちばん分かりやすい例でした。
**月1,000個・出品者2社・本体365日不在100%** の ASIN があり、それでも
**卸値は上限の2倍以上**で、しかも**500個単位でしか買えません**。

## `set_num` を見ないと判定が丸ごと嘘になる

通過6件の最小発注単位は **1 / 1 / 1 / 25 / 40 / 500 個**でした。
卸値が単価で安く見えても、**寝かせる現金は set_num 倍**です。

- `set[].price` = **単価・税抜**
- `set[].set_price` = **1口ぶんの金額＝実質の最小発注額**（今回は1万円未満から50万円超まで散っていた。実額は非公開）
- 成果物には**実額を書けない**（会員限定の取引条件）ので、`set_price` を
  「1万円未満／1〜5万／…／50万円以上」という粗い**帯**に落として出しました。判断には足ります。

## 卸値を成果物に書かずに判定を伝える書き方

売価は公開データなので、**率を書くと割り算で卸値が復元できます**。今回はこうしました。

| 出すもの | 区分 |
|---|---|
| 売価・monthlySold・出品者数・手数料率・FBA手数料・**買ってよい上限** | Keepa 由来＝公開可 |
| 卸値・上代・最小発注額の実数 | 会員限定＝**公開不可**（agent_output へ） |
| 卸値と上限の関係 | **帯**で表す（「上限以下（余裕は小さい・9割超）」「超過（1.5倍未満）」等） |

帯にすると復元できる幅が数百円〜数千円に広がり、かつ社長の判断材料としては十分でした。
**「率なら大丈夫」で処理しないこと。**売価を並べて載せる文書では率は実額と同じです。

## 卸値は1ヶ月では動かなかった（Amazon の売価は動く）

1ヶ月前（2026-08-31）の卸値と今日の卸値を6件で突き合わせたところ **全件同額・全件掲載継続**。
一方 Amazon の売価は1週間で 4,980→6,999 / 2,400→5,557 と動いています。

> **引き直す優先順位は「Amazon の売価 > 卸値」。**
> ただし卸値の再取得は0トークンなので、**確定させる直前には必ず引く**（掲載終了の検出も兼ねる）。

## ASIN 指定で引くか JAN 指定で引くか

トークン上限が硬いときは **`asin=` で引く（1 ASIN = 1トークン確定）**。
`code=<JAN>` は「返ってきた商品数」課金で、1 JAN が複数 ASIN を返すと額が読めません
（過去に残高 -101 まで落ちた）。
代償は**同一 JAN の別 ASIN（相乗り先の選択肢）が見えないこと**。既知の制約として成果物に書く。

## 追記（2026-09-30 / 成果物22）— 発注を決める1回だけは `offers` を引く

`current[COUNT_NEW]`（オファー本数）で出品者数を判定していたが、`offers=20` を付けて
実際に出品している社数を数え直すと、**2件が基準を大きく外れて落ちた**。

| ASIN | オファー本数 | 実際 | 結果 |
|---|---|---|---|
| B0D6GBWXPR（Switch ゲーム・ランク3,960位） | 6 | 大幅に多い | **除外**。最有力だった |
| B01BEH1OAC（H2O STEAMFX） | 2 | 大幅に多い | 除外 |

**オファー本数は「安全側に多く出る」と思い込んでいたが、逆に少なく出ることがある。**
36トークンで最有力候補が消えたのだから、発注前の1回は必ず引く。
同時に `stats.buyBoxIsAmazon` と `buyBoxIsFBA` も取れる。
**カートを Amazon 本体が持っている棚は買わない**（価格を下げても取れない）。
**カートが自己発送の出品者なら、FBA で出せば取りに行ける**＝選ぶ理由になる。

## 出口が決まると「在庫が寝る」の意味が変わる

社長判断（2026-09-30）で**売れ残りはメルカリで処分**と決まった。
それまでは「完売6ヶ月超＝落とす」だったが、**落とす理由ではなくなった**。

- 損失 = 発注額 − 処分回収額。経理の置き方に合わせて **出品価格＝売価の50%・手数料10%・送料500円/個**
- **卸率50%以下の品は、半値処分でも仕入れをほぼ回収できる**（推奨3件の損失は 0／5,910／12円）
- つまり**低卸率は「儲かる」だけでなく「損しにくい」**。回転が読めない品を取りに行くときの安全弁になる

## 条件は目的ではない（3回変わった）

同じ日に社長条件が3回変わった（6万→8万／利益率15%必須→下限なし／売価3,700→2,000）。
**その都度リストを作り直すのではなく、判定関数のしきい値だけを変えられる形にしておく**と5分で追従できる。
今回は `entry_pool.py` の条件部分を4行変えるだけで、26件 → 60件の入口リストになった。
