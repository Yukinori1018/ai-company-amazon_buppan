# 上場列の同名別会社と、Finder 一覧の取り直し（2026-10-21 夜間・T-20260930-001）

## 1. 上場列の取り違え（トミタ・LOGOS）
- 症状：燕市のトミタ（6名）が東証のトミタ 8147 に完全一致して層5（大手）に入った。ロゴス(LOGOS) は「ロゴスlogos」が親の核「ロゴス」（ロゴスHD＝北海道の住宅会社）に前方一致して子会社疑い。
- 原因：照合キーが短い完全一致を、別の根拠なしに大手として扱っていた（「社名が短い・同名別会社の可能性」の注記は付けていたが、層の判定は注記を見ていなかった）。和英併記を1語にしてから照合していた。
- 直し方（37_listed_dedup.listed_mark に一本化。51・52・56 はここを呼ぶ）
  1. 和英併記は split_aliases で割ってから照合する
  2. 照合キーが4文字以下（英字だけなら6文字以下）の完全一致は、gBiz の大手判定か既知の大手リストがあるときだけ「大手（上場）」。なければ「上場銘柄と同名…未確認」＝層5 に入れない
  3. 社名が親の核と同じ（イートアンド＝イートアンドHD−HD）は、核が5文字以上なら子会社疑い
- 採らなかった案：「gBiz で中小なら別会社」。グロース上場には法定中小がいる（ビタブリッドジャパン 542A など）。実データに当てて初めて分かった。**判定ルールを足したら既存キュー全行に当てて差分を見る**（今回 12i_上場判定の差分_20261021.csv）。
- 既存キューへの影響：層5 のうち上場だけが理由の行が約30行、層5 から外れる。うち半分ほど（ツムラ・TDK・ニッスイ・中村屋 など）は本物の大手で、gBiz が同名多数で確かめられないだけ。ノイズは増えるが「未確認」と書いて層3 で人が公式を見る（入口(e) の big_verify と同じ扱い）。シートは書き換えていない。

## 2. Finder の取り直し（入口g）
- 条件を1つも変えず、帯（b・c・d・e rank・a）の Finder 一覧を今日の状態で取り直すだけで、手持ちに無い ASIN が 6,918件出た（b 1,027／c 2,004／d 387／e 146／a 3,354）。一覧は2〜17日で2〜3割入れ替わる。
- 費用：probe（perPage=50）約11 token/帯、全件一覧 約110 token/1万件、product 1 token/ASIN。product が律速（20 token/分で約6時間）。
- キャッシュのタグに日付を入れる（finder のキャッシュはセレクションのハッシュなので、同じ条件だと前回の一覧を読んでしまう）。
- 手順の型：57_entry_g.py probe → list → fetch --until → build --until。build は 56_entry_f の build を差し替えて使う（PREV に 11g を足す）。

- 結果：2,600 ASIN を取って 214社（約8%）をキューに足した（5487〜5700位）。

## 3. 足す前に層3 の社名を目で見る
- v1（232社）の層3 にカルビー・コカコーラ・ドトール・ミシュラン・ヴィクトリアズシークレット等が18社いた。gBiz が「一致なし／同名多数」だと規模不明＝層3 に落ち、一次除外の大手リストに無い有名ブランドは素通りする。
- **書き込み後に層1〜3 の社名を一覧で見る**のを手順に入れる。混ざっていたら maker_rules.EXTRA_BIG に足し、退避から戻して build を打ち直す（キャッシュで0 token）。入口(f) v1 と同じ型の2回目。
- dōTERRA は nrm で ō が落ちて「dterra」になり、既存の doterra に当たらなかった。リストに表記ゆれを足す。

## 4. 失敗
- `until ! pgrep -f "57_entry_g.py list"` を同じ Bash の中で書いたら、その Bash 自身のコマンド行に文字列が入っていて pgrep が自分に当たり、無限ループした。**pgrep -f の検索語を自分のコマンド行に含めない**（PID を控えて `kill -0` で見る）。
