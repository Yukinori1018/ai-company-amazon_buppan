# unknown_stages run は「引き直し後のキュー」で不動点まで回す（2026-10-25）

## 何が起きたか
- 10/24 夜、`unknown_stages.py run` を2回続けると同じ5行が NO-GO→UNKNOWN→NO-GO と往復（295→300→295）
- 1回目：キューは引き直し**前**の台帳で作る → 段を回す → `ledger_refresh` で引き直し。この引き直しで、
  古い Keepa データ（12〜20日前取得）の90日価格窓が1日進んで価格点が外れ、5行が UNKNOWN に落ちた
- 2回目：その5行がキューに入り、s2 で取り直し → NO-GO に戻る

## 学び
- 「段→引き直し」を1回で終える処理は、引き直しがキューを増やす限り冪等でない。**引き直し後のキューを見て、新しく入った行が無くなるまで回す**
- ループの停止条件は上限ではなく「処理済みは REVISIT_DAYS の間 pending から外れる」で作る（§3.3-34）
- 続けるのは**新しく入った行だけ**にする。既存キューの溢れまで回すとバッチ（1回分の量）の意味が壊れ、トークンを一晩で使い切る
- 往復を見たら、まず前後のスナップショット（before/after_*_stages_*.json）を行ごとに diff して ASIN と変わった列を特定 → 生データの fetched と判定に使う「いま」を比べる。今回は Keepa を叩かずに全部特定できた
- `price_history` の「いま」は UTC 0時。JST 2時の実行は前日の UTC 日付で計算される（10/24 02:04 の run は now=10/23）。日付つきの再現ではこれを合わせる

## 再利用できる検証の型
