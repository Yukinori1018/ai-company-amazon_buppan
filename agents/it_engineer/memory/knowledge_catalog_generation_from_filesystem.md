# 一覧は「git に載っているもの」ではなく「そこに在るもの」から作る

2026-09-09 / T-20260909-003（タカシ）。
社長が T-20260904-004 の `03_…html` を成果物カタログから見つけられなかった件。

## いちばんの学び — 可視性と公開は別の軸である

カタログは GitHub の blob リンクを持つ手書き CSV だった。だから
**「GitHub に載っていない ＝ カタログに存在しない ＝ 社長には無いのと同じ」**
になっていた。しかし社長のローカルにはファイルは在る
（`~/Documents/AI Company Outputs/…` は deliverables へのシンボリックリンク）。

直すべきは「公開範囲」ではなく「一覧の作り方」だった。
カタログを**ファイルシステム走査**に変え、各行に `公開状態` を持たせて
「GitHub公開／ローカルのみ」を書き分けたら、社長の不満は
**1バイトも公開せずに**解消した。

> 「見えない」と言われたとき、公開の方を動かす前に、一覧の作り方を疑う。

## 依頼の前提（発注者の診断）を鵜呑みにしない

カズヨの原因分析は「ホワイトリストへの追記漏れで黙って落ちた」だった。
実際に中身を見たら、その HTML には**卸値(税込)の商品別テーブルが2つ**あり、
`.gitignore` のコメントに「載せてはいけないもの」として**名指しで書いてあった**。
追記漏れではなく意図的な除外。指示どおり `git add` していたら、
2026-08-31・09-06 に続く**3度目の卸値公開事故**を自分で起こしていた。

- 「未追跡の正当な成果物を追跡下に戻せ」と言われたら、**戻す前に中身を開く**。
- 70件の未追跡を全部当たった結果、取りこぼしは**ゼロ**だった。
  件数の多さは、そのまま「取りこぼしの多さ」ではない。

## ホワイトリスト .gitignore の副作用（型として記録）

`*` ＋ `!ファイル名` は漏えいには強い。だが
**新しい成果物が黙って追跡外になる**という副作用がある。危険の向きが逆になっただけ。

反転して「危険な**形**を落とす」に変えた（`*.csv` `*.jsonl` `_*cache.json` ＋名指し）。
判断の物差しは **行データが載る書式かどうか**。散文（md/html）は既定で載せ、
中身が危ないものは pre-commit が止める。

検算は「追跡ファイル数（723→723）」と「除外集合が同一か」の2つ。
`git check-ignore -v` の理由が `*` から `*.csv` や具体名に変わったことが、
そのまま「なぜ落ちているか人が読める」という改善になる。

## catch-all を検知する（自動修復はしない）

`git check-ignore -v` は**どの .gitignore の何行目で落ちたか**を返す。
理由が `*` なら事故、`*.csv` なら意図。この1点だけで警告を出せる。

- pre-commit は**警告のみ**（commit は止めない）。公開可否は社長・法務の領分。
- SessionStart リマインダー⑦にも同じ検査を出した。平常時は0行。
  ホワイトリスト方式が復活したその日に鳴る。
- 検証は必ず両方向。実リポで0件（正常な作業を邪魔しない）＋
  `*` を書いた使い捨てリポで2件（本当に鳴る）。片方だけでは検算にならない。

## 実装で踏んだ罠

- **自己参照で冪等が壊れる。** 生成した HTML カタログ自身が次回の走査対象になり、
  実行のたびに1行増えた。出力ファイルは走査から除く。
- **生成日を本文に書くと毎回差分が出る。** 比較時に日付行だけ落として、
  内容が同じなら**ファイルに触らない**（30分ごとの auto-sync を無駄に走らせない）。
- **既存 CSV をパスで索引すると、人が書いた文章を落とす。**
  フォルダ単位の行（`T-20260705-001/` が3行）は同じパスを複数行が共有していた。
  索引（先着）と全行リストの**両方**を持つ。226行→226行の引き継ぎを数字で確認する。
- **bash の二重引用符の中のバッククォートは実行される。**
  メッセージに `` `*` `` と書いたらグロブが展開されて
  `CLAUDE.md: command not found`。以前も同じ罠を踏んでいる（heredoc の版）。
  フックのメッセージにバッククォートを書いたら、必ず一度実行して確かめる。
