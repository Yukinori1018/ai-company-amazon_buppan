## この依頼はこう処理した（再利用の型）
1. 新しい判定は書かない。台帳と同じ採点 `score_20261004.build(row, cand, product, idx, names, idx_day, now, rank_counts)` を呼び、
   `idx` に**入力 CSV を NETSEA 索引と同じ形**（jan / unit_price_excl / min_lot_units / stock / title / supplier_url）で渡す。足すゲートだけ後から差し替える（実売・取り分・仕入れ・季節の窓）
2. Keepa は**手元の生データを先に引く**。1GB の jsonl でも、行ごとに `"eanList": [...]` を正規表現で抜いて対象 JAN を含まない行は json.loads しない → 3秒で読める
3. 足りない JAN だけ `code` 逆引き（stats=90&history=1&days=400・1トークン/商品）。候補の行だけ `asin=…&buybox=1`（3トークン/商品）
4. 出力は台帳32列＋補助列の CSV を agent_output に。台帳への合流は再採点担当（同時に別タカシが台帳を触っていた）

## 罠と直し方
- **出品の死と商品の終売を混ぜない。**セット品 ASIN は何年もランクが無いのが普通。同じ JAN の別 ASIN が直近60日に売れていれば「ランク消失・新品0」は終売の兆候にしない（初回は16件が誤って「終売疑い」）
- **取り分 ≦ 平均。**平均が3個/月未満なら出品者数（buybox）を取らなくても取り分 FAIL が決まる。family 合計の平均は上限なので、それで3未満なら FAIL
- **観測0回の出品は「売れていない」で FAIL**（観測が少ないだけなら UNKNOWN）
- `buyBoxPrice=-1`・`buyBoxSellerId=None` は「いまカートが立っていない」。取り直しても決まらない
- `score_20261004.build` の `pinned`（人が実画面で NO-GO にした行）を自前の判定で上書きしない
- `code` 逆引きの消費は 1 JAN あたり 1.5〜1.7。初期レート1.6だと予算を1割超えた → 2.0＋15%余裕に
- 🔴 **テストに会員限定の卸値を書かない。**SD 実画面の段価格（例の数字）をそのままテストに書きかけた。テストは架空の値と example.invalid で書く
