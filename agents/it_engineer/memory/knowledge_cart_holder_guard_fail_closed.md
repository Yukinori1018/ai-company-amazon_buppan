# カート保持者の判定は fail-closed に組む（UNKNOWN を GO に畳まない）

- 日付: 2026-09-30
- チケット: T-20260920-003
- 成果物: `workspace/output/deliverables/T-20260920-003/24_カート保持者ガード/`
- 関連: CLAUDE.md §3.3（この事故を受けて新設）

## 何が起きたか

商品ページの `#merchant-info` という **1つの要素だけ**を読んで「販売元＝第三者」と判定し、
Amazon 本体がカートを持つ ASIN（B0FVL8QST6）を社長に上げて12点・19,756円を発注させた。
本体がカートを持つ棚は、値下げしてもカートを取れない＝売れない。

## 設計として持ち帰ったこと

### 1. 「1つの根拠で PASS」を型で禁じる

カート保持者は独立3根拠（`stats.buyBoxIsAmazon` / `stats.buyBoxSellerId` /
`buyBoxSellerIdHistory[-1]`）＋期間統計（`buyBoxStats` の本体獲得率）で見る。

- **2本以上の一致がないと PASS にしない**
- **1本でも AMAZON を指したら即 FAIL**（多数決にしない。非対称でよい）
- 根拠どうしが**食い違ったら UNKNOWN**（黙って片方を採らない）

「複数根拠を突き合わせる」は運用ルールで書いても守られない。**関数の戻り値の型で守る。**

### 2. UNKNOWN を NO-GO に畳むと、次に何をすべきか分からなくなる

3値（GO / NO-GO / UNKNOWN）で出すのが正しい。

- NO-GO ＝ 調べた結果、駄目だと分かった → 落とす
- UNKNOWN ＝ 調べきれていない → **GO ではないが、調べれば通るかもしれない**

2値にすると「データが無い」と「本体が居る」が同じ箱に入り、後から見分けられない。
そして最悪なのは UNKNOWN を GO 側に畳むこと。**「データが無い＝安全」が今回の事故の本体。**

### 3. 取得上限に張り付いたら UNKNOWN（打ち切りの検出）

`offers=20` では21件目以降が返らない。「返ってきた20件に本体が居ない」は「本体が居ない」ではない。
`stats.current[COUNT_NEW]` と取得上限を比べ、超えていたら UNKNOWN にする。
**API のページングの端は、必ず判定の穴になる。**

### 4. 事故った現物を対照に入れてから完成とする

B0FVL8QST6 を同じツールに通して 3点すべて FAIL になることを確認した。
**「直しました」の証明は、事故のケースを再現して落とすこと。**テストだけでは足りない。

## Keepa の実務メモ（2026-09-30 実測）

- 本体判定に要るパラメータは `stats=365` `history=1` `buybox=1` `offers=20` の4点セット。
  - `buybox=1` → `stats.buyBoxSellerId` / `buyBoxIsAmazon`
  - `history=1` → `buyBoxSellerIdHistory`（`[ts, sellerId, ts, sellerId, ...]` の平坦配列。
    `"-1"` `"-2"` は**文字列**で返る＝数値の -1 と混ざるので str 化して判定）
  - `stats=365` → `outOfStockPercentage365[0]`（本体）・`buyBoxStats`（セラー別のカート獲得率）
  - `offers=N` → `liveOffersOrder` で**いま生きているオファーだけ**に絞れる
- **トークン実測 5.3〜6.0 / ASIN**（2 ASIN で12、3 ASIN で16）。回復 20/分。
  100件で600トークン＝30分ぶん。**広い絞り込みには使わない。発注直前の最後の関門に使う。**
- `liveOffersOrder` を使わず `offers` 全部を数えると、消えたオファーと同一セラーの重複出品
  （FBA＋自己発送）で出品者数が水増しされる。実例: offers 4本 → ライブ2本 → 出品者2社。
- `buyBoxStats` は「いま第三者でも期間中に本体がカートを取っていた」を拾える。
  スナップショットだけ見ていると取りこぼす穴で、**ここが4本目の根拠として効く。**
