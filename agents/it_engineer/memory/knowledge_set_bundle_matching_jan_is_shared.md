# まとめ売り突合 — JAN は単品とセットで同一／Keepa はセット品を最初から返している

- 2026-10-01 / T-20260920-003 / タカシ
- 関連: `knowledge_verify_field_semantics_not_names` / `knowledge_keepa_dropcount_is_polling` / CLAUDE.md §3.3-7・17

## 1. 結論から

**卸の「1点」と Amazon の「1個」をつなぐ鍵は `packageQuantity` と、JAN 逆引きが返す ASIN 群です。**
どちらも**すでに払ったレスポンスの中に入っていて、捨てていました。**

## 2. 構造的な原因（9/30・10/1 の単位ずれ2回の真因）

**JAN は単品とセットで同一です。**
旭化成 ズビズバ あみたわし `4901670106107` は、SD の「1点」「×10点」「×200点」が全部同じ JAN。
だから **JAN 突合はいつも単品 ASIN に当たります。**
これは読み間違いではなく**設計の穴**でした。個別の正規表現を足しても直りません。

そして日用消耗品の**単品は数式の上で黒字になりません**。

    必要売価 = (821 + 1.1 × 卸値税抜 × n) ÷ 0.8376
    821 = FBA 415 + 保管/納品/資材 206 + 誤差幅の固定ぶん 200
    0.8376 = 1 − 販売手数料 9.24%(税込) − 誤差幅 7%

**固定費821円は Amazon の1個につき1回しかかからない**ので、n を増やすと1点あたりが下がります。
卸178円のたわし: n=1 で 1,214円（売れない）／n=10 で 3,318円＝1点332円。

## 3. 🔴 最大の学び — 「1件に絞る」関数が母数を静かに殺していた

`discover._pick_best()` は「1 JAN に複数 ASIN がぶら下がったら、ランクが一番上位の1件を採る」。
**一番上位はほぼ単品**です。つまり**まとめ売りの口が並んでいるのに、必ず赤字になる口だけを見て落としていた。**

実測（1リクエスト10トークン）: JAN 1本で **10 ASIN**（×1 ×2 ×3 ×4 ×5 ×6 ×7 ×10 ×200）。
**Keepa の課金は「返ってきた商品数」**なので、**捨てた9件もすでに払っています。**
セット品を集めるのに追加トークンは **0**。拾い直すだけでした。

> **「代表を1件選ぶ」コードを見たら、選ばれなかったものが何かを必ず数えること。**
> くじ引きでないだけでは足りない。**選ぶ基準（ランク上位）が、欲しいもの（大きい口）と逆を向いていた。**

## 4. `packageQuantity` は商品名とは独立した2本目の情報源

| ASIN | 商品名 | `packageQuantity` | `numberOfItems` |
|---|---|---|---|
| B01MU0SNTZ | 【セット品】×4個 | 4 | -1 |
| B01MCR1XMK | × 3個セット | 3 | **1** ← 既定値が入る |
| B00H2E0JLW | 2個セット | **1** ← 落ちる | 2 |

- **一致したときだけ「確定」。**食い違ったら **大きい方**で計算して UNKNOWN（原価を安く見積もらない）
- **`numberOfItems` は判定に使わない。**1 が既定値として入る実例がある（多数決をすると壊れる）
- `0` / `-1` は「データなし」。**0 を「0個セット」と読まない**
- `packageQuantity` の上限は 1〜1000。商品名側の上限60（`600粒` 誤読対策）を構造化フィールドに
  当てると、×200 の実在する大口を切り落とす

## 5. 入口のフィルタが、まとめ売りで成立する商品を全部捨てていた

`run_supplier_first.tier()` は**単品の採算しか見ていなかった**。

| | 旧 | 新 |
|---|---|---|
| 卸1点の下限 | 300円 | **30円** |
| 卸ロット上限 | 24点固定 | **24 × セット数（最大240）** |
| 判定対象 JAN | 33,807 | **43,582** |
| 最優先（tier 0+1） | **2,596** | **12,084** |

旧フィルタは **卸300円未満1,120件・ロット24超1,619件**を入口で捨てていました。
**「300円」も「24点」も、単品でしか考えていなかった時代の遺物でした。**

> CLAUDE.md §3.1 の「条件は変数」は**自分が過去に書いた閾値にも効く**。
> 社長の条件だけを疑って、自分のコードの定数を疑っていなかった。

## 6. 単位を受け取る口を設計し直した（`価格の単位` 必須）

SD は同じ JAN に複数の口が並び、**画面の数字が1点あたりか1セットあたりかは口によって違う**。
`sd_wholesale.json` に `"価格の単位": "1点あたり" | "1セットあたり"` を**必須**にし、
**無い行は卸価格を取り込まず理由を `notes` に残す**。1セットあたりは `入り数` で割り、**切り上げ**。

> **2つのデータ源をつなぐ口は、単位を「渡させる」設計にする。**推測の余地を残すと必ず埋められる。

## 7. 「読めない」を「無い」と混ぜない（`trading_terms.py`）

取引条件の表（SD 163社・○108 / ×46 / 要確認9）が読めなかったとき、
**例外を投げず「読めていない」として UNKNOWN** を返すようにした。
例外にすると呼び出し側が握りつぶし、**ネットワークが死んだ晩に全件 ○ 扱いで走る。**
`None`（表の対象外＝NETSEA の先）と `要確認`（読めていない）を**別の値**にしてある。

## 8. この依頼の処理手順（再利用できる形）

1. 社長／秘書の「決定的な発見」を**自分で1回だけ実測して確かめる**（ここでは Keepa `code` 逆引き10トークン）。
   **確かめる前にコードを書かない。**今回はこの1回で設計が全部決まった
2. 純関数の新モジュールに切り出す（`set_family.py`）。UI も I/O も混ぜない
3. **既存の「1件に絞る」「下限で切る」箇所を全部洗う。**直すのは本体ロジックより先に入口
4. ネットワーク0のテストで数値を固定（カズヨの手計算 1,214円 と一致させる＝突合の証拠）
5. 既存テストが赤くなったら**契約が変わった印**。赤を消すのではなく**テストを新契約へ書き換える**
6. 夜間走行は**他チケットのジョブが終わるのを待ってから**起動（同じ Keepa キー・補充20/分）

## 9. 同じ Keepa キーの取り合いは「floor を下げて奪う」で解決しない

2026-10-01、T-20260930-001 の `20_fetch.py`（9,756 ASIN・100件/105トークン単位）が走っている間、
`--floor 0` で取りに行くと**両方止まります**（9/30 に実際そうなった）。
`launch_tonight.sh` で**相手のプロセスが消えるのを待ってから**起動する形にした（最大4時間）。
`rank_pass.py` のコメントにある「40で取りに行けば先に拾える」は**小細工**で、設計ではない。

## 10. 待ちの条件は「結果」で書く（2026-10-01 追記）

`while pgrep -f "20_fetch.py"; do sleep; done` で相手の終了を待つ launcher を書いたら、
**カズヨが SIGSTOP で止めたプロセスが `pgrep` に残り続け**、永久に起動しない形になっていました。
正しい条件は**残高そのもの**（`tokensLeft >= 300`）。相手が止まった/終わった/消えたのどれでも走り、
戻らなければ「誰かが使い続けている」という判定にもなります。

> **待ちの条件は、原因（相手の存在）ではなく結果（自分が欲しい状態）で書く。**

さらに、補充20/分に対して**相手は105単位・こちらは300単位**で待つので、
相手が走っている限り**こちらは必ず負けます**。残高の取り合いは閾値調整では解決せず、
**どちらを先に通すかを人が決める**しかありません。

## 11. PID の指定は必ず自分で確かめる（2026-10-01）

カズヨから「`20_fetch.py`（PID 27704）を SIGSTOP で止めた。トークンを確保した」と連絡が来ましたが、
**27704 は私自身の launcher の親シェルでした**（`20_fetch.py` は 99221）。
`ps -o pid,stat` で見たら 27704 が `T`（停止）・99221 が `S`（稼働）で、
**残高は6のまま・相手は batch 50 まで進んでいました**。

> **「確保しました」を受け取ったら、確保されたことを自分で測る。**
> トークンなら残高を読む。プロセスなら `ps -o stat` で状態を読む。
> 受け取った PID を信じて走り出すと、**何も空いていないのに走って両方止めます。**

## 12. 承認を増やしても候補は増えないことがある（2026-10-01）

NETSEA の一括取引申請で「77社へ申請・21社が即時承認」の報告を受けましたが、
**API が返す承認済みサプライヤーは 227社**（索引済221社＋**6社**）で、21社は反映されていませんでした
（Web の即時承認が API に出るまで遅れがある、という推測。確認はしていない）。

索引できた6社の中身:

| shop | 商品数 | ネット販売可 | **JAN を持つ商品** |
|---|---|---|---|
| 962326 | **787件** | 787件（全部可） | **0件** |
| 963678 | 4件 | 4件 | 4件 |

**最大の新規サプライヤーは787件すべてネット販売可なのに、JAN が1つもありません。**
当社の突合は JAN しかないので、**787件は見えているのに1件も当てられません**。索引は **+5 JAN** だけ。

> **「仕入れ先を増やす」＝「候補が増える」ではない。**増えるのは「JAN を持っている商品」だけ。
> 承認数で期待値を見積もると外します。申請レーンの効果は**社数ではなく JAN 数**で測ること。

# 季節 — 「死んでいる棚」と「今が季節外の棚」は別物（2026-10-01 追記）

## 13. 生存ゲートが区別できなかったもの

カズヨが SD レーンAで当てた1件: ナガクラ 栽培キット（卸480円 → Amazon `B001LOOR4E` ￥2,680・
**オファー1社・本体在庫なし**・利益率33%）。**価格差は実在した**のに、キーゾンで3か月0個で
カートも立っていない。生存ゲートは `NO-GO`。

**しかしレビュー153件＝過去は売れていた。**栽培キットは春物で7〜9月が端境期。
**「死んだ棚」ではなく「今が季節外の棚」だった。**

> **90日平均ランクも直近3ヶ月の実数も、この2つを区別できない。**どちらでも同じ顔をする。
> **「売れていない」を見たら、「いつ売れていたか」を見る。**

区別できるのは**ランクの12ヶ月履歴（`csv[3]`）だけ**で、
**`history=1` を足すだけで手に入り、課金は件数ベースなのでトークンは増えない**
（実測: 23商品すべてに入っていて1商品6,456点）。これも §3「払って得た数字は捨てない」と同じ型 ──
**取れるのに取っていなかった。**

## 14. 🔴 テストが見つけた3つの実バグ（設計の穴が全部ここに出た）

| 症状 | 原因 | 教訓 |
|---|---|---|
| 通年低調の棚が「11〜1月の棚」に化ける | 全月が同じように低調だと `peaks` が**全12月**になり `peaks_in_target()` が True | **「最良に近い月」を集める実装は、全月が同じとき全部を返す。**縮退した入力を必ずテストする |
| 冬物の11月がピークから落ちる | 許容幅1.6では12月7,000位に対し11月12,000位が外れる | **閾値は「山の肩」を落とす。**季節は月単位の山なので 2.0 にした |
| 季節の説明が出ない | 「90日平均は圏外だが現在は上がっている」の分岐が**季節判定より先**にあった | **新しい説明を足すときは、既存の分岐の「前」か「後」かを必ず確かめる。**ピークへ向かう途中はまさに「現在上がっている」形なので、先に古い分岐に吸われていた |

さらに `season_hint()` で **「土鍋」が春物に当たっていました**（`SPRING_WORDS` に「土」を入れたため）。
冬と春の両方にヒットして「不明」に落ち、冬物の最優先から外れていた。
**短い語を語彙に入れない**（「種」も「各種」「品種」に当たる）。

## 15. ゲートはデータ、順番はキーワード

季節のキーワード（「鍋」「加湿」）は**並べ替え専用**にし、**落とす・残すはランク履歴だけ**が決める形にした。
商品名から季節を当てるのは「18食入り」と同じ型の推測で、**同じ語が逆の意味になる**。

> **推測で作った材料は「順番」に使ってよいが、「可否」に使ってはいけない。**
> 順番を間違えても後ろで拾えるが、可否を間違えると二度と出てこない。

## 16. 「いま何月か」を条件に入れていなかった

10/1 に仕入れて納品して売れるまで2〜4週間。**狙うべきは11〜1月に売れるもの**で、
春物は在庫6ヶ月になり回転6ヶ月の既定を超える。
**それまでのパイプラインに「今日が何月か」という入力が1つも無かった。**
採算・競合・生存は全部「時点を持たない数字」として扱っていた。

> **在庫を持つ事業の判定に、カレンダーが入っていないのは設計漏れ。**
> 「6ヶ月で捌けるか」は見ていたのに、「いつから6ヶ月か」を見ていなかった。
