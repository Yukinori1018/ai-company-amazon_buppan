# Keepa Product Finder — 有効フィールドの実測と落とし穴（T-20260817-005 / 2026-08-21）

メーカー仕入れ v1.3 の実走（`workspace/output/deliverables/T-20260817-005/scan_v13.py`）で
Keepa Product Finder（`GET https://api.keepa.com/query`）を実測検証した結果。

## 最大の落とし穴：**未知のフィールドはエラーにならず、黙って無視される**

`{"bogusField_gte":1}` を投げても HTTP 200・`error:null` で返り、`totalResults` は
無条件検索と同じ（2.75億件）。**綴りを1文字間違えるとフィルタが効かないまま
「条件どおり抽出できた」と誤認する。** ドキュメントを読んで安心してはいけない。

**検証手順（確立した型）**: ベースライン selection の `totalResults` を取り、
フィールドを1つずつ足して `totalResults` が動くかを見る。動けば有効・同じなら無視されている。
1プローブ11トークン。数十トークンで数千トークンの無駄打ちを防げる。

## トークン経済の重要な発見：**perPage は 1000 まで通る**

過去メモには「perPage は最低50」とだけあったが、**上限も検証すべきだった**。

| perPage | 消費トークン | 1000件あたり |
|---|---|---|
| 50 | 11 | 220 |
| **1000** | **20** | **20** |

**Finder の課金は「10 + 件数/100」**。perPage=50 で20ページ回すのは
perPage=1000 の1発に対して **11倍の無駄**。ページングする前に perPage を上げる。

`product` は 1トークン/件。**`stats=365` に追加コストは無い**（stats=30 と同じ1件1トークン）。
過去1年最安値が欲しいなら遠慮なく `stats=365` を投げてよい。

## product レスポンスの読み方（実測）

- `stats.min[i]` は `[keepa時刻, 値]` または `null`。`stats=N` の **N日間**の最小値。
  **index 1 = NEW（新品最安）** が「過去1年最安売価」として最も素直で保守的。
  index 18（BUY_BOX）は `null` になる商品が多く、当てにできない。
- `stats.buyBoxPrice` は **-2**（＝カート無し/不適格）を返すことがある。`-1` だけを
  欠損扱いにすると -2 が価格として紛れ込む。`>= 0` で弾くこと。
- `stats.salesRankDrops30 / 90 / 180 / 365` はここから直読み。
- `monthlySold` — **下限付きの階級値。詳細は下の専用セクション参照**（2026-08-24 に再検証して記述を修正）。
- `brand` / `manufacturer` は `_product_to_amazon()` が捨てるので **raw dict から直読み**（既知）。

## 判定ロジック側で踏んだ落とし穴

- **`current_COUNT_NEW_lte=6` で絞っても、詳細取得すると出品者7の商品が混じる。**
  Finder のインデックスと product の current は更新タイミングが違う。**後処理で必ず再判定**する。
- **v1.3 の「レビュー5〜300＝あまり有名でない」は発売直後の大手SKUを素通しする。**
  実際に Anker / UGREEN / BANDAI / タカラトミー / BURTLE が残った。
  除外は社長判断の領域なので `規模フラグ` 列（大手/海外疑い・中小候補）を立てるに留めた。
- FBA 標準サイズ（45×35×20cm・9kg）判定は `packageLength/Width/Height`（**mm**）と
  `packageWeight`（**g**）から。欠落商品が一定数あるので「不明」区分を用意し、
  **除外せず列に出して人に渡す**（除外すると母数が大きく削れる）。

## 再利用のかたち

`scan_v13.py` は raw レスポンスを `raw/*.json.gz` に保存し、`--from-raw` で
**トークン0**で閾値を変えて再集計できる。閾値をいじる作業でトークンを二度使わない。
条件変更のたびに Keepa を叩き直す設計にしてはいけない。

## 「回転の速い順」に並べると必ず起きること（設計上の含意）

`sort: salesRankDrops30 desc` で取ると、**top100 は探索の最初の300件でほぼ確定する**。
実測: 300件時点の top100 と 4,002件時点の top100 は**完全に同一**だった。
理由は単純で、top100 の足切り（消化月数0.94＝ドロップ数32相当）を下回った時点で、
それ以降の行は原理的に top100 に入れないため。

→ **深掘りは top100 の質を上げない。深掘りが効くのは「母集団を厚くしたい」時だけ。**
　 100件が欲しいだけなら 300〜500件の詳細取得（＝30分未満）で足りる。ここを勘違いすると
　 2.5時間を無駄に使う。**先に小さく回して足切り値を確認してから深さを決めること。**

もう1つ: **回転の速い棚は偏る。** top100 の70%が家電＆カメラ／PC周辺、21件がリチウム電池・
電源系（モバイルバッテリー/充電器）だった。これは条件の欠陥ではなく必然。
ただしこの帯は PSE・FBA危険物（SDS）・初期不良/返品率→ODR の三重リスクを抱えるので、
**回転だけで並べたリストをそのまま「おすすめ」として出さないこと**。カテゴリ分散か
除外の論点として社長に上げる（T-20260817-005 では B案＝リチウム系21件除外を推奨した）。

## `monthlySold` の正体（2026-08-24 T-20260824-003 で再検証・記述を修正）

### 公式定義（T-20260824-001 でサトルが確定）

> 「過去1か月にこの商品が購入された回数。Amazon の検索結果ページの "bought past month" の値。
> **推定値ではない（It is not an estimate）**。ただし Amazon は "10+" "100+" のような
> **区切られた範囲でしか提供しない**。**大半のASINには値が無い。値はバリエーション単位**」

出典: `workspace/output/deliverables/T-20260824-001/keepa-glossary.md` §4 ／ `discrepancies.md` D6。
**「月間売上予測」と呼んでいたのは誤り**（予測ではなく実測値）。ただし「実測だから正確な数字」と
読むのも誤りで、**階級値かつ大半欠測**という但し書きとセットでしか使えない。

### 以前の記述と、実データによる再検証の結果

**以前ここには「月50個以上の商品にしか出ない／300件中233件で取得できた」と書いていた。**
保存済み raw JSON 4,002 ASIN（`T-20260817-005/raw/`・Keepa 0トークン）で検証した結果：

| 以前の記述 | 実データ | 判定 |
|---|---|---|
| 「月50個以上にしか出ない」 | 現在値の最小は確かに **50**。だが**同じ商品の `monthlySoldHistory` には 10/20/30/40 が実在**（1〜49 を履歴に持つ ASIN が **1,732/4,002**） | **要修正**。50 は Keepa の下限ではなく**その時期のたまたまの下限** |
| 「300件中233件」＝取得率78% | 全 4,002 ASIN では**値ありは 1,339件（33.5%）＝欠測 66.5%** | **要修正**。233/300 は探索初期の回転上位300件を見た数字で、母集団全体の率ではない |

**1〜49 は 2025-04〜05 と 2026-02〜03 に集中的に出現し、その前後では完全に消える**
（最終観測 2026-04-28 UTC）。Amazon 側の表示ポリシーが期間で切り替わっている。
→ **`>= 50` を前提にしたコードを書いてはいけない。** いつ 10 に落ちるか読めない。

### 実装で守ること

- **欠測はキーの不在**。`product.get("monthlySold")` は `None`。現在値に `0` や `-1` は出ない
  （4,002件中 0件）。ただし **`monthlySoldHistory` の中では `-1` が欠測マーカー**なので履歴側では弾く。
  履歴の末尾値と現在値は完全に整合していた（末尾 `-1` の 1,566件は現在値も全件欠測）。
- **`monthlySold=50` は「50〜99」の意味**。しかも値ありの **58.2% がこの最小階級に固まる**。
  売上換算するなら**下限見積り**としてしか使えない。
- **階級表をハードコードしない。** 実際に出た値は `50,100,200,…,1000`（現在値）だが、履歴には
  `250` という例外や `2000/3000/4000/5000` も出る。「50の倍数」で綺麗に閉じていない。
- **欠測を「売れていない」と読まない。** ドロップ数49で欠測（`B0DQCC4CTB`）、ドロップ数9で
  値50（`B0F1S2P3TM`）の実例あり。回転が速いほど出やすい傾向はある（ドロップ10-20帯で18.7%、
  32-50帯で84.3%）が、**足切りに使うと誤判定する**。
- **値はバリエーション単位**（公式）。色・サイズ違いが合算されるので、**単一 SKU の仕入れ数量計算に
  そのまま使うと過大評価**になる。
