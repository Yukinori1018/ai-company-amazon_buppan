# /buppan-todo に「根拠ゲート」を入れた — 誤判定を機械で潰す設計

2026-08-31 タカシ / T-20260826-002。社長の指示は「指摘されることなく、より正確に。
改善策を自分で考えて実行して」。**再発防止の仕組みを入れる回**でした。

## 起きた失敗を4つの型に分けてから設計した

これが一番効きました。「気をつける」では同じことが起きます。型に分けると、
どれが機械で潰せてどれが潰せないかが分かれます。

| 型 | 実例 | 機械化 |
|---|---|---|
| ① タイトルと要約で判定 | 開業日 8/20 を提出日と取り違え「未実施」と誤判定 | **入力を変えて潰した** |
| ② 資料の日付凍結 | 8/26 生成の記述が 8/28 の却下で覆っていたのに残った | **NG 判定にした** |
| ③ 動詞の読み違い | 「5条件を満たす」を「確認した」と読み替えて `[x]` | 警告どまり（残課題） |
| ④ 根拠IDの不整合 | 成果物カタログのチケットをレビュー規約の根拠にしていた | 実在チェック＋共起で警告 |

## ①への対策 ＝ 検査を足すのではなく「入力」を変える

最初は verify.py に検査を足すことを考えましたが、**判定が終わったあとに叱っても
やり直しのコストが高い**。そこで `prepare` の出力を変えました。

`evidence.py extract` が、資料に出てくる全 `〔T-…〕`（51枚）について
「現在地 / 完了報告 / 結果 / ログ」を抜き出した 130KB の1ファイルを作ります。
編集者はこれを読んでから判定する。**タイトルだけでは判定できない状態を作る**のが狙いで、
これは検査ではなく設計です。

教訓: 品質問題を見たら、まず「検査を足す」ではなく「間違えられない入力に変える」を探す。

## ②への対策 ＝ 日付比較だけだと「日付を書き換えれば通る」

`更新: YYYY-MM-DD` とチケットの `updated_at` を比べるだけだと、日付を今日に
書き換えた瞬間に検査が空振りします（vacuous pass）。そこでゲートを2枚にしました。

1. **日付**: 資料の更新日より新しい根拠チケットがあれば NG
2. **ハッシュ**: `prepare` 時点の各チケットの sha256 を索引に残し、`build` で照合。
   ズレていたら「読んだ内容と今の内容が違う」で NG。索引が無ければ（＝prepare 未実行）も NG

2 があるので、1 を通すには prepare を回すしかなく、prepare を回せば新しい本文が
抜粋に載ります。**単体では抜け道のある検査でも、組み合わせると抜け道が消える。**

例外を1つだけ置きました。**自分のチケット（マスターToDo 自身）はハッシュ照合から外す。**
作業ログを書くと必ずハッシュが変わり、毎回誤検知するからです。自分の作業ログは
そもそも根拠ではありません。

## ④の共起チェック — 警告は「数を絞る」ほうが効く

小項目の本文から識別力のある語（漢字3字以上・カタカナ3字以上・英字3字以上）を
長い順に8語取り、根拠チケットに1語も出てこなければ警告。形態素解析は入れません
（依存を増やすほどの精度差がない）。

チューニングで警告数がこう動きました。**ここが今回いちばん時間を使った所です。**

| 条件 | 警告数 |
|---|---|
| 本文の先頭一文だけから語を取る | 24 |
| 本文全体から取る | 18 |
| ＋ 根拠チケットの**成果物**も照合対象に入れる | 14 |
| ＋ 人が書いた裏書きの注記（`〔T-…・画面確認〕`）がある行は飛ばす | 8 |
| ＋ 語が1つしか取れない短文は2字語も拾う | **7** |

24件出す検査は読まれません。**読まれない警告はゼロ件と同じで、しかも「検査は通った」
という嘘の安心を配る分だけ有害です。** 7件なら全部見ます。

成果物まで照合対象に入れたのが効きました。「事実は成果物に書き、チケット本文は経緯だけ」
という書き方は普通にあって、本文だけ見ると正当な引用まで警告になります。
ただし**自分の成果物だけは除外**します（208項目の本文が全部入っているので必ず当たる）。

## わざと壊して NG を確認する（前回からの継続）

実在しないID / 存在しない memory / 日付凍結 / 更新行の欠落 / ハッシュ不一致 /
索引なし の6通りを壊して、全部 NG が出ることを確認してから納品しました。
PII の新パターンは「検出すべき7件」と「誤検出してはいけない文字列」の両方でテスト。
`@sellonamazonjp`（公式LINE）、Google Fonts の `wght@500`、CSS の `@media`、
`G201808410`（Amazon 政策ID）を巻き込まないところまで詰めています。

**検査を書いたら、通ることではなく落ちることを先に確かめる。**

## 既存成果物を壊していないことの示し方

実装後に prepare → build を回し、`01_master-todo.html` と `03_process-board.html` が
**更新前とバイト一致**することを diff で示しました。Mermaid の線の描き分け・
ズームボタン・縦積みレイアウトは社長の指摘で入っているので、ここが動いていない
という事実が一番強い証明になります（前回の render_html.py と同じ作法）。

## 機械で潰しきれなかったもの ＝ ③

「満たす」「一致させる」を『確認した』と読み替える誤りは、意味の判断なので
機械には無理です。やれたのは2つだけ。

- `judgement.md` に4語を追記し、「状態を指す動詞も物理事実」と明文化
- その動詞で終わる `[x]` に裏書きの注記が無ければ警告（現状2件）

残りは人の手順で担保します。**根拠抜粋を読む → 動詞で終わりの定義を先に決める →
現状がその状態にあるかを画面で確かめる**。抜粋を必ず読ませる①の対策が、
③にも間接的に効きます（7-1 は根拠チケット自身が「小口ではカートを獲得できない」と
書いていたので、本文を読んでいれば気づけた）。

## 検証中に見つかった副産物

動作確認で `prepare`→`build` を回している最中に、別セッションが新しいチケットを
1枚起票しました。ボードの「チケット総数」は `update_board.py` が自動同期するので
106→107 に動いたのに、`01_master-todo.md` 冒頭の手書き census
「（106枚 / done 61・doing 10・waiting 25・todo 10）」は動かない。**同じ資料の中で
数字が食い違う**状態です。

数えられる事実を人が手で書いている箇所は、遅かれ早かれ必ずズレます。
`evidence.py check` に census の照合を足しました（警告どまり。ボード側が自動同期
されるうえ、記述の性質が注記なので納品は止めない）。

なお、この確認作業でボードを 107 に書き換えてしまったので、**社長の成果物は
`git checkout` で元に戻しました。** ツールの検証で成果物の中身を動かさない——
中身の更新はヒデアキの担当で、次の `/buppan-todo` で正しく入ります。
