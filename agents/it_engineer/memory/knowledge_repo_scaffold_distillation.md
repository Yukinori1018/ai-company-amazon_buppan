# 運用リポジトリを「別事業へ転用する雛形」に蒸留する手順

初出: 2026-09-04 / T-20260904-002（Amazon物販事業リポ → ホームページ制作事業リポの雛形生成）
**「このリポのルールを別事業に持っていける形にして」系の依頼が来たら、着手前にこれを読むこと。**

## 依頼の型（再利用可能）

社長依頼「このリポで決めたルール・運用方法をコピー（必要に応じて修正）して、別プロジェクトに転用できる専用フォルダを作れ。作成後は自分で移設する」。

**最初に確認する3点**（これが決まらないと着手できない）:

1. **転用先の事業は何か** — agent.md の例示・法務論点・KPI 軸が全部これで変わる
2. **持ち出す範囲**（骨格ルールだけ／＋汎用ナレッジ／＋事業ナレッジも）
3. **出力先** — **コピー元リポの外に必ず出す**。本リポは PUBLIC + 30分ごと `git add -A` push なので、内側に作った瞬間に163ファイルの複製が公開される

## 判断の軸はこれ1本

**「事業が変わっても価値が変わらないか」**

- 仕組み・規律・失敗から生まれた運用ルール → 持ち出す
- 特定のサービス・商流・商品に紐づく知識 → 捨てる
- **迷ったら捨てずに残し、引き継ぎメモの「要判断リスト」に列挙する** — 判断を自分で握り潰さない

## 効いた手順

### 1. まず機械的にスコアリングして「読むべきファイル」を絞る

112本のメモリを全部読むのは無駄。事業固有語の出現数で当たりを付けてから、境界のものだけ冒頭8行を読む。

```bash
for f in $(find agents -path '*/memory/*.md'); do
  n=$(grep -ciE 'amazon|keepa|netsea|物販|FBA|SKU|仕入' "$f")
  printf '%4s hits /%4s lines  %s\n' "$n" "$(wc -l < "$f")" "$f"
done
```

**ただしヒット数だけで決めてはいけない。** 実際に効いたのは次の2パターンで、どちらもスコアが誤導する。

- **低ヒットなのに固有** — 抽象的な書き方をしているだけで中身は物販
- **高ヒットなのに汎用** — 「型」を Amazon の事例で説明しているだけ。**型は事業非依存**なので残す

### 2. memory の固有名詞は書き換えない

**これが今回いちばん大事な判断。** memory は過去の判断の**記録**であり、後から固有名詞を消すと
「いつ・何を見てそう判断したか」が失われ、記録としての価値がゼロになる。
教訓が汎用でも、根拠になった事例は事例のまま残す。書き換えるのは agent.md / skills / docs / CLAUDE.md（＝**規範**）だけ。

### 3. スクリプトは「grep してから」移植する

移植したシェル/Python は必ず次を潰す。文書だけ直しても動かないものが残る。

| 潰すもの | 今回の実例 |
|---|---|
| ハードコードされた絶対パス | `github-sync.sh` の `REPO="/Users/.../ai-company-amazon_buppan"` → `SCRIPT_DIR` から自動検出（`${AI_COMPANY_REPO:-...}` で上書き可） |
| launchd の Label | `com.aicompany.amazon-buppan.github-sync` → `SYNC_LABEL` 変数化。**事業ごとにユニークにしないと片方が動かない** |
| 外部サービスの実 ID | Notion の page_id / data_source_id / Table view URL → `{{ }}` 化 |
| 環境固有のデータ参照 | session-start.sh のリマインダー④⑤（存在しない deliverables を見に行き毎回誤警告）→ ブロックごと削除 |

**bash の `${VAR:-{{ PLACEHOLDER }}}` は書けるが、必ず実際に展開して確かめる**（`bash -n` は通っても展開が壊れることがある）。

```bash
CARD_ID="${OWNER_TASKS_CARD_ID:-{{ NOTION_OWNER_TASKS_CARD_ID }}}"; echo "[$CARD_ID]"
```

### 4. フックは「構文チェック」で終わらせず「実行」する

`bash -n` は通るのに JSON を吐かない・空出力になる、が普通に起きる。標準入力を作って実際に叩く。

```bash
export CLAUDE_PROJECT_DIR="$PWD"
echo '{"prompt":"…","session_id":"t1"}' | ./.claude/hooks/delegation-check.sh
echo '{"stop_hook_active":false}'        | ./.claude/hooks/owner-tasks-sync-check.sh
```

削った番号は**採番し直す**（⑥→④）。欠番を残すと次に読む人が「④はどこ？」と探す。

### 5. 移植先で「元リポの不備」に気づいたら、雛形側では直す

読み込みが深くなるので必ず何か見つかる。今回は3件。

- `workspace/README.md` が**旧ルールのまま更新漏れ**（「最終納品物はリポ外」。CLAUDE.md §6 は3層ルールに移行済み）
- `docs/notion-setup-guide.md` の Assignee 選択肢が5職種のまま（実態は9職種＋owner）
- `agents/general_affairs/agent.md` のリンク切れ（`skills/` を指すが実体は `memory/`）

**元リポは触らない**（依頼の制約）。雛形側だけ直し、引き継ぎメモに「元リポ側の不備を修正した」と書く。
※ 元リポの修正は別チケットとして秘書に上げるべき。

### 6. 「一律除外」の指示にも例外はある

指示は「`docs/reference/` は物販固有なので除外」だったが、`docs/reference/web-site-build/`（サイト制作の6工程プレイブック）は**転用先事業の中核オペそのもの**だった。
機械的に従うと最も価値の高い資産を落とす。**持ち出したうえで、判断の根拠と残るリスク（社長提供の外部資料＝第三者著作物の可能性）を引き継ぎメモに書いて社長に返す**のが正解。

### 7. 検証は最後にまとめて自動化する

```bash
# Markdown 相対リンク切れ（Python 15行で書ける。手で見るな）
# bash -n × 全 .sh / ast.parse × 全 .py / json.load × 全 .json
# grep -rniE 'sk-|secret|token|api[_-]?key|password' で秘密の自己点検
# grep -rho "{{ [^}]* }}" | sort | uniq -c でプレースホルダーの残数を数える
```

**秘密スキャンのヒットは全部「プレースホルダー・変数名・注意書き」になるはず。**
1件でも実値らしきものが出たら止まる。

## 転用先で真っ先に空になるもの（先に社長へ伝える）

事業が変わると **法務 memory がほぼ全滅する**（今回 17本 → 8本、うち HP 制作の知識は 0本）。
論点が丸ごと入れ替わるため（古物営業法・薬機法・PSE → 著作権・素材ライセンス・権利帰属・下請法・特商法・個人情報）、
**「移設後の最初の1本は法務への発注」**を引き継ぎメモに書いておく。これを書かないと、
規範（agent.md）だけ新しくて知識がゼロの状態で走り出す。

同様に、**経理の計算式は定義できても実測値がない**。最初の1案件が終わったら実測を memory に残させる。
（先行事業の最大のボトルネックが「推定値のまま進めたこと」だった＝`feedback_research_accuracy_blocker`）

## 出力物の型

生成先直下に **`SETUP.md`** を置く。この4章立てが機能した。

1. これは何か／持ち出した範囲／`git init` していない旨
2. 何を持ち出したか（表）／メモリ選別結果（役職別の 残/元）
3. 何を捨てたか（表・理由付き）
4. **移設後にやること（番号付き手順）** → フォルダ移動 → `git init` → §1 の穴埋め → Notion DB → シンボリックリンク → 自動同期 → 動作確認
5. **要判断リスト**（迷って残したもの／事業性質の違いで見直しが要る箇所）
6. 移植時に修正したパス・値の一覧（変更前 → 変更後）
7. 最初のセッションで秘書に投げるとよい依頼

**5 が本体。** 「迷ったので残しました、判断はお願いします」を明示的に列挙することで、
自分の判断で握り潰さずに済み、社長が後から見直せる。

## 追記（2026-09-04・秘書の受け入れ指摘を受けた是正）

雛形を納品したあと、秘書から**「元リポの矛盾がそのまま持ち込まれている」**という指摘を受けた。
蒸留作業でいちばん見落としやすい型なので、独立した節として残す。

### 見落とした型：「実体が消えたのに参照だけ残った」記述

CLAUDE.md §3 鉄則8 が「Notion『社長タスクまとめ』カード（Status=「まとめ」列）を最新化せよ」と書き、
同じ CLAUDE.md §6 が「まとめカードは廃止し waiting 列が引き継いだ」と書いていた。**同一ファイル内で矛盾していた。**
Notion の実態は page_id が 404、Status 選択肢も4つだけ。庶務は「存在しないカードを探して読み替える」を**3回**繰り返していた。

**なぜ初回で見落としたか。** 蒸留のとき私は「Amazon / Keepa / 物販という固有名詞」を検索軸にしていた。
この矛盾には固有名詞が1つも無いので、その grep には**原理的に引っかからない**。

### だから、蒸留では固有名詞 grep に加えて必ずやる3点

1. **規範ファイル同士の突き合わせ** — CLAUDE.md の §同士、CLAUDE.md と skills、skills と hooks。
   同じ概念（今回は「社長タスクの可視化先」）が2箇所以上に書かれていたら、**両方読んで一致を確認する**。
2. **参照先の実在チェック** — `§◯◯` という節参照は、その見出しが本当にあるか grep する。
   今回これで2件出た：`§チケット言及時の即時同期確認`（節そのものが無い）、`§着手前の可視化`（`§振り分けの原則` に改題済み）。
   Markdown の相対リンク切れは自動チェックしていたが、**「ファイルは在るが節が無い」は素通りしていた**。

   ```bash
   # CLAUDE.md 等が指す § 見出しが実在するか
   grep -rn "§[^ 。、）]*" CLAUDE.md | ...  # 参照側を集めて、被参照ファイルの ^# と突き合わせる
   ```
3. **memory と規範が食い違っていたら、memory のほうが新しいことがある** — 今回まさにそれ。
   マリエの `owner-tasks-summary-ownership.md` / `notion-sync.md` には
   「まとめカードは実在しない・可視化は waiting 列」と**正しく**書かれていた。
   現場（memory）が先に気づき、憲法（CLAUDE.md）が追随していない状態。
   **規範を信じて memory を疑うと逆になる。** 食い違いを見つけたら、日付と実照会の記録がある方を採る。

### もう1つの見落とし：外部サービスの実 ID

`agents/general_affairs/skills/notion-ticket-sync.md` §2 の接続先テーブルに、
**先行事業の Notion Database ID / Data Source ID / Table view URL / 親ページ ID がそのまま残っていた。**
初回の実 ID 検索を `.claude/commands/` にしか掛けていなかったのが原因。

これは「動くが間違ったところに書き込む」最悪の種類のバグで、
**新事業のチケットが旧事業のボードに書き込まれる**。データが壊れるまで誰も気づかない。

```bash
# 実 ID の全数検査（memory は歴史記録なので除外してよい）
grep -rnE '\b[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\b|\b[0-9a-f]{32}\b' . \
  --exclude-dir=.git | grep -v "/memory/"
```

**UUID とハイフン無し32桁 hex の両方を見る**こと。Notion は URL 内でハイフンを落とすので、片方だけだと漏れる。

### 是正で選んだ形（次も同じにする）

- **矛盾は「片方を消す」ではなく「実態に寄せて1本化」する。** 今回は waiting 列＝社長タスク一覧に統一し、
  同期先を `workspace/owner-tasks.md` の1つだけにした。
- **「なぜそうなったか」を注記として残す。** 「まとめカードは作りません」だけだと、
  半年後に誰かが親切心で作り直す。「廃止された経緯があり、庶務が3回 404 を踏んだ」まで書くと再発しない。
- **フックには『ここに書き足すな』と書く。** `owner-tasks-sync-check.sh` の冒頭に
  「ここに『Notion まとめカードも更新せよ』と書き足さないでください」と明記した。
  ルールは風化するが、実行されるファイルの中のコメントは触る人の目に必ず入る。
- **存在しない節を指していたら、参照を消すより節を作るほうが良いことがある。**
  `§チケット言及時の即時同期確認` は CLAUDE.md 鉄則7 が要求する運用として妥当だったので、
  秘書スキルに実体を新設した。参照だけ削ると、鉄則7 の手順が誰も書いていない状態になる。
- **元リポ側の是正は勝手にやらない。** 作業範囲は雛形の中だけと指示されていたので、
  引き継ぎメモに「元リポには同じ矛盾が残っている・別チケットで起票を」と明記して返した。
