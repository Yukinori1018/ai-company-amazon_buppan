# Keepa のトークン天井と、無人スキャンの設計（実測・2026-08-24 / T-20260817-005）

`knowledge_overnight_3000_scan` の続編。**「母数を取り続ける」系の依頼が来たら、まずここを読むこと。**

---

## 1. トークンは「貯められない」— これが母数の天井を決める

| 項目 | 実測値 |
|---|---|
| トークン上限 | **1,200**（これ以上は貯まらない） |
| 補充 | **20/分 = 1,200/時** |
| 12時間で使える総量 | **約 14,400** |

**上限が1,200しかないので「昼のうちに貯めて夜に一気に使う」ができません。**
つまり無人スキャンのスループットは、実装の巧拙ではなく **20トークン/分** で決まります。
社長に見積りを出すときは、この1行から逆算すること。

## 2. エンドポイント別の実単価〔実測・domain=5〕

| 呼び出し | 単価 | 備考 |
|---|---|---|
| Product Finder | 10 + ceil(件数/100) | perPage=1000 なら **1000件で20トークン**（激安） |
| `product?stats=365` | **1 / 件** | stats を付けても追加コストなし |
| `product?offers=20` | **6.4〜6.5 / 件** | 素の product の約6.5倍 |
| `seller` | 1 / ID | 一度引いたらローカルに貯めて二度引かない |

### `offers` は 20 未満を要求できない〔実測〕

```
offers=10 → {"message": "Either no or a minimum of 20 offers must be requested.",
             "type": "invalidParameter"}
```

**単価を下げる余地はありません。** 実セラー数（distinct sellerId）が要るなら 6.5トークン/件を払うしかない。
だから **安い判定（1トークン/件）を先に通した行にだけ offers を掛ける二段構え**が必須。
1段でまとめて `stats + offers` を取ると 6.5トークン/件、二段なら `1 + 通過率×6.5`。
通過率60%なら 4.9 vs 6.5 で、二段の方が3割安い。

### 実効レート〔実測〕

25件 / 7分53秒 / 216トークン ＝ **8.6トークン/件・約190件/時**。
（内訳: 詳細25 + offers 約22件×6.5 + 新規セラー名）
→ **12時間で約2,300件処理・候補1,200件前後**が物理的な天井。

## 3. バッチは「1リクエストの上限」ではなく「1周の所要時間」で決める

`product` は100件まで受け付けるが、**100件バッチは失敗だった**。

補充20/分に対し、100件バッチ1周のコストは 詳細100 + offers 約90×6.5 ≒ **685トークン ≒ 34分**。
その34分間、CSV も progress.json も1行も動かない ＝ **無人運転で生死が外から分からない**。
しかも途中で落ちたら100件ぶん取り直し。

**25件に落としたら約8分周期になった。トークン単価は件数ベースなので、コストは1トークンも増えない。**

> 教訓: 無人バッチのサイズは「APIの上限」ではなく **「1周が何分で終わるか」** で決める。
> 目安は **5〜10分**。それより長いと監視できず、短いとHTTP往復が無駄に増える。

## 4. 探索空間はシャードに割って「ラウンドロビン」で回す

母集団48,760件に対し12時間で処理できるのは2,300件（5%）。
**1シャードを掘り切ってから次へ行くと、成果物が最初の1帯だけで埋まる。**
実際、価格帯 1,500〜1,999円を掘り続けた結果、候補181件のカテゴリは
パソコン周辺62 / 家電46 と偏った（＝その帯の棚の性格がそのまま出る）。

対策: 価格帯で25シャードに割り、**1巡につき1シャードから1バッチだけ**食べて次へ回す。
各シャードの ASIN キューはメモリに持ち、Finder ページの再取得を避ける。

## 5. 再開の急所 — ページカーソルを進めるタイミング

Finder 1ページ = 1000件を DETAIL_CHUNK ずつ食べる設計にすると、**カーソルをいつ進めるか**が事故る。

- ❌ ページ取得の直後に `cursor += 1` … 途中で止めた回の**残り900件が二度と拾えない**
- ✅ **キューを食べ切ってから** `cursor += 1` … 再開時に同じページを引き直し（20トークン）、
  `seen` が既取得ぶんを弾いて残りだけが積まれる

テストで固定してある（`test_interrupted_page_is_resumed_not_skipped`）。
「母数を取り続ける」系のコードでは、ここが一番静かに壊れる。

## 6. 自動停止は4条件セットで持つ（社長の明示要望）

1. 通算時間（既定12時間）
2. トークンが枯れ、**60分以上回復しない**
3. **1巡まるごと新規ゼロ**が3回続く（＝掘り尽くした）
4. **`STOP` ファイル**の存在

### STOP ファイルは起動時に勝手に消さないこと

最初 `if STOP.exists(): STOP.unlink()` と書いたが、これは
**「止めたい」という意思表示を次回起動で握りつぶす**設計だった。
正しくは「STOP があったら起動を断り、消し方を案内する」。テストで固定した。

実走確認: `touch STOP` から **150秒以内**に安全停止し、CSV は全行残った。

## 7. 「取得済み」に入れるのは CSV に書き切ってから

```
❌ 詳細取得 → seen に記録 → 評価 → CSV 追記      # 途中で落ちると行が無いのに二度と拾えない
✅ 詳細取得 → 評価 → CSV 追記 → seen に記録
```

## 8. `.gitignore` は **ファイルを1つ作る前に**書く

2026-08-21 に `raw/*.json.gz` 23MB を履歴に混入させた（除去は §4.1 で社長判断待ちのまま）。
