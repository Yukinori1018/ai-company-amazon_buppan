# monthlySold は連続量ではなく「Amazon が表示しているか否か」の2値

記録: タカシ / 2026-09-29 / T-20260920-003（成果物 19）
姉妹編: `knowledge_monthlysold_hot_vs_cold`（存在する／しないの話）／`knowledge_keepa_dropcount_is_polling`

## 一行で

**`monthlySold` を「100→50→30」と下げる感度分析は無意味です。**
値は 50 / 100 / 200 / 400 / 1,000 … のような**離散の階段**しか取らず、
それ以外は**そもそもフィールドが無い**（None）。下げても該当する商品が存在しません。

## 実測（NETSEA 起点 268 ASIN・2026-09-29）

| monthlySold の値 | 件数 |
|---|---:|
| **None（フィールドが無い）** | **252（94%）** |
| 50 | 6 |
| 100 | 4 |
| 200 | 3 |
| 400 | 1 |
| 1,000 | 2 |

感度表に出た結果がそのまま証拠になりました。

| 緩めた先 | 通過件数 |
|---|---:|
| 100個以上（現行） | 1 |
| 50個以上 | **1** |
| 30個以上 | **1** |
| 10個以上 | **1** |
| **条件から外す** | **40** |

**1 → 1 → 1 → 1 → 40。**間が無いので、レバーは「使う／使わない」の2択だけです。

## だから設計はこうなる

1. **感度表に `monthlySold` の中間値を並べない。**「50に下げれば増える」は嘘になります。
   並べるのは「**外すか外さないか**」と、外した場合の中身の質。
2. 外した40件の質は**別の軸で示す**。今回は**売れ筋ランク**で示しました
   （40件のランク中央値は16万位、5万位以内はわずか5件、うち19件が同型の蛍光灯）。
   → 「40件に増えます」だけ書くと、社長は数を見て緩める判断をしてしまいます。
3. `monthlySold` が無い商品の実売を測りたいなら、**ランク本体**を使う
   （ドロップ数は観測回数であって販売数ではない）。

## 前絞りをランクでやるときの当たり（同データ）

`monthlySold ≥ 100` だった10件の旧ランクは **2,378〜4,018位**。
一方、旧ランク3万位以内なのに `monthlySold` が無かったものが18件ありました。

> **ランク上位は monthlySold の必要条件であって十分条件ではない。**
> ランクで前絞りするなら 3万位以内で十分（それより下から ms≥100 は出ませんでした）。

## 感度表を書くときの自戒

今回、最初は「採算（利益率）」で250件を前絞りしてから Keepa に投げました。
ところが律速は採算ではなく `monthlySold` で、**前絞りの軸を間違えていた**。
やり直しに53トークン余計に掛かりました（総338／上限400）。

> **律速が分かるのは1周回した後です。**だから1周目は小さく回し、
> 段ごとの残存件数（ファネル）を必ず出す。どこで落ちているかが見えれば、2周目の軸が決まります。
> 今回は「238 → 10」の1段だけが全体を決めていました。
