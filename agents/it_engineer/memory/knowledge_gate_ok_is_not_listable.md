# restrictions/approve の OK は「出品できる」ではない（2026-10-11 夜・T-20260930-001 担当S〜W 反映）

## 何が起きかけたか
- 62b（restrictions/approve の実画面）は「新品の申請経路がある」なら OK と出る。ブランド申請が要る商品も OK
- `apply_gate_checks()` は「OK かつ 10/10 lookupAsin が空」を「出品できる」と書いていた → 第1弾（＝そのまま出品できる）に入る
- 今夜の134 ASIN は全部 lookupAsin 未実測。カズヨが「出品許可の要否」列（要107／不要20）を足してくれたので、直さなければ**第1弾が 120 ではなく 174 になり、許可要の54社が「そのまま出品できる」に混ざる**ところだった

## 直し方（型）
- 証跡ファイルに要否の列があれば、それを優先して「出品許可が必要（…）／新品の申請経路あり」と書く＝第2弾
- 列が無い旧ファイルは従来どおり（lookupAsin が正）。**基準（第1弾の定義）は変えずに、入力の読み方だけ直す**
- 直したら「直さなかった場合の件数」と並べて報告する（120 vs 174）

## 同じ夜の手順（再利用可）
1. シート退避（FORMULA の JSON）・40_採算列と63 の .bak
2. xdup を「--through の範囲だけ」読む版で再照合（作業中のバッチを読まない）。部分一致の誤検知が多いので、実重複は判定列と公式URLで目視
3. `40_profit_cols.py --offline` → 既存行の差分0を確認（新規 ASIN の採算が無いと「採算あり」が減る）
4. **agent_output 側（シンボリックリンク）から** `sync_ledger.py --through=… --unchecked-out=…` を3回
5. 3回目のあと、collect() の期待値とシートを全セル突合。USER_ENTERED で日付がシリアル値になるので揃えて比較（素朴に比べると全行不一致に見える）
6. 前回シートの打診順と比べて「第1弾に入った社／外れた社」を社名で出す
