# 「取り分」で足切りすると、残るのはバリエーションの子に偏る（2026-09-12 / T-20260912-001）

## 何が起きたか

タケシの足切り「取り分 ＝ 30日ドロップ数 ÷ (出品者数+1) ≧ 月6個」を、出品ゲートで落ちた12件に当てた。
**残った3件は全部がバリエーションの子だった**（ドクターランドリー2色＝同じ親の兄弟、麗白）。単体は0件。

原因は構造的なもの。子は親ファミリーの売れ筋ランクを共有するので、ドロップ数も兄弟の売上で増える。
**取り分の降順で並べると、上位ほど「兄弟の売上を借りた子」になる。**
兄弟を2 SKU と数えると、同じ需要を二重計上する。

## 2つの物差しが逆を向く件がある

Amazon 公表の「過去1か月で◯点購入」（`monthlySold`）で見ると、次のように結論がひっくり返った。
- ドクターランドリー: ドロップ数では信用できない子。しかし公表値では足切りを大きく超える
- Brighte（単体）: ドロップ数では足切り未満。しかし公表値では超える

**足切りの結論を出すときは、ドロップ数と公表値の2列を必ず並べる。** 片方だけで書かない。

## 手順（再利用できる形）

1. 対象の ASIN を product API に `stats=30&history=0`、offers なしで一括照会する（1 token/件・最大100件/回）。
   `parentAsin` / `variations` / `monthlySold` が取れる。13件で13 token。
2. 既存スキャンの値（candidates.csv）で式を再計算する。order_set.py の「月販見込(推定)」と同じ値になるか検算する。
3. 列を分ける: 「バリエーション（子/単体）」「ドロップ数の信用（○/×）」「公表値ベースの取り分（参考）」。
4. 追跡ファイルには件数だけを書く。ASIN ごとの数値は `out/` にだけ置く。
   実装は `deliverables/T-20260912-001/share_calc.py`。

## 件数の食い違い（S6）の調べ方

「22件 vs 24件」は、断面の違う数字を1本の表に並べたことで生じた。
- 24 は回転ふるい時点の数字（サトルの確認前）
- 13 はサトルの確認後、`EXCLUDED_ASINS` を引いた数字
- 22 はどこにも無い数字（24−販売終了2 と一致するが、根拠は無い）

**件数の食い違いは、CSV から再集計して、各数字に「いつの断面か」「何を引いたか」を添えれば1回で解ける。**
記憶で説明しない。

## メーカー単位（本丸20社）で取り分を出すとき

T-20260906-005 の Keepa 検証は `/search` で存在確認をしただけで、販売データを保存していなかった。
**存在確認のついでに stats を保存しておけば、今回の再取得（約340 token）は要らなかった。**
次に「ブランドが Amazon にいるか」を確かめるときは、上位 ASIN の product stats まで取って残すこと。
追加は1社あたり10 token 程度で済む。
