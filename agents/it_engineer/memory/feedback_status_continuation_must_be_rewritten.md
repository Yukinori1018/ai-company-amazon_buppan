# 状態ファイルの「続き」欄は完了時に書き直す（2026-10-23）

## 何が起きたか
- `agent_output/T-20260930-001/entry_b_status.json` は、`status()` が `product取得済み` などの数値キーは上書きするが、
  人が手で書いた `続き` 欄（「残り2,353件・中断点 prod_wideB_0037〜」）は 10/16 00:05 のまま残っていた。
- 10/16 05:11 に入口(b) は全量完了していたのに、10/23 の夜間タスク（秘書）が `続き` 欄を読んで「残り2,353件を fetch せよ」と発注した。
- 数値キー（6053/6053）と `続き` 欄（3700/6053）が同じファイル内で矛盾していた。

## 処理のしかた（再利用できる手順）
1. 発注の前提（「残りN件」）は、状態ファイルの文章ではなく**実体**で確かめる：raw の `prod_<TAG>_*.json.gz` の本数×100 と order ファイルの件数、チケットの完了ログ。
2. fetch はキャッシュ済みなら消費0で即終わる。build は `--dry-run` で追加件数を先に見る。**追加0なら本番 build を流さない**（キューを書き直す・退避が増えるだけ）。
3. 新しい除外条件（例：56 の本体カート除外）が別スクリプトに無いときは、コードを足す前に**既にキューにある行を offline の buybox キャッシュで照合**して影響件数を数える（今回 786社中0社＝足す必要なし）。
4. 完了したら `続き` 欄を「残りなし＋完了日時」に書き直す。数値キーと文章欄の両方を見る。
