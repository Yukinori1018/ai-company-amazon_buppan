## 冪等の鍵を「JAN だけ」にしなかった理由

社長指示は「同じ JAN を二重登録しない」でしたが、鍵は **(仕入れ先, JAN)** にしました。
同じ商品が NETSEA と SD の両方にあるなら、それは**安い方を選べるという情報そのもの**です。
同一仕入れ先で入り数の違う口（SD の S1＝2点・S2＝3点）があるときは
**入り数の小さい口を残し、落とした口を備考に書く**。黙って捨てると
「1セット3点しか無い」を「1点で買える」と読み違えます。

## 見つけた既存バグ2件（列名から意味を推測した典型）

`discover.scan_suppliers()` が NETSEA の生データから読んでいたフィールド名が2つ間違っていました。
どちらも**エラーにならず、静かに全件 None**になっていました。

| 書いていた名前 | 正しい名前（公式スキーマ） | 影響 |
|---|---|---|
| `item_url` | **`product_url`** | `supplier_url` が全件空 → **§3.3-6（購入先URL が未確認なら GO にしない）で全件が UNKNOWN に落ちていた** |
| `stock_quantity` | **`set[].sold_out_flag`**（Y=品切れ/N=在庫あり） | 在庫が全件不明 |

**「UNKNOWN が多い」の原因が、判定の厳しさではなく取得漏れだった。**
UNKNOWN の山を見たら、まず**その列が本当に取れているか**を1件開いて確かめること
（memory: `knowledge_verify_field_semantics_not_names` と同じ型で、これで7件目）。

ついでに `product_name` / `consumption_tax_class` / `reference_price` も索引に入れました。
商品名が無いと台帳の「商品名」が全件「未確認」になります。

## 税込化は保守側に寄せる

NETSEA の `set[].price` は**1点の税抜**。シートは税込で持つので `×1.10`。
`consumption_tax_class` は 0/1/99 の意味が公式スキーマに書かれていないので
**推測で 1.08 にしません**。1.10（＝原価が高く出る＝保守側）にして、番号を備考に残します。
**原価を安く見積もる方向の推測はしない。**利益が出る方向に間違えるので。

## 「未確認」と「無し」を書き分ける

- 卸価格が取れない → `未確認`（**0 に畳まない**）
- SD の承認が無い → `卸価格未承認`（**申請すれば見える。NO-GO ではない**）
- NETSEA API に項目が無い（消費者直送可否） → `未確認`（**推測で ○/× を書かない**）
- `Amazonで該当ASINがあるか` が不明 → `未確認`（**「なし」と書かない**）
