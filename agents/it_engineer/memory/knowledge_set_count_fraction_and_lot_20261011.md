# セット数の分数・卸ロット表記・ケース数（2026-10-11 夜）

## やったこと（再利用できる手順）
1. 人の確認（set_check_*.csv）に分数「2/3」が入った → `score_20261004._num` に分数を読ませ、
   表示は `set_label()`（Fraction.limit_denominator(24)）。`int(n_set)` の箇所を grep で全部潰す
   （score / ledger_refresh / push_buy_candidates / order_plan の4ファイル）
2. order_plan の最小ロット換算は分数だと「卸の点数が整数になる Amazon 個数」まで切り上げる（2/3 → Amazon3個＝卸2点）
3. パーサは**人の確認全行（確度 高・中）で一致・誤り・UNKNOWN を数え、「原価を安く見る側の誤り 0」をテストにした**
   （test_set_check_20261011.py 1b）。結果：一致110・誤り3（すべて原価を高く見る側）・UNKNOWN127
4. ledger_refresh dry-run → 本実行 → もう一度 dry-run で差分0（冪等）。比較は数値の表示ゆれ（4280.00% と 42.8）を
   正規化してから。凍結する人の行は `L.is_human()` で数える（確認者=カズヨでも screen_checks 証跡の行は毎回引き直される）

## 見つけた型
- **テストが本番と違う引き方をしていた**：テストは JAN だけで卸の商品名を引き、本番は JAN→購入先URL。10/10拡張分は JAN 空なので
  テストでは卸名 None → 「NG 2件」はパーサではなくテストの引き方の問題だった。テストは本番と同じ関数（S.index_by_url）で引く
- **卸の商品名末尾の「xN」が最小ロットと同じなら入数（ロット）で、単価は1袋あたり**（国分ネット卸「蒟蒻ゼリー 130gx8」ロット8・人=8）。
  「50枚入」ロット50のマスクは x 形でなく1箱1点（人=1）なので、**x 形の末尾だけ**外す
- 「×24本入×(2ケース)」のケース数は別段。× か括弧の直後だけ拾う（「iPhone 15 ケース」に当てない）
- `MAX_PLAUSIBLE=60` が「2袋 × 64 個セット」の64を捨て、残った「2袋」で単品と読んでいた（原価1/64）。
  上限は束ね表記だけ120に広げ、中身の数（90包入）は60のまま
- 束ね表記の追加：「15本ロット」「【5個】」「(1g×150粒)×3」

## 結果と学び
- GO 2→2（増えず）。セット数が決まって採算が計算できた87行のうち **68行が C 等級＝赤字で UNKNOWN→NO-GO**。
  「セット数が決まれば GO が増える」は外れ。**単位を正しくすると赤字が見える**のが実態（§3.3-21 の再演）
- GO を増やす律速はセット数ではなく #5 カート・#9 キーゾン・#1-2 ゲートの人確認。gate_cart_queue は旧版が
  「前回 NO-GO だった行」限定で0件だったので、GO でも NO-GO でもない全行に広げた（6件）
- NETSEA 停止（10/7〜）の注記は `ledger_refresh.NETSEA_DOWN_NOTE`。復旧したら "" にするだけで消える
