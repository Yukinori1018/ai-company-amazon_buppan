# ZZH 同期（2026-10-27）：冪等確認の再実行が上流の中間ファイルを消していた

## 何が起きたか
- 入口(h) 3回目の build を冪等確認のためにもう1回走らせた（足す社0）。キューは追記型なので無傷だったが、
  `11i3_追加候補_入口h.csv` は毎回「w」で作り直す作りで、2回目は除外行98行だけになった
- sync_ledger は代表のFBA数を `11*_追加候補*.csv` から読む。ZZH の接触候補10社が全部「未確認：FBA数」→「対象外（基準未確認）」に落ちた
- dry-run の打診順が前回シートと同じ（第1弾151）だったことで気づいた。**新バッチを足したのに第1弾も第2弾も1件も動かないのは異常**として、新規 ASIN の判定経路を個別に出す（scratchpad の diag.py：sync_ledger.collect()＋dashin_order.assign を読むだけで回す）

## 冪等確認のやり方の修正
- 「2回目で差分0」を見るとき、追記先（キュー）だけでなく**上書き型の出力（11i{N}・12k{N}・status json）も md5 で見る**
- 再発防止として `56_entry_f.py` cmd_build に「足す社0で既存の候補行があれば OUT_CAND を書き換えない」を入れた

## 復元手順（再利用可）
1. 退避：キュー・status・11i{N}・12k{N} を `.bak_fix…` に
2. 窓口集めの batch（24_連絡先_batchXX.csv）を一時的に別フォルダへ（ledger_index が ASIN を既存台帳とみなして全部落とすため）
3. キューを build 直前の `.bak_entryh{N}_<時刻>` に戻して `58_entry_h.py build --round N`（prefetch 済みなら 0 token）
4. キューの md5 が元と一致することを確認 → batch・status を戻す
