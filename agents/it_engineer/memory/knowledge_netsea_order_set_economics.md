# NETSEA で「発注セット」を組むときの採算構造

初出: 2026-09-06 / T-20260904-004 A-2 本番適用
実装: `workspace/output/deliverables/T-20260904-004/build_order_sets.py`

## 商品リストではなく「発注単位」で出す

社長が実際にやるのは「商品を選ぶ」ではなく「**1社にまとめて発注する**」。
だから成果物は商品一覧ではなく、**サプライヤーごとの発注セット**にする。
1行1商品でも構わないが、`セットID` と `セットの説明`（何SKU・いくら・送料いくら）を必ず持たせる。

## 送料無料ラインの読み方（`GET /tariffs`）

**`gradual_border_price` は送料無料ラインではない。**`price2 == 0` のときだけ
「その金額以上で送料無料」。`price2` が正なら「安くなる」だけ。

実測で見た形:
- `border=10000 / price1=700 / price2=0` … 1万円以上で無料（普通の形）
- `border=1 / price1=990 / price2=0` … **切替金額が1円**＝実質すべて無料。
  API の値はこのとおりだが「実質常に無料」は解釈なので、そう書いて渡すこと

`/items` の `ship_fee` は 0.37% にしか値が入っていない。**送料は必ず `/tariffs` から取る。**

## 1SKU あたりの積み方は目的で逆になる

| 目的 | 積み方 |
|---|---|
| 1SKU の利益を最大化 | 上限（1万円）まで積む → `budget_filter.plan_purchase` |
| **SKU 数を増やす**（＝5〜10SKU を組む） | **下限（5千円）に届く最小の口数** → `plan_min_spend` |

同じ「予算5万円」でも、この2つは別関数にする必要があった。混ぜると 5SKU が組めなくなる。

## 実測（2026-09-06 / 26,942件から）

- 26,942 → 買ってはいけないリストで 9,816 → 予算で 80 → 中古確認で 78 → 4群で 77 → 回転で **32SKU**
- 32SKU を持つのは **12社**。うち **1社だけで5SKU以上を組めるのは2社**
- 残る10社のうち6社は送料無料ラインまで 10,576〜49,448円 足りず、単独発注なら送料 990〜1,200円

**予算そのもので落ちたのは 44件だけ。**予算段階の落選9,736件のうち94%は
「Amazon に商品が無い／赤字」で、予算とは無関係だった。
**「予算が厳しいから候補が出ない」は誤読になりやすいので、内訳を必ず分けて出す。**

## 1社完結より2社分散を推したときの理屈

1社完結セット（9SKU）は**全SKUが同一ブランド**になっていた。
そのブランドのゲートが1回閉じれば9SKU が同時に死ぬ。
2社合算セット（8SKU・粗利は1,763円少ない）は2系統に割れており、片方が死んでも片方は動く。

初回の目的が「1周を完走すること」なら、**粗利より全滅しないこと**を優先する材料を添える。
決めるのは社長。こちらは両方を並べて理由を書くところまで。
