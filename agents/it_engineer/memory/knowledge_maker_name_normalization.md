# Amazon ブランド文字列の正規化 — 実データで確認した汚れ方と対処

出典: T-20260831-001 Phase C。入力は `T-20260817-005/v14/03_メーカー名寄せ.csv`（822行）と
`T-20260804-001/contacts_batch1-4.json`（人手取得55社）。

## 結論（次に同じ作業をする人へ）

**正規化ルールを書く前に、必ず実データを1回スキャンして汚れの種類を数える。**
今回 `Counter` で数えたら ascii-only 525 / 括弧付き 124 / 法人格 11 だった。
この数字を見てからルールを書いたので、無駄な分岐を作らずに済んだ。

## 実在した汚れ（すべて822行の中にあった）

| 種類 | 実例 | 対処 |
|---|---|---|
| 不可視文字 | `‎バーベイタム(Verbatim)` | LRM/RLM/ZWSP/BOM/NBSP を明示的に除去 |
| 全角英数 | `ＡＮＤＥＲＹ` `ＹＡＺＡＫＩ` | NFKC |
| 法人格の合字 | `矢崎エナジーシステム㈱` | NFKC が `(株)` に開く → さらに `株式会社` へ |
| 法人格の位置 | 前株 `株式会社マーベラス` / 後株 `イースター株式会社` | **位置は動かさない**。照合時だけ落とす |
| 法人格の後の空白 | `株式会社 山本人形` | 法人格に隣接する空白だけ詰める |
| 括弧の和英併記 | `パナソニック(Panasonic)` `CASIO(カシオ)` `Eufy (ユーフィ)` | 外＝主表記、中＝別名。**順序は両方ある** |
| 括弧が訳語でない | `NBCユニバーサル…(LAQ)` | 訳語と決めつけず、単に別名として持つ |
| スラッシュ複数ブランド | `OM SYSTEM/オリンパス` `Ligare / ノーブランド品` | 先頭を主、残りを別名 |
| 中黒の異体字 | `ジャニーズ･エンタテイメント` vs `ジャニーズ・…` | 照合キーから記号を全除去 |
| 紛れ込んだ空白 | `ワー ナー・ブ ラザース・ホームエ ンターテイ メント` | 照合キーから空白除去 |
| 実体なし | `ノーブランド品` / `株式会社`（社名なし） | 分類で最初に弾く。追っても引けない |

## 踏んだ事故：和英併記を「単語」で割ると誤マッチする

`アストロプロダクツ Astro Products` を空白で単語分割して別名にしたら、
`Products` というキーで **`P&S Detailing Products` に誤マッチ**した。
`スクウェア・エニックス SQUARE ENIX` も `Square` で `Rolling Square` に当たった。

→ **単語ではなく「文字種の境界」で割る**（和名の塊 / ラテン文字の塊 の2つだけ作る）。
これで誤マッチ2件が消え、正しいマッチ15件は保たれた。
`normalize.split_scripts()` と `tests/test_normalize.py::test_splits_on_script_boundary_not_words` が回帰テスト。

## 「名寄せ済み」を信じない

822行は「名寄せ済み」の成果物だが、別名まで見て突合すると **12ペアの取りこぼし**が残っていた
（`LEGO(レゴ)` と `レゴ(LEGO)`、`イースター株式会社` と `イースター`、`ホンダ(Honda)` と `Honda` 等）。
実体は810社。

ただし **行は畳まなかった**。畳むと元シートと1:1で結合できなくなり、
社長の見ている v14 リストとの対応が崩れる。数を報告するに留めるのが正解。

## 列名から意味を推測しない（既存メモの再確認）

55社の `contacts_batch*.json` は `email` 列に**問い合わせフォームURL**が入っている行がある
（例: `"email":"https://www.sundaypaint.co.jp/contact-us"`）。
列名を信じて `メール` 列に流し込むと嘘になる。
`http` で始まるかどうか＝**値の形**で振り分けた。`knowledge_verify_field_semantics_not_names.md` と同じ罠。
