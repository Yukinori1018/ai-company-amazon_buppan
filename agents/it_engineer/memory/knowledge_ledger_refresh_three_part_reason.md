# 商品判定台帳の引き直し（T-20260920-003・2026-10-11）

社長指示（10/10 夜）：「仕入れられる商品を必ず台帳に加えろ。SD も。載せられない商品は基準を明示し『こう変えれば仕入れられる』を書け」。

## 手順（再利用できる型）
1. `26_候補提案パイプライン/ledger_refresh.py --dry-run` → `agent_output/.../ledger20261010/summary.json` で前後の件数を見る → 本実行
2. 書く前の全値を `before_*.json` に退避してから `ws.update("A2", 全行)`（様式・条件付き書式はシート側に残る）
3. 「確認者」にカズヨ等の人名がある行は**触らない**（§3.3-16）
4. 機械で全部通った行も **GO にしない**。UNKNOWN＋「機械判定は通過・実画面確認待ち」。上げる前に `consistency.check_row(S.as_row(s, full=True))` で算術を検算し、NG なら降格
5. SD はカズヨが人として見た卸価格（`sd_price_manual_*.csv`）があれば採算確定。**SD 品番は接尾辞なし**（`5053100` と `5053100S1`）なので前方一致で突き合わせる

## 学び
- **「台帳に入っていない39件」は事実ではなかった。**39件は全部台帳に居て、判定が 9/30〜10/01 の古いまま放置されていた。依頼文の前提も最初に数えて確かめる（§3.3-10）
- **台帳への追記が止まっていたのは別の口**：10/09 の新規逆引き 890件のうち台帳に入っていたのは14件（`push_ledger.py` が buy_candidates だけを流していた）。「1件判定したら1行」は**候補だけでなく全判定行**に効かせる
- **規定と実装のずれを2つ発見**（§3.3-22 の型）。①実売：実装は30万位より下で FAIL／§3.3-8 は10万〜50万位 UNKNOWN ②採算 C：実装は中央値20%未満かつ400円未満／§3.5 #18 は5%未満かつ400円未満。台帳側で読み替えて理由に明記したが、ライブラリ本体は未修正（秘書判断待ち）
- **セット数が未確定でも、候補の全部で等級が同じなら結論は動かない。**割れたら UNKNOWN にして「1点なら B・2点なら C」と両方書く（単位ずれは真偽）
- 採点は `date.today()` 基準なので、**日付が1日進むと季節の窓で落ちる行が出る**（10/09 候補43件 → 10/11 は20件が待ちに残った）。判定日を必ず列に書く
- 判定理由の「こう変えれば」は、ゲートごとの定型＋採算だけ数値（§3.5 B の原価上限＝max(売価−手数料−FBA−その他−売価×5%, …−400円)、`required_sell(…, 0.05)`、`bundle_advice`）。変えようがないのは「Amazon 本体がカート／新品申請経路なし／卸が Amazon 不可／JAN がカタログに無い／売れている根拠なし（季節ピークも無い）」
