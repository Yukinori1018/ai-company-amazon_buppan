# Python 3.9「Non-UTF-8 code」は長い1行の誤検知のことがある（2026-10-10 / T-20260930-001）

## 事象
- `60_apply_cart_check.py` が `SyntaxError: Non-UTF-8 code starting with '\xe4' ... line 4` で起動しない。カズヨは「sed で辞書を足して文字コードが壊れた」と判断していた。
- 実際はファイル全体が正しい UTF-8（`bytes.decode('utf-8')` も `py_compile` も通る）。**1行 800 字超に日本語を詰めた辞書行**を、Python 3.9.6 の**スクリプト実行時のファイル読込（トークナイザ）**だけが誤検知していた。

## 見分け方・直し方
1. `python3 -c "open(p,'rb').read().decode('utf-8')"` と `py_compile` が通るのに実行だけ落ちる → 文字化けではない。
2. 長い辞書・リストを**1行1要素**に分割する（`# -*- coding: utf-8 -*-` を付けても長い行のままだと再発しうる）。バックアップから復元する必要はない。
3. 辞書を機械で足すときは最初から1行1要素で書く。sed で1行に追記し続けない。

## ついでに見つけた不具合（同型に注意）
- 「空欄なら埋める」判定が、`未調査（batchEの範囲外）` という**プレースホルダを値ありと見なして**、10/5に実画面確認済みの246行に結果を書けていなかった。**プレースホルダ文字列は空欄として扱う**。
- 退避ファイル名が固定（`.bak_cart1005`）で、再実行のたびに元のバックアップを上書きしていた → 実行ごとに日時付き名へ。

## 基準チェック列の作り方（再利用）
- 判定ロジックは `deliverables/T-20260930-001/criteria_check.py` に分離（UI＝sync_ledger から呼ぶだけ）。値の優先順は 実画面 ＞ 候補CSV ＞ Keepa キャッシュ。Keepa の負値（-1/-2）は None。
- 出力は `OK` / `NG：理由` / `未確認：項目` の3値。理由に Keepa の値が入るので**シートにだけ出し、リポには集計件数だけ**。
- 落とし穴：入口フィルタを通った行を同じ Keepa キャッシュで再判定しても NG は出ない（循環）。効くのは実画面列・採算の平時売価・判定（本人カート）との突き合わせ。現在値の再確認をしたいなら Keepa の再取得が要る（有料 token）。
