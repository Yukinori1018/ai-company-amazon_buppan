# 「候補0件」は単一の原因では起きない。leave-one-out で測る

タカシ（IT）／2026-10-04／T-20260920-003
実装: `26_候補提案パイプライン/score_20261004.py` の `relax_table()`

## 何が起きたか

5日連続で候補0件。原価モデルを作り直し（成果物33）、価格履歴を入れ（本回）、
カート保持者判定を規定どおりに直した（§3.3-22）。**それでも 0〜2件。**

原価も売価も直したのに出ないので、**ゲートを1つずつ外して件数を数えた**（leave-one-out）。

| 無視する条件 | 候補数 |
|---|---:|
| 実売 | **46件** |
| 採算 | 20件 |
| 季節の窓 | 6件 |
| 価格の動き | 4件 |
| カート保持者 | 3件 |
| 仕入れ・セット数 | 2件（＝効いていない） |

**実売ゲート1本で44件落ちていた。**原価は主因ではなかった（§3.3-21 の再確認）。

## 自分のコードが条件を壊していた（§3.3-19）

実売の閾値を **ランク10万位以内**にしていた。ところが**このプールはランク30万位で集めた**
（memory `project_research_criteria_v13`）。**母数を30万位で集めて10万位で判定したら、
出ないのは当たり前。** 300,000 に戻したら 0件 → 17件。

→ **教訓：閾値を書くときは「母数をどの条件で集めたか」を確認する。**
  入口と出口で条件が違うと、原因が自分のコードにあることに気づけない。

## もっと重い発見：ランクが ASIN 単位の根拠になっていなかった

ランクで実売を代用していたが、**同じランク値を複数の ASIN が共有している**行が
266件あった（DNライティングの蛍光灯で 8 ASIN が 223,802位／239,411位／278,883位 を共有）。
これは**バリエーション family の共有ランク**で、
「この ASIN が売れている」根拠にならない（memory `knowledge_keepa_dropcount_is_polling`）。

実装: `velocity_of(product, shared_ranks)` — 全件のランク値を数えて、
**2 ASIN 以上が同じ値を持っていたら UNKNOWN に落とす**（人がキーゾンで実数を見る）。

`monthlySold` が取れていたのは **460件中9件（2%）**。

## 結論（戦略に渡すべき事実）

**入口が逆だった。**プールは NETSEA（卸）から入って Amazon に当てたので、
「仕入れは実在するが Amazon で売れていない棚」ばかりになった。
`monthlySold_gte` で**売れている棚から入る**向きが要る（`lane_selling_first.py`）。

## 再利用できる型

**候補0件の調査は、必ずこの順でやる。**

1. 各ゲートの PASS/UNKNOWN/FAIL を数える（全件・重複あり）
2. **最初に落ちたゲート**で分類する（どこで止まったか）
3. **leave-one-out**（1つ外したら何件か）← ここで初めて「どの条件が殺しているか」が出る
4. その条件の閾値を **母数を集めた条件と突き合わせる**
5. 緩めたときの件数を段階で出す（100k/150k/200k/300k/500k）

`score_20261004.py --relax` がこれを全部出す。**次に0件になったらまずこれを打つ。**
