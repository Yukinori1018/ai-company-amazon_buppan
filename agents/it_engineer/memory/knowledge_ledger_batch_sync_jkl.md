# 窓口採取バッチのシート反映の型（T-20260930-001・2026-10-11 担当J/K/L）

## 手順（次回も同じ）
1. シートを JSON で退避（agent_output/T-20260930-001/sheet_backup_before_<名>_<日付>.json。get_all_values(FORMULA)）
2. 完了報告の「寄せ先」を CSV と突き合わせ、未反映だけ直す（今回は L1115→K1016 のみ未反映。公開版も同じ1行を直す）
3. 40_profit_cols.py を再実行 → 旧CSVと ASIN キーで比較して既存行の差分0を確認
4. `python3 sync_ledger.py --through=batchL --unchecked-out=64_出品可否_未判定_<組>.csv`（dry-run→本番→もう1回→シート全セル一致）
   - 51列（基準チェック）・52列（出品可否）・53列（打診順）は sync_ledger の中で全部計算される。criteria_check / dashin_order を単独で回す必要はない

## 罠
- **採取途中のバッチ（24_連絡先_batchM/N/O…）が作業中にも増える**。除外リスト（--exclude）は30分で2回破れた。**「ここまで読む」（--through）で切る**
- 新しい行は出品可否だけでなく **カート保持者の実画面確認（30_verify_cart.tsv / 61_checked_asins.json）も未** なので、ゲート確認だけ済ませても dashin_order の検算で落ちる。ブラウザ作業はゲートとカートを1回で両方やるよう 64 に両方の列を出した
- 行数（943→1191）は増えても第1弾は 62→62。報告は「第1弾が増えない理由と、何をすれば何社増えるか（上限58）」まで書く（§3.3-36）

## 2026-10-15 追記：再確認（recheck）だけの回の型
- 新しい採取バッチが無く 24_連絡先_recheck_<日付>.csv だけ増えた回は、**行数は変わらない**（代表ASINで既存行を差し替えるだけ）。40_profit_cols.py の再実行は不要
- `--unchecked-out` の出力名は**サトルが同じ日付で出した 64_出品可否_未判定_<組>_<日付>.csv と衝突させない**（今回は `_RC4sync_` にした）。上書きすると担当の成果物が消える
- 前後比較は送信順で行位置がずれるので**位置ではなく「代表商品（Amazon URL）」キーで比べる**（位置比較だと2,085行が「変わった」と出るが、実際は902行で大半が送信順の振り直し）。打診順の区分ごとの増減がサトルの集計（接触候補・重複・除外の件数）と一致するかで検算する
