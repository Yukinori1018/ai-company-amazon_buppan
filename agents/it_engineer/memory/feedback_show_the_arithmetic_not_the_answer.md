## なぜ劣化したか（原因は列の削除。デザインではない）

PUBLIC リポに Keepa 由来の加工値を書けないという制約を、**Git 追跡外の `out/` に置く成果物にまで**
適用して、ドロップ数・月販見込・手数料内訳を列ごと落としていた。

**制約が効くのは追跡ファイルだけ。`out/` は `.gitignore` 済みで公開されない。**
社長が実際に開くのは `out/` の HTML なので、ここを削ると社長の手元だけが痩せる。
`.gitignore` を書いた本人（自分）が、その `.gitignore` の効果範囲を忘れて自主規制した形。

**教訓: 秘匿の判定は「ファイルが追跡対象か」で決める。「チケットが PUBLIC リポにあるか」ではない。**

## 「項目毎の数字」とは何を出すことか

社長の言う「どういう計算をしたのか分からない」は、結論の数字が信用できないという意味。
結論だけ出す限り何度でも同じ指摘が来る。**式と引き算を画面に置く。**

1. **式そのものを書く**（`.formula` ブロック）
   ```
   月販見込 ＝ 30日ドロップ数 ÷ (出品者数 + 1) ＝ 14 ÷ (14 + 1) ＝ 0.93 個/月
   回転月数 ＝ 出品数 ÷ 月販見込 ＝ 32 ÷ 0.93 ＝ 34.3 ヶ月
   ```
2. **利益は1行ずつ引く**。売価 → 卸値 → 販売手数料 → FBA配送料 → 基本成約料 → 保管料 →
   納品送料 → 返品引当 → 純利益。各行に「なぜその額か」を1列添える。
   **最後に検算行を出す**（横に足して合うか。丸め差があれば差額を書く）。
3. **推定は推定と書く**。ドロップ数は観測回数であって販売数ではない。
   「月◯個売れます」と書かない。用途は下限の足切りだけ、と毎回明記する。
4. **取れていない項目は「未取得」と書いて残す**。黙って列を消さない
   （今回: カート最終獲得日・カート不在率・バリエーション子は BuyBox 履歴が無く未取得）。

## 感応度を出すと、社長は初めて判断できる

「何が起きると赤字になるか」を SKU ごとに1行。今回入れたのは2つだけ。

- **値下げ耐性**: `Δ = 純利益 ÷ (1 − 販売手数料率)`。手数料も一緒に減るので分母が要る。
  「1,622円 → 1,119円 で利益ゼロ。同じ商品に出品者が14者」まで書くと自明になる。
- **保管料の膨張**: 見積は `storage_months=1.5`（3ヶ月で線形に売り切る＝平均在庫は半分）前提。
  実際に N ヶ月かかるなら `保管料 × (N/2) ÷ 1.5`。
  34ヶ月の SKU で 16円 → 183円/個、純利益 445 → 278円。**この1行が案の選択を変える。**

前提の定数（1.5ヶ月）はパイプライン側 `T-20260831-006/pipeline/config.py` にある。
二重定義になるので、コメントに「同値・意味」を書いて気づけるようにした。
