# 候補表の整合性検査 — 「2回目で0行」を成立させる作り方

2026-10-09 / T-20260920-003 / タカシ
実装: `scripts/sourcing_gate/consistency.py`（17検査）・`autofill.py`・`test_consistency.py`（80件）
設計と実測: `workspace/output/deliverables/T-20260920-003/38_整合性検査.md`

## 何を作ったか（一行）

候補CSVの算術を、**同じ公式料金表の関数（`fba_cost.py`）で引き直して検算**し、崩れていたら
数字を直さず**採算欄を空にして NG の印を立てる**。発注ゲート（`gate.py`）が `consistency: NG` を見て止める。

## 🔴 収束のしかけ（ここが一番の学び）

§3.3-17 は「是正スクリプトは2回目で0行になるまで完成していない」。素朴に書くと**原理的に収束しない**。

```
1回目: net_per_unit が NG → 採算欄を空にする → 印「NG: net_per_unit」
2回目: 採算欄が空なので net_per_unit は「対象外」→ 所見0件 → 印「OK」に書き換わる！
```

**是正が、その是正の根拠を消してしまう。**行が健全に見えるようになり、しかも毎回印が変わる。

対処は2つの組み合わせ。

1. **入力が無い検査は「不合格」ではなく「対象外」**にする（空欄を NG にしない）。
   そうしないと自分が空けた欄を自分が NG にし続ける。
2. **既にある印と詳細を読み戻し、新しい所見と「和」を取る。**
   消えた所見は「前回こう落ちた」として印に残り、新しい所見だけが増える。
   これで**印は単調増加＝安定**し、2回目が0行になる。かつ NG が消えて健全に見えることが起きない。

```python
prior_ng, prior_warn = _parse_mark(get(row, COLS.result))   # 印を読み戻す
all_ng = prior_ng | {f.check for f in res.blocking}         # 和を取る
lines.setdefault(f.check, f.line())                         # 既にある説明は上書きしない
```

**検算の型**：1回目・2回目・3回目を走らせ、`cmp` でバイト一致まで確認する。テストにも入れた。

## もう1つの罠：是正後のCSVを check すると「健全」に見える

採算欄が空なので所見は0件。そのまま読むと「表は綺麗になった」と誤読する。
→ **集計に「前回の NG の印が残っている行 N行」を必ず併記**し、exit code も 1 のままにした。
**自分が作った是正の副作用で、自分の検査が嘘をつく**構図なので、気づきにくい。

## 設計で決めたこと（次に同じものを作るとき再利用する）

| 決めたこと | なぜ |
|---|---|
| **数字を黙って直さない。空にするだけ** | どちらが正しいか分からない。直すと辻褄だけ合って嘘が一段深く潜る（§3.3-17） |
| **番兵も採算欄を空にする** | 印だけ付けて数字を出すと、解けなかった行が必ず利益率の上位に来る（2026-09-07 の事故。`knowledge_flag_without_suppressing_the_number`） |
| **売価と日付は消さない** | 採算の*入力*であって結果ではない。消すと「なぜ落ちたか」が読めない |
| **捨てた値は report JSON に原本ごと残す** | 隠すのではなく、独り歩きを止める |
| **`timeline_stale` は WARN に留める** | NG にすると表が1日古くなるだけで648行全部の数字が消える。鮮度は `max_age_days` が ASIN ごとに見ているので二重執行しない |
| **料率は「どの段か」を当てない** | カテゴリーがCSVに無い。**どの段でもないこと**と**崖の向きが逆**だけを見れば、出所に依存しない検査になる |
| **検査の失敗を合格にしない** | `fba_cost` が import できない／検査が例外 → NG。検査できないことを○にしない |

## 検査の作り方：逆算した値を出すと、人が読める

`1個手残り` が合わないとき「合いません」だけでは直せない。**手残りから売価を逆算して並べる**と原因が自明になる。

```
1個手残りが引き算と合いません。7,990 − 952 − 430 − 187 − 7,055 = -634円 ですが、表は -306円。
**表の手残りから逆算した売価は 8,318円** で、表の90日中央値 7,990円 と違います。
```

これで「価格を取り直したのに採算欄に反映されていない」と一目で分かった。
**不変条件の検査は、差分ではなく「崩れている側の値がいくらなら辻褄が合うか」を出す。**

## autofill の約束

1. **human 項目を PASS にしない。**UNKNOWN ＋「なぜ決まらないか」＋「取り方」。**空欄で埋めない**

## ゲートへの繋ぎ方：pseudo-item にして id を spec に入れない

`gate.evaluate` が `rec["consistency"]["result"] == "NG"` で Problem を足す。

- **`consistency` を spec の項目にしなかった**ので、`check_record.py set <ASIN> consistency --result PASS` は
  「未知の項目 id」で弾かれる＝**手でごまかす道が無い**
- ただし**フックの案内文が `set ... consistency` を勧めてしまった**（最初の実装）。
  案内が抜け道に見える文面になっていたので、`consistency` を案内対象から外して
  「CSVの算術を直して autofill で取り直す」に変えた。**ゲートを作ったら案内文も抜け道でないか読む**
- 記録が**無い**ときは止めない。ここで二重に fail-closed にすると過去の記録が全部無効になり、
  **ゲートを外す圧力**になる（21項目で既に止まる）

## 🔴 直し方：「宣言させる」設計にした（§3.3-19）

誤検知の根は「**表の列名（90日中央値）と、計算に使った値が違う**」こと。
閾値をいじるのではなく、**生成側に基準を宣言させた**。

```
採算の基準売価 / 基準売価の出どころ（実画面 / 90日中央値 / 180日中央値 / 現在価格）
```

検査は①宣言どおりに計算されているか ②その基準が**現在価格でないか**（§3.3-28）を見る。
→ 誤検知5件が消え、**現在価格で採算を組む行は依然として止まる**。両方が成立した。

**「2つのデータ源をつなぐ口は、単位を渡させる」は売価にも効く。**
単位（卸1点/セット）だけでなく、**どの値段で計算したか**も「渡させる」対象。

⚠️ 付随して踏んだ罠：出どころのラベルを `else: "現在価格"` で書いたら、
**価格が1つも取れていない146行が「現在価格」と表示された**。
**else 節にもっとも重い意味を置かない。**「取れていない」を明示的に分けること。

## 本物の発見：1,000円の崖を逆向きに踏んでいた（他エージェントの表で2行）

売価 1,122円 / 1,027円 なのに **FBA配送代行が「安い列」（売価1,000円以下用）の値**で計算されていた。

**不変条件の検査は、違反の事実より『どちらへ間違えたか』を書くと直してもらえる。**
