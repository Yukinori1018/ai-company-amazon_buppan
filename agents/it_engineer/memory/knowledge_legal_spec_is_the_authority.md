# 法務の仕様を実装するときは、写経せず読み込む。食い違いは握りつぶさず申し送る

2026-09-08 / T-20260907-001（法務判定 T-20260908-001 の #1 電気用品 v2 を実装）。

## 語彙をコピーしない

法務の `04_pse_rule_v2.py` / `03_pse_rules_v2.json` を **importlib で読み込んで動かす**。
語彙を自分のモジュールへ写すと、**法務が仕様を直したときに実装だけ古いまま黙って動き続ける。**
テストで固定した: `assert "ACアダプタ" not in src`（写経していないこと）。

## 3レーンの意味を潰さない

    HARD   … 自動除外
    REVIEW … **除外しない。**印を立てて候補に残す。ただし発注可ではない
    PASS   … その法律の対象外

**「通過＝発注可」にしない。** REVIEW は `requires_document_check` として持ち、
CSV に「要書類確認(通過≠発注可)」列と法務の確認文を出す。
印を立てるだけで数字を出し続けた事故（同チケット前半）と同じ轍を踏まない。

## 機械で判定してはいけないと書かれた所は、機械で判定しない

直管形LED（LED蛍光灯）は電安法の対象/対象外が**同じ商品名の中に混在**し、
商品名・JAN・カテゴリからは判別できない。**REVIEW で残して人間の現物確認に回す**のが正解。
`直管` を無条件に落とす条件を書くと、社長が「残す」と決めた商品が消える。**テストで固定する。**

## 仕様と実装が食い違って見えたら、実装を仕様に合わせて、食い違いを報告する

- 1E の語「電源」が `直管LEDランプ 電源内蔵型` を HARD にする一方、
  human_gate は同じ物を「丸PSEマークがあれば販売可」としていた
- 1F の「ライト」「スタンド」が **REVIEW 72件中59件（82%）** で光源以外を拾っていた
  （テーブルランナー "ライト"ベージュ＝色名／アンブレラ"スタンド"＝傘立て）

どちらも**実装側で緩めない。** 件数を添えて法務へ返す。
実装で握りつぶすと、法務が塞いだ穴が黙って開き直る。
**「除外はされないから実害は小さい」も書く**が、
「確認作業が5倍になり、本当に要る13件が埋もれる」という**コストも数字で書く。**

## 結果: 申し送った2件は、2件とも仕様側の誤りだった（2026-09-08 追記）

法務ハルオの回答は「**いずれも当職の誤りであり、実装は仕様どおりに動いていた**」。
**実装側で緩めず、現状の挙動をテストで固定して返した判断が正しかった**と明記された。

> 仕様と実装が食い違って見えたとき、**実装を仕様に合わせたうえで件数を添えて返す**のが正解。
> 「実害が小さいから」と実装側で握りつぶしていたら、仕様の誤りは永久に直らなかった。
> 空振り82%という**数字**を添えたことが、仕様の見直しを動かした。

v2.1 の実測効果（候補1,318件）: REVIEW 72→20、空振り 59→1、候補 1,305→1,318。
**母数を失わずにノイズだけ消えた。**

## 仕様が更新されたら、自分の「固定テスト」は役目を終える

申し送り中の挙動を固定したテストは、**仕様が直った瞬間に落ちる**。
これは回帰ではない。**テスト名に「法務へ申し送り」と入れておくと、
落ちたときに回帰か役目終了かを名前だけで判別できる。**
決着したらテスト名も実態に合わせて書き換える（申し送り中の名前を残さない）。

## 評価順そのものが仕様のときは、順序を変えたら仕様側のテストを回す

`1A〜1D → 1G → 1F_PRE → 1E → 1F → 1H`。
法務は「1F_PRE を新設した際に 1G を後ろに置き、v2.0 の判断が静かに失われた」欠陥を
自分のテストで検出している。**規則を1本足したら、既存規則との順序を全部洗い直す。**
（T-20260904-004 でも同じ形の失敗が起きている。順序依存の規則集での定番事故。）
