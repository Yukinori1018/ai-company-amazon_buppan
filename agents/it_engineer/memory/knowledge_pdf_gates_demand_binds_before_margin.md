# PDF のゲート（20%・FBA≤25%・月2回転）を NETSEA 母数に当てたら、効いたのは資金でもゲートでも利益率でもなく「取り分」だった（2026-09-14 / T-20260914-001）

## 結果の桁（実額は out/）

- 母数 26,942 → 本体なし・入数解決 7,576 → 単価 2,000〜5,000 で 2,477 → 利益率20%（大口・広告10%）67 → FBA配送代行≤利益25% 10 → 回転6ヶ月・取り分≥6 で **0**
- 線を 5% まで下げ広告 0 にしても、回転と取り分を通る単品は最大 4。**線の引き方の問題ではない**
- 取り分 ≥ 6 を持つのは 7,576 件中 57 件。ドロップ ≥ 20 で 20% が出る単品は 0

## 覚えること

1. **ゲートを当てる順番は「需要 → FBA比率 → 利益率」で見る。** 利益率で先に絞ると、残るのは売れていない棚（終売バイアス）。感応度表を出すと、利益率の線が効いていないことが一目で分かる
2. **「FBA配送代行 ≤ 利益25%」は単品相乗りを最初から捨てる条件。** 小型 288円 ÷ 0.25 ＝ 利益 1,150円以上。売価 2,000円なら利益率 58%。PDF がこれを置いた意図はそこにある。この条件を「厳しいから外す」のではなく「単品相乗りは対象外」と読む
3. **セット・N個パックで利益率は機械的に作れる（掛け目 ×1.3）。だから「通るセット 7 万通り」に意味はない。** 意味があるのは構成品の需要（最小ドロップ）と相互補完。組み合わせの総数を成果として書かない。需要根拠つき（構成品の取り分≥6）は 1 組だった
4. **N 個パックの型は実データで成り立つ**：単品 700〜1,000 円の日用消耗品（消臭剤・洗浄剤・歯ブラシ）は単品赤字→6 個パックで 20〜31%。FBA 配送代行が 1 回になる分がそのまま利益。ただし大手ブランドのゲート・既存パック ASIN・カート検証が未確認
5. **「資金 200 万」は制約になっていない。** 140 万を 1 回も使い切れない。規模の上限表を出すときは「候補数」列を必ず添える。SKU 数が候補数と同じなら、制約は資金ではなくプール
6. **次善候補は回転検証（カート）の列を必ず添える。** 取り分（ランク由来）が高くてもカートが取れていない ASIN が 7/7 だった。オファー本数 1 はブランド側の出品者である可能性（推測）

## 実装の型（再利用）

- 利益の引き算は `profit2026.py`（純関数・テスト付き・料率は fees.py から）。大口＝成約料 0・広告率は引数
- セットの梱包寸法は `combine_packages()`（最長2辺は最大・最短辺は合計・重量は合計。どれか欠けたら不明のまま）
- 組み合わせは総当たりでよいが、**出力は「需要根拠あり」と「利益率上位」の2本に分ける**。1本にすると需要根拠のある行が利益率順で埋もれる（実際 205 件中 1 件しか上位 2,000 に入らなかった）
- 8SKU は「PDFどおり」と「次善（利益率の線だけ下げる）」を区分列で分ける。回転・取り分は緩めない（社長の固定ルール）

## 並列3体で同じフォルダに commit するときの注意（2026-09-14 実測）

`git add <自分のファイル>` の直後に別エージェント（ハルオ）が `git commit` を打ち、**自分のステージ分が相手のコミット（5bc2c65）に混ざった**。index は共有なので、add と commit の間に他人の commit が入ると起きる。内容は失われないが、コミットメッセージが実態と合わなくなる。
対策: `git add` と `git commit` を同じコマンド行で続けて打つ（`git add … && git commit …`）。それでも混ざったら `git show --stat HEAD` で自分のファイルが HEAD に入っていることを確認して報告に書く。
