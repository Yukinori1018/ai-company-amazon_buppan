# 「要確認」の印を付けながら、その数字を出し続けてはいけない

2026-09-07 / T-20260907-001。**同じ形の不具合が同じリポジトリに2箇所あった。**

## 何が起きたか

入数（ケース入数）が読めなかった行に `要確認` の印を付けたあと、
**入数=1 のまま利益を計算して CSV に書いていた。**

```python
if needs_review:
    ev.review_reason = ev.pack_reason        # 印は付ける
wholesale_for_listing = candidate.wholesale_ex_tax * ev.pack_size   # pack_size は 1 のまま
```

入数を無視すれば利益は入数倍に膨らむ。つまり**解けなかった商品が必ず利益率の上位に来る**。
26,942行中2,113行がこれで、社長にお出しする上位10件が**全滅**した（利益率71〜78%が全部まぼろし）。

> **印を付けることと、数字を出さないことは別。**
> 印は下流が読み飛ばせるが、**数字は独り歩きする。**
> 判定できない行は、印ではなく**列を空にする**（`result = None`）。

## 同じ形が隣にもあった

`SUSPICIOUS_PRICE_RATIO`（売価が仕入の4倍超）の網も、
**コメントには「利益判定を出さず要確認に落とします」と書いてあるのに、実装は印だけ**だった。

**コメントが宣言している契約と、実装が食い違っていないかを疑うこと。**
コメントが正しくて実装が間違っている側だった。

## 判定モジュール自体は正しかった

`pack.py` は「読めた数」と「自信が無い」を分けて返す、よく書けた実装だった。
**壊れていたのは受け取る側。** 判定層をいくら丁寧に作っても、
呼び出し側が `uncertain` を無視したら意味がない。
**`uncertain` を返す関数を作ったら、全呼び出し箇所で参照されているかを必ず確認する。**

## 検算の型

「解けなかった」と自分で書いた行が、成果物の**上位**に来ていないか。
上位10件の判定理由を**目で読む**。件数の集計だけ見ていると気づけない。
