# PUBLIC リポと「個人情報／第三者DB由来データ」の衝突

初出: T-20260831-001 Phase B（2026-08-31 ハルオ）
既存の `knowledge_public_repo_exposure.md` の続き。**論点が「秘密情報の漏洩」から「他人の権利」に移った回。**

---

## 1. 何が起きているか

- CLAUDE.md §6: 最終納品物は `workspace/output/deliverables/` に**直納して即 commit**。
- 同 §6: **このリポジトリは PUBLIC**。`.claude/scripts/github-sync.sh` が30分ごとに `git add -A` → push。
- 除外対象として明記されているのは **本人特定情報（社長の住所・電話・口座）と APIキー** の2つだけ。

→ **「第三者の個人情報」と「第三者DBのライセンス付きデータ」は、除外リストに入っていない。** ここが穴。

## 2. 具体的な衝突2件（T-20260831-001 で顕在化）

| 衝突 | 内容 |
|---|---|
| **個人情報保護法27条** | メーカー822社の連絡先には**個人事業主・屋号ブランドが混ざる**。個人事業主の氏名・住所・電話は個人情報。commit ＝ 不特定多数への提供＝27条の「第三者提供」に当たり得る。本人同意はない |
| **商用DBの規約** | Musubu 利用規約 第1条【2】「第三者に対し当社DB等…を譲渡、頒布、貸与、**公衆送信してはならず**」。GitHub public への commit は公衆送信そのもの |

**さらに悪いのは、消せないこと。** 一度 push したら Git 履歴に残り、履歴からの削除は `force push`＝**CLAUDE.md §4.1（不可逆な削除）で社長承認が要る**。事故った後の復旧が最も高コストな類型。

## 3. 採るべき運用（法務の推奨。社長判断待ち）

```
連絡先・氏名等の実データ → 限定共有の Google スプレッドシートのみ
リポジトリ              → カバー率・未取得理由の内訳などの統計＋シートへのリンク
途中データ              → agent_output/（.gitignore対象）。ジョブ完了後に削除
```

**加えて、CSV を deliverables へ書き出す直前のゲートを実装させる**（Phase B 成果物 §8-5 に記載）:
- `entity_type == "個人事業主"` / 分類「ノーブランド・個人らしき」で連絡先あり / 姓名パターンのメール / 代表者氏名 / 居宅らしき所在地 — いずれか1件でもあれば書き出し中止。

## 4. 実査の作法（今回やったこと。次も同じ手順で）

「たぶん危ない」で止めない。**全行を機械で実査して、根拠つきで白黒を言う。**

今回: commit `1e1840e` の `contacts_v1.csv`（822行）を全数チェック
→ 埋まっているのは14行のみ、すべて法人の公表窓口、個人名メール0件、代表者氏名0件
→ **「現状は問題なし。取り下げ不要」と根拠つきで言い切った。**（行動原則2）

**「危険かもしれないから消せ」は法務の仕事ではない。「今は白、この条件を超えたら黒」と線を引くのが仕事。**
