# プラットフォームの表示が自己矛盾している時の申し入れ — 型

法務ハルオ／初版 2026-09-06（T-20260826-004・成果物08）
`knowledge_deadline_record_vs_extension.md`（06の型）→ `knowledge_broken_appeal_path_inquiry.md`（07の型）に続く3代目。
状況：**相手自身が「完了した」と通知したのに、別画面では「失敗」「停止」のまま**。

## 1. 相手の完了通知は「引用する。ただし結論を導かない」

最強の材料は相手の文言。だが使い方を誤ると、そこが唯一の梁になり、折られた瞬間に全体が落ちる。

| 書き方 | 相手の返し | 判定 |
|---|---|---|
| 「有効と通知したのだから解除せよ」 | 「その通知は別ストアに関するものです」の1行で終わる | **NO** |
| 「貴社の表示は矛盾しています」「バグです」 | 反証（内部仕様を知らないこちらが証明責任を負う） | **NO** |
| **逐語引用を事実として置き、そこから何も結論しない** | 説明するしかない | **採用** |
| `I am unable to reconcile these screens` | 同上。「整合を理解できずにいる」は反証の対象にならない | **採用** |

**引用は梁ではなく材料。**07 の「バグと書かず見つけられないと書く」と同じ思想を、矛盾ケースに適用したもの。

## 2. 定型メール反論への3点の仕込み

「それは登録完了の定型メールで本件と無関係」と返される余地は常にある（確率＝中）。潰し方：

1. **逐語のみ引用**（鍵括弧）。要約しない。要約は主張になる
2. **単発の1通にしない。**別の独立した事実（承認通知／書類提出日／相手側の数値 AHR・違反件数）と並置する。定型文だという反論は数値までは説明できない
3. **Reference ID を本文に明記。**定型か個別かの識別を相手の記録で行えるようにする

## 3. 事実の順序（矛盾ケース版）

①相手の完了通知の引用 → ②健全な側のストアの数値 → ③停止している側の違反の明細 → ④その申し立てリンクが提出できないページであること → ⑤2つの質問。

- ①②は「こちらは通過した側」。③④は「残る障害はこれだけ」
- ④から書くと不具合報告に落ちる

## 4. 未送信のまま失効した文書の扱い（今回の実務）

**07 は一度も送信されないまま前提が変わった。**この時にやってはいけないこと2つ。

- **「re-sending」と書く。**送っていないメールの再送は存在しない。相手の記録と食い違えばこちらの信用が落ちる
- **前の文書に紐づけた撤退条件をそのまま引き継ぐ。**送信していない以上、無回答期限は存在しない。**必ず再起算する**

README には「不使用」と**理由を1行**残す（破棄しない。型としては有効）。

## 5. 撤退条件の日付は「他チケットの期限から逆算する」

今回、別チケット（T-20260904-005 スーパーデリバリー）のフォールバック判定日が 9/12（金）。撤退条件を 9/11 以降に置くと**二つの期限が同日に潰れて打ち手が消える**。→ 9/10（水）17:00 に設定。

**撤退条件は3営業日という慣習で決めない。下流の期限から逆算する。**

## 6. 承認済みステータスに自分から触らない（再掲・今回強化）

米国ストアのバナー原文（2026-09-04 実測）：「提供された情報に変更が加えられると、**新しい認証が開始されます**」。

- 本文で**書類の再提出を申し出ない**。追加提出は相手が求めた時だけ
- 未完了の設定（銀行口座割り当て・税情報等）は**解決まで凍結**
- 確率は低くても不可逆性が高い（8ヶ月かかった承認）→ **採らない**

## 7. PUBLIC リポの伏せ字対象に Reference ID を追加

07 では 出品者名・マーチャントトークン・マーケットプレイス。**08 で `SPC-…` 形式の Reference ID を追加**。アカウントに紐づく識別子は一律 `［カズヨ記入］` の欄だけ作り、値はメール本文にのみ入力させる。警告文はファイル側に持たせる。
