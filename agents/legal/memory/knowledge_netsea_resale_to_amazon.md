## 1. 結論：会員規約に販路制限は無い。制限は「サプライヤーが商品単位で掛ける」

バイヤー会員規約 49,614字を全文検索して **転売／販路／再販／販売先／販売方法／ネット販売／販売不可 は 0件**。
「モール」3件は全て自社クーポン名。第15条は購入できることだけを定め、購入後の処分に条件を付けていない。

> **明文が無い＝禁止されていない。** ここは自信を持って「問題ありません」と言ってよい。

## 2. 制限は3層。**API だけでは判定が完結しない**（ここが最重要）

| 層 | 何 | どこで見る | API で取れるか |
|---|---|---|---|
| 1 | 可否テーブル（消費者直送／画像転載／**ネット販売**／ネットオークション／消費者向け商品説明）の ○✕ | 商品ページ `<table class="colAvailableInfo">`。**ログイン不要** | **取れる** |
| 2 | 同上のフラグ | `deal_net_shop_flag` `image_copy_flag` `deal_net_auction_flag` `direct_send_flag` `net_bulk_order_flag`（すべて `Y`可/`N`不可） | **取れる** |
| 3 | サプライヤーの**自由記述「販売条件」**（「Amazon不可」「売価厳守」等が書かれうる） | 商品ページの販売条件タブ | **取れない。**商品スキーマに該当フィールドが無い（`delivery_terms`＝出荷条件はあるが別物） |

**→ 運用は二段構え必須。**API で `deal_net_shop_flag=="Y"` に絞り、**発注前に商品ページの自由記述を人が読む。**
「フラグが Y だから安全」と機械任せにすると、自由記述の「Amazon不可」を踏む。

公式スキーマ：https://api.netsea.jp/docs/buyer/schemas/items.json （descriptionに日本語で「ネット販売可」と明記）

## 3. API の取得範囲は狭い。設計前提が変わる

公式ヘルプ（https://www.netsea.jp/help/manual/api.html）に明記：

> **（消費者直送可能かつ、取引申請が承認されているサプライヤーの商品に限ります。）**

**→ 「NETSEA 全体をスキャンして宝を探す」は API では成立しない。**取引申請が承認された範囲しか見えない。
スクレイピングでの代替も不可（robots.txt で named crawler 全面禁止、`User-agent:*` も `/api/` 等を Disallow。
加えて会員規約7条1項3号＝情報収集は事前承諾の例外なしで絶対禁止）。

## 4. 「売価厳守」条項に注意。法違反ではなく**実務の詰み**

実測サンプルの販売条件に「『定価販売』『売価厳守』等の記載のある商品の販売価格は記載を遵守して下さい」。
売り手側は再販売価格拘束（独禁法2条9項4号）に触れうるが、**当社は買い手なので違反主体ではない**。
問題は：従えば Amazon で価格競争できず、従わなければ取引申請の承諾を撤回される（サプライヤー規約7条2項）。
**→ 「売価厳守」表記のある商品は利益計算の前に候補から落とす。**

## 5. 【重大】NETSEA の納品書は「社内管理用」— Amazon のゲート解除に使えない可能性

https://www.netsea.jp/help/manual/invoice.html に明記：

> ダウンロードできる書類は、**社内管理用としてご利用ください。**
> 書式や項目の変更が必要な場合は、各サプライヤーへご相談ください。**書類発行を行っていない場合もございます**

**→ 「NETSEA で仕入れれば請求書が出るから出品制限を解除できる」は成り立たない。**
`knowledge_listing_restrictions_ungating` の要件（卸の請求書・180日以内・10点以上・購入者名と住所）を満たす
**正式請求書をサプライヤーが発行するかを、取引申請の段階で個別確認する**こと。

## 6. 古物商許可 — 「NETSEA は卸だから不要」は**言い切ってはいけない**

`knowledge_kobutsusho_license` の判定基準（新品かではなく「一度消費者の手に渡ったか」）は正しい。
だが **NETSEA には中古品が実在する**。実測：`/search/?keyword=中古` で **212件**、
例「**中古**vintage アクセサリー…ブローチ」。古物営業法2条1項の古物を売買する営業は許可が必要（2条2項1号）。

**→ 判定文は「NETSEA 仕入れ一般には不要。ただし中古・ヴィンテージ・USED・リユース表記の商品を1点でも扱うなら必要」。**
「卸サイトだから不要」で終わらせない。**プラットフォームの性質ではなく、個々の商品の来歴で決まる。**

## 7. 転売者にも義務が生じる法律（「輸入者じゃないから安全」は誤り）

| 法律 | 転売者の義務 | 根拠 |
|---|---|---|
| **電気用品安全法27条** | **PSE表示のない電気用品を販売・陳列してはならない。**1年以下の拘禁刑/100万円以下の罰金 | METI act_outline |
| **家庭用品品質表示法** | **表示義務者に「販売業者」が含まれる。**違反→指示→**事業者名の公表**→表示命令→販売禁止命令 | 消費者庁 outline_02 |

## 8. 第24条1項（バイヤー情報の公開）— 条文と実装が食い違う

条文は「事業者の氏名、住所、電話番号…は**ウェブサイト上で公開されます**」。
だが実測（非ログイン・2026-08-31）では**公開バイヤー名簿は存在しない**。
サプライヤーレビュー一覧（`/shop/order_review/<id>`、79件を確認）に出るのは
**業種・注文日時・注文商品名・過去1年間の購入回数のみ**で、氏名・住所は出ていない
（1件だけ投稿者が本文に自分で社名を書いていた＝自己開示であってシステム表示ではない）。

**実態は18条2項「取引申請したサプライヤーへの提供」と読むのが自然。**
ただし条文はそう書いていないので**断定しない**。不可逆性が極大（住所は回収不能）なので、
確率が中でもアラートを上げる。確定手段は①ログイン後のマイページ実確認 ②NETSEAへの書面照会（§4.1）。

**教訓：規約が「公開されます」と書いていても、実装がそうとは限らない。逆もまた然り。
実画面を見ずに条文だけで社長に報告すると、過剰にも過小にも間違える。両方見る。**

## 10. API 利用規約は**公開されている**（前回「別文書・射程外」とした宿題の回答）

所在：**https://api.netsea.jp/docs/buyer/openapi.json の `info.description`**。
ログイン不要で全文取れる。ReDoc の SPA（`/docs/buyer/`）を開こうとすると読めないので、**JSON を直接叩く**。

| 条 | 要点 |
|---|---|
| 2条 | **APIユーザー自身の便益をはかる商用目的**の使用を認める（＝仕入れ判断は目的内） |
| 5条3 | 書面許諾なくライセンスの販売・賃貸・再許諾、**ライセンスの使用/提供から収入を得る**こと禁止 |
| **8条2** | **得た情報を加工する場合は事前に書面承諾。**「加工」の定義は無い＝グレー |
| 10条 | 規約終了後、要請があれば情報・**加工物**を返還/廃棄し書面通知 |
| 13条 | 有効期間は**トークン認証日から半年**。再認証で延長 |
| 15条 | 秘密保持。書面承諾なく第三者に開示・漏洩禁止 |

**8条2 の判定：社内利用は可と解する（2条が商用目的を認めている）。外部公開・第三者提供・公開リポへの commit は明確に NO。**
グレーなので3点セット（リスクシナリオ／対応策／撤退条件）を判定書に付けた。

## 11. 手順として再利用できるもの

- **規約の一次取得は curl + タグ除去で足りる。**NETSEA は本体・サプライヤー・API とも静的に取れる。
- **禁止条項を見つけたら必ず「違反時の措置」条項まで読む**（前回の教訓。今回も維持）。
- **条文検索は「全文を落としてから grep」。**該当語が0件であることを示せると「禁止されていない」を根拠付きで言える。
  「見当たりませんでした」ではなく「**検索語7つで0件**」と書く。
- **実画面は raw HTML まで見る。**○✕ が `<i class="fa-regular fa-circle">` / `fa-solid fa-xmark` で表現されており、
  テキスト抽出だけでは可否が消える。前回のギフトショー `alt="※終了しました"` と同型の罠。
- **API を使う相手は OpenAPI の JSON を直接取る。**規約もフィールド定義も、UI より JSON のほうが確実で速い。
