# 公開ページ由来ルール／取引条件の漏えい検出の設計

初出：T-20260920-003（2026-09-21 ハルオ）。成果物：`workspace/output/deliverables/T-20260920-003/16_公開リポに残る取引条件の公開可否_法務判定.md`
上位：`knowledge_public_data_release_standard_ABCD.md`（4問と決定表）／`knowledge_public_url_vs_member_only_data.md`（3本足）

---

## 1. 追加した一本のルール（①の誤検知を止めるため）

> **公開ページ由来ルール** — ①非ログイン表示を取得当日に実測 ②出典URL＋取得日を併記 ③出典サイトの規約に発信・転載・秘密保持の禁止条項がない ④**出所が会員制卸（SD・NETSEA 等）でない** — この4条件を満たす取引条件は実額ごと成果物に書いてよい。

**④が要。**SD・NETSEA は公開ページに出ている情報でも、**会員である当社が発信することを契約で禁じられている**。①のルールを卸サイトへ横展開してはいけない。禁止条項の型（一般的発信禁止型／秘密保持型）で結論が反転する。

**「発信禁止条項がないこと」は `転載` `複製` `発信` `秘密` `無断` の全文検索で確認する。**今回2サイトとも該当0件。Shopify 系は `robots.txt` に「policy ページは crawlable」と自分で書いているので、意思表示の足が非常に強い。

## 2. API 応答は「非ログインで見えるか」を必ず実測してから条文に当てる

NETSEA の送料条件：サプライヤーページを非ログインで取ると **`送料無料` のラベルは出るが、境目の金額・未満時の送料・混載時の適用規則は HTML 中に存在しない**。加えて `robots.txt` に `Disallow: /api/`。
→ **API 規約15条1項が直撃。社名・ID を伏せても免責にならない**（条文は秘密性でも識別可能性でもなく「提供された情報」を対象にしている）。

## 3. 今回いちばん重要な学び — 依頼文の「残存0件」を鵜呑みにしない

依頼は「丸進の分は伏せ字化済み・追跡下の残存0件」だった。**実際には4ファイルに残っていた。**原因は検索語が `20,000円以上` 固定で、**漢数字表記（◯万円）と卸値の分布表**を拾えなかったこと。

**金額の残存チェックは、必ず「ラベル＋数値」の正規表現でやる。表記ゆれに `万` を入れる。**

```
(卸値|卸価格|上代|仕入単価|最小ロット|最低発注|送料無料ライン|代引手数料|掛け率)
[^\n]{0,15}([0-9０-９][0-9,０-９\.]{1,}|[0-9０-９一二三四五六七八九十]+万)
```

**「金額は一切記載せず」という自己申告が同じファイルに書いてあっても信じない**（14 の238行目がそう書きながら194行目に分布を書いていた）。`knowledge_netsea_public_repo_leak_judgment` §7 の「依頼文の事実は疑う」が、今回は**自社の完了報告**に対して効いた。

## 4. push 済みかは「origin/main」だけで判定しない

`origin/main` に無くても、**作業ブランチが push されていれば PUBLIC リポでは公開済み**。判定は必ずこれ。

```bash
git branch -r --contains <sha>          # どのリモートブランチに乗っているか
git log -S"<文字列>" --all -- '<path>'   # その文字列が入った commit を特定
```

## 5. フックがすり抜けた4つの穴（実測で切り分け）

| 穴 | 事実 |
|---|---|
| 粒度 | 漏れた卸値分布表は**4列**。md ルールは5列以上（`awk -F'|' NF>=7`）しか見ない |
| 散文 | 地の文の金額は意図的に通す設計。今回2箇所がここを通った |
| 差分範囲 | **新規追加ファイルのみ**検査。既存ファイルへの追記は素通り |
| 表記ゆれ | `万` が数値表現に入っていない |

**思想は正しく、語彙・粒度・差分範囲の問題。**報告にこの切り分けを書くと、ゲートを外す議論にならない。
なお **commit 時のゲートでは「過去に入り込んだもの」は永久に見つからない。**週次の全追跡ファイル棚卸し（検知のみ・自動修正なし）が要る。

## 6. 同じ語が別物を指すときは、語ではなく意味で止める

`月間販売数` は (a) Amazon の現在表示スナップショット＝A クラス（公開可） と (b) Keepa 履歴からの推計＝B クラス の2つを指す。フックは語一致で両方止めていた。
→ **A クラスを正とし、(a) を指す語だけ外す。意味が名前から判別できない列（`monthly_sold_real`）は安全側で残す。**
**A を通す根拠は規約上の白ではなく 2026-09-06 の社長判断＋実害ゼロ**（Keepa §11(1) は秘密性を要件にしていない）。フックのコメントにこの一文を残させること。落とすと「B も見えるから白」に展開される。

## 7. 誤検知対策は法務論点として設計に書く

保護効果ゼロの印は危険側の設定（`knowledge_public_url_vs_member_only_data` §4）。**除外条件を仕様として明記した**：agent_output 配下／伏せ字表現を含む行／`<!-- public-source: URL verified:日付 -->` が直前3行にありホストが出所台帳の「公開」区分／自社費用（ラベル限定で自然に外れる）／法務判定書。
**止めたときのメッセージにバイパス手段を書かない。**書けば常態化する。

本判定書は表を最大4列に抑え、実額を1つも書かず、`--no-verify` なしで commit が通った。**法務がバイパスを使うと翌週には全社の常態になる。**
