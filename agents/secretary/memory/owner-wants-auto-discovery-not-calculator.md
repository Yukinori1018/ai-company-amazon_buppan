# 社長の本命要望：自動リサーチ（Discovery）。手動計算機では刺さらない

**記録日: 2026-06-04 / 関連: T-20260521-005**

## 何が起きたか
利益判定エンジン（第1層・手動入力の計算機）を納品したところ、社長の率直な反応は
**「想像よりだいぶしょぼい」**。手入力で利益計算する電卓型は、社長の期待に届かない。

## 社長が本当に欲しいもの（原文ニュアンス）
> 「利益が取れそうな商品を Yahoo!ショッピング等の仕入れ先から**自動でリサーチ**して、
> その一覧を**利益表示**してほしい」

= **Discovery 型**（儲かる商品を勝手に見つけてランキング表示）。ADD×ONE / ERESA がやっている世界。
手動計算（Product Lookup 型）は補助でしかなく、単体では満足されない。

## 含意・次に活かすこと
- このプロジェクトで「ツールを作って」と言われたら、**まず Discovery（自動探索＋一覧）を想定**する。電卓型を最終成果物として出さない。
- Discovery 実現には Amazon 側データ源（売値・月販）が必須 → **Keepa API €49/月（§4.1）** が毎回の関門。Yahoo!ショッピングAPIは無料。
- 既に Discovery 型の一覧モック `deliverables/T-20260521-005/02_mockup.html` は存在。ギャップは「本物データ接続」だけ。
- 買う(ERESA)か作る(Keepa自社)かの A/B/C を提示したら **社長は選択を保留（dismiss）**。push しすぎない。社長は「自分のツールを持ちたい」志向が強い可能性 → ERESA(買う)に寄せすぎると刺さらないかもしれない。次は社長の主導でどちらに進めたいかを待つ。

## 見た目（UI）へのこだわり
「しょぼい」と感じさせない見た目・体験が重要。Streamlit素のフォームは安っぽく見える。
Discovery を作るなら一覧UI（モックレベル）の質感まで含めて設計する。
