# スキル：サブエージェントへの依頼分配

秘書が依頼内容に応じてどの担当に振るかを判断する手順です。

## ルーティング判断フロー

1. **依頼内容を1文で要約**（自分用に書き出す）
2. **キーワードマッチで一次判断**（下表）
3. **複数該当する場合は分解**して、それぞれの担当に並行発注
4. **どれにも該当しない場合**は、最も近い担当に振る。本当に担当が定まらない横断案件だけ、秘書が分解してから各担当に配る（分解した先の実務は必ず担当が持つ）

## 一次判断テーブル

| キーワード／領域 | 担当 |
|---------------|------|
| 商品リサーチ、市場調査、競合分析、ツール調査、業界ウォッチ、X/YouTube 動向、一次情報収集、比較表 | **リサーチャー** |
| 戦略、カテゴリ選定、SKU積み上げ、差別化、撤退条件、A/B/C＋推奨、勝ち筋設計、参入順序 | **プランナー** |
| 戦略案の仮想実行、シミュレーション、プレモーテム、3シナリオ予測、応手予測、撤退条件の磨き込み | **シミュレーター** |
| 金額、収支、予算、財務、税、コスト、ROI、利益、損益 | 経理 |
| 契約、利用規約、規約、法律、コンプライアンス、リスク、知財、商標 | 法務 |
| メール整理、ファイル整理、スケジュール、会議調整、情報整頓 | 庶務 |
| 文章、資料、台本、コピー、サムネ、編集、推敲、クオリティ | コンテンツ制作 |
| 社長専用ツール、自動化スクリプト、フック、MCP 連携、モック | **IT エンジニア** |
| 上記に該当しない、または横断的 | 秘書が**分解のみ**担当し、実務は各担当へ発注 |

## 振り分けの原則 — 原則すべて振る（抱え込み防止）

判定に時間をかけないための決め方です。「振るべきか」を考えるのではなく、**例外に当たるかだけを見る**。当たらなければ振る。5秒で終わります。

**秘書が自分の手で実行してよいのは、次の4つだけ。**

| # | 例外 | 具体例 |
|---|------|--------|
| 1 | 社長との対話そのもの | ヒアリング、確認、A/B/C＋推奨の提示、完了報告 |
| 2 | 統合と品質確認 | 複数担当の成果を束ねる、受け入れ可否を判定する、社長向けに要約する |
| 3 | チケット操作そのもの | 起票、`todo/doing/waiting/done` の移動、Notion 同期、`owner-tasks.md` の更新 |
| 4 | 1手で終わる事実確認 | ファイルを1つ読む、`git log` を1回見る、チケットの状態を確認する |

**この4つ以外は、規模・難易度を問わず担当へ Agent 発注する。** 例外4は「1手」が上限で、2手目が要ると分かった瞬間に担当へ振り直す（"ついでにもう1ファイルだけ" が抱え込みの入口）。

**例外に含めないもの（社長が名指しで否定した言い訳）**

- 「簡単だから自分でやる」「すぐ終わるから」「ついでにやっておきます」
- 「代行で進めます」（2026-06-01 指摘。担当がいるのに代行名義で本体作業を持たない）
- 「サブエージェントを立てるほうが手間だから」

**迷ったら振る。** 振りすぎて叱られた例はありませんが、抱え込みは3回叱られています（2026-05-27 / 06-01 / 08-21）。

**着手前の1行宣言（必須）**

> この作業は〔担当〕です（理由: ◯◯領域のため）

宣言してから発注する。振った後は秘書が成果を品質確認し、統合して社長へ報告する（窓口の一元化は維持）。

**なぜ振るのか（社長の言葉）**

> 「簡単な作業でもサブエージェントを使わないと、アウトプットの保存先がバラけたり、サブエージェントのナレッジが溜まっていかない。」

速さではなく**資産形成**が理由です。担当の `memory/` に知見が積まれ、成果物が `deliverables/<ticket_id>/` に揃うことが目的で、振ること自体が成果の一部だと理解してください。

**発注の可否を都度確認する必要はありません。** 担当が明確な作業を担当に発注することは、本リポジトリの運用既定です（CLAUDE.md §5「サブエージェントへの発注を既定とする」）。ただし §4.1（外部発信・課金・契約・不可逆な削除）はこの既定の対象外で、発注先のサブエージェントも実行できません。該当時は `waiting/` に出して社長承認を取ります。

## 「調査」「戦略」「仮想実行」を必ず分ける

社長から「◯◯について調べて、どう動くか提案して」型の依頼が来た場合、**1チケットにまとめず3段で分割する**：

1. **リサーチチケット**（assignee: researcher）— 事実シート＋論点シートを納品
2. **戦略チケット**（assignee: planner）— リサーチの成果物を入力に A/B/C＋推奨を提示
3. **シミュレーションチケット**（assignee: simulator）— タケシの戦略案を仮想実行、3シナリオ＋プレモーテムを返す。タケシとの往復で収束まで反復

> 秘書が自分でリサーチや戦略を抱え込まないための鉄則。「ついでに調べておきます」「ざっくり戦略案でいいです」を禁じ手にする。
> 仮想 PDCA の運用詳細は [pdca-with-simulator.md](pdca-with-simulator.md) を参照。

## 単一担当ケース

1. 該当担当宛のチケットを起票（`assignee` を設定）
2. `todo → doing` で起動
3. 進捗を監視、完了したら `~/Documents/AI Company Outputs/Amazon物販事業/<ticket_id>/` を確認して社長に報告

## 複数担当ケース（横断案件）

例：「新商品を出すので、価格設定（経理）と利用規約改訂（法務）とLP制作（コンテンツ制作）を進めて」

1. 親チケットを秘書名義で起票（`assignee: secretary`）、本文に依頼全体を記載
2. 子チケットを各担当別に起票し、親チケットの「タスク分解」欄に子の ticket_id を列挙
3. 子を並行起動
4. すべての子が `done` になったら親を `done` に
5. 統合した最終報告を社長へ

## 担当判断に迷った時

- **30秒考えて決まらなければ振る。** 迷いは「自分で受ける理由」にはならない（旧ルールはここが逆で、抱え込みの抜け道になっていた）
- 担当候補が2つある → **近いほうに振る**。ズレていれば担当から差し戻しが来るので、そこで振り直せばよい（SUBAGENT_PROTOCOL §1-2）
- 依頼が大きすぎて担当が定まらない → 秘書が**分解だけ**して、断片ごとに担当へ配る。分解した先の実務は持たない
- 社長の意図そのものが曖昧 → `waiting/` に出して A/B/C＋推奨で聴く（丸投げ質問は禁止）

## サブエージェント起動の手順

1. チケットを `tickets/doing/` に移動（`assignee` を担当ロール名で入れる）
2. Agent ツールを呼ぶ。`subagent_type` は `.claude/agents/` に登録済みのロール名を使い、未登録なら `general-purpose`
3. プロンプトは下の **§発注テンプレ** をそのままコピーして埋める（5要素を落とさない）
4. 担当は途中経過を `workspace/output/agent_output/<ticket_id>/`、最終成果物を `workspace/output/deliverables/<ticket_id>/` に置き、その場で commit する
5. 秘書が品質確認した上で社長に報告する（ローカルセッションなら `~/Documents/AI Company Outputs/Amazon物販事業/<ticket_id>/` にも複製）

## 発注テンプレ

Agent ツールを呼ぶときの定型文です。**5要素（人格・プロトコル・チケット・納品先・メモリ）を1つも落とさないこと。** 落ちた分だけ「保存先がバラける」「ナレッジが溜まらない」という社長の指摘がそのまま再現します。

```
あなたはこの会社の〔役割名〕「〔担当者名〕」です。まず `agents/<role>/agent.md` と
`workspace/SUBAGENT_PROTOCOL.md` と `CLAUDE.md` を読み、その人格・行動原則に従って作業してください。

担当チケット: `workspace/tickets/doing/<ticket_id>_<slug>.md`（必ず最初に読むこと）
リポジトリ: /Users/yukinori/Claude Code/ai-company-amazon_buppan

## 背景
〈なぜこの依頼が出たか。社長の発言があればそのまま引用する〉

## やること
1. 〈具体タスク〉
2. 〈具体タスク〉

## 制約
- 参照必須ファイル: 〈既存の関連ファイル〉。編集前に必ず全文を読み、他セクションを壊さないこと
- CLAUDE.md §4.1 該当（外部発信・課金・契約・不可逆な削除）は実行せず、チケットを waiting/ に回す
- 成果物は `workspace/output/deliverables/<ticket_id>/` に直納し、その場で git commit する（push はしない）
- **完了前に必ず `agents/<role>/memory/` に1ファイル以上、気づき・社長のこだわりを記録すること**
  （省略して完了報告しないこと）
- 完了したらチケット本文に「## 成果物」「## 完了報告」を追記し、カズヨ宛の報告を返す
```

### 5要素の意図（落とすとどうなるか）

| 要素 | 落とすと |
|------|---------|
| 役割の `agent.md` を読ませる | 人格・価値観が働かず、ただの汎用エージェントの出力になる |
| `SUBAGENT_PROTOCOL.md` を読ませる | 「現在地」「ログ」の更新と引き渡し作法が抜け、進捗が追えない |
| チケット ID を渡す | 作業が宙に浮き、監査もカタログ登録もできない |
| `deliverables/<ticket_id>/` 直納＋commit | worktree の消滅で成果物が消える／保存先が毎回変わる |
| memory 記録を完了条件にする | ナレッジが溜まらない。**今回の再発の本体はここ** |

> 2026-08-21: 3度目の同一指摘を受け、本節を新設。原因は (1) ハーネス側の「明示依頼が無い限り Agent を使うな」という既定と社内ルールの衝突、(2) 発注プロンプトを毎回手書きする高コストが「自分でやるほうが速い」を勝たせていたこと。(1) は CLAUDE.md §5 の運用既定（担当が明確な作業は担当に発注する）を明文化して解消、(2) はこのテンプレで解消する。
