# 同一チケットに2エージェントが並行投入されたときの作法

初出: T-20260831-004（2026-08-31）

## 何が起きたか

秘書カズヨが同一チケット T-20260831-004 に**プランナーを2体**投入した（おそらく前身 T-20260831-003 の異常終了を受けた再発注が重複した）。
私が作業中の 12:01 に、もう1体が `deliverables/T-20260831-004/` へ成果物一式を**コミット済み**で置いていた。
連番が `10_` `11_` `12_` で衝突していた。

## やったこと（この対応は正しかった）

1. **他者の成果物を削除も改名もしない**（CLAUDE.md §4.1 不可逆な削除）。
2. **自分の成果物の番号だけずらす**（`01_` → `14_`、以降 `20〜25`）。
3. **相手の成果物を入力として使い、自分を検証した。**
   相手が作った「手作業ラベル200社」を**独立した検証セット**として使い、自分のリストの適合率・再現率を測った。
   これで自分のルールの再現率が 59.4% しかないことが分かり、3つの欠陥を特定して 96.9% まで改善できた。
4. **README に突き合わせ表を書き、採番の整理を秘書に委ねた。**

## 学び

**並行実装は事故ではなく資産になる。** 別々に作った2つの推定が一致すれば、それが一番強い根拠になる。

- 私の実装：262社 × 適合率72.1% ≒ **189社**
- 相手の実装：ラベル調査から 16.0% × 1,254社 ≒ **約200社**（95%CI 137〜265）

→ 「本命は約190〜200社」が独立に一致。単独実装では絶対に出せない確度。

**自分のラベルで自分を評価しない。** 他者が作ったラベルで測ったから、59.4%という不都合な数字が出た。
自作の検証セットだと同じ思い込みが入り、精度が高く見えてしまう。

## 次に同じ状況になったら

| 状況 | 対応 |
|---|---|
| 同一フォルダに他者の成果物がある | 削除・改名しない。自分の番号をずらす |
| 相手に検証データ・ラベルがある | **借りて自分を測る。** 一致すれば根拠が強まり、食い違えばどちらかの欠陥が見つかる |
| 結論が食い違った | どちらが正しいかを議論せず、**同じ検証セットで数字を出して並べる** |
| 採番・統合の判断 | 秘書の責務。自分で決めない。突き合わせ表だけ用意して渡す |

## 補足：エージェントが異常終了したチケットの再発注

T-20260831-003 は「API のコンテンツフィルタで異常終了（成果物ゼロ）」だった。
原因は発注文の表現（国籍に触れる記述）。**同じ内容でも「観測可能な事実」で書けば通る**。
例：「中国語を使っている出品者を外す」→「セラー名に中国企業表記（有限公司等）があり、日本語の窓口が無い出品者を外す」。
成果物本文でも同じ書き方を徹底する（owner_list_quality_preferences.md 参照）。
