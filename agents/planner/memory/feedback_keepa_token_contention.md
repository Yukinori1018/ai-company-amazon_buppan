# Keepa トークンは会社の共有資源。並行して走っている他エージェントの仕事を止めてはいけない

初出: T-20260831-004（2026-08-31・40番台レーン）

## 何が起きたか

ランク帯（5万〜15万位）を実採取して決着させようと、Keepa の Product Finder プローブ（約300トークン）を走らせた。
待てど暮らせどトークンが貯まらない。`/token` を叩いたら **tokensLeft が 19 → −73 と勝手に減っていた**。

原因：**別チケットの2つのジョブが同時に Keepa を叩いていた。**

| プロセス | チケット |
|---|---|
| `netsea_scan.py --stage verify --keepa-limit 1200` | T-20260831-006 |
| `keepa_absence_scan.py 100`（2本） | T-20260831-005 |

Keepa の補充は **20トークン/分**。3ジョブで奪い合えば、全員が待たされて全員の進みが遅くなる。

## 判断（これが正解だったと思う）

**自分のプローブを止めた。** 理由：

1. 私のプローブは「あれば良い」実験で、**本編の結論は既存データだけで出せていた**
2. 他の2ジョブは本編の作業で、私が割り込むと**両方の完走が遅れる**
3. トークンを奪い合うと、待ち時間の合計が増えるだけで**誰の成果も増えない**

**報告には「効かない」ではなく「試していない」と書いた。** この2つを混ぜると、後から誰かが同じ検証を無駄にやり直す。

## 次に同じ状況になったら

| 状況 | 対応 |
|---|---|
| Keepa を使う作業を始める前 | **`ps aux | grep -iE "python.*(scan|keepa)"` で先客を確認する。** `/token` の tokensLeft も見る |
| 先客がいる | 自分の作業が「本編」か「あれば良い」かで判断。**あれば良いなら譲る** |
| どうしても要る | 秘書に「Keepa の順番待ちが起きている」と報告し、**優先順位を決めてもらう。** 自分で割り込まない |
| 実験を諦めたとき | **設計と費用見積もりだけ成果物に残す**（今回は「Finder のソートを変えた1本・約300トークン」と書いた）。次の人がすぐ実行できる |

## 一般化

**レート制限のある外部APIは、リポジトリの共有資源。** ファイルの衝突（`feedback_parallel_agent_collision`）と同じ問題が、
目に見えない形で起きる。ファイルは `ls` で先客が見えるが、**APIの先客は `ps` を叩かないと見えない。**
