# 仕入れ前チェックリスト v2 の設計（発注ゲートに載せる項目の作り方）

初出: T-20261004-001 タスク2（2026-10-04）／成果物 deliverables/T-20261004-001/02_仕入れ前チェックリスト_v2.md・checklist_spec_v2.json

## 何をしたか
- サトルの対応表（114ルール・提案 P1〜P8・論点 A〜E）を入力に、§3.5 を12→21項目に拡張。全項目 required、gate.py（PASS/FAIL/UNKNOWN・鮮度判定）にそのまま載る JSON を作った
- 既存 id は残した（spec 注記「id を変えると記録が孤児になる」）。意味を厳しくするのは可（記録は3日で切れるので移行の痛みは小さい）

## 設計の型（再利用できる形）
1. **1項目＝1つの事実で PASS/FAIL**。人が埋めるので「総合的に」系は作らない。どうしても複数の事実が入る項目は、value に書く形式（例「計n＝本体a／FBA b／即納 c／取り寄せ d」）を how に指定する
2. **「該当しない」は根拠付きの PASS**。gate は N/A を持たない。UNRESOLVED_RE（要確認|未確認|UNKNOWN|不明）に当たる語を value に書くと PASS にできないので、例文に「不明」を入れない（「不要」は可）
3. **鮮度は2段**：市場で動く事実3日（§3.3-26 実測）／商品・取引先の属性14日（リピート周期1.2〜1.5ヶ月より短い＝毎回取り直しになり §3.3-29 と矛盾しない）／終売7日
4. **閾値の曖昧さは理由の列挙で消す**：「在庫3〜6ヶ月は理由があれば可」→ 理由を「卸の最小ロット」「ゲート10点要件」の2つに限定して判定可能にした
5. **ゲートに入れないものを先に分ける**：アカウント単位（混合在庫）／機械検査（卸率70%・単位の不変条件）／発注時の操作／出品後・リピート。全部入れると発注案を書く時点で埋められない項目ができる
6. **検算は過去の事故を全部当てる**。今回10件→10件止まる。v1 で止まらなかったのは3件（貝印の異種セット・取り寄せ型・取り分小）
7. 作った spec は `gate.evaluate(asin, spec=items)` で読めるかを1回流して確かめる（全項目「欠落」が出れば形式は合っている）

## 論点の決め方（優先順位：社長の直接指示＞当社実測＞本）
- A：§3.3-28 を正。「安い＝保留」はやめ、前半45日/後半45日の中央値で下落トレンドを判定。playbook 入口4 は改訂対象
- B：6ヶ月は FAIL の線（社長既定）、本の1〜3ヶ月は数量の目安
- C：A（中央・悲観とも20%超）数量制限なし／B（中央5%以上）最小ロットで1回だけ／C（中央5%未満）落とす。社長「5%でも数を打つ」と §3.3-24 は同じ向き。§3.3-24 の B 定義には「悲観で0〜20%」の穴があったので B に含めた
- D：定点観測は「キーゾンと monthlySold が2倍以上ずれるとき」だけ必須。一律必須は鮮度3日と矛盾し発注が7日遅れる
- E：21項目。縮めると1項目に事実が複数入り、人が「だいたい OK」で PASS にする

## 事故の型（新しく項目化したもの）
- **異種セットの相乗り**（貝印 B01DBGGW8S・2026-10-04）：Amazon は「凸刃＋直線刃」の2品セットなのに、原価を直線刃×2で計算。カタログ JAN は直線刃単品の JAN。→ セット構成を**型番×数量**で書かせ（amazon_set_count）、卸で構成品ごとに品番を特定させ（wholesale_terms）、セット用 JAN の有無を見る（catalog_jan_match）。**数量（2）が合っていても構成が違えば原価は嘘になる**
- **取り寄せ型の出品者**：自動では落とさない。分母から外し（取り分は大きく出る）、その出品者の価格で売れた根拠と、メーカー在庫を確かめさせる
