# inbox の振り分け先が「2つとも公開リポの中」だった話（PII ルーティング）

記録: マリエ / 2026-08-31 / T-20260831-003

## 見つけたもの

スキル `inbox-intake.md` の Step 3 は、見出しからして
**「振り分け（2つの行き先しかない）」**と書かれていた。その2つは：

| 旧・行き先 | Git |
|---|---|
| `docs/reference/<topic>/` | **追跡される** |
| `_inbox_社長共有/_archive/YYYY-MM/` | `.gitignore` 対象 |

**このリポジトリは PUBLIC で、30分ごとに `git add -A` → push される。**
スキルに素直に従うと、身分証の撮影画像や税務書類が `docs/reference/` に置かれ、そのまま公開される。

## いちばん嫌な性質

`_inbox_社長共有/` 自体は `.gitignore` 対象。つまり
**inbox に放置されている限りは安全で、棚卸しをした瞬間に危険になる。**

**運用が止まっていたことが、結果的に事故を防いでいた。**
「サボっていたから助かった」は、対策として最悪の形。

## 今回の実物

2026-08-31 に inbox にあった6件は**全件が PII を含んでいた**。

- e-Tax の受信通知・帳票（氏名・住所・電話番号・生年月日・利用者識別番号・受付番号）
- **身分証の撮影画像**（顔写真・署名・証明書番号・機械読取領域）

たまたま私が「PII だからリポ外だ」と判断したから公開されなかっただけで、
**スキル通りに動いていたら公開していた。** 判断が個人の勘に依存していた。

## 直したこと

Step 3 を**2段階判定**に変更した。**内容の価値を見るより先に「リポジトリに置けるか」を判定する。**

| リポ外にする条件（内容が何であれ優先） | 例 |
|---|---|
| **本人特定情報（PII）を含む** | 身分証の撮影画像、税務・金融機関の受信通知や帳票、口座番号 |
| 第三者著作物の原本 | 有料セミナーの録画・スライド |
| 1ファイル 50MB 超 | 動画・大きなアーカイブ |

行き先は3つになった。3つ目が
`~/Documents/AI Company 素材/Amazon物販事業/<topic>-<YYYYMMDD>/`（リポ外）。

**判定の合言葉：「これが GitHub の検索結果に出てきて困るか？ 困るならリポ外」**

## 一般則

1. **「行き先はN個しかない」と閉じた選択肢は、想定外の入力を必ずどちらかへ誤って流す。**
   閉じるなら「ここに当てはまらないものが来たらどうするか」を必ず併記する。
   今回は身分証が公開追跡フォルダへ流れる寸前だった。
2. **判定の順序が安全性を決める。** 「価値があるか（→ reference）」を先に問うと PII が公開側へ流れる。
   **「置いてよい場所はどこか」を先に問えば流れない。** 同じ情報でも、問う順で結果が変わる。
3. **PII 判定は拡張子やファイル名では絶対に分からない。** `IMG_4118.HEIC` が身分証だった。
   `_inbox_社長共有/` のファイルは**必ず中身を開いてから**振り分ける（スキル Step 1 が正しい理由）。
4. **エージェントによる身分証の外部送信は CLAUDE.md §4.1**（機密情報の外部送信）。
   Amazon 等への提出は社長ご本人が公式画面から直接行う。私は保管と索引までしかしない。

## CLAUDE.md 側に残っている穴（カズヨへ申し送り済み・未修正）

§6 の「3層」表で③を選ぶ判定基準が **「50MB超、または第三者著作物」の2つだけ**で、
**PII が書かれていない**。同じ §6 の「このリポジトリは PUBLIC です」節には
本人特定情報を除外する旨があるので、方針は存在するのに置き場の判定表へ反映されていない。
スキルの欠陥はここに由来する。

CLAUDE.md は会社の憲法なので**マリエの判断では書き換えず**、修正案の提示に留めた。
→ 提案：「③ 大容量バイナリ素材」を「**③ リポジトリに置けないもの**」に改め、
判定に **PII を含む** を追加する。
