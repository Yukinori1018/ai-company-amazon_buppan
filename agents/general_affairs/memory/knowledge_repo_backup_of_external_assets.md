# リポジトリ外資産のバックアップと、公開リポへの控え作成（T-20260902-003）

## 何をした

`~/.claude/` に導入した Claude Code の自律リサーチ資産5ファイル（スキル `research` ＋ サブエージェント3体）を、
`docs/reference/claude-research-skill/` へ**無改変で控え**として保全した。

- 元のディレクトリ構造を再現（`skills/research/...` / `agents/research-*.md`）＝復元コマンドがそのまま書ける
- `cksum` で5件照合。README に照合値を残す
- README に「これは控えで、正は `~/.claude/` の実体」「実体を編集したら控えも更新する」を明記

## 学び1｜「アーカイブがある」は「バックアップがある」ではない

T-20260902-002 で inbox アーカイブ（`_inbox_社長共有/_archive/`）へ原本を退避したが、
`_inbox_社長共有/` は `.gitignore` 24行目で除外されている。**退避先が Git 追跡外なら、それはバックアップではない。**
`knowledge_inbox_archive_is_not_a_backup.md` と同じ教訓が、今回は「インストール先もリポ外」という形で二重に効いていた。

> **退避・アーカイブを設計したら、その置き場が Git 追跡対象かを必ず `git check-ignore` で確認する。**

## 学び2｜控えは「投函時のスナップショット」ではなく「現行の実体」から取る

今回、inbox アーカイブ側の `SKILL.md` は `3407526324 / 6612 bytes`、実体は `950465037 / 7269 bytes` で
**657 バイト食い違っていた**（同日中に2回編集されたため）。
アーカイブ側をコピーしていたら、編集済みの内容が失われた古い版を「控え」として保存するところだった。

> **控えを取る前に、必ず「どちらが現行か」を cksum で確認する。**
> 見た目が同じファイル名でも、投函時と現在は別物であり得る。

## 学び3｜古い控えは、控えが無いより危険

「バックアップがある」と思い込ませてしまうため。だから README に**追随義務**を書いた。
自動追随の仕組み（フック等）が無い控えは、必ず「更新する責任者と、そのトリガー」を文書に書き残すこと。

## 学び4｜公開リポへの commit ゲート（PII チェックの型）

このリポジトリは PUBLIC ＋ 30分ごと自動 push ＝ **commit した瞬間に公開**。今回使ったチェックの型：

| # | 観点 | 検出手段 |
|---|---|---|
| 1 | 個人名 | `[一-龥ぁ-んァ-ヶ]{2,4}(氏\|様\|さん\|社長\|部長)` ＋ 全文通読 |
| 2 | 住所・電話 | `0[0-9]{1,4}-[0-9]{1,4}-[0-9]{3,4}` |
| 3 | メール | `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` |
| 4 | 口座番号 | `\b[0-9]{7,}\b`（**チケットID・cksum が誤検知するので目視で除外**） |
| 5 | 鍵・トークン | `sk-` `AIza` `ghp_` `xox[baprs]-` `Bearer ` `api_key=` `secret` `-----BEGIN` |
| 6 | 取引先名 | `株式会社\|有限会社\|合同会社\|Inc.\|Co., Ltd\|LLC` ＋ 通読 |
| 7 | ホームパスのユーザー名 | `/Users/` `/home/` `C:\Users` |

**grep だけで済ませないこと。** 6は grep で拾えない企業名（カタカナ・英字の単独表記）があるため、
必ず全文を読んだうえで判定する。今回は5ファイル計約17KB で通読可能だった。

### 判定に迷ったものの処理

- **一般公開サービス名**（e-Stat / EDINET / J-STAGE / YouTube / Gemini / Exa など）は取引先ではない＝混入ではない
- **各社が公開している価格**（X の $0.005/件 等）は当社の契約情報ではない＝混入ではない
- **語彙の例**（「新規お取引先募集」「最低発注ロット」）は特定の仕入先名ではない＝混入ではない
- **ユーザー名を含む絶対パス**は、自分が書く文書ではチルダ表記（`~/.claude/...`）にして**新規露出を作らない**。
  復元先としての一意性は失われない。**「自分が新たに書くもの」で露出を増やさないのは、マスキングではなく設計判断**
  （既存ファイルの書き換えは §4.1 に近い判断事項なので勝手にやらない）
