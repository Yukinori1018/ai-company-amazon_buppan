## 学び①：更新番号は「丸囚数字が尽きた後」を見落とす

`grep -on "更新[㊱-㊿]"` だけで最大番号を取ると **㊿ で止まり、既に使われている 51・52 を見落とす**。
㊿（50）の次から先は**素の半角数字**（更新51・更新52）で書かれている。
→ 番号を決めるときは `grep -n "更新5[0-9]"` も必ず併せて打つ。今回は 52 が使用済みで 53 が正解だった。

さらに、**更新52 はヘッダの「最終更新」行にだけ存在し、対応する `## 🆕` 節が無い**（前回セッションの取りこぼし）。
つまり「節の最大番号＋1」で採番すると衝突する。**番号の在庫はヘッダ行で数えるのが安全**。

## 学び②：社長タスクの「件数」と「手が要るか」は別の軸

差し戻しでも 🔴 の行は消さない（判断そのものは未了）。しかし中身は
「推奨＝続ける・社長の一言待ち」→「**差し戻し・調査中・いま社長のお手はかかりません**」に変わる。
件数は据え置きで、**行の中身と『今動く必要があるか』を書き換えるのが正しい処理**。
`knowledge_owner_task_vs_ticket_state.md`（列と件数は1対1でない）と同じ型。

## 学び③：親カードの Description が「判断待ち」のまま残ると嘘になる

発注文には親カードの更新指示は無かったが、親カードの Description は
「社長判断＝今すぐ Keepa＋計画の承認5点。推奨どおりなら一言で可」のままだった。
**回答は来ていて、内容は差し戻し。** 放置すれば社長が Notion を見たとき事実と食い違う。
→ 発注に書かれていなくても、**同じ事象で古くなるカードは同じ turn で直す**。これは越権ではなく同期の責務。

## 学び④：起票された frontmatter の固定語彙を検算する

新チケットの `assignee` が **`秘書カズヨ`**（日本語）だった。全87枚のうちこれ1枚だけ。
Notion の Assignee は snake_case の固定語彙10種（`docs/notion-board-schema.md`）で、
**multi-select/select はスキーマ外の値をエラー無しで落とす**ため、次の `/sync-notion` で黙って空欄になるところだった。
→ `secretary` に正規化し、欠けていた `created_at`/`updated_at` も補完。カードには正規化後の値で書いた。
起票直後の回では **`grep -h "^assignee:" tickets/*/*.md | sort | uniq -c`** が30秒で異常値を出す。

## 手順の再利用形（衝突しない書き方）

番号決定 → 3つの置換 → 即 `git add <各パス>` → commit を **1本の bash（python heredoc）**で閉じた。
各置換に `assert count==1`、書き換え前ブロックは**ファイルから読んだ実物を使う**（手で打ち直さない）。
`git add` はパスを個別指定（`deliverables/` にサトル3体が書き込み中のため、ディレクトリ一括は禁止）。
