## 何があったか

## 書いてよい／いけないの線引き（この形を今後の型にする）

| 区分 | 例 | 判断 |
|---|---|---|
| **書いてよい** | 「e-Tax の受信通知で **2026-08-21 提出**を確認」／「提出済み」 | **事実の成立**だけを書く。第三者が悪用できる識別子を含まない |
| **書かない** | 利用者識別番号・受付番号・氏名・税務署名・口座番号・住所・電話番号 | **本人特定情報**（CLAUDE.md §6「除外し続けるもの」） |

- ポイントは「**証拠の中身を写さず、証拠を見た結果だけを書く**」こと。進捗管理に必要なのは後者だけで、前者は1文字も要らない。
- 迷いを減らすため、**伏せた事実そのものも1行添える**（例：「本リポジトリは公開設定のため、利用者識別番号・受付番号等は記載しません」）。後から読む人が「書き忘れ」と誤解して埋めにくる事故を防げる。
- 既存の owner-tasks.md には T-20260820-002 の項に**所轄税務署名がすでに書かれていた**。今回は自分が足した行ではないので**勝手に消さず**、カズヨへ「既存の記載に本人特定に近い情報がある」と報告するに留めた。**削除はカズヨ／社長の判断**（勝手な改変は非破壊原則に反する）。→ **同日カズヨの判断で除去が確定**（T-20260826-005）。報告して指示を待つ、が正解だった。

## 「確認3件」型のタスクを部分解消するときの書き方

T-20260826-002 の「確認だけお願いしたい3件」のうち1件だけが解消した。**行を消さない**。

- 解消した行は `~~取り消し線~~` にして「✅ 解消。〜で確認」と**根拠を残す**。消すと「もう聞かれない」ことは分かるが「**答えたのに反映されていないのでは**」という不安が残る。
- 見出しは「**3件 → 1件解消し、残り2件です**」と**増減が一目で分かる形**に書き換える。
- 残った件が別チケットに分離したら、**分離先のIDと次回お声がけ日を同じ行に書く**（T-20260826-005 / 8/27）。「どこへ行ったか分からないタスク」を作らない。
- **社長タスクの純増をヘッダで明言する**（今回は「純増0件＝独立チケットになっただけ」）。チケットが1枚増えると社長には「やることが増えた」と見えるので、増えていないなら増えていないと書く。

### 検索の型（次回そのまま使える）

1. まず**固有名詞そのもの**で全リポ検索する：`grep -rn "<税務署名>" . --exclude-dir=.git`
   - カズヨの指示は `grep -rn "税務署" workspace/ docs/ agents/` だったが、この範囲だと **`workspace/output/deliverables/` の成果物カタログCSVは拾えるが、リポ直下の他ディレクトリは漏れる**。**固有名詞での全リポ検索を必ず併走させる**こと。
2. ヒット件数を置換の前後で数え、`before -> after` で定量報告する（0 になったことが証跡）。
3. **自分のメモリファイルも検索対象**。伏せるべき値を「報告のために引用」して自分で書き残していることがある（今回まさにそれ）。

### Notion Labels にオプションを足すときの作法（同チケット）

`compliance` を Labels に追加した。MCP の DDL は `ALTER COLUMN "Labels" SET MULTI_SELECT(...)` で、**渡した選択肢リストで丸ごと置き換わる**。既存29件を色ごと全て書き出したうえで末尾に1件足すこと。既存を省くと他カードのラベルが消える。

- `compliance`（法令順守の運用）と `legal`（契約・法的リスク＝ハルオ案件）は**別物**。寄せると `legal` フィルタが濁るというのがカズヨの確定理由。
- 色は既存10色すべて使用済みだったため `yellow` を選択（`legal` の red と視覚的に分ける意図）。
- **既存カードへの遡及付け替えはしない**（今回追加した1枚のみ）。
