# ナレッジ: 「commit を止める」では公開は止まらない（自動同期の構造）

> **状態: 反映済み**（2026-08-24 凍結解除後にリポジトリへ復帰）。
> 執筆時は commit 凍結中だったため、いったん scratchpad（リポジトリ外）に退避していた。**その退避判断自体が教訓2の実例**。

初出: 2026-08-24 / T-20260824-001 の法務レビュー（ハルオ）＋タカシの実測を受けた commit 凍結

## 何が起きたか

法務レビューで「**Keepa 由来データ約12,000行が PUBLIC な GitHub リポジトリに commit 済み**」（API T&C §11(1)
reproduce / disseminate 禁止に触れうる）と指摘され、カズヨから **「社長の判断が出るまで新規 commit を止めてください」** と指示された。

**しかし `commit` を止めても公開は止まらなかった。**

`~/Library/LaunchAgents/com.aicompany.amazon-buppan.github-sync.plist`（`StartInterval: 1800`）が
`.claude/scripts/github-sync.sh` を30分ごとに実行し、スクリプトは **L82 `git add -A` → L85 `commit` → L134 `push`** を自分で行う。

→ **エージェントが commit するかどうかと、公開されるかどうかは無関係。**
　**リポジトリ内にファイルを書いた時点で、30分以内に公開される。**

## 持ち帰る教訓

1. **「commit を止める」は公開の停止策として不完全。** 止めるべきは**パイプラインの最終段（push）またはスケジューラ**であって、
   人間／エージェント側の手動 commit ではない。凍結を指示されたら、**まず自動化が何をしているかを実測して確認する**
   （`grep -n "git add\|git push" <sync script>` と plist の `StartInterval`）。
2. **凍結中は「書かない」が正しい。** commit しなくても `git add -A` に拾われるので、
   **メモリ・作業メモの類もリポジトリ内に書かない**。scratchpad（リポジトリ外）に置き、内容を報告して預ける。
   本ファイルがその実例。
3. **自動化は、止めたい理由を知らない。** 「30分ごとに全部 push」は平時には親切な仕組みだが、
   **公開してはいけないものが生まれた瞬間に、最速で事故を起こす装置に変わる**。
   自動化を入れるときは「**止め方**」と「**止めたことを誰が知るか**」をセットで設計すること。
4. **スケジューラの停止は自分で実行しない。** 永続設定の変更にあたるため、カズヨ経由で社長判断を仰ぐ。
   ただし**時間の見積もり（次回発火まであと何分か）を添えて報告する**。締切のない警告は動いてもらえない。

## 実測メモ（2026-08-24 時点）

- plist: `~/Library/LaunchAgents/com.aicompany.amazon-buppan.github-sync.plist` / `StartInterval: 1800`
- スクリプト: `.claude/scripts/github-sync.sh`（L82 `git add -A` / L134 `git push --quiet origin "HEAD:$BRANCH"`）
- ログ: `workspace/.sync/github-sync.log`
- **HOLD ルールあり**: 「直近5分以内に更新されたファイルあり（編集中とみなしコミット見送り）」→ 1回スキップされることがあるが、**次の回で必ず拾われる**。猶予であって回避策ではない。
- force push・ブランチ削除・main への自動マージはしない設計（分岐したら push せず停止）

---

## 2026-08-24 社長判断：**公開のまま継続**

社長のご判断は **「公開で良い」**。リポジトリは PUBLIC のまま、30分ごとの自動同期も継続することになった。

**ただし、この教訓は無効にならない。**

ここに書いてあるのは「公開してよいか」の答えではなく、
**「公開してよいかを判断する前に、何が自動公開されるのかを把握する」という手順の話**である。
**判断結果によらず有効。**

今回、社長は **リスクを知った上で「公開で良い」と判断された**。これは「知らないまま流れた」のとは全く違う。
次に同じ構造の問いが来たとき（別リポジトリ・別の自動化・別のデータ）、答えが「公開しない」になる可能性は普通にある。
そのときに効くのは判断の結論ではなく、**この手順**である。

### 手順として残す（次回そのまま使う）

1. 「公開を止めたい／止めた」という話が出たら、**まず自動化の実体を読む** — `grep -n "git add\|git commit\|git push" <sync script>` と plist の `StartInterval`
2. **人間／エージェントの commit を止めるだけでは足りないか**を判定する（`git add -A` なら足りない）
3. **次回発火まで何分か**を計算して報告に添える
4. スケジューラの停止は**自分で実行せず**、A/B/C＋推奨で上げる（永続設定の変更のため）
