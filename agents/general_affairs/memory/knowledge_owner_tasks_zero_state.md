# 社長タスクが「ゼロ」になる回の書き方（2026-09-03 / T-20260826-004 更新⑤）

## 何が起きた回か

8ヶ月止まっていた Amazon の本人確認が、9/3 の10分のビデオ面談で**承認された**。
社長タスクが一時的に無くなり、次の一手がカズヨ側（9/4 の日次チェック）に移った。
カズヨからの発注文にも「今回は『社長タスクがゼロになる回』です」と明記されていた。

## 学び①：「社長タスクはゼロです」と書く前に、**必ずファイル全体を grep する**

カズヨの発注文どおりに書くと `owner-tasks.md` 冒頭に

> **社長タスクは現在ゼロです。**

と書くことになる。**が、これは事実ではなかった。**
同ファイルの「🟡 社長の番」「🔴 今すぐ着手」「🟡 情報共有・ご判断待ち」「🟢 確認待ち」には、
別件の未チェック項目が10件以上残っていた（gBizINFO 登録、納税情報登録、セラースプライト契約、
Git 履歴からの第三者PDF削除のご判断 など）。

**発注者（カズヨ）が言う「ゼロ」は、たいてい『その件のゼロ』であって『ファイル全体のゼロ』ではない。**
ここを取り違えると、このダッシュボードの信頼性がまるごと落ちる（社長が「ゼロと書いてあったのに残っていた」と感じた瞬間、
以後この最上段は読まれなくなる）。

**採った書き方（これを型にする）**

- 見出し・表・最終更新スタンプのすべてで **「この件（T-XXXX）の社長タスクはゼロです」** とスコープを明示する
- 直後に1行の注記を置く：
  > ※「ゼロ」はこの最優先ブロックの話です。下の「🟡 社長の番」以下には別件のお願いが残っています。
  > ただし**アカウントが開くまで動かせないもの**が大半なので、今夜は何もなさらなくて結構です。
- **「残っているが、今は動かせない」まで書く**と、スコープを絞っても社長の体感は「今夜はゼロ」のまま保てる。
  スコープを正確にするために安心感を削る必要はない。

## 学び②：良い知らせは、削らずに大きく書く

このリポジトリの既定は「くどい表現を削る」（`feedback_writing_too_wordy.md`）。
だが**8ヶ月の停滞が解けた回**は例外的に、成果そのものを1ブロック取って書く価値がある。

- 見出しに結果を入れる（「本人確認が承認されました。8ヶ月の停滞が解けました」）
- **社長の行動と結果を接続する**：「当日その時間を空けてくださったこと、パスポートの原本をご用意くださったことが、そのまま結果になりました」
- 削るのは**言い回し**であって**事実**ではない、というルールはここでも同じ。上の一文は事実の記述。

## 学び③：事実と推測が食い違うときは、**両方書いて「断定していない」と明記する**

今回の典型例：
- **事実**：申し立て画面の URL のノード名が `verification-in-progress`（確認手続き中）に変わった
- **事実**：同じ画面の表示は「検証に失敗しました」のまま
- **推測**：面談の承認を受けてカナダ側 KYC が再審査に入ったのかもしれない

カズヨから「この確度の区別は残してください」と名指しで指示があった。
本文では **事実／推測をラベルで分け**、「カズヨは断定していません」と地の文に置いた。
`（確度：推測）` の注記も Notion 側に入れた。

**推測を消して事実だけ書くのは不誠実ではないが、不親切。**
社長は「動いているかもしれない」という情報があるから今夜送らずに待てる。推測は残す。ただしラベルを貼る。

## 学び④：「やらないでください」型の注意は、**理由とセットでないと守られない**

今回追加した注意：

> 今夜〜明日にかけて、社長ご自身で Amazon に何かを送らないでください。
> **承認がカナダ側の審査に反映されるまで通常1〜2営業日かかり、重複送信は審査列の最後尾に戻ります。**

「送らないでください」だけだと、良い知らせの直後で気分が上がっている社長は動いてしまう。
**損（列の最後尾に戻る）を書いて初めて止まる。**

## 手順の型（更新⑤で実際にやったこと）

1. **更新番号は現物を見て採番する**（カズヨの発注文の記憶に頼らない）。
   `grep -n "更新" workspace/owner-tasks.md | head` で直前が④と確認してから⑤にした
2. 直前版（④）は `<details><summary>📌 更新④の記載（…・記録として残置）</summary>` に畳んで残置。
   畳むときは `## 見出し` を **`**（当時の見出し）** …`** に変換する（details 内に `##` が残ると目次が汚れる）
3. **`<details>` と `</details>` の数を必ず数える**：`grep -c "<details>"` と `grep -c "</details>"` が一致すること。
   今回は 6/6。入れ子が5段あるので、目視では絶対に合わせられない
4. 最終更新スタンプ（12行目）を書き換え、**旧スタンプは `／前: ` で後ろに連結**して消さない
5. Notion カード本文に同じ内容の節を `insert_content`（position: end）で追加、
   Description と `date:UpdatedAt:start` を更新。**Status は動かさない**（状態遷移は秘書の責務）

## 成果物カタログ（この回の状況）

新規成果物なし。前回指摘のあった 05・06 は **md/html 4行とも登録済み**（CSV 168行中の 166〜169 行目）。
念のため `python3 scripts/catalog/sync_catalog_to_sheet.py` を実行し、シートを 169 行 × 13 列で全置換ミラー更新（HTTP 200）。
**全置換ミラーなので、新規行が無くても流して損はない。**「差分が無いから流さない」より「流して一致を確認する」ほうが安い。

# 追記：2日連続で「ゼロ」になった回（2026-09-04 / T-20260826-004 更新⑦）

## 何が起きた回か

9/4 午前に更新⑥（社長タスク＝「保存する」→「確認のために送信」の2クリック）を書いた**直後**に、
社長がその2クリックを実行され、**Amazon が受理**した。
`soa-coc/regional` の表示が 🔴「検証に失敗しました」→ 🔵「現在、出品者様の情報を検証しています」に変化。
**2026-08-26 から10日間ずっと出ていた失敗表示が解けた回。**
社長タスクは再びゼロ（＝この件については）。**同じ日のうちに更新⑥→⑦を積んだ。**

## 学び⑤：「ゼロ」は2日連続でも来る。**そのたびにスコープを書き直す**

更新⑤（9/3）でも更新⑦（9/4）でも「この件の社長タスクはゼロ」になった。
2回目だからといって注記を省かない。**社長が読むのは冒頭の1ブロックだけ**なので、
「ファイル全体のゼロではありません」という但し書きは**毎回書く**。省くと、
下の「🟡 社長の番」以下に残る別件（gBizINFO・納税情報登録・セラースプライト契約 等）が見えなくなる。

今回の書き方：

> ※ この「ゼロ」は、この最優先ブロック（日本店の停止の件）についての話です。
> **このファイル全体の社長タスクがゼロになったわけではありません。**

## 学び⑥：**前日の「解消」は、翌日の「完了」に昇格させる**

更新⑥では「サポート宛メール（成果物07）の送信 → **不要になりました**」が ✅ 解消だった。
更新⑦では、それとは別に「**2クリックを押していただき、受理された**」が ✅ 完了になる。

区別のしかた：

| ラベル | 意味 |
|---|---|
| ✅ **解消** | お願い自体が**要らなくなった**（社長は何もしていない） |
| ✅ **完了** | 社長が**実際に手を動かして片づいた** |

社長にとって「自分がやって進んだ」と「やらずに済んだ」は体験がまったく違う。混ぜない。

## 学び⑦：**「受理された」は「完了した」ではない。チケットを done にしない**

今回いちばん気持ちよく書ける材料（10日続いた赤表示が消えた）が来たが、

- アカウントは**まだ停止中**
- KYC は**審査中**（最大10営業日）
- CA の違反1件・AHR 0・ヘッダー一時停止中は**未更新のまま**

カズヨの発注文にも「**まだ done ではありません**」と明記があった。
**進展の大きさに引きずられて状態を進めない。**状態遷移は秘書の責務でもある。
owner-tasks.md の末尾にも「このチケットはまだ完了ではありません〔waiting〕」と1行入れた。

## 学び⑧：**未更新の表示は「想定内」と書きつつ、断定の有無を必ず添える**

CA の違反1件・AHR 0・ヘッダー一時停止中が変わっていないことについて、
カズヨの発注文は「KYC の審査結果が出てから更新されるものと見ています。**カズヨは断定していません。**
この確度の区別は残してください」と明示していた。

書き方：

> - **カズヨの見立て**：KYC の審査結果が出てから更新されるもの。
> - **ただし断定はしていません。**事実＝これらの表示は変わっていない／推測＝審査結果を待って更新される。

**事実と推測を1行ずつ分けて並べる**のがいちばん短く、いちばん誤解されない。

## 学び⑨：期限は「消えた」と書かず、**「充足したと見る（要確認）」で置く**

9/12（書類再提出10日）・9/14（19日）は本日の提出で手当てされたと考えられるが、
Amazon からの受領通知は来ていない。**表から消すと、外れたときに誰も気づけない。**
表に残したまま「見通し」列を足し、`本日の提出で充足したと見ています（要確認）` と書いた。
10/5・10/25 は「継続中。審査が最長（9/18 頃）でも間に合います」と併記。

## 手順（更新⑦で実際にやったこと・⑤の型をそのまま踏襲）

1. `grep -n "^## 🚨🚨" workspace/owner-tasks.md` で**直前が⑥**と確認してから⑦を採番
2. 旧⑥を `<details><summary>📌 更新⑥の記載（…・記録として残置）</summary>` に畳み、
   `## 見出し` → `**（当時の見出し）** …` に変換
3. **`<details>` / `</details>` の数を数えて一致を確認**（今回 8/8。入れ子6段）
4. 12行目の最終更新スタンプを書き換え、旧スタンプは `／前: ` で連結して残す（更新③→④に採番）
5. Notion カード（`3c8b0a40-44fa-8118-853f-db403231379a`）本文に
   `## 2026-09-04（続）提出が受理され、KYCは審査中へ` を `insert_content`（position: end）で追加。
   Description と `date:UpdatedAt:start` を更新。**Status は waiting のまま動かさない**
6. 成果物カタログ：**新規成果物なし**（`deliverables/T-20260826-004/` に変化なし）＝CSV 追記・シート同期とも不要
