# カタログ漏れは「長く waiting に居るチケット」で必ず起きる

2026-09-02 / T-20260826-004（日本店アカウント停止）の同期回で発見。

## 何が起きていたか

`workspace/output/deliverables/T-20260826-004/` に成果物が**6ファイル**（01〜04＋HTML＋README）
積み上がっていたのに、マスターCSV には **1行も登録されていなかった**。8/28 から数えて5日ぶん、
法務ハルオ・IT タカシ・リサーチャー サトルの3人ぶんの納品が丸ごと抜けていた。

## なぜ漏れたか（構造の問題であって、誰かの怠慢ではない）

カタログ更新のトリガーは、スキル上「`deliverables/` に新しい成果物が出たとき」だが、
**実務上の起動タイミングは「チケット完了の締め作業」に寄っている**（skills/deliverables-catalog.md §3-4）。

- **done にならないチケットは、締め作業が永遠に来ない。**
- T-20260826-004 は 8/26 起票から一度も done になっていない `waiting` の長寿チケット。
  しかも「社長の番」で止まっているため、こちらの手では絶対に done にできない。
- その間も成果物だけは増え続ける。**止まっているのはチケットであって、納品ではない。**

## 次回からの判定（これを機械的に回す）

同期の依頼を受けたら、状態遷移の有無にかかわらず**必ず**次を打つ。1秒で済む。

```bash
# 当該チケットの成果物が全部カタログに載っているか
ls workspace/output/deliverables/<TID>/
grep -c "^<TID>," workspace/output/deliverables/T-20260601-001/deliverables-catalog.csv
```

ファイル数（ノイズ除く）と行数が合わなければ、その差が漏れ。
**HTML併出力は2行**（MD版とHTML版で別行）、**README も1行**として数える。既存チケットの前例に揃える。

さらに全体の取りこぼしを一発で見るなら:

```bash
# deliverables にフォルダがあるのにカタログに1行も無いチケット
for d in workspace/output/deliverables/*/; do t=$(basename "$d");
  grep -q "^$t," workspace/output/deliverables/T-20260601-001/deliverables-catalog.csv || echo "未登録: $t"; done
```

## 教訓

**「完了したら登録する」という設計は、完了しないものを取りこぼす。**
カタログの起動条件は「チケットが終わったとき」ではなく「**ファイルが増えたとき**」。
long-running な waiting チケットこそ、成果物が最も積み上がる場所だと覚えておく。

## 2026-09-06 追記 — 「全チケット横断で漏れを数える」1行スクリプト

カズヨの依頼は T-20260906-005 / -006 の2件だったが、依頼分（11行）を入れた直後に
**全チケットを横断でスイープ**したところ、**追跡済み成果物があるのにカタログ行が0のチケットが4件**あった。

| チケット | 状態 | 追跡ファイル | カタログ行 |
|---|---|---:|---:|
| T-20260904-005（スーパーデリバリー 追加書類） | waiting | 3 | 0 |
| T-20260906-002（ドロップ数の正体） | doing | 14 | 0 |
| T-20260906-003（母数引き直し・夜間自走） | doing | 7 | 0 |
| T-20260906-004（NETSEA商品URLの公開可否） | **done** | 3 | 0 |

**この追記の要点は、漏れが `waiting` 固有ではなかったこと。** 前段の記述は「長く waiting に居るチケット」を
原因に挙げていたが、今回は **doing 2件と done 1件**でも漏れていた。真因はもっと単純で、
**「カタログ更新はカズヨが依頼したチケットにしか走らない」**という運用の形そのものにある。
依頼が来ないチケットは、状態が何であれ永久に登録されない。

### 機械的なスイープ（依頼分を片付けた直後に必ず打つ）

```bash
for t in $(git ls-files workspace/output/deliverables/ | cut -d/ -f4 | sort -u); do
  n=$(grep -c "^$t," workspace/output/deliverables/T-20260601-001/deliverables-catalog.csv)
  [ "$n" -eq 0 ] && echo "未登録: $t ($(git ls-files workspace/output/deliverables/$t/ | wc -l) files)"
done
```

**「ファイル単位で未登録を数える」やり方は使えない。** 最初にそれを書いたら314件出た。
カタログは複数ファイルを1行に束ねる（スクリプト群・実測ログ群）ので、**ファイル数と行数は一致しない設計**。
**チケット単位で「行が0か」を見る**のが唯一ノイズの出ない判定。

### 走行中のジョブをカタログに載せるとき

T-20260906-003 の `stats_進捗.csv` は夜間ジョブが走りながら書き換えている。
`knowledge_deliverables_catalog_sync.md` の「更新中のものは要約を書かない」に従うと登録できないが、
**チケットごと落とすほうが害が大きい**（存在自体が見えなくなる）。判断：
**備考の冒頭に `【途中経過】` と書き、「完走後に最終値で要約を更新する」ことを明記して登録する。**
ハーネス（スクリプト・README・plist）は走行と無関係に確定しているので普通に登録してよい。
