## 2026-08-23 / T-20260817-005 / Notion MCP が未接続で同期不可

- **事象**: サブエージェント（マリエ）セッションから Notion カンバンへ同期しようとしたが、**`notion-*` の MCP ツールが1つも存在しなかった**。
  `ToolSearch` を `+notion` / `create pages database` の2通りで引いても 0 件。
- **原因**: このリポジトリに **`.mcp.json` が存在しない**（あるのは `.mcp.json.example` のみ）。
  `~/.claude.json` 側も `mcpServers: []` / `enabledMcpjsonServers: []` で、**このマシンのこのプロジェクトには Notion MCP が接続されていない**。
  → トークンは `.mcp.json` に書く設計（CLAUDE.md §7.1）なので、example のままではホスト型 MCP が起動しない。
- **影響**: T-20260817-005 の Notion カード更新（UpdatedAt=2026-08-23、本文「結果要約」の最新化）が**未実施**。Status は doing のままなので**列の移動は不要**＝ドリフトは UpdatedAt と本文のみで軽微。
- **教訓（再発防止）**:
  1. **Notion 同期を発注される前に、まず MCP の存在確認をする。** ツールが無い環境では「同期しました」と言えない。無いなら**着手前にその旨を宣言**してから残りの作業を進める。
  2. マリエ側の agent 定義が `tools` を絞らず全継承にしているのは Notion MCP を確実に使うため。ただし**継承しても、そもそも接続されていなければ意味がない**。全継承＝使える保証ではない。
  3. 復旧手順は `.mcp.json.example` → `.mcp.json` へコピーし `NOTION_API_KEY` / `NOTION_DATABASE_ID` を埋める（**社長の手作業。トークンは機密**）。その後 `/sync-notion` で一括リコンサイルすれば、この日の取りこぼしも自動で吸収される。
- **申し送り**: カズヨへ「Notion 同期は未実施。MCP 接続のあるセッションで `/sync-notion` を1回流してください」と引き渡し済み。

## 2026-08-24 / T-20260824-003・T-20260824-004 / **同じ失敗の2回目**（サブエージェントに Notion ツールが降りてこない）

- **事象**: カズヨからの発注（T-20260824-003 を done 列で新規作成／T-20260824-004 を todo 列で新規作成）を実行しようとしたが、
  マリエのサブエージェントセッションに **`notion-*` ツールが1つも存在しなかった**。
  `ToolSearch` を `+notion` / `notion create pages update page query database view fetch` / `database page workspace wiki card kanban` の3通りで引いて 0 件。
  起動時に提示される deferred tool 一覧にも notion 系は1つも含まれていない。
- **前回との違い＝ここが新しい発見**:
  - 前回（2026-08-23）は「このプロジェクトに Notion MCP が接続されていない」と結論づけた。**それは不正確だった。**
  - **同じ 2026-08-24 のうちに、別セッションでは `notion-fetch` が動いて ticket DB のスキーマ実照会に成功している**
    （`owner-tasks-summary-ownership.md` の「教訓」節に記録あり）。
  - → つまり Notion（ホスト型コネクタ）は**親セッション側では生きている**。落ちているのは接続そのものではなく、
    **サブエージェントへツールが継承されていない**という一点。`.mcp.json` の不在は依然として事実だが、真因はそこではない。
- **したがって `agents/general_affairs/agent.md` 冒頭の前提は誤り**:
  > 「全ツールを継承させることで Notion MCP を確実に使えるようにしています」
  **`tools` を省略しても、ホスト型コネクタはサブエージェントに降りてこない。** 2回連続で同じ壁に当たった。
- **影響**: 下記2枚のカード作成が**未実施**。リポジトリ側は正（done/ と todo/ に配置済み）なので、ドリフトは Notion 側の欠落2枚のみ。
- **回避策（今回の実際の運び）**: カズヨへ**そのまま貼れる MCP ペイロード**を渡し、親セッション側で実行してもらう。
  マリエ側は owner-tasks.md 更新と成果物カタログ同期（どちらもローカル完結）を完了させて前進を止めない。
- **恒久対策の候補（カズヨ判断）**:
  - A. Notion 同期だけは**親セッション（カズヨ）が実行する**と運用を確定させ、skills/notion-ticket-sync.md の責務記述を「マリエが payload を作り、カズヨが投げる」に改訂する
  - B. `.mcp.json` を実体化して**プロジェクトスコープの MCP** にする（＝サブエージェントにも降りる可能性が高い）。ただしトークンは機密・本リポは PUBLIC で30分ごと自動 push のため、`${ENV_VAR}` 参照か headersHelper 必須（`.mcp.json.example` の警告どおり）
  - **推奨は B → 成功したら A は不要**。B が通らないなら A に倒す。どちらも社長の手が要る（トークン）ので waiting 案件。
- **教訓**: 「同じ失敗の記録が既にある」と気づいたら、**前回の原因分析を疑ってかかる**。
  前回の結論（接続が無い）が正しければ 2026-08-24 の別セッションで notion-fetch が動いた説明がつかない。
  **記録は残っていたのに、原因が間違っていたので再発した。**記録するだけでは再発は止まらない。
