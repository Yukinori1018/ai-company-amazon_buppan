# `_inbox_社長共有` の運用 — 崩壊事故の記録と教訓

記録: マリエ / 2026-08-21 / T-20260821-009

## 何が起きたか

社長から「共有したファイルが整理されていない。最初の方はきちんと運用されていたが、今はできていないみたい」。
実測で **21件（xlsx 1 / PNG 20）が最長12日間滞留**。うち**2件はどのチケットにも紐づいていない完全な取りこぼし**だった。

## 真因（一言）

> **後片付けが「チケットのタスク分解に、起票者が手書きで1行足したときだけ実行される属人的ステップ」だった。**

2026-06-10 の T-20260610-001 には
`- [x] 原本の整理・移動（57ファイル → ...）＋ inbox クリーンアップ` という行が**実在する**。
これがあったから inbox は空になった。2026-08 の T-20260811-001 / T-20260812-001 には**無い**。それだけの差。

**「最初はできていた」理由が、そのまま「今できていない」理由だった。**
仕組みで回っていたのではなく、たまたま1行が書かれていただけ。運が続くわけがない。

## 学び（他の領域にも効く一般則）

### 1. 「ルールが無い場所は、必ず放置される」

`grep -rn "_inbox"` の結果、CLAUDE.md にも agents/ にもルールらしき記述はゼロだった。
記述があったのは README.txt（社長向けの使い方説明）だけで、**エージェント側の「誰が・いつ・どう処理するか」が未定義**。
誰の責務でもない仕事は、誰もやらない。当たり前だが、実際に21件溜まるまで誰も気づかなかった。

### 2. 「プル型トリガー（社長の申告が起点）は、いずれ必ず止まる」

旧 README.txt の手順は ①置く → **②チャットで「入れた」と伝える**。
2026-08 の資料受け渡しは主流がチャット貼り付けへ移り、inbox は「たまに使う裏口」になった。
**裏口に置かれて、かつ申告されなかったファイルは永久に放置される。** xlsx と FireShot 026 がまさにこれ。

→ **社長の記憶を前提にした運用は設計してはいけない。** 会社側から毎回声をかける形（プッシュ型）に直す。

### 3. 「.gitignore 対象は全フックの死角になる」

既存フック3本（session-start / ticket-notion-sync-reminder / owner-tasks-sync-check）の発火条件を実際に読んだ結果、
**いずれも `workspace/tickets/` 等の追跡ファイル変更が起点**。inbox は Git 差分に出ないので、どのフックも反応しない。

ただしこれは**原因ではなく増幅要因**。仮に Git 追跡下にあっても、片付けルールが無ければ
「差分に出るが誰も片付けないファイル」になるだけだった。**原因と「なぜ気づけなかったか」を混同しない。**

### 4. 「原因候補を渡されても、同格として扱わない」

秘書から5つの原因候補をもらったが、実地で裏取りすると
**真因2つ（ルール不在・プル型依存）＋ 増幅要因3つ（gitignore・責務未登録・受け皿未定義）**に階層が分かれた。
5つ全部に対策を打つのは正しいが、**どれが要（かなめ）かを言わないと、次に似た事故が起きたとき判断できない**。
今回の要は「検知の自動化」。ルールを書くだけでは、読む人がいなければ元通りになる。

### 5. 「放置されたファイルは、散らかっているだけでは済まない」

実害が2つ出た。

- **FBA納品代行業者 比較表**（08-09 受領・12日死蔵）が、現行チケット **T-20260817-006 の判断根拠を一部覆していた**。
  同チケットは「先に契約すると月額固定費 2,000〜4,000円が出続けるから急がない」と評価しているが、
  本資料によれば**就労支援系（A型/B型）は月額固定費ほぼ無料**。論拠は一般物流系にしか当てはまらない。
- **FireShot 026（Keepa 出品者概要）** が未反映のまま。納品済み Keepaマニュアルにも memory にも記述がなく、
  **ナレッジに穴が空いていた**。

→ 棚卸しは「片付け」ではなく **「発掘」**。中身を開かずに拡張子とファイル名だけで振り分けていたら、
　 両方とも `_archive/` に埋葬して終わっていた。**必ず全件開くこと。**

## 振り分けの型（次回そのまま使える）

行き先は**2つだけ**。判断基準は行動原則1「直近3ヶ月使ったか／これから使う見込みがあるか」。

- 今後も参照する → `docs/reference/<topic>/`
- チケットで消費済み → `_archive/YYYY-MM/<ticket_id>_<内容>/`

`docs/reference/` に置くときの追加判断（先例が既にある）:
- 第三者動画由来のメディア → `.gitignore` 追加でローカル保持、索引 README だけ Git 追跡（`poipoi-pocket` 方式）
- 公開情報の要約・軽量ファイル → Git 追跡してよい（`fba-prep-center` 方式）
- 分量があればテキスト版を併置（memory `owner_html_output_rule`）

**どちらに置く場合も `README.md` を必ず添える。**
README のないアーカイブは「何だったか分からない箱」になり、結局いつか捨てられる。

## 破棄判断のときめき基準（今回の適用例）

破棄候補に挙げてよいのは**情報価値ゼロと断言できるもの**だけ。今回は `.DS_Store` の1件のみ。

> **「もう使わないと思う」はアーカイブの理由であって、削除の理由ではない。**

AMZScout の14枚は「A案＝契約しない」で決着済みだが、T-20260812-001 に
「③簡易OEM の実行フェーズで無料トライアル残回分を検証する」と明記があるため**再利用の見込みあり**＝残す。
**チケット本文に将来の再利用が書かれていないか、必ず確認してから破棄候補に入れること。**

なお削除は CLAUDE.md §4.1（不可逆な削除）。マリエは実行しない。リストアップして秘書経由で社長承認。

## 報告の作法（今回の反省）

Before/After の「節約容量」を **0バイト**と正直に書いた。削除ゼロなので当然だが、
整理の成果を容量で語る癖があると、**捨てなくていいものを捨てる圧力**になる。
今回の問題は「重い」ことではなく「行き先が決まっていない」ことだった。**指標は問題に合わせて選ぶ。**

また、自分が書いたレポートの数字（孤児ファイル件数）を §1 と §5 で食い違わせた。
**納品前に自分の成果物内の数字の整合を必ず突き合わせること。**
