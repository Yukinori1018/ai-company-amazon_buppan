# `_inbox_社長共有` の運用 — 崩壊事故の記録と教訓

記録: マリエ / 2026-08-21 / T-20260821-009

## 何が起きたか

社長から「共有したファイルが整理されていない。最初の方はきちんと運用されていたが、今はできていないみたい」。
実測で **21件（xlsx 1 / PNG 20）が最長12日間滞留**。うち**2件はどのチケットにも紐づいていない完全な取りこぼし**だった。

## 真因（一言）

> **後片付けが「チケットのタスク分解に、起票者が手書きで1行足したときだけ実行される属人的ステップ」だった。**

2026-06-10 の T-20260610-001 には
`- [x] 原本の整理・移動（57ファイル → ...）＋ inbox クリーンアップ` という行が**実在する**。
これがあったから inbox は空になった。2026-08 の T-20260811-001 / T-20260812-001 には**無い**。それだけの差。

**「最初はできていた」理由が、そのまま「今できていない」理由だった。**
仕組みで回っていたのではなく、たまたま1行が書かれていただけ。運が続くわけがない。

## 学び（他の領域にも効く一般則）

### 1. 「ルールが無い場所は、必ず放置される」

`grep -rn "_inbox"` の結果、CLAUDE.md にも agents/ にもルールらしき記述はゼロだった。
記述があったのは README.txt（社長向けの使い方説明）だけで、**エージェント側の「誰が・いつ・どう処理するか」が未定義**。
誰の責務でもない仕事は、誰もやらない。当たり前だが、実際に21件溜まるまで誰も気づかなかった。

### 2. 「プル型トリガー（社長の申告が起点）は、いずれ必ず止まる」

旧 README.txt の手順は ①置く → **②チャットで「入れた」と伝える**。
2026-08 の資料受け渡しは主流がチャット貼り付けへ移り、inbox は「たまに使う裏口」になった。
**裏口に置かれて、かつ申告されなかったファイルは永久に放置される。** xlsx と FireShot 026 がまさにこれ。

→ **社長の記憶を前提にした運用は設計してはいけない。** 会社側から毎回声をかける形（プッシュ型）に直す。

### 3. 「.gitignore 対象は全フックの死角になる」

既存フック3本（session-start / ticket-notion-sync-reminder / owner-tasks-sync-check）の発火条件を実際に読んだ結果、
**いずれも `workspace/tickets/` 等の追跡ファイル変更が起点**。inbox は Git 差分に出ないので、どのフックも反応しない。

ただしこれは**原因ではなく増幅要因**。仮に Git 追跡下にあっても、片付けルールが無ければ
「差分に出るが誰も片付けないファイル」になるだけだった。**原因と「なぜ気づけなかったか」を混同しない。**

### 4. 「原因候補を渡されても、同格として扱わない」

秘書から5つの原因候補をもらったが、実地で裏取りすると
**真因2つ（ルール不在・プル型依存）＋ 増幅要因3つ（gitignore・責務未登録・受け皿未定義）**に階層が分かれた。
5つ全部に対策を打つのは正しいが、**どれが要（かなめ）かを言わないと、次に似た事故が起きたとき判断できない**。
今回の要は「検知の自動化」。ルールを書くだけでは、読む人がいなければ元通りになる。

### 5. 「放置されたファイルは、散らかっているだけでは済まない」

実害が2つ出た。

- **FBA納品代行業者 比較表**（08-09 受領・12日死蔵）が、現行チケット **T-20260817-006 の判断根拠を一部覆していた**。
  同チケットは「先に契約すると月額固定費 2,000〜4,000円が出続けるから急がない」と評価しているが、
  本資料によれば**就労支援系（A型/B型）は月額固定費ほぼ無料**。論拠は一般物流系にしか当てはまらない。
- **FireShot 026（Keepa 出品者概要）** が未反映のまま。納品済み Keepaマニュアルにも memory にも記述がなく、
  **ナレッジに穴が空いていた**。

→ 棚卸しは「片付け」ではなく **「発掘」**。中身を開かずに拡張子とファイル名だけで振り分けていたら、
　 両方とも `_archive/` に埋葬して終わっていた。**必ず全件開くこと。**

## 振り分けの型（次回そのまま使える）

行き先は**2つだけ**。判断基準は行動原則1「直近3ヶ月使ったか／これから使う見込みがあるか」。

- 今後も参照する → `docs/reference/<topic>/`
- チケットで消費済み → `_archive/YYYY-MM/<ticket_id>_<内容>/`

`docs/reference/` に置くときの追加判断（先例が既にある）:
- 第三者動画由来のメディア → `.gitignore` 追加でローカル保持、索引 README だけ Git 追跡（`poipoi-pocket` 方式）
- 公開情報の要約・軽量ファイル → Git 追跡してよい（`fba-prep-center` 方式）
- 分量があればテキスト版を併置（memory `owner_html_output_rule`）

**どちらに置く場合も `README.md` を必ず添える。**
README のないアーカイブは「何だったか分からない箱」になり、結局いつか捨てられる。

## 破棄判断のときめき基準（今回の適用例）

破棄候補に挙げてよいのは**情報価値ゼロと断言できるもの**だけ。今回は `.DS_Store` の1件のみ。

> **「もう使わないと思う」はアーカイブの理由であって、削除の理由ではない。**

AMZScout の14枚は「A案＝契約しない」で決着済みだが、T-20260812-001 に
「③簡易OEM の実行フェーズで無料トライアル残回分を検証する」と明記があるため**再利用の見込みあり**＝残す。
**チケット本文に将来の再利用が書かれていないか、必ず確認してから破棄候補に入れること。**

なお削除は CLAUDE.md §4.1（不可逆な削除）。**承認をどう受け取ったかで実行可否が変わる**（社長からの一次承認なら実行可／伝聞なら差し戻す）。詳細は本ファイル末尾「不可逆削除の実行可否は『承認をどう受け取ったか』で決まる」を参照。

## 運用上の事故: 並行セッションによる commit の巻き込み（2026-08-21）

`git add` でステージした自分のファイルが、**並行して動いていた別セッションの `git commit` に
そのまま取り込まれた**（commit 5ece40a = ticket_id 衝突改番。本作業とは無関係）。
ファイルの欠落はゼロだったが、**コミットメッセージが作業内容を説明しない状態**になった。

背景: 作業開始時点で、別セッションが既にチケットのリネーム3件を index にステージ済みだった
（`git status` の `RM` 表示）。`git commit -- <paths>` でパス限定コミットを試みたが、
その実行前に相手側が先に commit を打ち切ってしまった。

**次回の対策:**

1. 作業開始時に `git status --short` を撮っておき、**自分以外のステージ済み変更があるかを先に確認**する
2. ある場合は `git add` を使わず、最初から **`git commit -- <自分のパス>`** のパス限定コミットで一撃で閉じる
   （`git add` してから commit するまでの窓が、巻き込みの危険地帯）
3. 巻き込まれたら **履歴は書き換えない**（`reset --hard` / `rebase` / force push は CLAUDE.md §4.1）。
   ファイルの存在を `git cat-file -e "HEAD:<path>"` で全件確認し、**チケットのログに
   「どのコミットに入っているか」を記録**して追跡性を回復させる。これが唯一の正しいリカバリ。

## 不可逆削除の実行可否は「承認をどう受け取ったか」で決まる（2026-08-21）

社長判断で `.DS_Store` の削除に **A（削除可）** が下り、カズヨ経由で実行を指示された。
**マリエは伝聞承認と判断して実行せず、差し戻した。**

→ **結果**: 実際にはカズヨが**社長からチャットで直接受けた一次承認**だった（「全部Aで進めて」）。
　 承認を受け取った当人であるカズヨが、対象を実地確認のうえ削除を実行（2026-08-21 13:25）。
　 **差し戻しの判断自体は原則として正しく、運用として維持された。**事実認識の1点だけが誤っていた。

### 線引き（3段）

| 承認の種類 | 定義 | 実行の可否 |
|---|---|---|
| **一次承認** | 社長がチャットで**その相手に直接**与えたもの | **受領した本人が**、対象を実地確認のうえ**実行してよい** |
| **伝聞承認** | 承認を受けた者を経由して別エージェントへ伝達されたもの | **受け取った側は実行しない。承認を直接受けた者へ差し戻す** |
| 承認なし | まだ承認が無い | 実行しない。リスト化して秘書経由で仰ぐ |

**「マリエは絶対に実行しない」は誤り。正しくは「社長から直接承認を受けたなら実行できる／
秘書など他のエージェント経由なら差し戻す」。**旧版の書き方だと、社長から直接承認をもらった場面でも
止まってしまい、自分の手を不必要に縛ることになる。

### なぜ伝聞では止めるのか（原則は維持する）

対象が `.DS_Store`（実害ゼロ・自動再生成）だったから軽く見えるが、
**次に同じ経路で来るのが本物のデータだったときに効く線引き**。ここを緩めると、その時に止められない。
カズヨからも「運用として維持する」と明示的に確認された。

### 止めるときの作法（重要）

**止めるだけでは仕事にならない。**「実行できません」で終わらせず、次の3点をセットで渡す。

1. **なぜ実行しないかの理由**（どの規定に基づくか）
2. **対象を限定した実行コマンド**（相手が1コマンドで終わる状態にする）
3. **実行しなくても実害が無いことの説明**（あるいは、ある場合はその影響）

今回はこの3点を揃えて差し戻したので、カズヨ側は事実誤認を1行で訂正するだけで前に進めた。
**差し戻しは「止める」ではなく「正しい実行者に渡す」**と考える。

### 不可逆操作は必ず監査可能にする

実行者・日時・対象（フルパス/件数/サイズ/種別）・事前確認・事後確認の5点をチケット本文に残す。
書式の実例は T-20260821-009「①の実行記録（監査用）」。

**「何を消さなかったか」も記録する。**実行しなかった記録は、後から効く。

### 事実確認についての反省

「伝聞である」と**断定**して差し戻したが、実際には一次承認だった。
承認の伝達経路は、こちらからは見えないことがある。
→ 次回は「**伝聞に見えるので確認したい。社長から直接受けた一次承認ですか？**」と
　 **経路を問う形**で差し戻すほうが、相手の手数が1往復減る。
　 断定せずに確認する。止める判断は変わらないが、**言い方で相手の時間が変わる**。

## 発掘した資料が「誤っていた」場合の後始末（2026-08-21 / T-20260821-010）

T-20260821-009 で発掘した FBA代行比較表を、サトルが公式裏取りした結果 **誤り18件**が判明した
（相違9・出典が一次情報でない2・裏取り不能2・重大な記載漏れ5）。

**学び：発掘して終わりではない。「発掘した資料が正しいか」まで面倒を見て初めて棚卸しが完了する。**
マリエは「T-20260817-006 の判断を覆す資料です」と勢いよく報告したが、
**その資料自体が AI 生成で未裏取りだった**。結果は「判断は維持・論拠だけ差し替え」で、
覆ったのは論拠のほうだった。発掘時に**裏取り未実施であることを明記していたのは正解**だったが、
「覆します」という表現は前のめりだった。次からは「**覆す可能性がある（要裏取り）**」と書く。

### AI 生成資料の壊れ方（サトルの検証で判明・横展開する価値あり）

> **全部が間違っているのではない。料金項目はよく一致する一方で、
> 「都合の良い要約だけが残り、制約条件（保証金・最低ロット・契約区分・追加料金）が消える」。**
> **判断をひっくり返す情報ほど利用規約・FAQ に埋まっていて、AI がそこを落とす。**

実例：タイシン「初期費なし」→実際は**保証金5万円**／FBA代行センターの**小口契約不可の記載漏れ**（当社は小口＝そもそも契約不可）。
どちらも「その業者を選べない」という結論に直結する情報で、要約からきれいに消えていた。

### 収納した資料に警告を貼る（今回の対応）

原本は**修正せずそのまま保全**し（AI 生成物の原本として価値がある）、
`docs/reference/fba-prep-center/README.md` の**冒頭に警告ブロック**を置いた。

- 「単独で判断に使わないでください」＋ファクトシートへの併読リンク
- **危険な誤記を名指しで表にする**（一般論の注意書きでは読み飛ばされる）
- 出典が一次情報でないもの（見積アグリゲータ・別会社のブログ）も明示

→ **原本は直さず、警告と差分を別レイヤーで管理する**のが正しい。原本を書き換えると
「AI が何を間違えたか」の証拠が消え、同じ検証を将来もう一度やる羽目になる。
