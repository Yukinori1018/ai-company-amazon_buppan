# 担当: 社長タスクまとめ の維持（2026-05-27〜／2026-08-24 全面改訂）

## 概要

社長が「次に何をすべきか」を1枚で把握するダッシュボードの維持は**マリエ（庶務）の担当**です。情報整頓＝庶務の本分のため。社長フィードバック（2026-05-27）でカズヨから正式に移管されました。

## 対象は **1層だけ**（ここを読み違えないこと）

| 層 | 実体 | 備考 |
|---|---|---|
| 真実（唯一） | `workspace/owner-tasks.md`（リポジトリ） | マリエが手で最新化する |
| 社長が Notion で見る場所 | **ticket DB の `waiting` 列そのもの** | 専用カードは存在しない。waiting 列が役割を引き継いだ（CLAUDE.md §6） |

> **⚠️ 「📋 社長タスクまとめ」という Notion カードは実在しません。**
> 過去のメモリには page_id `36db0a40-44fa-815b-a60b-f854b6cd431d`・**Status=「まとめ」列に常駐**と書かれていましたが、
> **どちらも現存しません**（経緯は末尾の「教訓」節）。カズヨから「まとめカードも更新して」と依頼が来ても、
> **更新すべき実体は無い**ので、下記の手順4（waiting 突合）に読み替えて実行し、その旨を報告に書くこと。

## 更新の進め方

カズヨから発注を受けたら:

1. `workspace/tickets/{todo,doing,waiting,done}/` を走査し、**社長アクションが必要なもの**（owner 依存・§4.1 承認待ち・情報提供待ち・レビュー待ち・社長自身の手作業待ち）を抽出する
2. `workspace/owner-tasks.md` を更新する（区分と「最終更新」日付の体裁は維持）
   - 区分: 🚨 緊急 / 🟡 社長の番 / 🔴 今すぐ着手 / 🟡 情報共有・ご判断待ち / 🟢 確認（レビュー）待ち / ℹ️ 自動で進みます
   - **`doing` のチケットを 🔴🟡🟢 に入れない。** 社長の手が要らないものは ℹ️「自動で進みます」へ。社長タスク欄が濁ると waiting 列の価値が落ちる
3. ~~Notion まとめカードを同期~~ → **不要**（実体が無い）
4. 代わりに **突合**する: owner-tasks.md に書いた社長タスクが、対応チケットで **`Status=waiting` になっているか**
   - 社長が「自分の番」を見る場所は waiting 列。**owner-tasks.md に書いたのに waiting に無い、が新しいドリフト**
   - ローカル `.md` の `status` と Notion カードの `Status` の**両方**を見る（片方だけだと分岐由来のズレを見逃す）
5. **Before / After**（増えた／解消した社長タスク）を添えてカズヨへ報告する

## 判断のルール（過去に迷った点の確定版）

- **「別チケットで解消されるかもしれない」を理由に社長タスクを消さない。** 解消は**確定してから**。可能性で消すと、消えたことに誰も気づかない。代わりに「〜で解消される可能性あり・急がなくて結構です」と**注記**する（2026-08-24 カズヨ裁可）
- **`priority` / `labels` が frontmatter に無いときは推測で埋めない。** 起票者が入れる欄。Notion の Priority 列が空になるのは仕様どおりで、報告に「欠落」と書いて起票者へ返す（`ticket-frontmatter-contract.md`）
- 社長が承認した体裁（区分・書き方）は維持する。大きく変える時はカズヨ経由で社長確認

## 教訓（この節は消さない）

### なぜ「2層」だと思い込んでいたか

2026-05-27 の移管時点では、Notion 側に実際に「📋 社長タスクまとめ」カードが存在し、
ticket DB の **Status=「まとめ」** 列に常駐していました。当時の記述は**正しかった**。
その後カードが廃止され CLAUDE.md §6 に「waiting 列が役割を引き継いだ」と明記されましたが、
**このメモリだけが更新されずに残りました。**

### いつ・どうやって1層と確定したか

- **2026-08-23（T-20260817-005 の作業中）**: page_id `36db0a40-…431d` に更新をかけたところ **404 object_not_found**。
  `Status='まとめ'` で照会しても該当0件。CLAUDE.md §6 と突き合わせて廃止済みと判断し、**末尾に訂正を追記**した。
- **2026-08-24（T-20260824-001 の同期時）**: `notion-fetch` で **ticket DB のスキーマを実照会**し、
  **Status の選択肢が `todo` / `doing` / `waiting` / `done` の4つのみで「まとめ」が存在しない**ことを確認。
  `Labels` 側には「まとめ」オプションが残っているが、**これを持つカードは0件**。→ **1層で確定**。
- 同日、カズヨ裁可により**冒頭ごと1層構造へ全面改訂**（この版）。理由は「訂正が末尾にあっても、冒頭を読んで作業に入る人には届かない」から。

### 持ち帰るべき教訓

1. **メモリに書いた「接続先の実値」は腐る。** page_id・列名・URL は特に。404 が出たら「自分の書き間違い」より先に「**仕様が変わった**」を疑い、CLAUDE.md（憲法）と突き合わせる
2. **訂正は末尾に足すのではなく、冒頭を直す。** 追記だけだと、最初の3行を読んで作業に入る人（＝次のセッションの自分）が誤解する。追記は暫定処置、**冒頭の書き換えまでやって完了**
3. **「無いこと」は推測でなくスキーマ実照会で確定させる。** 404 は「消えた」以外にも権限・IDミスで出るが、スキーマに選択肢が無いことは動かぬ証拠になる

## 2026-08-26 / T-20260826-002 — 「社長タスクが増えない納品」の書き方

### 状況

208項目のマスターToDoリストの納品。**社長タスクは1件も増えていない**が、
量が多いので、書き方を間違えると社長に「また仕事が増えた」と読まれる納品だった。

### 採った書き方（次も踏襲する）

見出しの直後に、**増減の結論を先に置いた**。

> **社長タスクは増えていません。** 既存の waiting（§4.1承認3件・本人手作業4件・判断待ち3件・レビュー12件）を
> ToDoの項番に紐付けて整理し直しただけです。

そのうえで「確認だけお願いしたい3件」を**表で**分離した。ポイントは3つ:

1. **「タスク」と「確認」を言葉のうえで分ける。** 判断・承認・手作業は「タスク」、
   画面を1つ開けば済むものは「確認」。混ぜると全部が重く見える
2. **確認1件ごとに「影響」列を付ける。** 「なぜ聞かれているか」が分かると即答できる。
   例: 青色申告 →「未提出なら期限は開業日から2か月以内」
3. **`- [ ]` チェックボックスは1個だけ。** 3件を3個のチェックボックスにすると
   「社長タスク3件増」に見える。1エントリ内の表に畳む

### 突合の結果（毎回やる機械検査）

```
comm -13 /tmp/ot.txt /tmp/w.txt   →  0件（waiting 23枚すべて owner-tasks.md に掲載済み）
```

`awk 'NR>s'` の `s` は「最終更新」行の行番号。最終更新行には過去の経緯として
大量のチケットIDが載っているため、**ここを含めると①の検査が常に0件になって意味を失う**。
必ず最終更新行より後ろだけを対象にする。

### 教訓

**量の多い納品ほど、増減の結論を先に書く。** 社長が最初に知りたいのは
「で、私は何をすればいいのか」であって、成果物の規模ではない。
208項目という数字は、**社長タスクが増えていないことを言った後**に置く。

## 2026-09-02 / T-20260826-004 — 「状態遷移なし・中身だけ入れ替わり」の同期

## 2026-09-02（続）/ T-20260826-004 更新③ — 「社長タスクが減る同期」と、訂正の書き方

同じ日に**3回目**の同期。今回は前2回と性質が違い、**社長タスクが純減**した回。

### 社長タスクの増減（Before / After）

| | 内容 |
|---|---|
| ✅ 解消 | 2ファイルの添付／「すべての書類を提出」 → **社長ご自身の操作で 9/2 01:13:45 に完了**（画面にタイムスタンプ） |
| ✅ 解消 | Google 翻訳の15分リハーサル → 日本語面談が可能と確定し**必須ではなくなった** |
| 🆕 新規 | 平日 10:00〜21:30 JST に**日本語でビデオ面談（約10分）**。パスポート原本・カメラ付きPC・Chrome/Safari |
| ⚠️ 注意（新規） | この画面は放置するとセッションが切れる |

**純減 −1件**（解消2・新規1）。しかも残ったタスクは1本だけ。冒頭の「最終更新」行と 🚨🚨 の入れ替わり表の**両方に「お願いはこれ1本だけです」を先に置いた**。

### 型として残すこと

1. **解消を先に、新規を後に書く。** 前2回（純増+1／±0）と違い今回は純減。**減った回こそ「減った」と明示する**。
   社長は長い経緯を追っていないので、書かないと「まだ4ステップ残っている」と読まれる。
2. **「不要」と「保険」を書き分ける。** カズヨから明示的に「**不要と言い切らないでください**」と指示があった。
   日本語予約でも英語話者が対応した実例があるため、Google 翻訳は**格下げであって廃止ではない**。
   `✅ 解消` 行にも「（保険として任意）」を必ず添える。**格下げを廃止と書くと、当日詰む。**
3. **訂正は本文の見出しに出す（2回連続で同じ判断）。** 9/1 の「通訳を手配する余地が構造的にない」は
   9/2 午前に「誤りの可能性が高い」、9/2 深夜に「**誤りでした**」と2段階で確度が上がった。
   owner-tasks.md では**「9/1 に何と言ったか」と「9/2 に何が正か」を2行の表に並べた**。
   訂正だけ書いて元の記述を消すと、社長が何を訂正されたのか分からない。**訂正は必ず対で書く。**
4. **⚠️注意事項は増えてもチェックボックスを増やさない。** 今回「情報を編集を押さない」に加えて
