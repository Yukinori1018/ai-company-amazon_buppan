# メモリ：inbox アーカイブは「控え」であって「バックアップ」ではない（マリエ）

**発生: 2026-09-02 / T-20260902-002**（自律リサーチ用エージェント3体＋スキル `research` の導入と inbox 退避）

## 何が起きたか

社長が `_inbox_社長共有/files3/` に投函された5ファイル（`research-collector.md` /
`research-verifier.md` / `research-integrator.md` / `SKILL.md` / `external-sources.md`）を、
カズヨが `~/.claude/agents/` と `~/.claude/skills/research/` へ設置済み。
マリエの仕事は inbox の退避だけ、という一見単純な依頼だった。

退避しながら気づいたのが次の構図。

```
インストール先 ~/.claude/          → リポジトリ外。Git 追跡なし
inbox アーカイブ _archive/2026-09/ → .gitignore 24行目で追跡外。Git 追跡なし
──────────────────────────────────────────────
結果：この5ファイルは「どこにもバックアップされていない資産」
```

**inbox から `_archive/` へ動かすと、片付いた感じがする。しかし追跡外から追跡外へ
動かしただけで、保全レベルは1ミリも上がっていない。**

## 教訓（次に効く形）

### 1. 退避先を決めたら「Git 追跡されるか」を必ず口に出す

inbox-intake スキル Step 3 は「PII をリポ配下に置かない」＝**入れてはいけない方向**の判定は
厳しく書いてあるが、**入れないと消える方向**の判定は書かれていない。行き先3つのうち
`_archive/` と `~/Documents/AI Company 素材/` は**どちらも追跡外**なので、
ここに入れたものは全部この穴に落ちる。

判定の追加質問：

> **このファイルの実体は、`_archive/` 以外のどこかに Git 追跡された形で存在するか？**
> No なら、リポジトリ内に控えを置くべきかを報告に必ず書く。

### 2. 「PII でない・第三者著作物でない・小さい」なら、リポ内控えが選択肢に上がる

今回の5ファイルは技術的な指示文のみ・計 16,638 バイト。
公開リポジトリに置いて困る要素がゼロなので、`docs/reference/<topic>/` に控えを置ける。
**ただしこれは社長のご判断が要る話**（勝手に増やすと `docs/reference/` が肥大する）なので、
実行せず論点として引き渡した。

### 3. `~/.claude/` 配下の資産は、この会社では構造的に消えやすい

`~/.claude/agents/` `~/.claude/skills/` `~/.claude/settings.json` はどれもリポ外。
**エージェント定義やスキルという「会社の作り方そのもの」が、Git 管理の外側にある。**
今回は5ファイルだったが、同じ構造で今後も増える。棚卸しのたびに同じ穴に落ちる可能性が高い。

## やったこと（手順の再利用形）

依頼が「インストール済みのファイルを inbox から退避する」型だったときの定型：

1. **同一性を自分で再検証する。** 「カズヨが cksum 一致を確認済み」と言われても、
   自分でも `cksum` を取る。退避は `mv` なので、**移動後にもう一度取って**
   インストール先とまだ一致することを確認する（今回は移動前後の2回とも一致）
2. `_archive/YYYY-MM/<ticket_id>_<内容>/` へ `mv`（`cp` ではない。inbox 直下を空にするのが目的）
3. README.md に**インストール先の絶対パス**を書く。これが無いと、
   将来「このファイルはどこに置けば効くのか」が分からない箱になる
4. `.DS_Store` は削除してよいが、`file` で種別を確認してから消し、監査ログ5点をチケットに残す
5. `ls -la` で inbox 直下を確認して報告

### `.DS_Store` の削除スコープは指示どおりに切る

今回、`files3/.DS_Store` の削除は明示的に承認されていたが、
`_inbox_社長共有/.DS_Store`（直下）は**指示スコープ外だったので残した**。
どちらも無害な OS 生成ファイルであり、実害の差はゼロ。それでも線を引いたのは、
inbox-intake スキル Step 4 の考え方――**「次に同じ経路で来るのが本物のデータだったときに効く線引き」**
――をここで崩さないため。承認された対象と、ついでに目に入った対象は、別物として扱う。

## Notion 同期で引っかかった点

frontmatter に `labels: [tooling, research, inbox]` と書いたが、**Notion の Labels
（multi-select）に `inbox` という選択肢が存在しなかった**。

選択肢を増やすこともできたが、既存語彙の `ops` に寄せて
`[tooling, research, ops]` に**リポジトリ側を直した**。理由は、
語彙が増えるほど「同じ意味の別ラベル」が生まれてカンバンの絞り込みが効かなくなるから
（`infrastructure` と `infra` が両方存在しているのが既にその例）。

**手順：カード作成前に `notion-fetch collection://<data_source_id>` でスキーマを取り、
Labels の既存選択肢と突き合わせる。** 存在しないラベルを投げると同期が落ちる。
