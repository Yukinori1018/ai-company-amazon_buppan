## 同期漏れの根本原因（2点）

1. **ホスト型 MCP**：シェル/フックから直接 Notion API を叩けない（ローカルにトークン無し）。同期はエージェントが MCP を呼ぶ手動作業 → 秘書の片手間で漏れが再発（T-20260520-011 でドキュメント対応したが再発した）。
   - 対策：責務一本化＋ PostToolUse 強制フック（`.claude/hooks/ticket-notion-sync-reminder.sh`）。チケットファイル変更を検知し「未同期で turn を終えるな」と additionalContext で促す。**完全自動化は原理的に不可、強制関数が最善手**。
2. **ブランチ分岐**：クラウドセッションごとに別ブランチ。チケットの真実が複数ブランチに散在し、Notion は累積するためどの単一ブランチとも一致しない。
   - 対策：`/sync-notion`（非破壊リコンサイル）を朝夕ルーティンに組込。Notion 専用カードは削除せず社長に要確認報告。

## Labels の選択肢追加は非破壊でできる（2026-08-21 実証）

`notion-update-data-source` の DDL で追加できる:

```
ALTER COLUMN "Labels" SET MULTI_SELECT('まとめ':blue, 'research':pink, ...)
```

**重要な落とし穴：`SET` は選択肢セットを丸ごと置き換える。**
既存の選択肢を書き並べに含めないと消える（＝そのラベルが付いたカードの値も失われる）。
今回は事前に「Labels を使っているカード＝0件」を確認し、既存の `まとめ` を必ず含めて実行した。
**実行前に必ず `WHERE "Labels" IS NOT NULL AND "Labels" != '[]'` で使用状況を確認すること。**

## ⚠️ `git commit` はステージ全体を拾う（2026-08-21・自分の事故）

`git add -A <自分のパス>` で自分の分だけ足したつもりでも、**`git commit` はインデックス全体を
コミットする**。並行セッション（T-20260821-009 のマリエ）が同時に `git add` していたため、
私のコミット **5ece40a**（ticket_id 改番）に**相手の成果物14ファイルが巻き込まれた**。

CLAUDE.md・`.claude/hooks/session-start.sh`・`skills/inbox-intake.md`・
`deliverables/T-20260821-009/` 一式が、無関係なコミットメッセージの下に入っている。
**データは失われていない**（履歴の書き換えはしない＝§4.1 の不可逆操作に近く、直すほうが危険）。
起きたのは**帰属のずれ**だけ。

**次から必ず：**

```bash
git diff --cached --stat        # コミット直前に「何が入るか」を必ず目で見る
git commit -- <path> [<path>…]  # パスを明示すればステージ全体を巻き込まない
```

このリポジトリは**複数セッションが同じ作業ツリーを共有する**（今日は最大4体が並行）。
「自分が add したものだけが staged」という前提が成り立たない。
`git status` で他エージェントの変更を見かけたら、**触らないだけでは足りない。commit の仕方も分ける。**

## Notion の自動リンク化に注意（2026-08-21 / T-20260811-001 同期時）

Notion に書き込むテキスト中の **`名前.md` / `名前.co.jp` のような「ドット＋TLD風の綴り」は、
自動的にリンク化される**。`テキスト版.md` と書いたら `[テキスト版.md](http://テキスト版.md)` という
無効なリンクになった。`CLAUDE.md` `inbox-intake.md` でも同様に発生する。

**対策:**
- プロパティ（Description 等）の平文では**拡張子を書かない**。「テキスト版」「索引」のように言い換える。
- ファイル名を示す必要があるときは**バッククォートでコードスパンにする**（`` `keepa-usage-guide.md` ``）。
  コードスパン内は自動リンク化されない。本文のファイルパス列挙が無事だったのはこのため。

書き込み後は `notion-fetch` で直読みし、`](http://` が混入していないか目視すること。

## 同じ論点に2人が書き込むときの整理（2026-08-21 / T-20260817-006）

マリエが先に「③の根拠が覆る」注記を入れ、後からヒデアキが正式な訂正セクションを納品した。
Notion 上で**同じことが2回書いてある状態**になり、カズヨから「重複していたら正式版を残して自分の注記側を整理」と指示。

**整理の型（次も使える）:**

1. **正式版（担当者の成果物）を主にする。**先に置いた自分の注記は、正式版に無い情報だけ残して畳む。
2. **消すのではなく統合する。**マリエの注記にあってヒデアキ版に無い要素（検証範囲6/1/2社・§4.1の但し書き）は正式版の末尾に寄せた。
3. **時制を合わせる。**「差し替える**べき**論拠」→「差し替え**た**論拠」。対応前に書いた見出しが残ると、
   読み手は「まだ終わっていない」と誤解する。**着手前に書いた文言は、完了時に必ず読み直す。**
4. **上流の表も直す。**本文に訂正セクションを足しても、ページ上部の結論表が旧記述のままだと矛盾する。
   今回は「3点の評価」表の③セルが旧論拠のままだったので、ローカルに合わせて訂正マーク付きに更新した。
   **追記だけして既存の要約を直し忘れる**のが一番起きやすい事故。
5. **旧記録は `<details>` に畳んで保全。**消すと「何を信じて何が違ったか」の経緯が失われる。

### Notion 本文が別セッションに書き換えられていたときの対処

`update_content`（exact match 置換）が **No matches found** で落ちた。原因は**他セッションが同じカード本文を編集していた**こと。

- **リトライで exact match を追いかけない。** churn 中は次も外れる。
- **末尾に日付つきの「【最新】」節を `insert_content` で足す**のが正解。非破壊で、かつ
  「上のほうに古い記述がありますが**この節が最新です**」と**明示的に打ち消しを書く**。
- カード本文を1つに保つ原則（`replace_content`）は**自分だけが書いている時の話**。
  複数セッションが同時に触る日は、**追記＋打ち消し**のほうが安全。

### owner-tasks のヘッダを他セッションが更新していた場合

最終更新ヘッダの先頭文字列を決め打ちで置換しようとして assert に落ちた（他セッションが自分の分を先頭に足していた）。
**`> **最終更新: YYYY-MM-DD（マリエ・` までの共通接頭辞だけを掴んで、その直後に自分の分を差し込む**形にすれば衝突しない。
後続（他セッションの記述）は「／前: 」で繋いでそのまま残す。**他人の更新記録を消さない。**

### 追記（2026-08-24・エージェントが API 529 で途中終了したときの復旧手順）

T-20260824-005 の同期中、**Anthropic 側の 529（一時的な過負荷）でタスクが途中終了**した。
「①〜③進めます」と返した直後に落ちたため、**カズヨ側にはどこまで進んだかの記録が残らなかった**。

**結論：実際には①〜③すべて完了していた。**再実行していたら、カタログに3行が**二重登録**されるところだった。

## 復旧の原則（カズヨの言葉をそのまま残す）

> **エージェントが途中で落ちた場合、報告が無いことは「やっていない」を意味しない。**
> **再実行の前に、まず現物の状態を確認する。**

**報告と実作業は別のもの。** 報告は作業の最後に来るので、**落ちるときは「作業済み・報告なし」の形で落ちる確率が高い**。
これは構造上そうなるのであって例外ではない。

## 確認の順番（冪等でない作業ほど先に見る）

1. **二重実行が壊すもの**から確認する。**成果物カタログのCSV（行追加）が最優先**
   — 要約更新は冪等だが、**行追加は冪等ではない**。`python3 -c` で該当 TicketID の行数を数える
2. **Notion カード** — `notion-query-data-sources` で TicketID を引く。**存在するかだけでなく、
   プロパティが埋まっているか・本文が空でないか**まで見る（`notion-fetch`）。
   「カードはあるが本文が空」が中途半端の典型
3. `owner-tasks.md` / チケットファイル — `grep` で該当 TicketID を引く
4. `git log` と `git status` — コミット済みか、未コミットで残っているか

## やってはいけないこと

- **「たぶんやっていないだろう」で再実行する。** 特に行追加・カード作成・シート同期。
- **逆に「たぶんやっただろう」で確認を省く。** 中途半端で止まっている可能性は必ずある。
- **確認せずに全部やり直す。** 今回カズヨが「足りない分だけ」と切り分けてくれたのが正解の形。

## 設計上の含意

**冪等な作業ほど復旧が楽になる。** カタログ同期スクリプト（全置換ミラー）は何度実行しても同じ結果になるので
落ちても怖くない。**怖いのは「追記」型の操作**（CSVの行追加・Notionのカード作成・`insert_content`）。
追記型を実行するときは、**実行前に「既に存在しないか」を確認する一手**を入れておくと、
落ちた後の復旧が確認だけで済む。

## 成果物の微修正でカタログ CSV を触るかの判断基準（2026-08-26 / T-20260826-002）

`03_process-board.html` に凡例ブロックを1つ足しただけの改訂で、CSV を更新すべきか迷った。**基準は「内容要約の記述が、その改訂によって事実と食い違うか」**。

- 今回の要約は「Mermaid図3枚（…）にA〜Fの6セクションを添えた1枚もの」。凡例はセクション C の**内側**に入っただけで、図の枚数もセクション数（A〜Fの6本）も変わっていない → **要約は依然として正確なので CSV は無変更**（＝シート同期の再実行も不要）。
- 逆に、**成果物が増減した／ファイル名が変わった／要約が名指ししている構成要素（枚数・セクション数・対象範囲）が動いた**場合は必ず CSV を更新する。

## 並行セッションに commit を横取りされた（2026-08-26 / T-20260826-002）

**事象**: チケットと memory を編集し `git add <2ファイル> && git commit` した直後、「nothing to commit, working tree clean」で失敗。原因は**同時刻に走っていた別セッション（T-20260826-001 側）が `git add -A` 相当で全変更を巻き取ってコミットした**こと（`6f211b0`）。内容は失われていないが、**私の変更が他チケットのコミットメッセージの下に埋まった**。

**教訓**
- 変更は失われていないので**慌てて再コミットしない**。まず `git show HEAD:<path> | grep` で自分の変更が HEAD に入っているか確認する。入っていれば作業完了扱いでよい。
- `git commit` が「nothing to commit」で落ちたら、それは失敗ではなく**横取りのサイン**。`git log --oneline -3 -- <path>` でどのコミットに入ったかを特定し、報告に「コミットIDは他チケット名義」と一言添える。
- 夜間の並行セッション中は `git add -A` を使うセッションが混ざる前提で動く。自分は常に**パス指定の `git add`** に留める（他人の作業中ファイルを巻き込まないため）。

## `compliance` ラベルの不在と、B案運用との食い違い（2026-08-26 / T-20260826-003）

T-20260826-003 の frontmatter は `labels: [ops, compliance]`。**`compliance` は Labels の29オプションに無い**ため `ops` のみ設定してカード作成した。

- 発注時のカズヨの指示は「**既存オプションに無いものがあれば設定せず報告**」。上節に書いた既定（**B案＝既存語彙へ寄せる**）だと `compliance` → `legal` に丸める判断もあり得たが、**その turn の明示指示が既定に優先する**と判断し、丸めずに未設定で報告した。
