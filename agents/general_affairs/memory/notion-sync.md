## 同期漏れの根本原因（2点）

1. **ホスト型 MCP**：シェル/フックから直接 Notion API を叩けない（ローカルにトークン無し）。同期はエージェントが MCP を呼ぶ手動作業 → 秘書の片手間で漏れが再発（T-20260520-011 でドキュメント対応したが再発した）。
   - 対策：責務一本化＋ PostToolUse 強制フック（`.claude/hooks/ticket-notion-sync-reminder.sh`）。チケットファイル変更を検知し「未同期で turn を終えるな」と additionalContext で促す。**完全自動化は原理的に不可、強制関数が最善手**。
2. **ブランチ分岐**：クラウドセッションごとに別ブランチ。チケットの真実が複数ブランチに散在し、Notion は累積するためどの単一ブランチとも一致しない。
   - 対策：`/sync-notion`（非破壊リコンサイル）を朝夕ルーティンに組込。Notion 専用カードは削除せず社長に要確認報告。

## 「Notion に無いフィールド」を先に確認する（2026-08-21 / T-20260821-005）

`related:`→`related_tickets:` の一括改名を「Notion 同期が大量に走る」前提で発注されたが、
**実際には Notion 書き込みは1件も不要だった**。`next_check_at` と `related_tickets` は
**Notion に存在しないリポジトリ専用フィールド**だから（本スキル §3 の注記どおり）。

→ **一括改名の前に「そのキーは Notion のどの列にマップされるか」を必ず確認する。**
マップされないキーなら、ファイルを何十枚触っても同期はゼロ件。所要時間の見積りが1桁変わる。

同じ回で `parent:`→`parent_ticket:` も直したが、こちらは ParentTicket 列にマップされる。
ただし該当2枚は**Notion 側には既に正しい親が入っており**、ローカルだけがずれていた。
＝**ドリフトは「どちらが古いか」を毎回確かめる。** ファイルが真実という原則は、
「ファイルが常に新しい」という意味ではない。

## Labels の選択肢追加は非破壊でできる（2026-08-21 実証）

`notion-update-data-source` の DDL で追加できる:

```
ALTER COLUMN "Labels" SET MULTI_SELECT('まとめ':blue, 'research':pink, ...)
```

**重要な落とし穴：`SET` は選択肢セットを丸ごと置き換える。**
既存の選択肢を書き並べに含めないと消える（＝そのラベルが付いたカードの値も失われる）。
今回は事前に「Labels を使っているカード＝0件」を確認し、既存の `まとめ` を必ず含めて実行した。
**実行前に必ず `WHERE "Labels" IS NOT NULL AND "Labels" != '[]'` で使用状況を確認すること。**

### ラベル語彙そのものが散らかっている（未解決・要判断）
