## 同期漏れの根本原因（2点）

1. **ホスト型 MCP**：シェル/フックから直接 Notion API を叩けない（ローカルにトークン無し）。同期はエージェントが MCP を呼ぶ手動作業 → 秘書の片手間で漏れが再発（T-20260520-011 でドキュメント対応したが再発した）。
   - 対策：責務一本化＋ PostToolUse 強制フック（`.claude/hooks/ticket-notion-sync-reminder.sh`）。チケットファイル変更を検知し「未同期で turn を終えるな」と additionalContext で促す。**完全自動化は原理的に不可、強制関数が最善手**。
2. **ブランチ分岐**：クラウドセッションごとに別ブランチ。チケットの真実が複数ブランチに散在し、Notion は累積するためどの単一ブランチとも一致しない。
   - 対策：`/sync-notion`（非破壊リコンサイル）を朝夕ルーティンに組込。Notion 専用カードは削除せず社長に要確認報告。

「ファイルが常に新しい」という意味ではない。

## Labels の選択肢追加は非破壊でできる（2026-08-21 実証）

`notion-update-data-source` の DDL で追加できる:

```
ALTER COLUMN "Labels" SET MULTI_SELECT('まとめ':blue, 'research':pink, ...)
```

**重要な落とし穴：`SET` は選択肢セットを丸ごと置き換える。**
既存の選択肢を書き並べに含めないと消える（＝そのラベルが付いたカードの値も失われる）。
今回は事前に「Labels を使っているカード＝0件」を確認し、既存の `まとめ` を必ず含めて実行した。
**実行前に必ず `WHERE "Labels" IS NOT NULL AND "Labels" != '[]'` で使用状況を確認すること。**

## 判断待ちカードは「決着したら選択肢を消す」（2026-08-21）

waiting カードの本文に A/B/C の選択肢を書いて社長判断を仰いだあと、
**判断が下りたら選択肢を結論に差し替える**こと。秘書の指摘：
「判断済みの選択肢が残っていると、**次に見た人が未決だと誤読する**」。

カード本文は履歴ではなく**現在地**を映す鏡。ログは `.md` 側が持っているので、
Notion 側は「いま何が決まっていて、次は誰の番か」だけを残す。

実務手順：`notion-update-page` の `command: "update_content"` ＋ `content_updates`
（old_str / new_str）で該当ブロックだけ差し替える。
**old_str は `notion-fetch` で取得した実テキストをそのまま使う**——
自分が書いた markdown は Notion 側で正規化されており（太字の入れ子や表がタグ化される）、
書いたつもりの文字列では一致しない。

## 担当変更は「社長が見る場所」にも書く（2026-08-21）

T-20260817-006 の担当がカズヨ→ヒデアキに変わった件。Notion の Assignee 列と
`owner-tasks.md` の最終更新サマリだけでは足りず、**社長が実際に読むタスク項目そのもの**に
1行入れた。社長は長い更新サマリを読まない。**変更は、その人が見る場所に置く。**

あわせて「**社長の手順は増えない**」と明記した。担当が変わると社長は
「自分の窓口も変わるのか」「やり直しか」と身構える。社内の都合であることを先に打ち消す。

## ⚠️ SQL クエリの結果は遅れる。検証は notion-fetch で（2026-08-21・重要）

改番後に `notion-query-data-sources`（SQL）で全件突合したところ、**直前に更新して確認済みの値が
古いまま返ってきた**（T-20260821-001 を done にしたのに waiting、T-20260817-006 の Assignee も旧値）。
`notion-fetch` でページを直接読むと**正しく done**。**SQL 側のインデックスが遅延している。**

→ **書き込み直後の検証に SQL を使わない。** 「戻っている」と誤認して二重に書き直すと、
本当に正しい値を壊す。**権威ある読み取りは `notion-fetch`。**
SQL は一覧の俯瞰・ID の集合比較には使えるが、**プロパティ値の真偽判定には使わない。**
