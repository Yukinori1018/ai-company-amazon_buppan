# 知見: owner-tasks.md に「期限つきタスク」が初めて現れた回の扱い（2026-09-04 / T-20260904-005）

## 何が新しかったか

スーパーデリバリーの入会審査で追加書類3点を求められ、**提出期限 2026-09-17・無返信＝登録キャンセル**という
条件が付いた。owner-tasks.md にはそれまで **日付が決まっているタスクが1件も無かった**。
既存はすべて「先方待ち」「審査待ち」で、社長が遅れても失われるものが無い種類だった。

**期限つきタスクは、既存の区分（🚨緊急 / 🟡社長の番 / 🔴今すぐ着手 / 🟡情報共有 / 🟢確認待ち / ℹ️自動）の
どれにも収まらない。** 🚨🚨 の中に混ぜると、いま最優先の案件（Amazon 停止）に埋もれて期日が見えなくなる。

## 採った書き方（この型を踏襲する）

1. **新しい区分 `## ⏳ 期限つき（YYYY-MM-DD）` を最上段に新設した。** 🚨🚨 の**直前**。
   既存の 🚨🚨 ブロックは「この件の社長タスクはゼロです」と明記していたので、
   **実際に社長の手が要るのは新しい期限つきタスクだけ**という状態だった。最上段に置く根拠はそこにある。
   （🚨🚨 に社長タスクが残っている状況なら、順番は改めて考え直すこと。緊急度と期日は別の軸。）
2. **見出しの直下で「なぜ最上段なのか」を1文で説明した。**
   「ほかの項目は先方待ちで期日がありませんが、これだけは 2026-09-17 を過ぎると自動的に失われます」。
   説明が無いと、最上段に来たこと自体が「これが一番大事」という誤ったメッセージになる。
3. **残り日数を書く。** 「残り13日（本日 9/4 起算）」。日付だけだと社長が毎回逆算する。
   **逆算はこちらでやる。**
4. **止まっている点を数で絞る。** 「3点のうち2点はすでに出せます。止まっているのは1点だけです」。
   提出物が3枠あっても社長が動かすのは1つ。**枠の数ではなく社長の手数を書く**（T-20260826-004 の教訓の再適用）。
5. **チェックボックスは1個。** 「方針決定 ＋ 返信メール送信」は2手だが、1つの意思決定から連なる一連の作業なので
   1エントリに畳んだ。カズヨからも「1件として追加」の指示。**手数と件数を混同しない。**
6. **「いま即答いただく必要はありません」を明記した。** B 案の成立可否をサトルが確認中で、
   確認結果が出る前に決めさせると判断材料が足りない。**期限つきタスクほど「いつ答えればよいか」を書く。**
   期日だけ書いて猶予を書かないと、期日 = 今すぐ、と読まれて別の作業が止まる。
7. **2つ目の期限（2026-11-30 のサイトオープン条件）は ⚠️ 行にして、チェックボックスを増やさなかった。**
   まだ行動を求めていないため。**未来のタスクは予告として書き、タスクとしては数えない**
   （knowledge_owner_tasks_top_section_rewrite.md / T-20260904-002 の型）。

## 続報（同日・更新⑦）— 「方針は決まったが、実行はブロックされている」タスクの畳み方

社長判断が出た。**A案（Amazon を大口へ切替）を採用。ただし Amazon の画面が復旧してから。**
カズヨの推奨は B だったが、社長判断は A。**推奨が通らなかった回でも、推奨した理由は本文に残さない**
（決着した論点を残すと、まだ議論中に見える）。決着済みの4択は「ご返事は不要です」の一語に畳んだ。

### この型の難しさ

社長タスクは **「解消」でも「継続」でもない**。方針決定は解消したが、返信メール送信は残っている。
ただし **Amazon が復旧しないと着手できない**（`blocked_by: T-20260826-004`）。
カズヨから明示指示があった。**「社長が『いま手を動かす必要がある項目』としてはカウントしない。件数を水増ししないこと。
ただしセクション自体は残し、状態が読み取れる形に」**。

### 採った書き方（次も踏襲する）

1. **開いたチェックボックス `- [ ]` を1個も立てない。** 方針決定は `- [x] ✅ …確定しました` へ倒し、
   残る一手は **`🔒 残る一手（着手できません・お待ちください）`** という**チェックボックスなしの小見出し**にした。
   `- [ ]` は「社長が今できること」の記号。**できないことに `- [ ]` を立てると、できない仕事を催促していることになる。**
   検算: `grep -cE '^- \[ \].*T-20260904-005'` → **0件**が正。
2. **見出しで「いま手はかからない」と言い切る。**
   `## ⏳ 期限つき（2026-09-17）— **A案で決定済み。実行は Amazon 復旧が条件です。いま社長のお手はかかりません**`。
   期日が見出しに残っているので、これを書かないと「期限が迫っているのに放置している」と読まれる。
3. **セクションを消さない理由を、セクション自身に書く。**
   「この項目は社長タスクとして数えていません。ただし 9/17 という期日は生きているので、状況が読み取れるよう残しています」。
   **数えないことと隠すことは違う**（T-20260903-001 の型の再適用）。
4. **日付は3つだけを表にした。** 9/8（Amazon 判定）／**9/12（フォールバック判定）**／9/17（SD 期限）。
   「誰が動くか」列を付けたのが効いた。3行のうち社長が動くのは最終行だけだと**表の形で**分かる。
5. **「社長の出番はいつか」を明示した。** 「早ければ Amazon 復旧後、遅くとも 9/12 以降。どちらもメールを1通送る以上のことはお願いしません」。
   **ブロックされたタスクは、いつブロックが解けるかを書かないと、社長が毎日気にし続ける。**
6. **9/12 で未復旧でも「方針は変えない」と書いた。** C案は方針変更ではなく**期限を後ろへ倒す動き**。
   これを書かないと、フォールバックが「A案の失敗」に見えて、9/12 に余計な判断を求めることになる。

### ブロック関係は「両側」に埋める（カズヨが実施・型として記録）

カズヨは T-20260904-005 に `blocked_by: T-20260826-004` を入れるだけでなく、
**追跡側の T-20260826-004 に `unblocks_on_recovery: [T-20260904-005]` と「🔔 復旧時に必ず発火させること」節**を入れた。

> **片側だけの依存は必ず切れる。** 待っている側にだけ書いても、待たれている側を見ている人は気づかない。
> Amazon 復旧を日次で追っているのは T-20260826-004 のほうで、**そこに「復旧＝SD の実行トリガー」と書いてあって初めて発火する。**
> 「復旧しました」で報告を終えず、同じターンで相手のチケットを動かすところまでが一続き、と明記させるのが要点。

### Notion 側

Status は **waiting のまま**。動かしたのは **本文（末尾に「社長判断」節を追加）・Description 全面差し替え・UpdatedAt** の3つ。
Description の前版は「A〜D の社長判断待ち」のままで、**カード一覧を見ただけでは決着済みだと分からなかった**。
**判断が出た回は、必ず Description を書き直す**（積み上げず全面差し替え。積むと1000字を超えて読まれない）。
