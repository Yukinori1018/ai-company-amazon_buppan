# 知見: owner-tasks.md に「期限つきタスク」が初めて現れた回の扱い（2026-09-04 / T-20260904-005）

## 何が新しかったか

スーパーデリバリーの入会審査で追加書類3点を求められ、**提出期限 2026-09-17・無返信＝登録キャンセル**という
条件が付いた。owner-tasks.md にはそれまで **日付が決まっているタスクが1件も無かった**。
既存はすべて「先方待ち」「審査待ち」で、社長が遅れても失われるものが無い種類だった。

**期限つきタスクは、既存の区分（🚨緊急 / 🟡社長の番 / 🔴今すぐ着手 / 🟡情報共有 / 🟢確認待ち / ℹ️自動）の
どれにも収まらない。** 🚨🚨 の中に混ぜると、いま最優先の案件（Amazon 停止）に埋もれて期日が見えなくなる。

## 採った書き方（この型を踏襲する）

1. **新しい区分 `## ⏳ 期限つき（YYYY-MM-DD）` を最上段に新設した。** 🚨🚨 の**直前**。
   既存の 🚨🚨 ブロックは「この件の社長タスクはゼロです」と明記していたので、
   **実際に社長の手が要るのは新しい期限つきタスクだけ**という状態だった。最上段に置く根拠はそこにある。
   （🚨🚨 に社長タスクが残っている状況なら、順番は改めて考え直すこと。緊急度と期日は別の軸。）
2. **見出しの直下で「なぜ最上段なのか」を1文で説明した。**
   「ほかの項目は先方待ちで期日がありませんが、これだけは 2026-09-17 を過ぎると自動的に失われます」。
   説明が無いと、最上段に来たこと自体が「これが一番大事」という誤ったメッセージになる。
3. **残り日数を書く。** 「残り13日（本日 9/4 起算）」。日付だけだと社長が毎回逆算する。
   **逆算はこちらでやる。**
4. **止まっている点を数で絞る。** 「3点のうち2点はすでに出せます。止まっているのは1点だけです」。
   提出物が3枠あっても社長が動かすのは1つ。**枠の数ではなく社長の手数を書く**（T-20260826-004 の教訓の再適用）。
5. **チェックボックスは1個。** 「方針決定 ＋ 返信メール送信」は2手だが、1つの意思決定から連なる一連の作業なので
   1エントリに畳んだ。カズヨからも「1件として追加」の指示。**手数と件数を混同しない。**
6. **「いま即答いただく必要はありません」を明記した。** B 案の成立可否をサトルが確認中で、
   確認結果が出る前に決めさせると判断材料が足りない。**期限つきタスクほど「いつ答えればよいか」を書く。**
   期日だけ書いて猶予を書かないと、期日 = 今すぐ、と読まれて別の作業が止まる。
7. **2つ目の期限（2026-11-30 のサイトオープン条件）は ⚠️ 行にして、チェックボックスを増やさなかった。**
   まだ行動を求めていないため。**未来のタスクは予告として書き、タスクとしては数えない**
   （knowledge_owner_tasks_top_section_rewrite.md / T-20260904-002 の型）。

## 公開リポジトリの扱い — 「受け皿を作る」こと自体が事故予防になる

今回の提出物は **本人確認書類・開業届の控え・住所入りの申込画面**。CLAUDE.md §6 の「除外し続けるもの」に真正面から該当する。

  置き場が無い状態でファイルが来ると、人は「とりあえず deliverables」に置く。**先に正しい置き場を用意しておくと、
  間違った置き場が選ばれない。**
- README に書いたのは禁止事項だけでなく、**なぜ止まらないか**の構造。
  「commit しなければ大丈夫」は誤り（30分ごとの `git add -A` に拾われる。knowledge_public_repo_autosync.md）。
  **止まるのは「そもそも Git 追跡対象に置かない」ことだけ**、と書き切る。
- **除外は実測で確かめる。** `git check-ignore -v <path>` を実行し、`.gitignore` の何行目で効いているかまで確認した。
  「gitignore 対象のはず」で済ませない。
- 原本 PDF（`_inbox_社長共有/`）は**動かさない**という明示指示があった。棚卸しは方針決定後。
  **inbox に置きっぱなしにする判断も、理由を書けば正当な判断になる。**書かないと次回「放置」に見える。
