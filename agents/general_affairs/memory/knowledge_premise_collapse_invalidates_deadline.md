# 前提が消えると期限も失効する — 「差し引きゼロだが中身が入れ替わる」同期の型

（2026-09-09 / T-20260826-004 done ＋ T-20260909-001 新規 の同期で確立）

## 何が起きたか

日本ストアの再開が確定し、T-20260826-004 が waiting → done。同時にカナダ継続対応が
T-20260909-001（doing）として新規起票。**社長タスクの増減は ±0**だが、中身は総入れ替えだった。

- 消えたもの：更新⑩の「Seller Central にサインインする」（社長は既に実施済み）
- 増えたもの：なし（新チケットは doing ＝カズヨが回す）
- 変わったもの：**waiting 列が1件減る**／**旧撤退条件 2026-09-10 17:00 が失効**

## 学び（次回も同じ判断をする）

1. **±0 の同期こそ丁寧に書く。** 件数が動かないと「更新不要」に見えるが、社長が見るのは件数ではなく
   「次に何をするか」。**解消したタスクを消し、残す事実を ⚠️ 行に落とす**のが本体作業。
2. **期限は「前提」とセットで管理する。** 撤退条件 2026-09-10 は「日本で売れない状態の継続」が前提。
   前提が消えたら期限は自動失効し、性質も変わる（撤退条件 → エスカレーション条件）。
   **期限を機械的に延長しない。失効と引き直しは別物**として書き分ける。
3. **「タスクではないが知っておくべき事実」は ⚠️ 行で残す。** 今回は
   ①「支払いが保留中」は未解除（出品再開＝入金再開ではない）②旧撤退条件の失効。
   チェックボックスにすると社長タスクが水増しされ、waiting 列の価値が落ちる。
4. **旧ブロックは削除せず `<details>` に畳む。** ただし畳む前に**未消化チェックボックスを
   `[x] 解消済み` に変える**こと。畳んだ中に `[ ]` が残ると、開いた社長が「まだ宿題がある」と誤読する。
5. **停止を前提にした注記は全文検索して訂正する。** 今回 `停止中〔T-20260826-004〕` が
   アーカイブ外に6箇所あった。本文だけ更新して注記を放置すると、同じファイル内で矛盾する。
   **取り消し線＋「2026-09-09 更新」で上書きし、削除はしない。**
