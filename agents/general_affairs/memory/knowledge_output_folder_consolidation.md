置き場が4箇所に散らばった成果物を `workspace/output/deliverables/` 1箇所へ畳んだときの手順書。
**同種の「散らかった場所を畳む」依頼はこの型で再利用できる。**

## 1. いちばん大事な結論：「重複だから捨てて良い」は調べる前の思い込み

チケットには調査結果として「**C は全件 A と重複・独自0件**」と書かれていた。
実際に `diff -rq` を回したら **C 側にしか無いパスが140件**、うち**内容が真にユニークなものが82件**あった。

> **教訓：前工程の調査結果を信用して突合を省略しない。** 畳む作業は不可逆に近いので、
> 「独自0件」と言われていても自分の手でハッシュ突合するまで動かない。

## 2. 消失0件を証明する手順（この型をそのまま使う）

### ① 着手前に台帳を取る

```bash
( cd "$DIR" && find . -type f ! -name '.DS_Store' -print0 | sort -z | xargs -0 shasum > before_X.txt )
```

### ② 「保全されているか」は3段階で判定する

畳む側の全ファイルを次の3分類に落とし、**孤児が0件になるまで畳まない**。

| 判定 | 方法 |
|---|---|
| **A に同内容あり** | SHA-1 が A 側のハッシュ集合に含まれるか |
| **Git 履歴に保全** | `git hash-object <file>` → `git cat-file -e <blob>` が成功するか |
| **孤児（本当に失われうる）** | 上のどちらでもない → **deliverables へ移送する** |

**`git hash-object` + `cat-file -e` が決め手だった。** 今回 C の82件のうち **79件は Git 履歴に blob として現存**していた
（T-20260817-006 サイトの日付スナップショット群）。これを確認できたので、
「本当に救出が要るのは3件だけ」と絞り込めた。**これをやらないと82件を無駄に deliverables へ積むことになった。**

### ③ 作業後に突合する

```bash
comm -23 before_paths.txt after_paths.txt   # 消えたもの → 0行であるべき
```

実績：A 805 → 817ファイル、**消失0件**。

## 3. ハマったところ

### shasum 出力を awk で切ると日本語・空白入りパスが壊れる

```bash
awk '{ $1=""; print }'    # ダメ。パス中の空白で分割される
cut -c43-                 # 正解（SHA-1 40桁 + スペース2つ = 42文字）
```

最初これで「11件増えた」と誤検知し、差分リストが70KBに膨れた。**パスに空白と日本語が入る前提で組む。**

### 5.6GB のファイルがあると `shasum` がタイムアウトする

Bash ツールの2分制限を超える。**先に `find -size +50M` で大物を特定し、分離して扱う。**

### AppleScript で Finder に問い合わせるとハングする

`osascript` で Finder にフォルダを開かせようとすると、**自動化権限の許可ダイアログが社長の画面に出て応答待ちで固まる**。
シンボリックリンクが Finder から辿れることの確認は、権限不要な方法で足りる：

```bash
[ -L "$L" ] && [ -e "$L" ] && [ -d "$L" ]        # 壊れていないリンクか
mdls -name kMDItemContentType "$L"               # → "public.folder" なら Finder は透過的に辿る
```

`kMDItemContentType = "public.folder"` は **Spotlight/LaunchServices がリンクをフォルダとして解決している**証拠。
Finder はこれと同じ解決を使うので、これで確認は十分。

### `.gitignore` の拡張子一律禁止は行き過ぎになる

「50MB超はリポに入れない」というルールを実装しようとして `*.mp4` を禁止にしたら、
**T-20260817-006 のモック用 92KB 動画まで除外された**。Git はサイズでフィルタできないので拡張子で代用したくなるが、
`.mp4` `.jpg` `.zip` は Web 成果物の小さな素材として正当に登場する。

**結論：一律禁止にしてよいのは、この事業で例外なく大容量の生キャプチャ／配布アーカイブだった形式だけ**
（`.mov` `.dmg` `.iso` `.tar` `.tgz`）。サイズ判断は文書化されたルールで行い、
**恒久対策は「50MB超をコミット前に弾くフック」**（タカシ案件・未実装）。

> **分岐のあるルールは必ず片方が忘れられる。**

## 8. 破棄フェーズ（2026-08-26 追記・社長承認後の実行）

社長より「破棄で良い。」の承認を得て `_archive_20260826/` 2箇所を処分した際の型。

### 8.1 「承認が出た＝そのまま消す」ではない。直前にもう一度突合する

承認は**退避時点の調査結果**に基づいて出ている。承認から実行までの間に状況が変わっている可能性があるので、
**`rm`／ゴミ箱移動の直前に、全ファイルをもう一度2軸で判定する**。

| 軸 | 方法 |
|---|---|
| deliverables に同内容あり | 退避側の SHA-1 が deliverables 全ファイルの SHA-1 集合に含まれるか |
| Git 履歴に保全 | `git hash-object <file>` → `git cat-file -e <sha>` |

実績：266件 → `DELIVERABLES+GIT` 173 / `GIT` 91 / **孤児 2**。
**「孤児0件のはず」で流していたら、この2件を気づかず捨てていた。**

### 8.2 PDF は「中身が同じでもハッシュが違う」— 8バイトの罠

孤児と判定された2件は、deliverables 側に**同名・同サイズ**のファイルがあった。`cmp -l` で見ると **異なるバイトは8つだけ**：

```
/CreationDate (D:20260705131414+00'00')   ← 退避側
/CreationDate (D:20260705170441+00'00')   ← deliverables 側
```

`/CreationDate` `/ModDate` の生成時刻だけ。**同じ HTML から出力し直しただけ**だった。

**PDF・Office 文書・zip はハッシュ突合では「別物」に落ちる。** 生成時刻・UUID がヘッダに焼き込まれるため。
判定する手順：

1. `cmp -l A B | wc -l` — 異なるバイト数を数える。数十バイト以下なら書誌情報だけの疑いが濃い
2. `cmp -l` の先頭オフセット周辺を `dd` + `strings` で覗く → `/CreationDate` `/Producer` `/ID` なら確定
3. 内容そのものを比較する：PDF なら stream を zlib 展開して `cmp`

```bash
python3 - "$f" out.bin <<'PY'
import sys,zlib,re
d=open(sys.argv[1],'rb').read(); out=[]
for m in re.finditer(rb'stream\r?\n',d):
    s=m.end(); e=d.find(b'endstream',s)
    try: out.append(zlib.decompress(d[s:e]))
    except Exception: pass
open(sys.argv[2],'wb').write(b'\n'.join(out))
PY
```

これで**完全一致**が取れれば「情報は失われない」と断言できる。**サイズ一致だけを根拠に断言しない。**

### 8.3 それでも捨てない — 取り決めは文字どおり守る

内容一致を証明できても、カズヨとの取り決めは「**どちらにも無いファイルが1件でもあれば破棄を中止**」だった。
そこで**孤児2件だけを保留フォルダへ逃がし、残り264件を処分**した。全部止めると承認往復が1周増え、
全部捨てると取り決めを破る。**「未検証のものだけ手を付けない」が両立解。**

保留先には必ず README を置き、①なぜ残したか ②内容は同一と証明済みであること ③次に誰が何をすれば終わるか を書く。
**保留フォルダを無説明で作ると、それ自体が次の「散らかり」になる。**

### 8.4 破棄の手段は `mv ~/.Trash/`。Finder AppleScript は使わない

- **`rm` は使わない**（§4.1）。ゴミ箱へ `mv` すれば復元可能＝可逆。
- **ゴミ箱を空にしない。** 完全削除は社長ご自身の一手。
- `osascript` で Finder に削除させる方法は**2分ハングの実績あり**（自動化権限ダイアログ待ち）。`mv` 一択。
- ゴミ箱内は移動元が分かる名前にする（`_archive_20260826_Documents` / `_archive_20260826_ClaudeCode`）。
  同名フォルダを2つ放り込むと、あとから「どっちのどれか」が分からなくなる。

### 8.5 破棄後に必ず確認する3点

1. **元の場所から消えたか**（`[ -e "$SRC" ]`）
2. **社長の閲覧口（シンボリックリンク）が生きているか** — `[ -L ] && [ -e ] && [ -d ]` ＋ `mdls -name kMDItemContentType` が `public.folder`
3. **他事業のフォルダが無傷か** — `~/Claude Code/AI Company Outputs/` には テスト事業・動画投稿事業 が同居。`ls` の結果を報告に残す

## 10. 「公開を止める」依頼の型（2026-08-26 追記）

社長ご判断が **②-a「現状維持」→ 同日 ②-b「PDFは非公開に」** と改定された。判断は覆る。**覆ったときに素早く動けるよう、
前の判断で作った資料（法務レビュー）を捨てずに保全しておいたのが効いた。**

### 10.1 「GitHub に置かないで」＝2段階ある。1段階目だけで「消しました」と言わない

| 段階 | 作業 | 効果 | 承認 |
|---|---|---|---|
| **第1段階** | `git rm --cached` ＋ 実体をリポ外へ ＋ `.gitignore` | **今後のコミットに入らなくなる**。HEAD からは消える | 通常承認で可 |
| **第2段階** | `git filter-repo` ＋ 全ブランチ force push | **履歴からも消える** | **§4.1（不可逆）＝別途の社長承認** |

**第1段階だけでは `raw.githubusercontent.com` から取得できるままである。** ここを曖昧に報告すると、
社長は「消えた」と理解して次の手を打たない。**報告で必ず明示する。**

### 10.2 第2段階の判断材料は「壊れるもの / 壊れないもの」で出す

「force push が要ります」だけでは判断できない。実測して2列に分ける。

**壊れる** … 直書きされたコミットSHA（`git grep -nE '(コミット|commit) *`?[0-9a-f]{7}'` で15箇所出た）／全ブランチ（ローカル・**リモートのみのブランチも**）／自動同期スクリプト（分岐検知で停止）／他 worktree（再クローン）
**壊れない** … 成果物カタログの GitHub リンク（**`blob/<ブランチ名>/` 形式なら SHA を含まないので無傷**。ここは実際に確認するまで分からなかった）／Finder のシンボリックリンク／Notion（チケットIDで紐づく）

**「実効性の窓」も判断材料。** fork 0・star 0・Software Heritage 未収録なら今やる意味がある。**時間が経つほど閉じる**ことを伝える。

### 10.3 原本を外に出したら、参照元の README を必ず直す

リンク切れの放置は「隠した」だけで「整理した」ではない。3点セットで書く。

1. **原本の所在**（リポ外の絶対パス）
2. **なぜリポに置かないのか**（このリポは PUBLIC ＋ 30分ごとの `git add -A` 自動 push）
3. **由来チケットと経緯の表**（いつ入り、いつ気づき、いつ外したか）

今回、リンク修正のついでに **一元化で既に無効になっていた旧パス記述も見つかった**。関連箇所をまとめて直す。

### 10.4 `.gitignore` はパスだけでなく「判定基準」を書く

`docs/reference/.../xxx.pdf` と1行足すだけでは、次に別の教材を持ち込む人が同じことをする。
**「これは誰が作ったか」→ 当社でなければ原本はリポ外**という判定基準と、
**リポに残してよいのは当社が読んで書いた要約・判断であって、原本の丸写しではない**という線引きをコメントで書く。

## 11. 誤情報の訂正は「削除」であって「書き換え」ではない

`docs/reference/fba-prep-center/` の比較表に、実在4社について当社自身が「相違9件」と認定した誤りが公開されたままだった。
**当時の方針「AI 生成物の原本として保全し、差分はファクトシート側で管理」が、誤情報の公開継続を生んでいた。**

> **教訓：「原本を保全する」と「誤りを公開し続ける」は両立しない。**
> 第三者について書いた誤りを保全する必要はない。原本は Git 履歴に残る。

### 11.1 訂正の4原則

1. **確実に誤りと分かっている値だけ削除**（検証済みのものに限る）
2. **推測で書き換えない。** 誤った値を別の不確かな値に置き換えるのは悪化させる
3. 削除箇所は `【未確認】` と明示し、**なぜ削除したかを併記**（黙って消すと、後の人が「元から空欄」と誤解する）
4. 正しい値は**当社の検証済み成果物へ誘導**する

### 11.2 「誤りではないが欠落」には手を出さない

記載漏れ5件（物価対応調整金5%・最低ロット目安 等）は追記しなかった。**追記は新たな事実主張**であり、
削除（＝主張を取り下げる）とはリスクの向きが逆。**取り下げは自分で、主張はサトルの再調査を経てから。**

### 11.3 同じ内容が2形式で公開されていたら両方直す

`.md` と `.xlsx` に同じ表があった。**片方だけ直すと、直っていない方が生き残って引用される。**
`.xlsx` は openpyxl で該当セルを書き換え、先頭に「⚠️訂正について」シートを追加した。
**訂正後は機械的に検査する**（`grep` と全セル走査で、誤った値の文字列が0件になったことを確認）。

## 12. 同一リポで並行作業しているときは git を触る前に status を見る

`git rm --cached` を実行した直後、**別セッションのエージェントが `git add -A` 相当のコミットを打ち、私のステージングを取り込んだ**
（T-20260826-002 のコミットに PDF の削除が混入）。結果は同じだが、コミットメッセージと内容が対応しなくなる。

- カズヨからも「同じ turn 内で git を触るエージェントが他にいないよう順番に」と指示があった。**これは実在するリスク。**
- **ステージングしたら間を空けずコミットまで済ませる。** `git rm --cached` → 別作業 → コミット、の順にしない。
- 事後に気づいたら**履歴を書き換えて直そうとしない**（§4.1）。報告に事実として書けば足りる。
