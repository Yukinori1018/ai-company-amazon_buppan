# 「同期漏れ」と言われたら、まずカードの有無ではなく中身のずれを疑う

初出: 2026-09-12 / カズヨ依頼「09-06〜09-12 の Notion 突合（非破壊）」

## 何が起きたか

依頼文は「同期が漏れているものがある」だったが、`TicketID` 前方一致（`T-202609`）で rows モード照会したら
**依頼された7枚＋同期間の全チケットのカードは1枚残らず存在していた**。Status も全件一致。
実際のずれは次の3種類だけだった。

| ずれ | 該当 | 原因 |
|---|---|---|
| Labels が空 | T-20260908-001 / -002 | 未登録ラベル（`pse` `discontinued`）でカード作成が400になり、**ラベルを外して作った**と見られる |
| Labels が1個欠け | T-20260909-002 | 未登録ラベル `order-set` |
| UpdatedAt・本文が古い | T-20260908-002（第3弾 9/12）／T-20260909-002（ゲート確認 9/12） | ログ追記は状態遷移ではないのでフックの「起票/移動」リマインドに乗らない |

## 手順（再利用可）

1. **rows モード**で `TicketID string_starts_with 'T-YYYYMM'` を1回（SQL の利用上限を消費しない。100件まで）
2. ローカル frontmatter を awk で一括抽出して突合（Status / Assignee / Labels / UpdatedAt）
3. 本文は `grep -oE` で**本文中の最新日付**を数える → Notion の UpdatedAt より新しければ本文も更新対象
4. 未登録ラベルは data source を fetch → **既存全件＋新規**で `ALTER COLUMN ... SET`（今回 47→50、返却値で件数を数えた）
5. `update_properties` → `update_content`（old_str/new_str で節ごと差し替え。`insert_content` は重複する）→ `notion-fetch` で読み返し

## 気づき

- **frontmatter の `updated_at` がログ追記で更新されない**（-002 は 09-08 のまま、-009-002 は 09-09 のまま、実際は 09-12 まで追記あり）。
  Notion は本文の実日付に合わせて 09-12 とした。frontmatter 側の是正は起票・更新者（カズヨ／担当）の領分なので報告に留めた。
- `assignee: it-engineer`（ハイフン）が T-20260907-001 / T-20260909-002 でまた出た。Notion 側は `it_engineer` に読み替え済み。3回目の報告。
- 会話開始時の git status で「staged の HTML」（T-20260908-002 の 01_…html）が見えても、**後で見るとワーキングツリーにもインデックスにも無い**ことがある。
  スナップショットを根拠にカタログへ載せない。`git ls-files` で今の実在を確かめる。
- 依頼外の差分（T-20260909-003 / -004 のラベルが Notion では英語の別ラベル）は、既に誰かが意図して寄せた形跡があるため**触らず報告**にした。
  非破壊原則は「消さない」だけでなく「意図が読めない整形を上書きしない」も含む。
