# Notion 同期は「書いた」で終わらせない — 読み返して初めて完了

記録日: 2026-09-09 / 契機: T-20260909-004（社長が「Notion に反映されていない」と指摘。本日2度目の報告と実態の食い違い）

## 今回の結論：カードは存在していた

社長の指摘を受けて DB を実照会したところ、**T-20260909-004 のカードは実在した**。

- 作成時刻 `2026-09-09 01:15:01Z`（＝10:15:01 JST）
- ローカルの commit `7a52f84` は `10:14:31 JST`
- **commit の30秒後に作成されており、同一 turn 内同期のルールは守られていた**

つまり前回の「作成済み」という報告自体は虚偽ではなかった。**にもかかわらず社長には見えなかった**。ここが本質。

## なぜ見えなかったか（構造要因）

Kanban ビューの設定を実際に読んだ結果：

```
groupBy: { property: "Status", sort: { "type": "manual" } }
```

**グループ内が手動ソート**なので、新規カードは列の**最下部**に積まれる。
2026-09-09 時点で `doing` は28枚・`waiting` は28枚。**新しいカードほど見つけにくいボードになっている。**

→ 「起票直後の高優先チケットが、最も見つけにくい位置に置かれる」という逆転が起きている。

**教訓**: 「同期した」＝「社長に見える」ではない。可視化が責務なら、**見える位置に出たか**まで含めて考える。
（時刻の可能性も排除できない：社長が 10:15 JST より前に見た場合は物理的に存在しなかった。両方を並べて報告し、どちらかに断定しないこと。）

## 手順として固定すること

1. **書き込みAPIの成功レスポンスを完了の根拠にしない。** `{"page_id": "..."}` が返っても、それは受理の証明であって反映の証明ではない。
2. **書いた直後に読み返す。** 検証には `notion-fetch`（ページ直読み）を使う。
   - `notion-query-data-sources`（SQL）は**インデックス遅延で古い値を返すことがある**（T-20260822-001 に先行記録あり）。「消えた」と誤認して二重に書き直すと正しい値を壊す。
   - 今回は SQL と fetch の両方で一致を確認した。`page_last_edited_at` が自分の書き込み時刻に更新されているかを見るのが確実。
3. **報告には読み返した実際の値を貼る。** 「更新しました」ではなく「Status=doing / Labels=["workflow","ops"] を読み返して確認」と書く。

社長の指摘を1枚だけ確認して終わらせず、DB 全142行とローカル138枚を突合した。結果：

## Labels が黙って落ちる問題（再発防止の本命）

Notion の multi-select は**スキーマに無い選択肢を渡すと、エラーにならず無視される**。
frontmatter に日本語ラベルを書いたチケットは、Notion 側の Labels が軒並み null になる。
根本解決は T-20260822-001（todo・マリエ担当・2026-08-21 起票のまま滞留）で、
「frontmatter を英字スラッグに寄せる」方針まで書かれている。**着手されていないので毎回同じ穴に落ちる。**

→ 秘書へ：この todo を上げるか、少なくとも新規起票時は `docs/notion-board-schema.md` の語彙から選ぶ運用にしたい。
