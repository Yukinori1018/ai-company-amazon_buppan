# 古い監査結果を根拠に不可逆操作の承認を取らない（2026-09-21・T-20260909-004）

## 何が起きたか

2026-09-09 の監査で見つけた「Notion の重複カード1組＋幽霊カード3枚」を残課題として社長に上げ、
2026-09-21 に「統合＆削除して下さい」という §4.1 の承認をいただいた。
削除の着手前に Notion を実照会したところ、**削除すべきカードは1枚も存在しなかった。**

- `T-20260809-001` の重複 → **2026-09-12 のマージ `56abdd5` で解消済み**。片方は `T-20260809-002` へ採番し直され、別チケットとして正しく生きていた。
- 幽霊 `T-20260806-001/002/003` → 同じマージで**ローカル実体が取り込まれ**、孤児ではなくなっていた。

しかも **是正の経緯は当のカード本文に「2026-09-12 追記」として書いてあった**。
つまり、カードを1枚開けば分かることだった。

## 教訓

1. **不可逆操作の承認を取る前に、対象の生存を取り直す。**
   監査結果には賞味期限がある。12日あれば別セッション・別ブランチのマージで状況は変わる。
   「残課題」として繰り越した項目を蒸し返すときは、**繰り越した時点の記述ではなく現物を見てから**社長に上げる。
2. **削除の指示を受けたら、まず「消すものが本当にあるか」を確認する。**
   承認は「あるなら消してよい」であって「無くても何か消せ」ではない。
   承認があることは、対象の存在確認を省略してよい理由にならない。
3. **突合は機械で全件やる。**目視で「2枚ある気がする」は当てにならない。
   - 重複：`SELECT TicketID FROM <collection> GROUP BY TicketID HAVING COUNT(*)>1`（SQL モード・軽い）
   - 幽霊：Notion の TicketID 集合 − `workspace/tickets/*/T-*.md` のファイル名先頭 の差集合
   - 逆向き（カード欠落）も同時に出す。今回はこちらに実ドリフトが1件あった（`T-20260920-004`）。
4. **削除しなかったことも成果物として残す。**「何もしませんでした」で終えると、次に同じ古い監査結果がまた掘り起こされる。
   `deliverables/<ticket_id>/archive/README.md` に「削除を実行しなかった理由」を書いて、繰り越しの連鎖を断つ。
