# ナレッジ: 成果物カタログの同期（マリエ定常責務）

初出: 2026-08-24 / T-20260824-001（Keepa公式用語定義集）の登録

## 手順（2ステップ・毎回これだけ）

1. **マスターCSVへ行を追記**: `workspace/output/deliverables/T-20260601-001/deliverables-catalog.csv`
2. **シートへ同期**: `python3 scripts/catalog/sync_catalog_to_sheet.py`
   → HTTP 200 と `[OK] 同期成功: … 書き込み N 行 x 13 列` が出れば完了（全置換ミラー・冪等）

## CSV の実仕様（ここを外すと壊れる）

| 項目 | 実値 |
|---|---|
| 列数 | **13列固定**。`チケットID / ToDo・タスク名 / 成果物タイトル / 内容（要約） / 暫定結果 / 種別 / GitHubリンク / リポジトリ相対パス / 担当 / 形式 / 作成日 / 社長レビュー / 備考` |
| 改行コード | **CRLF**（`lineterminator="\r\n"`。LF で書くと行が混在する） |
| BOM | **ヘッダー行にあり**。読むときは `encoding="utf-8-sig"`、追記は `"a"` で BOM に触らない |
| 末尾改行 | あり。追記前に確認する |

**必ず Python の `csv` モジュールで書く。** 要約に読点・改行・引用符が入るため、手書きの文字列連結は事故る。
書いた後に **`csv.reader` で読み直し、全行が13列であることを assert する**（今回この検証で列ズレ0を確認）。

## 行の書き方（社長・後続AIが読む前提）

- **「暫定結果」列はチケット単位で同じ文言**にする。同一チケットの成果物が複数行に分かれるので、
  どの行から見ても「このチケットが今どういう状態か」が分かる必要がある。冒頭に **【社長レビュー待ち】【完了】【確定】** の状態タグを置く。
- **「内容（要約）」は具体的な固有名詞と数値を入れる。** 「用語定義集」ではなく
  「未確定3ラベルのうち2件を Seller Object の公式定義で決着。`avgBuyBoxCompetitors` は売上ではなく競合出品者数」まで書く。
  カタログは**検索して当てる**ための道具なので、抽象語だけの行は存在しないのと同じ。
- **「備考」には落とし穴と入口を書く。** 「★社長の入口」「BOMあり」「0トークンで再計算可」など、
  次に触る人が最初に知りたい一行。
- **GitHub リンクはファイル=`/blob/`、ディレクトリ=`/tree/`**。ブランチ名を含むので、ブランチが変わると切れる（既知の弱点）。
- 担当列は frontmatter の `assignee` と同じ語彙（`researcher` / `secretary` / `it_engineer` / `general_affairs` …）。
  **1チケットでも成果物ごとに担当が違うことがある**（今回はサトルの4本＋カズヨの実機キャプチャ1本）。行ごとに正しく振る。

## 環境の分岐（重要）

- 同期は **HTTPS POST のみ**で動くのでクラウド／夜間自走からも実行できる設計。
- ただし接続情報 `scripts/catalog/.catalog_sync.env` は **ローカルにしか存在しない**（gitignore対象）。
- **クラウド回で `.env` が無いときは、環境変数 `WEBAPP_URL` / `SHARED_TOKEN` を渡すか、CSV追記までで止めて次のローカル回で同期する。**
  **CSV追記を飛ばしてはいけない**（真実はCSV側。シートはミラーなので後から追いつける）。
- 着手前に **`ls -la scripts/catalog/`**（`-a` を忘れると隠しファイルの `.catalog_sync.env` が見えない）で有無を確認する。

## 判断のポイント

- **README.md も1行として登録する。** カズヨの依頼リストに載っていなくても、索引は成果物。過去のチケット（T-20260817-005）も README 行がある＝**カタログの慣行に合わせる**。
- **`agent_output/` 配下は登録しない。** `.gitignore` 対象で消えるうえ、今回のように**第三者著作物（公式HTML30ページ）**が入っていることがある。
  カタログに載せるのは `deliverables/` 配下だけ。

## 追記 2026-08-24: 「行を増やす」か「要約を更新する」かの判断

同じチケットの成果物が**改訂された**とき（ファイル名は同じで中身が育った場合）は、
**行を増やさず、既存行の「成果物タイトル」「内容（要約）」「暫定結果」「備考」を最新化する。**

- 行を増やすと、**同じパスの行が2つ**できる。カタログは「チケットID × 成果物」の一覧であって版管理台帳ではないので、
  古い行が残ると**どちらが最新か分からなくなる**（＝カタログの価値が消える）。
- 版が上がったことは **タイトル末尾に `v2` / `v1.2`** を付け、**要約の冒頭に【v1.2 2026-08-24】と日付付きで何が変わったか**を書いて表現する。
- **「暫定結果」はチケット単位で全行を一括更新する。** 1行だけ直すと、同じチケットの他の行と食い違う。

### 実例（T-20260824-001 / 2026-08-24）

6行を追加した数時間後に4ファイルが改訂された。**行数は126のまま**、内容だけを更新した。
`keepa-glossary.html` は 95KB → **117KB / 32表**に成長し、**§0.5 の4列対応表**が新設された点を要約の先頭に置いた。
併せて関連チケット **T-20260817-004 の既存行も v1.1 → v1.2** に更新（別チケットでも、内容が更新されたら追随する）。

### 更新後の検証は毎回2つ

1. `csv.reader` で読み直して **全行13列** ＋ **総行数が意図どおり**（増やしていないなら変わらないこと）
2. **BOM・CRLF・末尾改行が保たれているか**をバイト列で確認（`utf-8-sig` で書き戻すと BOM は維持される）

## 追記: カタログに載せない／まだ載せないもの

- **他セッションが `git add` 済みでまだ commit していない成果物は、その場では登録しない。**
  カタログの GitHub リンクは**コミット済みであることが前提**で、未コミットのパスを書くと**リンクが404**になる。
  見つけたらカズヨに「新しい成果物があります・commit 後に登録します」と報告して預ける。**黙って登録も、黙って無視もしない。**
- `workspace/output/agent_output/` 配下は登録しない（gitignore・第三者著作物が入りうる）。

## 追記: 「複数セッションが同じチケットに納品する日」の回り方

2026-08-24 は1チケット（T-20260824-001）に **サトル（調査）／ハルオ（法務）／タカシ（実装設計）／ヒデアキ（関連チケットの改訂）** が
数十分おきに commit を重ねた。カタログを1回で決めようとすると必ず取り残す。

**回り方（この日で確立）**

1. **カズヨの依頼範囲を先に片付ける**（頼まれた行の追加・更新）。
2. その直後に **`git ls-files <deliverables/チケットID>/`** を打ち、**カタログに無い追跡済みファイル**を洗う。
   `ls` ではなく `git ls-files` を使うのは、**未コミットのものを拾わないため**（未コミット＝リンクが404）。
3. 増えていたら**その場で追加登録する**。カズヨの依頼に無くても、`deliverables/` に出た成果物の登録は**マリエの定常責務**（CLAUDE.md）。
4. **関連チケット側の改訂も追う。** 今回は T-20260811-001 が第2版→第3版になっていた。
   「このチケットの成果物」だけ見ていると、**同じ調査結果を反映した別チケットの改訂**を落とす。

**判断**：churn の最中でも登録する。「落ち着いてから」は落ち着かないまま忘れる。
**版が動いたら要約の冒頭に【第3版 2026-08-24】と日付付きで書く**運用にしておけば、後から追い越されても事故にならない。

## 行の粒度の決め方（2026-08-24 / T-20260824-003 で確定）

deliverables に5ファイル出ても、**カタログは5行にしない**。「社長／後続AIが検索して当てる単位」で束ねる。今回の割り方:

| 束ね方 | 実例（T-20260824-003） | 形式列 |
|---|---|---|
| README/索引は必ず単独1行 | `README.md` | `md` |
| **同一内容のテキスト版とHTML版は1行**（リンクはHTML側＝社長の入口、備考にmd版の場所） | `monthly-sold-distribution.md` + `.html` | `html/md` |
| **スクリプトとその生出力は1行** | `analyze_monthly_sold.py` + `analyze_output.md` | `py/md` |

→ 5ファイル = **3行**。判断基準は「**社長がこの2つを別々に探すか？**」。探さないなら1行。
既存の T-20260824-001 の行も同じ割り方（`.html` を代表にして `形式=html/md`）になっており、**カタログ全体で一貫している**。
逆に分けるべきなのは**担当が違うとき**（同一チケットでも `assignee` が変われば必ず別行）。

### 今回の実施記録

- 追記3行 → 128行 → **131データ行 / 132行（ヘッダ込）**。`sync_catalog_to_sheet.py` で HTTP 200・`132 行 x 13 列` 書き込み成功。
- `--dry-run` を先に流して**行数とヘッダのBOM保持を目視**してから本送信した。この順番は毎回守る（全置換ミラーなので、壊れたCSVを送ると全部壊れる）。

## 追記: 「未コミットなら要約を書かない」が実際に効いた（2026-08-24）

サトルの最終反映を待って要約更新を保留した判断が正しかったことが、結果で確認できた。
待たずに書いていれば、`f05c7db` の1コミットで**書いたそばから全部古くなっていた**。

**変化量が大きい**：`keepa-glossary.html` は 117KB/32表 → **145KB/40表**、
`discrepancies.md` は **D11 が D区分→A区分へ格上げ＋全面差し替え**、**D8 は D区分→C区分へ移設**、
**「要確認」区分が 0件**に。**区分の件数表そのものが書き換わった**ので、要約は原型を留めていない。

### 判断ルール（確定）

- **「更新中」と分かっているものは、完了報告が来るまで要約を書かない。** カタログは真実のミラーであって速報ではない。
- ただし **待つ理由と、いつ書くかは必ず報告に書く**。黙って保留すると「やり忘れ」と区別がつかない。
- **待てない場合**（依頼者が今すぐ必要とする等）は、要約の冒頭に **「【途中経過 YYYY-MM-DD 時点】」** と明記して書く。
  日付があれば、後から見た人が古さを判定できる。

### 全体を読み書きするスクリプトの注意（今回ヒヤリとした点）

CSV を「読む → 全行を書き戻す」形で更新している。**読んでから書くまでの間に他セッションが行を追加していると、それを消してしまう。**
今回は総行数が **129 → 137** に増えていた（他セッションが T-20260824-003/004 の8行を追加していた）。
**スクリプトの冒頭で読み直しているので消さずに済んだ**が、これは運任せに近い。

**対策**：更新スクリプトは必ず **①その場で読む → ②メモリ上で書き換える → ③即座に書き戻す** を1回の実行で完結させる。
**読んだCSVを別の会話ターンにまたいで持ち越さない。**
そして**書き戻し後は必ず総行数を出力し、「増減が意図どおりか」を目視する**（今回 129→137 の増加に気づけたのはこの出力のおかげ）。

## 追記 2026-08-24: 「同じ主題で2つの成果物が並ぶ」ときのカタログの書き方

社長レビュー「余計なことがゴチャゴチャ書かれている。整理して正式な用語集に」を受け、
**同じ主題（Keepa用語）で2チケット・2つの成果物**が並ぶ状態になった。
T-20260824-001＝調査記録（保全）／T-20260824-005＝正式な用語集。

**このとき最も大事なのは「どちらを見ればよいか」を全ての面に書くこと。**
片方だけに書くと、もう片方から入った人が迷う。今回は**4面すべて**に住み分けを書いた。

| 面 | 書いた内容 |
|---|---|
| カタログの新規3行（暫定結果） | 「★住み分け＝005が正式版・001は調査記録（削除せず保全）」を全行に |
| `owner-tasks.md` の新エントリ | 「日常的に引くのは正式版」 |
| `owner-tasks.md` の旧エントリ（001） | 「📌 こちらは調査記録。**2つとも読む必要はありません**」 |
| Notion カード（001） | 「このチケットは調査記録になりました」＋対比表 |

**旧側に注記を入れるのを忘れやすい。** 新しいものを登録すると仕事をした気になるが、
**社長が古い方のエントリから入る可能性は消えていない。**「新を足したら旧に道標を置く」までが1セット。

### 「行を増やす」か「要約を更新する」かの再確認

- **同じファイルが改訂された** → 行を増やさず要約を更新（既定）
- **別チケットで新しい成果物が作られた** → **新規行を追加するのが正**（今回はこちら）

見分け方は「**リポジトリ相対パスが同じか**」。パスが違えば別の成果物なので行を足す。
今回は `T-20260824-001/keepa-glossary.md` と `T-20260824-005/keepa-glossary-official.md` で**別パス**＝新規行。

### 素材の誤りが後から見つかることを前提にする

ヒデアキが素材（サトルの調査＝質は高い）から**是正2件**を出した。
**カタログの要約は「その時点の最良」であって「確定」ではない。**
だから要約には**確認日**を必ず入れ、備考に**「何を根拠にしたか」**を書く。
根拠が書いてあれば、後から素材が覆っても、どの行を直せばよいかを追える。

依頼文が挙げていたのは 01_master-todo.md（+.html）/ 02 / 03 の**3点**。

|---|---|---|
| 01_master-todo.md | 1行 | 本体 |
| 01_master-todo.html | **別の1行** | 既存慣行。「（HTML版）」「（PDF版）」は独立行にする（例: T-20260703-001 / T-20260826-001） |

### CSV の列数は13。スキル文書の12列は古い

`deliverables-catalog.md` の列設計は12列だが、**実CSVは「暫定結果」が5列目に入った13列**。
追記前に必ず `head -1` で実ヘッダーを見ること。スキル文書より**実ファイルが正**。
（追記後に `set(len(r) for r in rows)` が `{13}` になることを機械検算した）

### 手順のテンプレ（次回そのまま使える）

```bash
head -1 <CSV>                      # 実ヘッダーで列数を確認（スキル文書を信じない）
tail -c 200 <CSV> | od -c          # 行末が \n で終わっているか（追記の事故防止）
ls -la workspace/output/deliverables/<ticket_id>/   # 「N点」を鵜呑みにしない
python3 <append script>            # csv.writer(lineterminator="\n") で追記
python3 -c "... set(len(r)) ..."   # 全行の列数が揃っているか機械検算
python3 scripts/catalog/sync_catalog_to_sheet.py    # HTTP 200 と行数を目視
```

- CSV は `encoding="utf-8-sig"` で**読み**、`encoding="utf-8"` で**追記**する
  （先頭に BOM があるため。追記時に utf-8-sig で開くと BOM が二重に入る）
- 内容（要約）にカンマを使わない。読点「、」か「/」で代替する（既存行の流儀）
- GitHubリンクのブランチは `git branch --show-current` の実値を使う（今回 `claude/nighttime-work-checkin-iTWEa`）
