# 新規1枚の同期ついでに全件突合すると、取りこぼしが必ず出る

初出: 2026-09-07 / T-20260907-002（GSC インデックス警告カードの新規作成）

## 何をしたか

発注は「新規チケット1枚を Notion へ作成＋ owner-tasks.md 更新」だけだったが、
**ついでに repo 全131枚 × Notion 全130枚を突合した**ところ、ドリフトが6種類出た。
突合そのものは Bash 2行で終わる。**新規1枚の同期のたびに回してよいコスト。**

```bash
# repo 側の (ticket_id, 状態) 一覧
for d in todo doing waiting done; do for f in workspace/tickets/$d/*.md; do
  echo "$(grep -m1 '^ticket_id:' "$f" | awk '{print $2}') $d"; done; done | sort > /tmp/repo_tickets.txt
# Notion 側は SQL で "TicketID || ' ' || Status" を引いて sort し、comm で両方向を見る
comm -23 /tmp/repo_tickets.txt /tmp/n.txt   # repo にあるが Notion に無い ＝ 取りこぼし
comm -13 /tmp/repo_tickets.txt /tmp/n.txt   # Notion にあるが repo に無い ＝ 孤児カード
```

**注意: Notion の SQL は100行で `has_more: true` になって黙って切れる。**
`WHERE "TicketID" > '<最後のID>'` で2回目を引き、必ず件数を数えてから突合する。
切れたことに気づかずに comm すると、**存在するカードが全部「取りこぼし」に見える。**

## 出た6種類と、それぞれの扱い

| 種類 | 件数 | 私が何をしたか |
|---|---|---|
| repo にあるが Notion にカードが無い | 5（T-20260831-002/-004/-005/-006・T-20260906-007） | **作成した**。純増・非破壊＝マリエの定常責務そのもの |
| repo=doing / Notion=waiting | 1（T-20260521-005） | **Notion を doing に寄せた**。片方向ミラーなので repo が正 |
| Notion にしか無い（孤児カード） | 3（T-20260806-001/-002/-003） | **触っていない。**社長確認案件として報告 |
| TicketID 重複カード | 1（T-20260809-001 が2枚） | **触っていない。**同上 |

### 孤児カードを消してはいけない理由（再確認）

`find` でも `git log --diff-filter=D` でも痕跡が出ない＝**リポジトリに一度も存在しなかった**カード。
「消えた」のではなく「Notion で直接作られた」可能性が高い。非破壊原則どおり報告に留める。
**痕跡が無いことは、消してよい根拠ではなく、経緯が分からない根拠。**

### 状態ドリフトは「どちらが正か」で迷わない

T-20260521-005 は過去のメモリに「本来 waiting であるべき」と書かれていた。
だが**それは実体（repo）を動かす話であり、カズヨの責務**。私がやるのは鏡を合わせることだけ。
repo=doing なら Notion も doing。**実体の是非を鏡の側で忖度すると、どちらが正か分からなくなる。**

## labels は「片方だけ直さない」を5件まとめて実行した

新規ラベルを毎回足すとボキャブラリが膨らむ（既に `infrastructure`/`infra` が両立している）。
既存47件へ寄せて、**リポジトリ側の frontmatter も同じ値に書き換え、ログ行に理由を残す**までが1セット。

| 元 | 寄せ先 | 理由 |
|---|---|---|
| `automation` `launchd` `always-on` | `overnight` `infra` | 夜間無人稼働＝既存語で足りる |
| `redesign` | `strategy` | 設計のやり直し＝戦略側 |
| `research-method` `survey` | `research` | 手法も調査も `research` の下位 |
| `profit` | 削除 | `sourcing`+`pipeline` で表現済み |
| `adapters` | `dev` | 実装対象名はラベルにしない |
| `homepage` `search-console` | `website` `seo` | 同義語の増殖を避ける |

**新設は3件だけに絞った**（`website` `seo` `satoy-select`）。自社サイトは既存語で表現不能な新ドメインで、
兄弟チケット T-20260825-001 が既に `website` `satoy-select` を使っており、今後も再発するため。
`ALTER COLUMN "Labels" SET MULTI_SELECT(...)` は**全置換**なので、既存44件を色ごと全列挙して47件にした
（書き込み後に件数を数えて確認：44→47）。

## owner-tasks.md 側

社長タスクは **純増 +1**。ただし中身は「Go/NoGo を返す」の1本だけなので、
`- [ ]` は1個に畳み、判断材料（やる価値／やらない実害／社長のお手／なぜ承認が要るか／期限）は
チェックボックス内の表に入れた（T-20260826-002 で確立した「確認1件ごとに影響列」の型の踏襲）。

冒頭「最終更新」行にも**先に結論**を置いた：
「**サイトの緊急修正は不要です。お返事1本で済みます。**」
警告メールが起点の案件は、書き方を誤ると「サイトが壊れた」と読まれる。**否定を先に書く。**

## 突合の結果（機械検査）

```
comm -13 /tmp/ot.txt /tmp/w.txt  →  0件（waiting 29枚すべて owner-tasks.md に掲載済み）
```
※ `awk 'NR>12'`（「最終更新」行より後ろだけ）を対象にすること。最終更新行には過去の経緯として
大量のチケットIDが載っており、含めると検査が常に0件になって意味を失う。
