# owner-tasks の更新番号が並列セッションと衝突し、自分の節が他人の commit に混入した（2026-09-15 / T-20260915-002）

## 何が起きたか

- 発注：T-20260915-002 のサトル5体納品（9bafae5）の同期。発注文は「続き番号の更新節」。読んだ時点の最新は㊵なので㊶で書いた
- 書いた直後に NETSEA 側のセッション（T-20260915-001）が 08e5337 で「更新㊶」、b7e47b6 で「更新㊷」を commit。**b7e47b6 は owner-tasks.md をファイルごと add したため、未 commit だった私の㊶節がその commit に混入**した（私の commit ではない）
- 結果、ファイル上は「㊷（ヘッダ）→ 他人の㊶ → 私の㊶ → ㊵」の並びになり、番号が重複した

## 直し方（再利用できる手順）

1. Edit 後に「file had been modified on disk」の注記が出たら、**commit 前に** `git log -3` と `grep -n "^## 🆕 .*更新" owner-tasks.md` で番号の実物を見る
2. 番号が重なっていたら、次の空き番号（今回は㊸）に振り直し、先頭（ヘッダ直後）へ移す。**移動・ヘッダ行・ℹ️ 行は1本の python で一括置換**し、各置換に `assert count==1` を付ける（Edit を3回に分けると、その間に他セッションが書く）
3. 節内に「番号：㊶→㊸に振り直し（理由）」を1行残す（他人の commit に旧番号の版が残っているため）

## 教訓

- 「続き番号」は発注時点の番号を信じず、**書く直前の grep で決める**。夜間は複数セッションが owner-tasks を同時に書く
- 他セッションが `git add <file>` するとき、私の未 commit の変更も一緒に入る。**owner-tasks のように共有されるファイルは、書いたらすぐ commit** する（Notion など後の作業を待たない）
- ログや CSV など他の自分の変更は、cacheinfo で自分の行だけ stage する方式が引き続き有効

1. 実物照合：`git log -4`（7c909de）・`ls tickets/*/ | grep 20260915` で -001/-002/-003 が各1件
