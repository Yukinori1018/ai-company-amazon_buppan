# 社長タスクが「ゼロ」でも、書くべきことが残る場合がある — 「触らないでください」型の注意

作成: 2026-09-04（T-20260826-004 更新⑧ / T-20260904-004 の同期）

## 何が起きたか

owner-tasks.md の最上段が更新⑦（KYC 審査中）で止まっており、その後チケット
`workspace/tickets/waiting/T-20260826-004_jp-account-suspension.md` に3つの新事実が
記録されていた（カナダKYC完了・米国ストアがクリーン・出品は3か国とも停止中）。
これを更新⑧として追記した。

## 学び1：**「社長タスクはゼロ」と「社長に伝えることはゼロ」は別物**

今回の最重要事項は**お願いではなく禁止**だった。

> 米国側の認証完了バナー：「提供された情報に変更が加えられると、新しい認証が開始されます」
> 「銀行口座情報の再認証が必要となる場合があります」

つまり社長が善意で設定（銀行口座割り当て・RFC・適格請求書登録番号）を進めると、
**完了したばかりの本人確認がやり直しになる**。タスク欄が「ゼロ」だと社長は
「じゃあ他を進めておこう」と動くのが自然なので、**ゼロと書く回では「しないでいただきたいこと」を
必ずセットで最上段に置く**。今回は結論ブロックの直後に blockquote で1本立てた。

## 学び2：断定していない箇所は、断定していない形のまま写す

チケットには「カズヨの読み（断定しない）」という節が明示されている。
owner-tasks 側でも「事実＝カナダ側の表示は変わっていない／推測＝KYC 完了に伴って更新される」
と**事実と推測を分けた1行**を残した。要約すると断定に化けやすいので、
分離の1行を消さないこと。

## 学び3：PUBLIC リポでのケース番号

チケット本文にはケース番号（`SPC-USAmazon-...`）が載っていたが、
owner-tasks.md には**過去1件も登場していなかった**（grep で確認）。
メールアドレス `satoyselect@gmail.com` は3件の前例あり。
→ **既存の書き方に合わせる**＝メールアドレスは書く、ケース番号は書かない。
併せて ⑦「変わらない前提」の非記載リストに「ケース番号」を追加した。

判断手順：`grep -o` で当該種類の文字列が既に何件あるか数える。ゼロなら書かない。

## 学び4：更新ブロックの積み方（このファイル固有の型）

- 最上段に `## 🚨🚨 最優先（日付 更新N）— 結論見出し`
- 直前の回は `<details><summary>📌 更新N-1の記載（要約・記録として残置）</summary>` で包み、
  元の `## 見出し` は `**（当時の見出し）** ...` に書き換える（`##` のまま残さない）
- `</details>` は**ファイル末尾側にまとめて積まれている**（入れ子のため）。
  追記後は必ず `<details` と `</details>` の個数一致を確認する（今回 9 / 9）。
- ヘッダーの「最終更新」行は**別番号**（更新⑤＝最優先ブロックの更新⑧）。
  `更新N（🚨🚨最優先ブロック＝更新M）` の形式を踏襲し、旧文は `／前:` で連結して残す。

## 学び5：Notion の Labels は存在するオプションしか使えない

T-20260904-004 の frontmatter labels は
`[research, sourcing, maker-shiire, netsea, keepa, first-purchase]` だったが、
DB の multi_select に `sourcing` と `first-purchase` は**未定義**。
存在する4つ（research / maker-shiire / netsea / keepa）だけでカードを作成した。
新規オプションを増やすと Notion 側の選択肢が汚れるので、
**まず `notion-fetch` でスキーマを引いて既存オプションを確認**してから作る。
