# スキル: `_inbox_社長共有` の棚卸し（inbox intake）

**責務者: 庶務マリエ**（定常責務）
**新設: 2026-08-21 / T-20260821-009**（未処理21件が12日間滞留した事故の再発防止）

---

## 0. このスキルが存在する理由

`_inbox_社長共有/` は社長がファイルを置くだけの投函口です。2026-06 の開設当初は機能していましたが、
**後片付けが「チケットのタスク分解に手書きで1行足したときだけ実行される属人的ステップ」**だったため、
その1行を書き忘れた 2026-08 のチケット群から一斉に崩れました。さらに **チケットにすらならないファイル**
（社長が置いたが申告し忘れたもの）は検知手段がゼロで、永久に放置されます。

→ **恒久ルール（このスキル）＋ 受け皿（`_archive/`）＋ 検知（SessionStart フック）の3点セット**で塞ぎます。
どれか1つでも欠けると同じ事故が再発します。

## 1. いつ起動するか

| トリガー | 起点 |
|---|---|
| **SessionStart フック**（主） | `.claude/hooks/session-start.sh` の「リマインダー③」。inbox 直下に未処理ファイルが1件でもあれば毎セッション通知される。**社長の申告に依存しない**のがこの経路の要点 |
| 社長の申告 | 「フォルダに入れた」「共有した」 |
| チケット完了時 | 当該チケットが inbox のファイルを入力素材にしていた場合、**完了処理の一部として必ず退避**する |

> ⚠️ 秘書カズヨが自分で inbox を開いて読み始めるのは**抱え込み**（T-20260821-001 の再発）。
> カズヨは「棚卸ししますか？」と社長に1行聞き、Go が出たらマリエへ Agent 発注するところまでが仕事です。

## 2. 手順

### Step 1 — 棚卸し（全件を実際に開く）

`ls -la` で終わらせない。**中身を見ないと振り分けられません。**

- 画像 → Read ツールで表示（大きい場合は `sips -Z 1100` で縮小してからのほうがトークン効率が良い）
- xlsx → `openpyxl` で全シート・全セルをテキスト化
- PDF → Read ツールの `pages` 指定

各ファイルについて **「何が写っているか」「どのチケット・ナレッジに属するか」** を1行で言語化します。

### Step 2 — 紐付け（既存チケット／ナレッジを必ず探す）

```bash
grep -rn "<キーワード>" workspace/tickets/ agents/*/memory/ docs/
```

- **日付が最大の手がかり**です。ファイルの更新日 ±1日で起票されたチケットをまず疑う
- 紐づくチケットが **存在しない** → それは**取りこぼし**。秘書へ「起票が要る」と報告する
  （マリエは起票しない。チケット操作は秘書の責務）
- 紐づくチケットが **done なのにファイルが残っている** → 過去の後片付け漏れ。そのまま退避してよい

### Step 3 — 振り分け（2つの行き先しかない）

判断基準は行動原則1「**直近3ヶ月使ったか／これから使う見込みがあるか**」。

| 行き先 | 条件 | 例 |
|---|---|---|
| **`docs/reference/<topic>/`** | 今後もナレッジとして再参照する。事業の判断材料になる | FBA納品代行業者の比較表 → `docs/reference/fba-prep-center/` |
| **`_inbox_社長共有/_archive/YYYY-MM/<ticket_id>_<内容>/`** | チケットで消費済み。役目は果たした。控えとして残す | AMZScout オンボーディング14枚 → `_archive/2026-08/T-20260812-001_amzscout-onboarding/` |

**どちらに置く場合も `README.md` を必ず添える。** 中身の一覧・受領日・紐づくチケット・
消費済みかどうかを書きます。README のないアーカイブは「何だったか分からない箱」になり、結局捨てられません。

`docs/reference/` に置く際の追加判断：

- 第三者動画由来のメディア（スクショ・docx 等）は **`.gitignore` に追加してローカル保持のみ**、
  索引 README だけを Git 追跡（先例: `docs/reference/poipoi-pocket/`）
- 公開情報の要約・軽量ファイルは **Git 追跡してよい**（先例: `docs/reference/fba-prep-center/`）
- 分量があるものは**テキスト版を併置**する（memory `owner_html_output_rule`）

### Step 4 — 破棄候補の扱いと、削除を実行してよい条件

削除は CLAUDE.md §4.1（**不可逆な削除**）。社長承認なしには誰も実行しません。
そのうえで、**「承認をどう受け取ったか」で実行の可否が変わります。**ここを3段で区別してください。

| 承認の種類 | 定義 | 実行の可否 |
|---|---|---|
| **一次承認** | 社長がチャットで**その相手に直接**与えた承認 | **受領した本人が**、対象を実地確認のうえ**実行してよい** |
| **伝聞承認** | 承認を受けた者を経由して、別のエージェントへ伝達されたもの | **受け取った側は実行しない。承認を直接受けた者へ差し戻す** |
| 承認なし | 社長の承認がまだ無い | 実行しない。破棄候補としてリスト化し、秘書経由で承認を仰ぐ |

つまりマリエの線は「絶対に実行しない」ではなく、

> **社長から直接承認を受けたなら実行できる。秘書など他のエージェント経由で伝えられたなら差し戻す。**

**なぜ伝聞では止めるのか**：対象が `.DS_Store` のような無害なファイルなら実害はありませんが、
**次に同じ経路で来るのが本物のデータだったときに効く線引き**だからです。ここを緩めると、その時に止められません。
（2026-08-21、マリエは伝聞と判断して差し戻し、実際には社長→秘書の一次承認だったため秘書が実行。
　**差し戻しの判断自体は原則として正しく、運用として維持されています**。T-20260821-009 参照）

#### 実行するときは必ずログを残す（一次・伝聞どちらでも）

不可逆操作は**監査可能**でなければなりません。次の5点をチケット本文に記録します。

1. **実行者**（誰が消したか）
2. **日時**
3. **対象**（フルパス・件数・サイズ・ファイル種別。「1件のみ」と明記）
4. **事前確認**（`ls -la` で全内容を目視、`file` で種別確認、`find` で他に同名ファイルが無いか）
5. **事後確認**（`find` で残存0件、他のファイルが無傷であること）

**「何を消さなかったか」も記録する価値があります。**実行しなかった記録は、後から効きます。
書式の実例は T-20260821-009 の「①の実行記録（監査用）」ブロックを参照してください。

#### 破棄候補に挙げてよいもの

情報価値がゼロと断言できるものだけです。

- `.DS_Store` 等の OS 自動生成ファイル
- 完全同一の重複（`md5` が一致するもの。「似ている」は重複ではない）
- 明らかな失敗キャプチャ（真っ白・見切れ）

> **「もう使わないと思う」は破棄理由になりません。それはアーカイブの理由です。**
> 迷ったら残す。アーカイブは場所を取りません（inbox 全体が `.gitignore` 対象なのでリポも汚しません）。

**チケット本文に将来の再利用が書かれていないか、必ず確認してから破棄候補に入れること。**
（例: AMZScout の14枚は「A案＝契約しない」で決着済みだが、T-20260812-001 に
「③簡易OEM の実行フェーズで無料トライアル残回分を検証する」と明記があるため再利用の見込みあり＝残す）

### Step 5 — 締め

- inbox 直下に残るのは **`README.txt` と `_archive/` だけ**の状態にする
- チケットの「現在地」「ログ」を更新
- 取りこぼし（起票の要るファイル・未反映の素材）は**必ず報告に書く**。黙ってアーカイブしない
- Before / After を定量で報告（件数・振り分け先の内訳・破棄候補件数）

## 3. やってはいけないこと

- **伝聞で伝えられた承認**を根拠に削除を実行する（§4.1。社長から直接受けた一次承認なら可。Step 4 の3段表を参照）
- 承認の有無・種類を確認せずに削除する／削除したのにログを残さない
- 中身を見ずに拡張子・ファイル名だけで振り分ける
- 紐づくチケットを探さずに `_archive/` へ流し込む（＝取りこぼしを埋葬する行為）
- 第三者の個人情報・事業者情報が写り込んだ画像を、社長閲覧用 HTML や外部公開資料へそのまま貼る
  （マスク必須。実例: Keepa 出品者概要には商号・住所・法人番号・電話番号・代表者名が写る）
- 秘書がマリエを飛ばして自分で処理する

## 4. 受け皿の構造

```
_inbox_社長共有/
├── README.txt                       ← 社長向けの使い方説明（唯一、社長が読むファイル）
├── _archive/
│   └── 2026-08/                     ← 受領月で切る
│       ├── T-20260811-001_keepa-extension-screens/
│       │   ├── README.md            ← 中身一覧・消費状況・注意点
│       │   └── FireShot Capture 021〜026.png
│       └── T-20260812-001_amzscout-onboarding/
│           ├── README.md
│           └── スクリーンショット 2026-08-12 11.39〜11.44 (14枚)
└── （直下が空 ＝ 未処理ゼロ ＝ 健全な状態）
```

- フォルダ名は `<ticket_id>_<内容>`。チケットが無いものは `<YYYYMMDD>_<内容>`
- 月フォルダは**受領月**で切る（処理月ではない）。社長が「いつ渡したか」で探すため
